# E10 — Speed-Scaled Walk Playback (clip rate follows ground speed)

> **Conditional — entry gate.** Build after `E10--enemy-steering-feel` lands, and only if its acceleration/deceleration ramps make the fixed-rate walk clip visibly foot-slide on the movement-feel fixture (the follow-up named in `E10--enemy-locomotion-animation` § Open questions). The gate is a playtest observation, not a metric; this spec exists so firing it is a promotion, not a design session.
>
> **Composes with:** `E10--enemy-locomotion-animation` (its locomotion intent carries a squared, pre-steering `speed_xz_sq` — this spec performs its own post-steering linear-speed read rather than consuming that value directly) and `E10--enemy-steering-feel` (the source of the speed ramps that expose the problem).

## Goal

Scale the walk clip's playback rate from the agent's measured ground speed so foot cadence tracks the floor during acceleration, deceleration, and arrival easing — removing the treadmill-slide that a fixed-rate loop shows under ramped speeds.

## Background (the time model)

- **There is no playback-rate concept in the runtime.** Clip-local time is a pure function of a single global animation clock: `state_time` (`crates/postretro/src/scripting/systems/mesh_anim.rs:161`) computes `elapsed = anim_time − entered_at (+ phase for loops)`. No dt is integrated in the animation module; the only rate knob is the global slow-mo clock multiplier. A per-entity rate is net-new capability.
- **Animation state is a component.** `MeshAnimation` (`crates/entities/src/components/mesh.rs:112`) on `MeshComponent` carries `states`, `current_state`, `entered_at`, crossfade bookkeeping. The state machine (`switch_animation_state`, `SwitchResult` — `mesh.rs:320`, `mesh.rs:286`) lives there; per-frame sampling lives in `mesh_anim.rs` via `animate_entity` (`mesh_anim.rs:208`), called from the render-frame collector (`crates/postretro/src/scripting/systems/mesh_render.rs`).
- **Order:** sim tick (AI switches states, steering moves the agent) → render frame (resolve pending stamps, sample poses). The measured speed is produced in the sim tick and consumed at sampling time.
- **Time-slicing constraint.** Distant agents resample poses at stride 1/2/4 (`mesh_render.rs:31-74`). The current stateless time model makes skipped frames free — the next sample lands at the correct absolute time. Any rate mechanism must preserve that property; a naive per-frame accumulator advanced only on resampled frames would stall distant agents' phase and jump on resample.
- **Reference speed exists.** `AgentComponent::move_speed` is the speed at which the authored walk cycle reads correctly (the enemy's full chase speed); `rate = speed_xz / move_speed` needs no authored data.
- **Remote enemies carry no agent.** In co-op, a remote enemy replicates its `Transform` (presented client-side from a per-`NetworkId` buffer of server-tick-stamped samples, `netcode/interpolation.rs`) plus `current_state` only (`WireMeshAnimationState`); the client attaches descriptor mesh presentation but none of `Brain`/`Agent` (`netcode/remote_materialize.rs`), so the sim-tick rate path never runs for it. The shared descriptor table — including the `ai` block's `moveSpeed` and state names — is client-known, so the reference speed needs no wire field either.

## Scope

### In scope

- **Rate computation.** Per agent, per sim tick, after steering resolves: `rate = clamp(speed_xz / move_speed, RATE_MIN, RATE_MAX)`, from a fresh, dedicated read of `agent_steering::path_state(..).velocity` XZ magnitude (linear speed; `AgentComponent::move_speed` read at the same site). This is a second, separate read from the AI pass's locomotion-intent value — that value is last-tick, pre-steering, and squared (`speed_xz_sq`), unsuited to this computation. Applies only while the current animation state is the looping locomotion (walk) state; all other states run at rate 1.
- **Rebased scaled time (the design).** Store `(rate, rebase_time, rebase_elapsed)` on `MeshAnimation` (runtime-only, `#[serde(skip)]`). `now` is the `anim_time` parameter already threaded into `sim::simulate_tick` — the slow-mo-scaled, freeze-gated animation clock, never sim/script/tick time. When the sim tick updates the rate, rebase: `rebase_elapsed += (now − rebase_time) × old_rate; rebase_time = now`. At sampling, the walk state's clip-local time is `rebase_elapsed + (anim_time − rebase_time) × rate` — continuous across rate changes by construction, a pure function of the clock between changes, and therefore stride-safe with **no per-frame mutation** in the render collector (the collector borrows the registry immutably; all writes stay in the sim tick). Continuity with sampling holds only because both sides read the same `anim_time`.
- **Clamps.** `RATE_MIN`/`RATE_MAX` module constants (e.g. 0.5–1.5): below-epsilon speeds never reach this path (the locomotion intent selects idle there); the clamp guards mid-band distortion. `move_speed <= 0` yields rate 1 — guards against NaN/inf from the division.
- **Remote enemies (client-side derivation).** Remote co-op enemies never run the sim-tick update (no local `AgentComponent`), so the client derives their walk rate from the motion it actually displays: the remote interpolation buffer reports the presented segment's XZ speed (bracketing-pair position delta over its server-tick span; held branches report 0; velocity-bearing extrapolation uses the sample velocity), the reference speed and walk-state name come from the shared descriptor table's `ai` block (`moveSpeed`, `states.alert`) cached at remote-enemy materialize time, and the per-frame client sampling step feeds the same `clamp(speed_xz / move_speed, RATE_MIN, RATE_MAX)` into the same Task 2 rebase substrate with `now` = the frame's animation clock. No new wire field. Accepted limitation, by design: the derived rate tracks the *interpolated* motion — it trails true host-side speed by the interpolation delay (50–250 ms) and is piecewise-constant per snapshot segment; feet track the floor the client renders, which is exactly that interpolated motion, so a replicated host-side rate would be *worse* (it would lead the displayed motion by the delay).
- **Crossfade weights unscaled; outgoing leg scaled.** Fade weight/progress keeps real-clock timing (`active_fade`, `mesh_anim.rs:240`, and the interrupt-capture progress read — unchanged). The outgoing leg's *clip-local time* during a fade — and the matching leg in a smooth-interrupt capture — instead advances on the previous-side rebase triple (Task 2), continuous with the scaled time the walk state was showing at the switch instant. A non-scaled outgoing state's triple snapshots to rate 1, reproducing today's real-clock `anim_time − previous_entered_at` exactly.
- **Pre-split.** `mesh.rs` is 1294 lines — over the split threshold. Behavior-preserving extraction of the animation state machine (`MeshAnimation`, `AnimationState`, switch/restart/resolve fns) into its own module before extending it.

### Out of scope

- Authored rate fields, reference-speed overrides, or rate curves in descriptors — the typedef is codegen'd (`gen-script-types`); promote an authored surface only if modders ask, as its own boundary-inventoried follow-up.
- Walk/run blend trees, directional locomotion blends, additional clips.
- Scaling attack, death, or idle states; player/viewmodel animation.
- Changing the time-slicing strides or forcing resamples on rate change — continuity of the scaled-time function makes that unnecessary.

## Acceptance criteria

- [ ] An agent moving at its full `move_speed` samples the walk clip at the authored rate (rate = 1 within float tolerance); at half speed the clip-local time advances at half rate (runnable unit test on the rate function and the rebased-time evaluation over a simulated clock).
- [ ] A step change in speed produces no discontinuity in clip-local time: evaluating scaled time immediately before and after a rebase yields the same value, and clip-local time is monotone non-decreasing through an accel→decel ramp (runnable unit test on the rebase math).
- [ ] Rate is clamped to the configured min/max at extreme speeds (runnable unit test at near-zero and above-`move_speed` inputs).
- [ ] Sampling at arbitrary clock times — including stride patterns that skip 2 and 4 frames — matches continuous evaluation of the same rebased function (runnable unit test evaluating the scaled-time function at strided vs. dense time points).
- [ ] Crossfade timing is unchanged: fade weight for a walk↔idle transition under a scaled walk state progresses on the real clock (existing crossfade tests remain green; one new test with an active rate ≠ 1).
- [ ] The outgoing walk leg's clip-local time is continuous across a walk→idle crossfade: evaluating the outgoing leg immediately after the switch yields the same clip-local time the walk state showed immediately before it — no phase jump — while the fade weight over that same window still advances on the real clock (runnable unit test on the previous-side snapshot and outgoing-leg evaluation, covering both the crossfade sampling path and the smooth-interrupt capture path).
- [ ] Non-walk states are byte-identical in behavior: attack/death/idle sampling paths untouched (existing `mesh_anim` and FSM animation tests remain green).
- [ ] Pre-split lands behavior-preserving: all existing `mesh.rs` and animation tests green before the rate change begins.
- [ ] Sim-tick wiring is verified end to end: after a sim tick with `current_state` a non-walk state, the stored rate is 1; in the walk state, it tracks the clamped post-steering measured speed; a sub-epsilon rate change performs no component write (rebase skipped).
- [ ] Remote-enemy rate derivation is verified on synthesized data: an interpolation buffer whose bracketing samples encode a known XZ displacement over a known server-tick span reports that XZ speed at a bracketed render tick, and 0 on the held branches; feeding that speed through the client rate step with a known reference speed produces the expected clamped rate and continuous rebased scaled time across a segment change; a remote entity whose `current_state` is not the cached walk state receives no rate write (runnable unit tests on the buffer speed query and the client rate step).

## Tasks

### Task 1: Pre-split mesh.rs animation half
Behavior-preserving extraction: move `MeshAnimation`, `AnimationState`, `AnimStamp`, `SwitchResult`/`switch_animation_state`, `RestartResult`/`restart_animation_clip`, `resolve_pending_animation_stamps`, `InterruptPolicy`, `FadeSourceKind`, `InterruptedOutgoing`, and `DEFAULT_CROSSFADE_MS` from `crates/entities/src/components/mesh.rs` (1294 lines) into a sibling animation module, re-exporting so all importers of `components::mesh` compile unchanged or with import-path-only edits — there are many beyond the obvious animation call sites (netcode replication, reactions, hit zones, scripting-core's `data_descriptors` re-exports), so the re-export strategy, not path edits, is what keeps them green. All tests green; no logic changes.

### Task 2: Rebased scaled-time substrate
Add the runtime-only `(rate, rebase_time, rebase_elapsed)` fields to `MeshAnimation`, a rebase method, and a scaled-elapsed evaluation used by the walk state's `state_time` path in `mesh_anim.rs`. Rebase on rate update: `rebase_elapsed += (now − rebase_time) × old_rate; rebase_time = now`. Evaluate scaled elapsed at sampling: `scaled_elapsed = rebase_elapsed + (anim_time − rebase_time) × rate`. `now` and `anim_time` are the same clock — the `anim_time` parameter already threaded into `sim::simulate_tick`, never sim/script/tick time; continuity with sampling holds only because both sides read it. `RATE_MIN`/`RATE_MAX` module constants, suggested band 0.5–1.5. Make `rebase_time` an `Option<f64>`: pending on reset, filled by `resolve_pending_animation_stamps` alongside `entered_at`; the scaled-elapsed evaluation falls back to elapsed 0 (or `entered_at`-relative) while pending, mirroring how a pending `entered_at` already reads as just-entered; a rate update (Task 3) that lands while `rebase_time` is still pending sets the rate without accumulating elapsed (no prior `rebase_time` to accumulate from). Seed `rate` at 1 via `#[serde(skip)]` paired with an explicit serde `default` fn returning 1.0 (or a wrapper struct for the `(rate, rebase_time, rebase_elapsed)` triple whose `Default` seeds rate 1) — a bare `#[serde(skip)]` on a `f32` deserializes to 0.0, which would freeze the pose; `MeshComponent` round-trips serde via netcode replication, so the default matters. Reset the rebase state on state entry via a shared helper called from both `switch_animation_state` and `restart_animation_clip` (`mesh.rs:469`), so a new state — or a walk restart — starts at elapsed 0 regardless of prior rate and never carries stale rebase state.

Mirror the triple on the *previous* side: `previous_rate`, `previous_rebase_time: Option<f64>`, `previous_rebase_elapsed` — runtime-only, `#[serde(skip)]` with the same default-rate-1.0 treatment as `rate` (`MeshComponent` round-trips serde via netcode replication, so a bare skip-to-0.0 default would freeze the outgoing pose here too). The shared state-entry reset helper resets the incoming (new) state's triple to elapsed 0 at both call sites; only `switch_animation_state`'s normal-switch branch — the one that already records `previous_state`/`previous_entered_at` — additionally snapshots the OUTGOING state's live triple into the previous-side fields immediately beforehand. The pending-collapse and hard-cut-from-unresolved-state branches in `switch_animation_state`, and `restart_animation_clip`'s self-hard-cut, record no `previous_state` and correspondingly skip the snapshot — there is no distinct outgoing leg to preserve. `previous_rebase_time` pending semantics mirror `rebase_time`: a snapshot taken while the outgoing side's own `rebase_time` was still pending leaves `previous_rebase_time` pending too, and the scaled-outgoing evaluation below falls back the same way pending `rebase_time` already does. A non-scaled outgoing state (resting rate 1) snapshots to rate 1, reproducing today's exact unscaled behavior; a scaled walk snapshots the rate it was showing at the switch instant.

The outgoing leg's clip-local time during a fade is then `previous_rebase_elapsed + (anim_time − previous_rebase_time) × previous_rate` — this replaces the unscaled `anim_time − previous_entered_at` in the outgoing leg the crossfade sampler resolves, and in the matching previous-side legs the smooth-interrupt capture samples (its captured-incoming leg reads the identical previous-side state, and its captured-outgoing leg — carried across a chained interrupt — needs the same treatment: the stash that preserves that leg across the switch must carry its own rebase triple alongside its existing state name and entry stamp, or the executor may instead capture the leg's already-scaled pose value at stash time; either satisfies the requirement that no capture path samples a previously-scaled walk leg through an unscaled entry-stamp delta). Fade *weight/progress* is unaffected by any of this: the crossfade window computation and the interrupt-capture progress read keep reading `previous_entered_at`/`entered_at` on the real clock, exactly as today.

Unit tests: rebase continuity, pending-rebase fallback, clamped rates, stride-vs-dense equivalence, previous-side snapshot on switch-out (scaled walk → non-scaled state reproduces continuity with no phase jump; non-scaled → non-scaled reproduces today's exact unscaled behavior), fade weight stays real-clock while the outgoing leg's clip time is scaled, serde round-trip never yields rate 0 on either side.

### Task 3: Sim-tick rate update
In the sim tick, after steering resolves (so the tick's final velocity is read), update each brain-driven agent's animation rate: compute `clamp(speed_xz / move_speed, RATE_MIN, RATE_MAX)` from `agent_steering::path_state` velocity (linear XZ magnitude, a fresh read distinct from the AI pass's squared `speed_xz_sq`) and `AgentComponent::move_speed`, guarding `move_speed <= 0` to rate 1 (avoids NaN/inf from the division). Rebase the entity's `MeshAnimation` — using `now` as the `anim_time` parameter passed into `sim::simulate_tick` — when the rate changes beyond a small epsilon (avoids rebasing every tick on noise). Applies only when `current_state` is the locomotion state — the alert-mapped walk state, `AiStateMap::animation_for(LogicalState::Alert)` per the reference descriptor; otherwise the rate rests at 1. Constants live beside the module's existing tuning constants.

### Task 4: Client-side remote-enemy rate derivation
Remote co-op enemies carry no local `AgentComponent` and never run Task 3's sim-tick update, so without this task their walk clip plays at rate 1 and foot-slides. Derive the rate client-side from the interpolated motion the client displays, in three pieces. **(a) Speed source:** extend `RemoteInterpolationBuffer` (`netcode/interpolation.rs`) so resolving a presented pose also reports the presented XZ speed — for the Interpolated branch, the bracketing pair's XZ position delta divided by its server-tick span in seconds (via `SERVER_TICK_MICROS`); the Extrapolated branch uses the newest sample's velocity XZ magnitude; both Held branches report 0 (the displayed pose is frozen). AI enemies replicate Transform-only samples (`velocity: None`), so the bracketing-pair finite difference is the normal path. **(b) Reference data:** cache `(move_speed, walk_state)` per remote enemy from the shared descriptor table's `ai` block — `AiDescriptor::move_speed` and `states.alert`, the same alert-mapped walk state Task 3 gates on — read in `client_receive_and_apply` (`netcode/mod.rs`) where the `RemoteEnemyMaterialize` loop already has the descriptor table in scope. Store it in a `ClientReplication`-owned map keyed by `NetworkId` (add `network_id` to `RemoteEnemyMaterialize`; both construction sites in `client.rs` have it in scope), cleared in `apply_despawn` and on level unload alongside the interpolation buffers. An enemy whose descriptor lacks an `ai` block gets no entry and rests at rate 1. **(c) Rate write:** in `ClientReplication::sample_into_registry` — the per-frame, mutable-registry client step that already writes presented remote poses before the render collectors run (so no collector mutation; stride-safety holds exactly as on the host) — for each mapped remote entity with cached data whose `MeshAnimation.current_state` equals the cached walk state, compute `clamp(speed_xz / move_speed, RATE_MIN, RATE_MAX)` (guard `move_speed <= 0` to rate 1) and apply it through Task 2's epsilon-guarded rebase method. `now` is the frame's animation clock — the `frame_anim_time` value `main.rs` computes for the frame — threaded `net_sample_remote_interpolation` → `client_sample_interpolation` → `sample_into_registry`; it must be the same clock the frame's sampling reads, per Task 2's continuity requirement, never sim/tick time. The derived speed is piecewise-constant between snapshots, so the epsilon guard lands rebases at snapshot cadence (~30 Hz), not per frame. Non-walk states rest at rate 1; a wire-applied state switch needs no special handling — the client apply routes through `switch_animation_state`, so Task 2's shared state-entry reset clears rebase state for free. Accepted, documented limitation: the rate trails true host speed by the interpolation delay and holds at `RATE_MIN` during a brief starvation freeze — correct for feet tracking the *rendered* floor motion, and why no wire field is added.

## Sequencing

**Phase 1 (sequential):** Task 1 — file split; Tasks 2–4 touch or extend the extracted module's surface.
**Phase 2 (sequential):** Task 2 — the substrate Tasks 3 and 4 write to.
**Phase 3 (concurrent):** Task 3, Task 4 — both consume Task 2's rebase method and are otherwise independent (Task 3 is the host sim-tick path; Task 4 is the client frame step in netcode files).

## Open questions

- **Rebase epsilon.** Rebasing on every tick is correct but noisy; a small rate-delta epsilon (e.g. 0.02) trades imperceptible cadence error for fewer writes. Tune during implementation; both are correct by the continuity AC.
- **Walk-state identification.** "The looping locomotion state" is today exactly the alert-mapped walk state from the reference descriptor. If future archetypes name multiple locomotion states, identifying them may need a state-table flag — deferred until such an archetype exists.
