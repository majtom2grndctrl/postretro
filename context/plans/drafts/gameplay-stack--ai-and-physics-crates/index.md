# gameplay-stack--ai-and-physics-crates

## Problem

Developer-raised, the epic's final milestone. After M2 the gameplay monolith did not shrink — it moved from the binary into `postretro-sim`, now the workspace's largest crate at roughly double the binary (sizes in `research.md`). Enemy AI is the churn locus yet lives inside sim, so every AI edit recompiles sim and its large `postretro-netcode` dependent. The primary metric is warm-cache compile time, not raw LOC. When this is done, an AI-logic edit recompiles `postretro-ai` and relinks the binary, rebuilding neither `postretro-sim` nor `postretro-netcode`; a new `postretro-physics` leaf carries collision, movement, and kinematic movers out of sim so routine sim-proper edits compile a smaller crate; the spatial query types are provably thread-shareable for the pathfinding work that follows; and runtime performance is unchanged.

## Decisions

- **`postretro-ai` sits above `postretro-sim`; sim stops depending on ai.** Carve `scripting_systems/ai/` into `postretro-ai`. The decisive edge is the tick call: `sim::simulate_tick` / `simulate_tick_with_presentation_aim` take `&mut AiRuntime` and call `run_ai_tick_with_navigation_and_impact` directly. Invert it — sim exposes that call as an injected closure (the `post_movement` / `on_impact` pattern the seam already uses), the binary constructs `AiRuntime` (it already does; sim never constructs it in production) and supplies the closure. Only the binary calls `simulate_tick` in production; netcode's `#[cfg(test)]` harnesses also call it and update to the new seam (see Path). Without the inversion the carve is a directory rename — editing ai would still rebuild sim, netcode, and the binary.
- **Divergence from the committed M3 framing.** The epic hub and `development_guide.md` §Target shape frame M3 as a "scripting-VM decomposition" — sink the script store + reaction dispatch to `scripting-core` (the epic hub adds inverting a host→systems registration). Source at read-at falsifies that premise: ai has zero non-test references to the script store or reaction dispatch, `scripting-core` already owns both, `AiRuntime` is plain data, and no host→systems registration exists (sim calls ai directly). The VM-decomposition work is already done or never applied. Both docs are corrected at promotion; the milestone shrinks to the tick inversion plus the extractions here.
- **`AiHost` trait in sim, synchronous, effects-only.** The injected seam exposes AI's world *effects*: spawn a projectile (returns the new id or none), apply damage, test quiescence, run the deferred-impact callback. Synchronous because the attack path acts then observes within one tick — `spawn_projectile` returns an id the AI branches on, and melee damage is read back by `is_quiescent` before impact dispatch. Deferred "intent" output is rejected: a fire-and-forget batch cannot express act-then-observe without changing behavior. Mechanism in sim, AI is the policy above it.
- **The production `AiHost` impl is reachable from `postretro-ai`'s tests through a `test-support` feature.** sim owns the trait and its concrete impl; the ordering tests that today guard the synchronous contract — act-then-observe, same-batch cross-kill, faction-sentiment view scoping — live in `ai_tests.rs` and move up into `postretro-ai`. They must drive the real sim-backed impl, not a hand-rolled stub, or they degrade to proving an adapter passthrough. sim exposes the impl under a `test-support` feature that `postretro-ai` dev-depends on (the `postretro-combat-model` / `postretro-net` precedent).
- **Two graph queries and two constants sink below both consumers.** `locomotion_animation` and `rest_animation` (both `fn(&BehaviorGraphDescriptor) -> Option<&str>`) and the state-field constants `FACTION_STATE_FIELD` / `ARCHETYPE_TOLERANCE_STATE_FIELD` move down. The load-bearing property is that each lands below every consumer — netcode's client-apply and the sim host — so neither depends on ai; `postretro-foundation`, where `BehaviorGraphDescriptor` already lives, is that home. This severs the one production `netcode → ai` edge (netcode reads `locomotion_animation` in its client-apply path) and the sim-host → ai constant edges (`impact_policy`, `scripting/builtins/data_archetype`). After the sink netcode depends only on sim, so an AI edit never rebuilds it.
- **`postretro-ai` depends on sim + foundation + `postretro-physics`.** It uses sim's `AiHost` trait, `weapon::ProjectileLaunch`, `agent_steering`, and `nav`; foundation's graph/IR types; and `collision` from the physics leaf below. sim does not depend on ai.
- **Extract `postretro-physics` (collision + movement + kinematic_mover) as a leaf below sim.** Shrinks the sim compilation unit for the frequent sim-proper edits (scripting host, weapon, combat). Verified closed production subtree: `movement → collision` only; `kinematic_mover → collision + movement`; `collision` is a zero-dependency leaf. Everything that reads collision — AI perception, sim `weapon`, netcode — takes a clean down-edge. Leaf placement holds only while movement and kinematic movers stay near-stable; that compile trade-off is owner-accepted (`research.md`). `postretro-physics` is a working name; final name is the owner's.
- **`nav` stays in sim.** The multi-threaded-pathfinding project will rewrite it; churny code stays high so its edits do not rebuild a leaf's dependents. `nav` depends down on `postretro-physics` for `collision`.
- **Reads stay concrete; runtime performance is preserved.** AI's hot reads (perception raycasts on `collision::CollisionWorld`, `nav::{find_path, distance_xz}`, `combat_positioning`, `agent_steering`) stay direct shared-ref calls, never routed through the `AiHost` handle — the reason is borrow shape (holding the effect handle across queries is the exact interleaving that blocks multi-threaded pathfinding), not vtable cost. Both extractions are plain module moves — concrete types, no new dynamic dispatch — so cross-crate inlining and per-tick crossing cost match M2's proven sim↔netcode boundary (`research.md` §Runtime safety).
- **MT-readiness ships as guard rails, not the mechanism.** Add `Send + Sync` static assertions on `NavGraph` (sim) and `CollisionWorld` (physics), and a design note pinning the real blocker — registry borrows via `perception::enemy_eye` interleaved with `find_path` in the AI tick — as the pathfinding project's first task. `find_paths_batch` is deferred to that project: its signature (request identity, result ordering, per-thread A* scratch) is the scheduler's to decide, and committing it now without its consumer is a stub.
- **Non-goals.** No spatial-substrate crate — `NavGraph` / `CollisionWorld` are already `Send + Sync`, Rc/RefCell-free, and passed by shared ref, so a boundary enforces a property that already holds, and extracting soon-to-rewrite `nav` as a leaf is backwards. No deferred-intent AI output; no dynamic dispatch on AI's hot read paths. No `find_paths_batch` this leg. No further sim split — `weapon` reaches up into `scripting_systems` (sim-core) and the scripting host is the second churn locus, so neither is a clean leaf this leg; no binary-side extraction. No AI-behavior, wire-format, scripting-semantics, or SDK-typedef change; behavior-preserving; no net-new `unsafe`.

## Path

Non-binding. Re-ground against the live tree if source moved since read-at. Derivation and the full edge inventory are in `research.md`.

- **Sequence.** Physics extraction first — a mechanical move of a closed subtree, an easy green checkpoint. Then the AI carve and tick-edge inversion on the settled graph. Then the MT-readiness asserts and note.
- **The tick seam** is `sim::simulate_tick` / `simulate_tick_with_presentation_aim`, already fully data-injected (`plans/done/M15--p0-headless-sim-seam/`). The `AiRuntime` parameter and the direct `run_ai_tick_with_navigation_and_impact` call become the injected `AiHost` closure; `AiTickInputs` stays the read surface.
- **Precedent.** `plans/done/E19--renderer-gpu/` moved a subtree in one cut so `super` paths survived — a partial cluster does not compile, so move each crate wholesale. `postretro-combat-model` / `postretro-net` show the `test-support` / `dev-tools` feature pattern for test helpers reached across a new boundary; netcode's two test-only `AiRuntime::new` uses and its production `locomotion_animation` call follow the foundation sink.
- **Shape and rival.** Chosen: AI above sim, tick edge inverted. Strongest rival: AI as a sim sibling over a shared spatial-substrate crate — rejected because the substrate's thread-safety already holds and `nav` is about to churn (`research.md`).
- **Watch.** `kinematic_mover`'s one `scripting_systems::health` reference and `movement`'s one `alloc_probe` reference are both test-only at read-at — re-verify before moving the crate; each crosses the new boundary behind `test-support`, never `#[cfg(test)]`. netcode's `#[cfg(test)]` harnesses call `simulate_tick` and construct `AiRuntime`, so the tick-seam signature change lands in those harnesses too. `data_archetype::find_descriptor` is a pure lookup over the already-injected descriptor slice (Open questions).
- **Manifests.** New crates declare `dev-tools` where they carry debug paths and the binary forwards it (as for net / renderer). `research.md` holds the per-crate dependency and feature inventory.
