## Corrections
- **A client's clean disconnect reaches the host as a timeout.** Path: "the clean disconnect is a `NetClient` method that sends netcode's disconnect packets", and `close_cause_from` maps `DisconnectedByClient` to `CloseCause::Disconnect`. Actual: `NetcodeClientTransport::disconnect` sends a single netcode `Disconnect` packet, synchronously and unacknowledged. On the host, renet_netcode handles it by calling `RenetServer::remove_connection`, which reads the reason from the server-side connection object. That object never records one, so the reason defaults to `DisconnectReason::Transport` (renet 2.0.0 `server.rs:129`). A netcode keepalive timeout takes the same path. Only local clients (`disconnect_local_client`) ever produce `DisconnectedByClient`, so over the netcode transport `close_cause_from` always returns `Timeout`. Approach: before each `transport.update`, `NetServer` samples `transport.time_since_last_received_packet` for every connected client. A `Transport`-reason disconnect from a client whose sample plus `dt` is under netcode's timeout cannot be a timeout, so it closes as `CloseCause::Disconnect`. A timeout needs the last packet to be older than the timeout window, and every other disconnect path carries its own non-`Transport` reason, so this rule is exact rather than a heuristic. Losing the one disconnect packet falls back to a keepalive timeout, which takes 15 s. The loopback acceptance rows lose no packets, so this fallback does not affect them. Task 1 tests this first. The Decision ("the host closes the slot as a disconnect, not a timeout") stands.
- **`returnToFrontend` carries no source or origin.** `SystemReactionCommand::ReturnToFrontend` is argumentless, and `refuse_client_level_verb` warns on a client whatever fired the step. Approach: `ReturnToFrontend`, `LeaveSession` and `EndSession` commands each carry `dispatch_source` and the fire context's `FireOrigin`. The App drain warns for `EveryMachine(OwnState)` and logs at debug for every other origin. Origin decides only how loudly a refusal logs, never what the step does, so the Decision "only role decides what a step does" stands. `loadLevel` and `restartLevel` keep their warning, which existing tests and `scripting.md` §10.4 rely on.
- **A post-`wait` `endSession` on a client is dropped by the scheduler, not by the drain.** `endSession` is a host consequence, so `ClientLanding` drops it and `report_client_drop` logs a generic warning that does not name `leaveSession`. Approach: `report_client_drop` adds the `leaveSession` hint when the dropped step is `endSession`. It keeps today's rule that only an own-state tail warns. This meets the Acceptance wording for both the direct case and the post-`wait` case.
- **Steps after a leave.** The brief says "queued steps after `leaveSession` in the same reaction, and the `fire` targets they reach, drop". The frame-end drain cannot tell which reaction queued a command: `fire` targets carry their own fire context. Approach: once a leave lands, the rest of that drain drops at debug. Store writes and grants already applied at dispatch, so nothing they wrote is lost. The steps dropped beyond the leaving reaction's own belong to a level that is being unloaded in the same frame. Pin P1 ("the level queue holds only the leave's frontend requests") and P15 require this outcome anyway. This is a clarification and keeps the Decision's meaning.
- **The running client poll ignores transport failure.** The `Running` frame calls `let _ = client.update(dt)` (main.rs, before `client_drain_control`), while the world-less path returns `WorldLessPoll::Failed`, and only a host acts on that. A host-side ending must surface on both paths. Approach: `NetClient` reports the end of an established connection, or the failure of its last connect attempt, as a typed `ConnectionEnd`. Both poll paths route it to the client's leave path, in the same Control-drain position as a session-ended cause, so the ending takes effect before that frame's ticks.

## Delegated answers
- **Should leaving or an ended session show the player a notice?** Answer: a log line only, the brief's default. Reason: the engine has no player-facing notice surface outside mod-authored UI trees. Choosing that surface and its wording is a UI decision for the in-app join brief (order 3), which first gives the player a way to act on the notice. No notice ships here, so this brief does not need to cover the client's failed host-named load.
