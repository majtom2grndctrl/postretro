## Problem
Owner-raised, from a 5 h 54 m hallway bake on the owner's Mac. Parallelism was deferred while maps were small (`research.md` §Prior deferrals). `stress-warren-hallway-inspection.map` breaks that assumption. The base SH bake is 56% of the wall time and already runs at the 14-permit cap, so more threads cannot help it; cheaper rays can. The rest of the build averages about 3 busy cores, not 14. The causes are all in code. The lightmap bake is a serial loop over (atlas layer × light), with a fork-join barrier and a serial tail between each pair. Each small cache entry pays a full-device fsync and a create-and-rename in one flat directory, which leaves the delta SH stages idle in syscalls. Under the 2 GiB default the start-of-build prune evicts the hallway's SH family, so each rebake re-bakes it. Stages with no data dependency run one after another. Every ray walks the BVH unbounded and unordered, testing geometry past its segment end or behind its nearest hit. When done, the hallway bake keeps its permits busy outside the base SH bake, every bake does less traversal work per ray, and output bytes are unchanged.

## Decisions
- **Yardstick: the hallway map on the owner's Windows PC, under pinned conditions.** The hallway bakes there in about 9 h, against about 6 h on the Mac. The conditions are in `research.md` §Measurement conditions, and every before/after number comes from them. The binary is a cargo `--release` build of `prl-build` running warm (cache enabled); cargo's release profile is not `prl-build --release`, which is the cold, uncached ship bake. Small fixtures prove determinism only. The dev profile's opt-level stays as is: it trades bake speed for compile speed during iteration, this brief measures release builds, and changing it is its own decision.
- **Output bytes do not change, in either mode.** The cold `--release` bake is the ship source of truth (`development_guide.md` §1.4). Output must not depend on thread count (`build_pipeline.md` §Build Cache, Determinism invariant). Every lever reorders, overlaps, or prunes work; none changes the math.
- **Scope: idle cores, serial sections, and per-ray traversal cost; not ray count.** Cutting rays per probe or per texel belongs to the `lighting-scale--*` drafts. A nearest-hit query returns the same hit it does today, ties included, and byte identity proves it.
- **The governor contract holds.** Each parallel work item enters the governor once, at its outermost boundary. A permitted item never waits on another permitted item. Pause and throttle stay live (`build_pipeline.md` §Progress reporting). Light-axis lightmap parallelism is a bounded window of lights in which each (light, chart) item enters the governor once, with no nested permit; `plans/done/shadowmask-bake-scaling` Task 2 (`bake_shadowmask_atlas_with_window`) is precedent only. A partition's cache get and put run outside the permit, as in delta SH: the permit guards ray work, not cache I/O.
- **Stage overlap (lever 3) is built only if measurement warrants it.** After levers 1 and 2 land, measure the hallway under the pinned conditions. Build lever 3 if it shows at least 15 minutes of wall time outside the base SH bake with under half the permits busy while a stage lever 3 could start early waits; otherwise skip it and record the numbers (`research.md` §Lever 3 gate). If built, stages overlap under `build_pipeline.md` §Progress reporting: exactly one foreground stage, an overlapped stage begins in the background, one global governor.
- **Lever 4 is optional.** Per-stage serial setup is unmeasured. The executor profiles it and cuts only what the profile shows; it carries no Acceptance row (`development_guide.md` §1.4).
- **Hallway peak RSS does not regress.** Lever 1's window bounds resident partitions. If lever 3 overlaps any SH-family stage, re-derive the copy-chain factor behind `--sh-delta-working-set-max-size` (`plans/done/lighting-scale--compile-peak-ram`), which counts co-residency under today's one-stage-at-a-time order. Hosts and evidence: `research.md` §Peak memory.
- **Atlas preparation stays after the SH family.** `build_pipeline.md` §Atlas preparation and SH ordering calls that order load-bearing: Direct SH Delta can clear entity-shadow selection, and deterministic channel assignment must finish before the fused atlas walk. The SH family also bakes uncut geometry: the cut rebuilds the pre-atlas face-identity set after it, so SH cache keys stay density-independent (`build_pipeline.md` §Compiler pipeline, step 10).
- **Cold and warm share the structure.** The lightmap's serial (layer × light) loop runs in both modes (`bake_fused_prepared`). A lightmap fix must speed up `--release` too, not only the cached path.
- **Cache writes drop the per-entry `sync_all`.** `build_pipeline.md` §Build Cache calls the cache disposable, `get` verifies blake3, and the temp file plus atomic rename already turn a killed or torn write into a miss. Only power loss is affected, and it also yields a miss. Entry format and keys are unchanged.
- **The start-of-build prune spares each map's record.** Per map, it spares the entries that map's last successful build read or wrote, plus every entry later builds of that map read or wrote, until the next successful build of that map replaces the record. A killed or failed build therefore never costs work, and a build of another map does not expose this map's set. A lightmap or shadowmask section-memo hit also marks the per-light partitions it summarizes as used. The budget, still 2 GiB by default, caps everything else, and `StageCache::warn_if_live_set_exceeds` reports the total spared set against it. The mechanism is the executor's and needs persisted per-map state, since `live_entries` is in memory only. Lever 2 changes `touch_for_lru`, and a hit must still mark its entry as used. `build_pipeline.md` §Build Cache already states the rule, marked not yet built; the same change drops the marker. Argument: `research.md` §Cache budget on large maps.
- **Lever 5's baseline is today's per-face BVH leaf set.** Bakes keep the per-face tree under `bvh-leaf-clustering`, which lands after this brief.
- **Baselines are taken on main after `lightmap-oversize-cells-and-faces` (#544).**

## Acceptance
### Automated
- [ ] A cold `--release` fixture bake is byte-identical before and after, at `-j 1` and at the default `-j`.
- [ ] A warm all-miss bake followed by a warm all-hit bake of the same fixture emits identical `.prl` bytes, and both match the pre-change warm bytes. The all-hit bake reads every entry the all-miss bake wrote, with zero cache misses.
- [ ] With a window of at least two lights, a later light's partition that is ready before an earlier one's is still folded and consumed after it. A test holds the earlier light's first chart until the later light's partition is ready. It records fold and consume order as ascending by global light index, and emits the window-1 bytes. (pin P1)
- [ ] For rays aimed exactly at an edge two triangles share, the nearest-hit query returns the same distance and normal as today's full scan. The triangles meet at a crease, so their normals differ. The fixture has one such edge inside a single face's leaf and one between two faces' leaves. Occlusion queries give today's answer for segments ending just short of, exactly at, and past a blocker.
- [ ] A ray lying in a BVH node's bounding-box face plane, parallel to it, and a ray starting on the triangle the traversal reaches first, each give today's nearest-hit and occlusion answers. (pin P2)
- [ ] Lowering permits to 1 mid-lightmap-bake leaves at most one lightmap ray-work item running once in-flight items drain. A bake started at one permit, and one lowered to one while a window is partly baked, each complete with the unthrottled bytes. Pause stops new items within the lightmap bake and within any stage that now overlaps another. (pin P3)
- [ ] At one permit, with a lightmap window of at least two lights, a test holds one light's partition cache put open, and in a second case a cache get. Before the held I/O is released, another light's chart ray work starts; the test fails if it does not. At most one chart item runs at a time, and the bake completes with the unthrottled bytes. (pin P11)
- [ ] If lever 3 is built: two stages that previously ran one after another now run together, exactly one stage holds foreground throughout, and the background stage's progress advances before the foreground stage finishes.
- [ ] If lever 3 takes AnimWeightMaps' lightmap-emptiness input before the fused walk finishes, that input equals the finished section's `blocks.is_empty()` for no static lights, all-SDF static lights, and a lightmap section-memo hit. (pin P4)
- [ ] On a fixture with more lights than the lightmap window, at a permit count above the window, the lightmap bake never holds more baked-but-unfolded light partitions than the window allows. The count includes partitions awaiting cache write, fold, or shadowmask consume. The count reaches the window, in a cold bake and in a warm all-miss bake.
- [ ] The `lightmap_stage::predicted_peak` prediction includes the lightmap window's resident partition bytes: on the window fixture it rises with the window size, and at a window of one it equals today's prediction plus one partition.
- [ ] On a fixture where one light reaches only some of a layer's charts, plus a directional light, the culled bake emits the unculled partition bytes. The lightmap stage's progress still completes at its published total. (pin P5)
- [ ] Regression guard for dropping the fsync (passes today): deleting or truncating a cache entry, or killing the build mid-write, gives a miss on the next build, never a wrong hit.
- [ ] Lightmap, shadowmask, delta-SH, and weight-map stage tests pass with their assertions unchanged. Cache-load counts come from `StageCache::test_access` rather than captured log lines, since log capture is per-thread.
#### Cache prune
Unless a row says otherwise, it runs under a budget smaller than the map's set. Each build opens its cache through `construct_stage_cache`, `prl-build`'s own build-start sequence.
- [ ] The next build of a map keeps every entry the previous successful build wrote and every entry it only read, and still evicts an entry neither touched. The only-read entry was written before the previous build began. (pin P6)
- [ ] A build stopped after reading and writing entries, before its end-of-build step, is followed by a build of the same map. The second build's prune keeps every entry the stopped build read or wrote, and every entry of the last successful build. (pin P7)
- [ ] After a no-edit rebuild whose lightmap and shadowmask section memos both hit, a build that changes one light's intensity re-bakes only that light's partitions and hits every other light's. (pin P8)
- [ ] Building map A, then map B, then A again: the third build has zero cache misses. (pin P9)
- [ ] A build of A that fails at parse, between two successful builds of A, changes nothing: the third build evicts the same entries it would without the failed build, and has zero cache misses. (pin P10)
- [ ] On a small project whose live set fits the budget, repeated builds that each orphan older entries leave the cache at or below the budget after each start-of-build prune.

## Path
Levers keep their labels. They are listed by the hallway wall time each addresses. Symbols and derivation are in `research.md`.
- **Lever 5: BVH traversal, the base SH bake's 11,939 s plus every other bake's rays.** Every site hands the stock `traverse_iterator` an infinite ray. The one closest-hit site, `sh_bake::closest_hit`, tests every leaf that ray crosses. Each occlusion `segment_clear` exits on its first hit but still visits leaves past the segment end, so a clear segment tests everything behind the light. Shape: a caller-defined query on the same iterator that also rejects nodes entered beyond the segment end, or beyond the best hit so far. Visit order is unchanged, so today's tie winner is too. But the iterator visits left child first, so the best hit may shrink late, and the bound may prune little for SH's 256 infinite closest-hit rays per probe; their share of SH cost against the soft-visibility shadow rays is unmeasured. Rival: a stack-based near-child-first walk that keeps the nearest hit by the key (distance, depth-first leaf rank, triangle offset), which reproduces today's winner. `nearest_traverse_iterator` is the weaker rival: heap per ray, no node distance to stop on. The saving is unmeasured. Profile one hallway SH group first, comparing the bound-only query on the stock iterator against near-first with the tie key; either shape keeps output bytes identical.
- **Lever 1: lightmap light axis, about 7,400 s at 4 or fewer cores.** Bake several lights' partitions for one layer at once, then fold them serially in global light order; `IncrementalLayerAccumulator::fold_partition` documents that order as the determinism guarantee. Keep the per-chart work units. Take the cache put, fold, and shadowmask consume off the ray-work barrier, in the main loop and in the lightmap-hit, shadowmask-miss loop. `bake_shadowmask_atlas_with_window` is a reuse candidate for the bounded window, which also sets lever 1's added peak memory. Cheap companions:
  - cull each light's chart list by the light's bounds; today every chart is walked for every light;
  - build each layer's face list once, not per (layer, light) in `bake_light_layer_controlled`;
  - hoist `probe_indices` per light;
  - compute `atlas_layout_fingerprint` once per bake and the light-only hash parts once per light, and skip the `layer_input_hash` pre-pass when there is no cache.

  Rival: keep lights serial and split charts into texel tiles. That fixes the large-chart tail but not the per-partition serial tail.
- **Lever 2: cache write path, delta SH stages at about 650 s plus tax inside every cached stage.** Beyond the fsync, each put does a create, several unbuffered writes, and a rename in a directory of about 142k entries. Each hit opens the file a second time in `touch_for_lru`. On this map that is the whole cost of Direct SH Delta.
- **Lever 3: overlap independent stages, up to about 1,000 s before levers 1 and 2; built only if the measurement after them clears the 15-minute bar (Decisions).** The five SH-family stages overlap one another. Their one join point is Direct SH Delta's post-bake usability check against Direct SH's output; the delta plans and entity-shadow selection come from `plan_delta_bakes` before SH starts. AnimLightChunks and AnimWeightMaps overlap the fused lightmap walk: they read atlas placement and the BVH. Their one read of lightmap output is `lightmap_section.blocks.is_empty()` in `layout_animated_atlas`, which must be derived before the walk or taken at a join after it. Otherwise only an unused `&mut geometry` borrow in `bake_fused_prepared` blocks them. Atlas preparation does not move. Overlap mostly helps the I/O-bound delta stages.
- **Lever 4: serial setup redone per stage.** Candidates:
  - `probe_grid_layout` BSP queries, once per SH stage;
  - affinity decomposition, recomputed by each delta bake after the plan already ran it;
  - a scan over every geometry vertex per delta entry;
  - an O(n²) chunk-overlap assert that runs in release;
  - serial BC6H, BC5, and shadowmask coloring.

  None is measured. Profile before cutting.

First slice: lever 1 on the lightmap bake alone, proven byte-identical, then one hallway lightmap timing. It carries the largest measured idle-core share and the most determinism risk.
