# prl-build TUI Enhancements

## Goal

Two focused quality-of-life improvements to the `prl-build` interactive TUI (`crates/level-compiler/src/tui/`). (1) Collapse the long "Compile steps" sidebar into an automatic accordion: stages are grouped into named sections, and only the section holding the active stage is expanded. (2) Add a pre-bake configuration screen that prompts for the bake's quality parameters with production-vs-rapid-iteration guidance, shown when the operator did not already set any quality flag on the command line. Both are presentation-only — neither changes a single byte of the emitted `.prl`.

## Scope

### In scope

- **Accordion sidebar** in the full-layout Compile-steps panel: a fixed, ordered set of named sections partitioning the 23 pipeline stages; only the active stage's section expands; collapsed sections show a label row plus a status/progress summary.
- **Pre-bake config screen**: an interactive modal, shown only in TUI mode when no quality flag was passed, that edits the numeric bake-quality parameters and the build mode, displays guidance, validates against the CLI parser's existing rules, and either starts the bake with the chosen values or cancels cleanly.
- **Parser change**: track which quality flags were explicitly supplied so the config screen's trigger condition can be evaluated.
- **Launch-seam change**: derive the stage cache from the *post-config* `Args` so a build-mode edit actually takes effect (see Task 2 — this is load-bearing, not incidental).

### Out of scope

- Any change to compact-layout rendering (`draw_compact`). The accordion is a full-layout-only change; compact already renders just the focused step.
- Editing input/output paths, `--format`, `-j/--jobs`, `--cache-dir`, `--verbose`, `--sh-analyze*`, or `--sh-protect-aabb` from the config screen. The screen covers bake-quality parameters and build mode only; every other flag stays CLI-only. The resolved input/output paths are *displayed* read-only for orientation (not editable).
- Manual expand/collapse of accordion sections. The open section is always the one containing the active stage — no navigation keys.
- Terminal behavior outside the config-to-bake handoff. The config form and running-bake view share one `TuiSession`, preserving one continuous alternate screen; cancellation and errors still restore the normal terminal before reporting.
- Changing the plain (non-TTY) reporter, the running-bake controls (pause, core throttle, log scroll), or the detach path.
- New quality parameters or new presets stored in the map/PRL. The screen edits existing CLI-equivalent values only.

## Direction

**Problem.** Two symptoms of the same cause — the interactive compiler surfaces too much at once and configures through an opaque flag set. The steps sidebar lists all 23 stages as a flat scroll, and bake quality is driven by a dense flag list (`--sh-probe-spacing`, `--lightmap-density`, `--soft-shadow-samples`, `--sdf-voxel-size`, `--release`/`--no-cache`) whose production-vs-iteration meaning lives only in `--help`. Both are presentation gaps in the TUI front end, not defects in the compile pipeline.

**Prior commitments.** `build_pipeline.md` §"Progress reporting, controls, and logging" fixes the front-end contract: the orchestrator (`pipeline.rs`) drives a `Reporter` (`reporter.rs`) per stage and never assumes a frontend; the `TuiReporter` (`tui.rs`) renders when stdin/stdout/stderr are all TTYs. "Progress is display-only" — counters never flow back into bake output, so the `.prl` stays byte-identical to a straight-through build. Both enhancements live entirely inside the TUI front end and preserve that invariant: the accordion is pure rendering, and the config screen only mutates the parsed `Args` (and the cache derived from it) *before* the bake worker starts, exactly as if the operator had typed the same flags. The stage set and its order are owned by `pipeline.rs` (`StageId`, `ORDERED_STAGES`); the accordion's section grouping is a display-only overlay keyed by `StageId` and does not touch that ownership. The warm-vs-exact bake branch is gated solely by whether the pipeline receives `Some(StageCache)` or `None` (`pipeline.rs` reads the cache handle, never `args.release`/`args.no_cache`); that fact drives the launch-seam ordering in Task 2.

**Alternatives rejected.** For the sidebar, a scrollable flat list with manual fold controls was rejected: the operator watching a bake wants the active work in view without input, and the pipeline already defines a single active stage to follow — automatic accordion needs no keys and cannot desync from the bake. For configuration, a separate `--preset production|fast` flag was rejected as the primary lever: it adds a parallel configuration surface to maintain and still hides the individual values. The screen instead edits the existing flags directly, so there is exactly one source of truth (the `Args` fields) and the guidance teaches the real knobs.

The closest rival is a **read-only confirmation screen** — show the effective quality values plus guidance, Enter to start / Esc to cancel, no in-place editing — which would drop the field editor, the validation, and the untouched-density rule. Rejected on the audience: the screen exists to make the tool accommodating to level designers who are less comfortable with the command line, and a read-only screen forces exactly the operator it targets to cancel, reconstruct the right flag, and re-run. Editing in place is the feature, not incidental to it. The cost the read-only rival avoids is real but bounded — the validation is a small, well-specified mirror of the parser's rules (four numeric checks against named constants), and the KVP subtlety is one pinned rule with a test — and it is the cost of keeping the less-technical designer inside the tool.

## Acceptance criteria

**Accordion sidebar (full layout only)**

- [ ] The Compile-steps panel renders the four fixed sections (Parse, World, Lighting, Pack) whose members together are exactly the pipeline stages present for the map, in `ORDERED_STAGES` order; a section with no present stage renders nothing.
- [ ] Exactly one section is expanded at a time: the section containing the active stage. Its member step rows render (with their existing per-step markers); every other present section shows only its label row.
- [ ] Every section header row (expanded and collapsed alike) carries a status summary: a glyph reflecting the section's aggregate state and a completed-count readout (done/total member steps, where "done" counts members whose status is Done or Skipped, matching the aggregate rule). The aggregate is: Failed if any member is Failed; else Active if any member is Active; else Done if all members are Done or Skipped; else Pending. The aggregate glyph reuses the existing per-step status markers (the `step_line` marker set) for the corresponding status.
- [ ] The open section is derived deterministically: the section of the active stage (`TuiState::active_index()`); when no stage is active, the section of the **last non-Pending step** — defined as the present step with the greatest `ORDERED_STAGES` index whose status is not Pending; when nothing has started (all Pending), the first present section. The failure case is subsumed by this rule (a failed build's `Failed` frontier is the highest-index non-Pending step) — there is one rule, not two competing ones.
- [ ] With two stages Active at once (the pipeline holds `EntityShadowLights` open while `DirectShDeltaBake` runs), only the section of `active_index()`'s stage (the most-recently-begun) is open. Because those two stages are co-sectioned (see the partition invariant), the other Active stage is never orphaned into a collapsed header, and the open section does not flip while both are Active.
- [ ] On build failure the section containing the failed stage is expanded (via the last-non-Pending rule) and that stage shows the failed marker; no step renders a live spinner.
- [ ] When the expanded section's rows plus the collapsed header rows exceed the panel height, the active stage stays visible (the existing centered-scroll fallback applies over the rendered rows), including across an open-section change that alters the total row count.
- [ ] The active-stage progress footer (percent, ETA, and determinate progress bar) is unchanged.
- [ ] Compact layout output is unchanged from the current behavior.

**Config screen**

- [ ] In TUI mode, when none of the gating quality flags was supplied on the command line, the bake is preceded by an interactive screen listing the four numeric quality parameters (SH probe spacing, lightmap density, soft-shadow samples, SDF voxel size) and a build-mode choice (rapid iteration vs production), each with a current value and one-line guidance, plus the resolved input/output paths shown read-only.
- [ ] Displayed default values and guidance are derived from the live default constants (`sh_bake::DEFAULT_PROBE_SPACING`, `lightmap_bake::DEFAULT_TEXEL_DENSITY_METERS`, `lightmap_bake::DEFAULT_AREA_SAMPLE_COUNT`, `lightmap_bake::SOFT_PROBE_SAMPLES`, `sdf_bake::DEFAULT_VOXEL_SIZE_METERS`), so they never drift from what the parser applies.
- [ ] The lightmap-density row's current value shows the effective density under existing precedence (`resolve_lightmap_density(args.lightmap_density, map_data.lightmap_density)`), i.e. the worldspawn `_lightmap_density` KVP when the map sets one, else the engine default — not the engine default blindly. The row indicates when the value comes from the map KVP versus the default.
- [ ] Confirming (Enter) starts the bake using the screen's values; the resulting build is byte-identical to running `prl-build` with the equivalent flags for the same input — for the numeric parameters **and** the build mode. Verified at unit grain via the testable proxies (post-config `apply_outcome` writes the expected `Args` fields; build mode → `stage_cache == None`/warm-`Some` per C1/C2), since full byte-identity needs an actual compile; a true byte-identity integration test is optional, not required for this AC.
- [ ] Selecting production makes the bake take the exact ship path: the stage cache is derived from the post-config `Args`, so production yields `stage_cache == None` and a build byte-identical to `prl-build --release`; rapid iteration yields the warm cache and a build equal to `prl-build` with no quality flags. Build-mode maps as: production → `release = true` (`no_cache` left false; the cache decision honors `release`), rapid iteration → both false.
- [ ] Editing a field applies the CLI parser's validation rules (probe spacing, density, voxel size each finite and > 0; soft-shadow samples an integer ≥ `SOFT_PROBE_SAMPLES`). An invalid entry is rejected inline and blocks starting the bake until corrected.
- [ ] If the lightmap-density field is left untouched, `Args.lightmap_density` stays `None` so the worldspawn `_lightmap_density` KVP precedence is preserved; editing it sets the override.
- [ ] The screen redraws every loop iteration and handles `Event::Resize` by clearing and redrawing (mirroring the running-bake loop), so a resize mid-edit shows no stale cells.
- [ ] Cancelling the screen (Esc, `q`, or Ctrl-C) exits without baking and returns success; the config `TerminalSession` is restored to the normal screen before the cancellation message and the warning summary print. The terminal is likewise restored before any error from the screen propagates.
- [ ] When any gating quality flag (`--sh-probe-spacing`, `--lightmap-density`, `--soft-shadow-samples`, `--sdf-voxel-size`, `--release`, `--no-cache`) is supplied, the screen does not appear and the bake runs with the supplied values. Non-gating flags (`-j`, `-v`, `--uncompressed-irradiance`, `--cache-dir`, etc.) neither suppress the screen nor are edited by it.
- [ ] In plain (non-TTY) / `--no-tui` mode the screen never appears, regardless of which flags were supplied.

## Tasks

### Task 1: Accordion sidebar for the Compile-steps panel

Rework the full-layout Compile-steps sidebar (`crates/level-compiler/src/tui/tui_render.rs`, `draw_steps` / `step_line` / `active_scroll_offset`) into an automatic accordion. **Split first:** move the Compile-steps-panel rendering into a new `tui/tui_steps.rs` submodule (behavior-preserving move of `draw_steps`, `step_line`, `active_scroll_offset`, and the steps-panel tests; add `mod tui_steps;` to `tui.rs`). Widen to `pub(super)` whatever the moved code references from `tui_render.rs` — at least the footer's `SECONDARY` color and `progress_bar_line`/`divider_style`, plus `PRIMARY`/`MUTED` — rather than a fixed list; `draw_compact` and the footer keep using those. `draw_steps` itself must become `pub(super)` so `draw_full` (which stays in `tui_render.rs`) keeps calling it across the new module boundary. (`ACTIVITY_FRAMES` lives in `tui.rs`, the parent module, and is already reachable from any child via `super::` — no change needed for it. The glyph consts `PROGRESS_FILLED`/`PROGRESS_EMPTY` stay private inside `progress_bar_line`, which does not move.) Then add the section grouping: a fixed, ordered table mapping each `StageId` to one of four named sections, defined once in the tui module — **Parse** (Parsing, DataScript, TexValidation), **World** (Partitioning, Visibility, Geometry, BVH Build, Cell Visibility, NavMesh), **Lighting** (LightmapBake, SH Bake, Delta SH Bake, Direct SH Bake, Animated Direct SH Bake, EntityShadowLights, Direct SH Delta Bake, ShadowmaskAtlas, ChunkLightList, AnimLightChunks, AnimWeightMaps), **Pack** (SDF Atlas Bake, TextureMips, Packing). This table is fixed, not a starting point — it is a contiguous, total partition of `pipeline::ORDERED_STAGES`, and it co-sections the only pair of stages that can be Active simultaneously (`EntityShadowLights` and `DirectShDeltaBake`, both in Lighting). Add a unit test asserting three properties over every `StageId`: each stage appears in exactly one section (totality); flattening the table reproduces `ORDERED_STAGES` in order (contiguity); and no section boundary falls between `EntityShadowLights` and `DirectShDeltaBake` (the co-section guard). `ORDERED_STAGES` is currently private to `pipeline.rs` — either widen it to `pub(crate)` there, or have the test derive the canonical order from `pipeline::planned_stages(...)` (which returns descriptors in `ORDERED_STAGES` order); do not assume direct access. Build the render row list from `TuiState.steps` (already filtered to `predicted_present` stages): for each section with ≥1 present step, emit a header row (label + aggregate status glyph reusing the `step_line` marker for the aggregate status + a `done/total` count where done = members with status Done or Skipped); if the section is the open one, follow it with that section's present step rows. Determine the open section per the AC-pinned rule: the section of `TuiState.active_index()`'s stage; when `active_index()` is `None`, the section of the last non-Pending step (greatest `ORDERED_STAGES` index whose status ≠ Pending — the failure case is subsumed here); the first present section when every present step is Pending. Aggregate a section's status from its present members' `StepStatus` (Failed if any Failed; else Active if any Active; else Done if all Done/Skipped; else Pending). Preserve the centered-scroll fallback (`active_scroll_offset`) but compute it over the rendered row list, tracking the active step's row index, so the active step stays visible when headers + open rows overflow. Leave the footer (active progress bar + ETA) and `draw_compact` untouched. Cover with `TestBackend` render tests keyed to the pin-table rows P1–P8 (§Orderings): only the active section expands; collapsed and expanded headers both show a summary; a zero-present-step section is omitted; overlapping actives keep one open section (P1); a skip-heavy no-animated-lights run advances the open section monotonically (P4); the completion frame opens Pack with no spinner (P7); a mid-list failure opens the failed stage's section via the last-non-Pending rule (P8); and overflow keeps the active step visible (P5).

### Task 2: Pre-bake configuration screen

Add an interactive configuration screen shown before the bake in TUI mode when no quality flag was set, editing the bake-quality parameters with guidance.

**Parser change** (`crates/level-compiler/src/main.rs`): the hand-rolled `parse_args_from` currently overwrites local defaults in place, losing the explicit-vs-default distinction for `probe_spacing`, `soft_shadow_samples`, and `voxel_size` (`lightmap_density` already distinguishes via `Option`). Track which of the gating quality flags were seen — `--sh-probe-spacing`, `--lightmap-density`, `--soft-shadow-samples`, `--sdf-voxel-size`, `--release`, `--no-cache` — and carry that on `Args` (e.g. a `quality_flag_supplied: bool`, set true if any of those six appeared).

**Launch-seam restructure** (`main.rs`): `stage_cache` is currently built in `main` from `args.release || args.no_cache` **before** the `match reporter_mode` block, and the pipeline gates the warm-vs-exact path solely on `Some`/`None` of that handle — it never re-reads `args.release`/`args.no_cache`. A build-mode edit in the screen (which runs inside the Tui arm) would therefore never reach the cache, silently baking the approximate warm path under a "production" choice. Fix the ordering: extract the cache-construction logic (the `--release`/`--no-cache` decision, directory resolution, `prune_to_budget`, logging) into a helper and call it from the *post-config* `Args`. The Plain arm builds the cache as today. The Tui arm builds it **after** the config screen returns Start (or after determining the screen will not run), so the cache reflects the final `args`. `let args = parse_args()?` becomes `let mut args`.

**New module** `crates/level-compiler/src/tui/tui_config.rs` (add `mod tui_config;` + a `pub use` for the entry point to `tui.rs`): a modal that enters a `TuiSession` and returns that same session with `ConfigOutcome::Start`, so the running-bake view continues in the same alternate screen without a normal-terminal repaint. It renders a form of the four numeric quality parameters, a rapid-iteration/production build-mode choice, and the resolved input/output paths (read-only) — each editable row showing label, current value, and one-line guidance built from the live default constants (interpolated like `help_text` does, never hardcoded). The lightmap-density row's current value is the effective density `resolve_lightmap_density(args.lightmap_density, worldspawn_density)`, labelled by source (map KVP vs default). **Decompose for testability, mirroring the existing `draw` (pure, `TestBackend`-tested) vs `render_loop` (terminal-coupled) split** — do not build a monolith: a pure form-state model, a pure `validate_field` (the numeric rules below), a pure `apply_outcome(&mut Args, &FormState)` writeback (the build-mode → `release`/`no_cache` mapping and the touched-density rule), and a pure `draw_config(frame, &FormState)` render fn exercised by `TestBackend` — with `run_config_screen` as the thin `TuiSession::enter()` + input-loop shell over those seams. The enumerated tests (C1/C2 build-mode writeback, validation boundaries, C6 resize, effective-density display) are written against the pure seams, not by driving a real terminal. The shell's input loop redraws every iteration and handles `Event::Resize` by clearing and redrawing (mirror `tui_worker.rs`'s `render_loop`). Editing model: free-text per-field entry into a string buffer (digits, one decimal point, backspace), committed and validated on Enter or field change; the CLI parser's rules apply (finite and > 0 for probe/density/voxel; integer ≥ `lightmap_bake::SOFT_PROBE_SAMPLES` for samples); an invalid buffer is rejected inline and blocks confirm. Keys: field navigation, in-place editing, Enter to confirm, Esc/`q`/Ctrl-C to cancel (raw mode delivers Ctrl-C as a key event, as in the running-bake loop). The entry point — `run_config_screen(args: &mut Args, worldspawn_lightmap_density: Option<f32>) -> anyhow::Result<ConfigOutcome>` — returns Start or Cancel: on Start it writes the edited values back into `Args` (build mode → `release`/`no_cache` per the AC; an **untouched** density field leaves `Args.lightmap_density = None` to preserve KVP precedence, an edited one sets `Some`; the three other numerics are always written, which equals their default when untouched) and transfers the live `TuiSession` to the bake runner; on Cancel it drops the session, restores the normal terminal, and signals abort. Errors follow the same restore-before-reporting rule. A panic is deferred until terminal cleanup, then reports on the normal terminal.

**Wire it up** (`main.rs`, `ReporterMode::Tui` arm, after `prepare` / `planned_stages`): when `reporter_mode == Tui` and `!args.quality_flag_supplied`, call `run_config_screen(&mut args, prepared.map_data.lightmap_density)` before deriving the cache and calling `run_tui`; on Cancel, print a cancellation message, print the warning summary, and return `Ok(())` without baking; on a screen `Err`, print the warning summary (mirroring `main`'s existing `.inspect_err(|_| log_sink.print_warning_summary())` early-exit pattern; `log_sink` is still owned at this call site) before propagating; on Start, derive the cache from the edited `args` and proceed into `run_tui`. `precheck_output_dir` and `prepare` run before the screen (as they do today), so the output-dir precheck stays on the normal terminal, ahead of any alternate-screen entry. The screen must never run in `ReporterMode::Plain`. Quality parameters do not affect `planned_stages` (`planned_stages` is a pure function of the map's `lights` via `map_needs_sdf_atlas`; stage presence is content-driven, never quality-driven), so editing `args` after `planned_stages` cannot stale the plan and the existing `prepare → planned_stages → run_tui` order is unchanged apart from the inserted screen and the moved cache derivation.

Cover with tests keyed to the pin-table rows C1–C6 (§Orderings): the gating helper (screen shown iff Tui and no gating flag supplied); parser tracking of each of the six gating flags; production → `stage_cache == None` → exact path (C1) and rapid-iteration → warm cache (C2); validation acceptance/rejection at the boundaries including the samples floor; the untouched-density-stays-`None` rule and the effective-value display for a map with a `_lightmap_density` KVP; build-mode → `release`/`no_cache` mapping; and `planned_stages` invariance under all quality-param values (P9).

## Sequencing

**Phase 1 (concurrent):** Task 1, Task 2 — independent. Task 1 reworks the running-bake sidebar renderer; Task 2 adds a pre-bake modal plus a parser field and a launch-seam restructure. They share no logic; both add one `mod` line to `tui.rs` (`tui_steps`, `tui_config`) and Task 2 additionally restructures the `main` cache/launch block, which Task 1 does not touch — a trivial merge touchpoint.

## Rough sketch

- **Sections table.** A `&[(&'static str, &[StageId])]` const (or equivalent) in the tui module. The partition test iterates every `StageId` variant (exhaustive list or match) and asserts totality, contiguity against the canonical `ORDERED_STAGES` order (accessed per Task 1), and the `EntityShadowLights`/`DirectShDeltaBake` co-section guard.
- **Row model.** A helper that, given `&TuiState`, produces an ordered `Vec` of render rows (`Header{label,status,done,total}` | `Step(&StepState)`) with only the open section's steps included, plus the active step's row index for the scroll fallback. `draw_steps` renders that list and runs `active_scroll_offset` over it.
- **Config outcome.** `enum ConfigOutcome { Start, Cancel }`; entry `run_config_screen(args: &mut Args, worldspawn_lightmap_density: Option<f32>) -> anyhow::Result<ConfigOutcome>`.
- **Cache helper.** Extract `main`'s current `if args.release || args.no_cache { None } else { Some(StageCache) }` block (directory resolution, `prune_to_budget`, logging) into a helper taking `&Args`, called post-config in the Tui arm and as today in the Plain arm.
- **Guidance strings.** Build with `format!` interpolating the default constants, e.g. rapid-iteration = warm cache + approximate grouped indirect SH (fast, not shippable); production = `--release` exact whole-volume SH + monolithic lightmap (slow, shippable); soft-shadow samples default 32, higher = softer penumbra/slower; lightmap density default 0.04 m/texel, smaller = finer/slower; probe spacing default 1.0 m, smaller = denser SH/slower; SDF voxel default 0.5 m, smaller = finer occluders.

## Open questions

None blocking.

- **Guidance-prose duplication (accepted).** The production-vs-rapid-iteration explanation already exists in `--release`'s `--help` text. The config screen adds one line of guidance per parameter, which overlaps that prose. Accepted as bounded: the numeric *defaults* stay drift-guarded (derived from the constants, per AC), and the overlap is one short line per row, not a second authored explanation. Not worth a shared-string extraction that would couple the screen module to `help_text`.
