# Lighting Scale — Adaptive SH Probe Density

> **Status:** draft. Spike-led thin vertical slice. **Gated on its own Task 1 measurement** — Tasks 2+ proceed only if the spike confirms adaptive brick density brings the direct-SH delta under target.
> **Track:** Lighting / build pipeline — the O(n³)-storage root-cause lever behind the direct-SH delta storage-buffer wall.
> **Related:** `context/lib/build_pipeline.md` §Octahedral irradiance volume bake, §PRL section IDs (id 34/35 base atlases, id 27/41/45 deltas) · `context/lib/rendering_pipeline.md` §4 (Animated SH delta volumes / Baked direct for dynamic receivers / Promoted static lights), §7.1 step 5 (SH compose passes) · `context/plans/done/lighting-scale--sh-delta-footprint-instrumentation/` (the shipped measurement prerequisite whose recorded evidence this consumes) · `context/plans/done/sh-array-atlas/` (base-atlas D2→D2Array, landed) · `context/plans/done/perf-animated-sh-light-culling/` (the sparse-CSR affinity-cell delta form this extends, and its findings note) · `context/lib/experimental_spikes.md`.

## Goal

The direct-SH delta (`DirectShDeltaVolumes`, PRL id 41) stores one dense 64-probe brick per `(affinity cell, selected light)` CSR entry, at every reached cell, at full base-grid probe density. Measurement (shipped instrumentation, recorded 2026-08-04) shows this is overwhelmingly the SH-storage problem: on the stress map at `--sh-probe-spacing 2.0 --lightmap-density 0.8 --soft-shadow-samples 64`, the direct-delta payload is **401,154,048 B (~383 MiB) of 447,193,334 B total SH data** — already **~3× over the 128 MiB WebGPU `max_storage_buffer_binding_size` spec floor** that is the tracked end-state target. The burden is spread across many broad-reach lights (largest single light: ~9.3 MiB, 528 CSR entries), so no per-light fix can work. Replace uniform per-cell storage density with **adaptive** density — full-density bricks near surfaces, coarse bricks in open air, nothing where unreachable — to cut the delta pool by the ~8–10× industry precedent and bring it under the 128 MiB floor — and, per the owner's hardware target (very performant on GTX 10-series, runnable on laptops), toward the tighter 64 MiB hardware-budget default the Hardware target section derives — with the historical 512 MiB wall as the intermediate milestone. This spec leads with a measurement spike that decides whether surface-biased density is the right lever before committing the format change; if it lands, no texture-array migration of the delta is needed (decision recorded in Task 6).

## Scope

### In scope

- **Task 1 spike (gate).** A bake-time, output-preserving analysis pass over the emitted direct-SH delta CSR: classify each emitted affinity cell by surface proximity, compute each brick's coarse-reconstruction error from the already-baked probe data, and report the **projected** delta footprint under surface-biased coarsening — against both the 128 MiB floor and 512 MiB — on the stress map at the exact dense configuration (`--sh-probe-spacing 1.33 --lightmap-density 0.2 --soft-shadow-samples 64`). Changes no baked bytes. Gates everything below.
- **One adaptive mechanism, end-to-end through the live direct-SH delta path.** Two density levels per affinity cell: full 64-probe bricks near surfaces, coarse 8-probe corner bricks in open air, dropped entries where a light's contribution is negligible. The 4×4×4 affinity brick is the existing primitive — the gap is a *per-cell level* + *per-entry pool offset indirection* + *cap*, not a new spatial structure.
- **An indirection** from CSR entry → (level, contiguous pool offset), carried in the id-41 section (version bump 1→2) and consumed by the direct compose pass — the Unity APV `ProbeBrickIndex` / Unreal VLM indirection-texture analog, collapsed to the affinity-cell CSR this engine already has.
- **A bounded pool / hard memory cap** on the adaptive delta pool bytes (the Unreal VLM *Maximum Brick Memory* analog, with fail-loud instead of Unreal's silent detail-brick culling). The bake fails loud with a named error when over cap; the loader independently re-validates and rejects, all-or-nothing.
- **Runtime integration on the direct path only:** the direct compose compute pass reads bricks through the indirection and reconstructs coarse cells' per-probe deltas; the composed direct atlas output is unchanged, so **no sampler shader changes** (warrant below, Rough sketch).
- **Logging discipline:** one-line footprint/level-histogram summaries at `log::info` in prl-build; per-cell detail behind `-v/--verbose`; runtime footprint once per load (dev-tools builds); nothing per-frame.
- **Task 6 findings note:** measured footprint vs. the 128 MiB floor and 512 MiB, shrink factor, compose dispatch time, manual-visual read, and the fallback decision (is a delta texture-array migration still worth drafting).

### Out of scope (non-goals)

- **The indirect `DeltaShVolumes` (id 27) path.** Same CSR shape, would benefit identically, but the thin slice proves adaptivity on the **direct** delta — the dominant payload (401 MB of 447 MB SH total at 2.0 m; id 27 measured 37.5 MiB on campaign-test after the sparse-CSR work). Extending to id 27 is deferred breadth, recommended-or-not in Task 6. Nothing forecloses it: id 27 shares `AFFINITY_FACTOR`, `PROBES_PER_CELL`, and the CSR conventions (`crates/level-format/src/delta_sh_volumes.rs:18-40`), so the id-41 contract is directly transplantable.
- **Adaptive packing of the base SH atlases (id 34/35).** Already `texture_2d_array` (sh-array-atlas); their pressure was a 2D-dimension limit, not the storage-buffer wall. The base probe grid is consumed as-is. Foreclosure cost of deferring: none — the composed-atlas output shape is deliberately preserved (Invariant I1), so a later base-atlas change meets the same seam.
- **A multi-level subdivision hierarchy** (arbitrary-depth APV/VLM brick trees). The slice ships exactly two stored levels + absent. The wire contract keeps the level field wide enough that more levels are additive (Wire format), so escalation is a follow-on, not a rewrite.
- **Per-cluster streaming / residency of bricks.** Separate epic. Priced: the pool stays CSR-per-affinity-cell with whole-brick contiguity, which is the cell-alignable shape a residency system would want; nothing here fights it.
- **Probe relocation / virtual offset** (moving bake sample positions out of geometry — DDGI relocation, APV virtual offset). Base probe positions are untouched; this spec changes which probes *store delta data*, not where any probe sits. The engine's shipped analog for bad probes is sampling-side: per-probe `validity` plus Chebyshev depth-visibility weighting (`context/lib/rendering_pipeline.md` §4 "Indirect", "Probe depth moments"). Priced: nothing here writes or forecloses probe positions; a relocation spec would touch `sh_bake.rs` probe placement, which this spec does not modify.
- **Runtime re-subdivision when lights move.** Selected lights are static-positioned; adaptivity is a bake-time spatial decision.
- **Lowering `REQUIRED_STORAGE_BUFFER_BINDING_SIZE`.** The stopgap is currently **2 GiB − 8** (`crates/renderer/src/render/renderer_init_resources.rs:126-134`), documented as load-bearing on above-spec hardware. This plan makes it non-load-bearing on the direct-SH path (the payload fits the 128 MiB floor); shrinking the requested constant waits until the indirect path (id 27 on large maps) is also confirmed under floor — Task 6 records the state.
- **Probe/SH order and tile geometry changes.** `tile_dimension = 6`, `tile_border = 1`, the octahedral encoding, and the f16 tile payload are unchanged (`crates/level-format/src/direct_sh_delta_volumes.rs:32-33`, `crates/level-compiler/src/direct_sh_bake.rs:76-77`); only which probes are stored at what density changes.
- **Bake-time reduction.** Neutral-to-favorable side effect, not a goal.

## Direction

**Problem.** The direct-SH delta stores a dense 64-probe brick for every `(reached affinity cell, selected light)` pair regardless of whether the cell is open air where per-light direct irradiance varies slowly — so payload scales with probe density cubed times per-light reach, and dense settings blow through any storage-buffer budget. Cause, not symptom: the 2 GiB−8 limit stopgap and the historical 1.22 GiB incident are both downstream of uniform per-cell storage density.

**Prior commitments.** (0) **Hardware target (owner, this spec forward): very performant on NVIDIA GTX 10-series, at least runnable on laptops.** This is stricter than the documented envelope — `context/lib/rendering_pipeline.md` §10 names the GTX 16-series (Turing) as the perf floor — and this spec diverges deliberately: Pascal 10-series is the binding constraint for its numbers (budget section below). Capture the widened floor in `context/lib/` at promotion, not during drafting. (a) The instrumentation spec (`context/plans/done/lighting-scale--sh-delta-footprint-instrumentation/index.md`, Goal) commits to "a sparse layout under the 128 MiB WebGPU spec floor" as the tracked end-state — this spec is that work for the dominant payload. (b) `perf-animated-sh-light-culling` locked `AFFINITY_FACTOR = 4` as a workgroup-coupled invariant and shipped the CSR + portal-reach clip this extends; its findings note measured **11.3% within-cell occupancy** on the indirect path and named a variable-stride fork as the latent optimization — this spec is that fork's direct-path sibling, with a level indirection instead of an occupancy bitmap. (c) Pre-release no-compat-shim policy (`context/lib/development_guide.md` §1.6): version bump, reject old sections, no migration. (d) The all-or-nothing direct-delta reject posture (`context/lib/build_pipeline.md` §DirectShDeltaVolumes) is preserved, not relaxed.

**Alternatives rejected.**
- *Per-light outlier culling / footprint gating:* killed by measurement — the largest light is ~9.3 MiB of 383 MiB; the burden is structural, spread over many broad-reach lights.
- *Delta texture-array migration* (move `delta_subblocks` out of a storage buffer into a `texture_2d_array`, escaping `max_storage_buffer_binding_size`): rejected as the *primary* lever, but **not** because it saves nothing — that dismissal would be wrong, and the honest comparison matters if the gate fails. Moved as-is it only relocates bytes: VRAM, disk, and load time keep scaling O(n³), and the compose read gets more complex (texel addressing vs. the flat two-word load at `crates/renderer/src/shaders/direct_sh_compose.wgsl:110-117`). Its real attraction is that a texture can carry **block compression where a storage buffer cannot**, and this engine already ships BC6H for the irradiance atlas at ~8× smaller in VRAM (`context/lib/rendering_pipeline.md:95`) — a win of the same order as adaptive density. Two things qualify it, one of which is weaker than it looks: BC6H being RGB-only is **not** an obstacle, because every compose pass consumes `.rgb` only and never reads the fourth half (`direct_sh_compose.wgsl:176`, `sh_compose.wgsl:214`, `animated_direct_sh_compose.wgsl:215`), even though the format stores 4 halves per texel (`DELTA_TILE_TEXEL_F16_COUNT = 4`, `crates/level-format/src/delta_sh_volumes.rs:31`). The genuine obstacles are that deltas are **signed** (they ring negative — `direct_sh_compose.wgsl:172-174` — so it needs the `Bc6hRgbSfloat` variant, not the `Bc6hRgbUfloat` already in use) and that block compression is **lossy applied to a difference signal**, where error is more perceptible than on absolute radiance. So the reason to prefer adaptive density is that it removes bytes without a lossy-format gamble and without a second decode path — not that the alternative is worthless. The two are also **largely non-additive**: if adaptivity lands the pool near the hardware budget, compressing it further buys little against real quality risk. Note **no such spec exists in `context/plans/`** — the Task 6 decision is whether it ever needs drafting, not whether an existing spec is retired.
- *Occupancy bitmap with variable per-cell stride* (the perf-animated findings fork): stores only non-zero probes; finer-grained than level bricks but needs a per-cell popcount/prefix-sum on every shader read and has no notion of coarse *reconstruction* — it can only drop zeros, not thin slowly-varying regions. The level scheme subsumes its win where deltas are near-zero (drop the entry) and beats it where deltas are smooth-but-nonzero (coarse brick).
- *Silent degrade-to-fit* (Unreal's Maximum Brick Memory culls the most-detailed bricks until under budget): rejected — silent quality contraction violates the house fail-loud posture; the author gets a named error and chooses density or cap.

## Industry survey — mechanisms, and what this spec does with each

| Mechanism (source) | What it is | Disposition here |
|---|---|---|
| Brick of 64 probes, multi-level subdivision by geometry density, min/max probe spacing (Unity APV) | 4×4×4-probe bricks at several subdivision levels, denser near geometry | **In scope, collapsed to 2 levels.** The affinity cell already is the 64-probe brick; this adds the level axis. Full multi-level tree = deferred escalation, format leaves room. |
| `ProbeBrickIndex` / indirection texture (Unity APV, Unreal VLM) | World position → brick pointer at the right level | **In scope.** Collapsed to per-CSR-entry (level, pool offset) — the CSR already resolves world pos → cell → entries. |
| Maximum Brick Memory (Unreal VLM) | Hard memory budget; over-budget culls most-detailed bricks silently | **In scope as the cap, fail-loud instead of silent cull** (reason in Alternatives rejected). |
| Detail-brick placement near static geometry; detail bricks also culled where lighting is "nearly equal" (Unreal VLM) | Refinement criterion includes lighting variance, not just geometry proximity | **In scope for the spike:** Task 1 measures *both* classifiers — surface distance and per-brick coarse-reconstruction error — and their correlation, so the emission policy in Task 3 is chosen on data. |
| Probe classification / inactive probes (RTXGI DDGI: close backface hit + >25% backface rays ⇒ inside geometry, deactivate) | Stop paying for probes that cannot contribute | **In scope in cell-granular form:** dropped CSR entries (negligible-contribution cells) are the classification analog; the portal-reach clip already drops unreachable cells. Per-probe deactivation inside stored bricks = deferred (the occupancy-bitmap territory). |
| Probe relocation / virtual offset (RTXGI, Unity APV) | Move probe capture points out of geometry | **Rejected here** — position-side fix for a sampling problem this engine already handles read-side (validity + Chebyshev weighting); out of this spec's layer (see non-goals, priced). |
| Dilation (Unity APV) | Overwrite invalid probes with valid-neighbor averages | **Rejected here** — same read-side rationale; deltas subtract from a base whose validity weighting already suppresses bad probes at sample time. |
| Streaming cells (Unity APV), per-sublevel brick streaming (Unreal VLM) | Load/evict brick groups by camera | **Deferred (separate epic)**, priced: whole-brick contiguity per cell keeps the pool residency-friendly. |
| Sky occlusion (Unity APV) | Runtime sky-light re-lighting through baked occlusion | **Rejected** — indoor portal engine, fully baked static skyless lighting model; no consumer. |
| Camera-centered cascades, fixed per-cascade resolution (Godot 4 SDFGI: 4–8 cascades, each doubling cell size; default lowered to 4 for performance) | Memory bounded *by construction* — cascade count × fixed cell counts — not by a cap; adaptivity is distance-from-camera, runtime-recomputed | **Rejected as a mechanism, adopted as a posture.** Camera-relative runtime cascades do not translate to a bake-time static format (our density criterion is surface proximity, fixed at compile). What transfers: Godot bounds probe memory structurally and treats bounded cost as non-negotiable on small-engine hardware — this spec's cap serves the same end, fail-loud because a static bake can afford to refuse where a runtime cascade must degrade. |
| Probe-to-probe occlusion against leaks; walls must exceed a voxel at the rendering cascade (Godot 4 SDFGI) | Leak suppression is built into the probe structure, not left to content | **Already shipped read-side** — per-probe validity + Chebyshev depth-visibility weighting (`context/lib/rendering_pipeline.md` §4 "Probe depth moments") is this engine's equivalent; no new work in scope. |
| Sparse, author-extensible probe placement for dynamic objects (Godot 4 LightmapGI: automatic placement via a subdivision setting, plus hand-placed probe nodes densifying regions that need it) | The baked path's dynamic-object capture uses *sparse* probes with author-controlled local density — never a dense uniform volume | **Adopted as the closest-peer endorsement of this spec's direction.** Godot — the nearest engine to this project's posture (small, open, modder-friendly) — never ships a dense uniform probe volume on its baked path at all; sparse-with-local-density is its table stakes. Where Unity/Unreal say "multi-level brick hierarchy" and Godot says "sparse probes, densify where needed," this engine follows the Unity/Unreal *mechanism* (bake-time bricks — our lighting is baked-static and grid-indexed) at Godot's *scale ambition* (two levels, not a deep tree). Hand-authored density hints are deferred breadth (an authoring KVP could bias the classifier later; nothing here forecloses it). |
| Per-volume authored bounds + fixed subdivision; "not suited to low-end hardware such as integrated graphics" (Godot 4 VoxelGI); half-resolution GI project setting | Memory and cost bounded by authored volume; low-end hardware explicitly warned off the expensive path, with a cheaper knob offered | **Posture adopted via the hardware target below** — the expensive path must fit the named low-end target or fail loud at bake, not silently degrade at runtime. Half-res-style runtime quality knobs are out of scope (this spec's footprint is storage, not fill rate). |
| Local reflection probes with blend margins (Godot 4 ReflectionProbe) | Seams between probe regions crossfaded over an authored margin | **Rejected here** — runtime blend margins treat seams after the fact; this spec prevents them at the source (coarsen only where Task 1's measured reconstruction error is low). Godot-style blending would add a runtime cost the compose pass does not need if the classifier is honest. |

Godot findings are from documentation search extracts (docs pages 403'd through the proxy), marked accordingly; mechanism names and settings (`generate_probes_subdiv`, `LightmapProbe`, cascade count/cell size, occlusion) are as documented.

## Hardware target and memory budget

The owner's target binds this spec's numbers: **very performant on GTX 10-series, at least runnable on laptops.**

**VRAM reality.** The 10-series spans ~3 GB (1060 3GB, 1050) to 8 GB (1070/1080); the **1060 6GB is the realistic volume target**, the **3 GB parts and shared-memory laptop iGPUs are the floor**. The delta pool is one consumer among many: at the measured 2.0 m stress configuration, *total* SH sections were 447 MB, of which the direct delta was 401 MB — and baked-lighting residency also includes the lightmap atlases, the base id-34/35 atlases, the runtime-composed direct atlas (a second full-size `Rgba16Float` D2Array when promotion is active — created at `crates/renderer/src/render/sh_volume.rs:549-554`, format pinned at `crates/renderer/src/render/sh_volume.rs:1160-1180`), the shadowmask atlas, and the shadow pools, before any texture, geometry, or framebuffer byte. A 128 MiB delta pool alone is ~4% of a 3 GB card; uniform-density SH at dense settings (~1.3 GB projected) is flatly unshippable on the floor card. The honest budget stance: on the 3 GB floor, **total baked-lighting residency should stay under ~1 GB**, which prices the direct-SH delta pool at **tens of MiB, not hundreds** — below the 128 MiB WebGPU floor, which is a *binding-correctness* bound, not a hardware budget.

**Cap defaults, two tiers (consumed by Task 4).** The engine-side loader ceiling stays **128 MiB** — it exists to guarantee an accepted section binds on any WebGPU-spec device, and is not a quality judgment. The bake-side `--direct-delta-max-size` default is **64 MiB** — ~2% of the 3 GB floor card, leaving room for the rest of the lighting stack; a map that needs more raises the knob deliberately (up to the loader ceiling) and the findings note records the tension. If Task 1 projects the dense stress map's adaptive pool between 64 and 128 MiB, the flagship map failing the default knob is the mechanism working — an author-visible decision, not a spec defect; Task 6 revisits both numbers with measurements in hand.

**Pascal fp16 (consumed by Task 5).** Consumer Pascal (compute capability 6.1: GTX 1050–1080) executes native fp16 arithmetic at **1/64 the fp32 rate** — a hardware cliff, per NVIDIA's Pascal tuning guidance and community measurements (search-extract sourced). The current compose pass is already on the right side of it: `delta_subblocks` stays f16 **at rest** (no CPU expansion — `crates/render-cpu/src/sh_compose.rs:250` and the keeping-f16 round-trip test at `crates/render-cpu/src/sh_compose.rs:452`; raw u16 bytes uploaded at `crates/renderer/src/render/direct_sh_compose.rs:99`), and the shader converts on read via `unpack2x16float` — which returns `vec2<f32>` — so every arithmetic operation in `compose_main` is f32 (`crates/renderer/src/shaders/direct_sh_compose.wgsl:108-116,162-177`). **This is the contract: f16 storage, f32 arithmetic.** Task 5's coarse-brick reconstruction must keep it; do not introduce WGSL `enable f16` / native half arithmetic into this pass as an "optimization" — on the target hardware it is a 64× slowdown, not a win.

**Perf posture.** The adaptive read adds one indirection fetch per CSR entry and, on coarse cells, an 8-tap trilinear reconstruction per texel — ALU-bound work in a pass that runs on load, on promotion-weight change, and once when weights return to zero, not every frame (`context/lib/rendering_pipeline.md` §7.1 step 5). Task 6 records the before/after dispatch time and names the adapter measured on; a 10-series measurement is preferred where available, and the findings note must say which class of GPU produced the number.

- [ ] A manual-visual A/B on the stress map (dev-tools direct-SH / entity-shadow views, normal render path with probe depth-visibility weighting active) shows no objectionable artifact, banding, or popping on baked-static-direct-lit entities — specifically watching boundaries where density changes level. Parity to the uniform bake is explicitly not the goal (the uniform storage is the baseline being abandoned); seams are what the check hunts.

## Tasks

### Task 1: Surface-proximity + reconstruction-error footprint spike (measure-and-report; gate)

Add an analysis pass to the direct-SH delta bake that runs after the sparse CSR and probe payload are built and before the section is returned, changing no emitted bytes. Site: `bake_direct_sh_delta_volumes_controlled` in `crates/level-compiler/src/direct_sh_bake.rs:307-427` — at the stats block (`crates/level-compiler/src/direct_sh_bake.rs:378-410`) the function holds the CSR (`affinity_offsets`/`affinity_lights` from `build_csr`, `crates/level-compiler/src/direct_sh_bake.rs:349-350`), the per-entry cell ids (`csr_entry_cells`, `crates/level-compiler/src/direct_sh_bake.rs:356`), the full `delta_subblocks` f16 payload (`crates/level-compiler/src/direct_sh_bake.rs:357-373`), and the grid layout (`probe_grid_layout`, `crates/level-compiler/src/sh_bake.rs:148-190`). Compute, per emitted affinity cell: **(a) surface distance** — distance from the cell's probe region to the nearest world triangle, classified into *near-surface* (keep 64-probe density), *open-air* (coarsen candidate), *negligible* (drop candidate). Reuse the point-to-triangle machinery in `crates/level-compiler/src/sdf_bake.rs:487-500` (`nearest_triangle_distance`; currently private — hoist to `pub(crate)` or mirror the pattern) with its AABB lower-bound rejection; `point_in_solid` (`crates/level-compiler/src/sdf_bake.rs:471-480`) covers the in-geometry case. **(b) coarse-reconstruction error** — for each CSR entry, reconstruct all 64 probes' delta tiles by trilinear interpolation from the 8 corner probes (in-cell local coordinates ∈ {0,3} per axis; in-cell order is x-fastest, matching the emitted payload) and record max/mean per-texel f16 error vs. the stored dense brick; also record per-entry near-zero-ness (drop oracle). ## Rough sketch

**Slice shape — thin vertical slice, spike-first.** The uniform→adaptive change is fundamentally a new indirection *contract* consumed across compiler, format, loader, and one compute pass; proving it once through the live direct path — the dominant payload — locks the contract with real data before any fan-out (id 27, multi-level, streaming). Specifying the full adaptive system up front is the monolith the roadmap's sibling-spec guidance warns against; the fan-out fork is decided in Task 6 on measured data.

**The primitive already exists; the gap is level + offset + cap.** `AFFINITY_FACTOR = 4` / `PROBES_PER_CELL = 64` (`crates/level-format/src/delta_sh_volumes.rs:25,28`; compiler mirror `crates/level-compiler/src/affinity_grid.rs:35`), the portal-reach clip (`decompose_affinity_for_lights`, `crates/level-compiler/src/affinity_grid.rs:134-187`), and the CSR (`crates/level-compiler/src/direct_sh_bake.rs:349-353`) are shipped. Unity APV and Unreal VLM are this brick + a per-region subdivision level + an index + a bounded pool; the slice adds exactly those three, collapsed onto the existing CSR.

**Where the win comes from.** Every reached cell today stores 18,432 B per light (64 probes × 144 halves × 2 B; `delta_probe_f16_stride` at `crates/level-format/src/delta_sh_volumes.rs:313-314`, default stride `crates/level-format/src/delta_sh_volumes.rs:35-37`). A coarse cell stores 8/64 of that (2,304 B, 8×); a dropped entry stores nothing. The analogous indirect-path measurement (perf-animated findings: 11.3% of sub-block probes non-zero on campaign-test) and the open-air-dominated stress-map geometry are why ~8–10× is plausible — Task 1 replaces plausible with measured.

**Measurement basis.** Measured at 2.0 m (instrumentation evidence, 2026-08-04): direct-delta payload 401,154,048 B across 21,764 CSR entries; SH sections 447,193,334 B; largest light 9,732,096 B / 528 entries; small-fixture runtime footprint matched the compiler payload byte-for-byte, so the measurement path is trusted. The historical ~1.22 GiB at 1.33 m/0.2 remains credible — a naive cubic extrapolation from 2.0 m lands in the same broad range — but grid/portal boundary effects make extrapolation unusable as proof; cite it as corroboration only, never as a measured 1.33 m number. What is validated: per-cell storage density is the right *kind* of lever (the payload is structural, many-light, ~3× over floor at 2.0 m). What is not yet validated: that the surface-biased policy clears the target or preserves quality — precisely Task 1's job on the dense configuration.

**Contract discipline.** Per the style guide, this spec states constraints (per-entry level; entry→(level, offset) indirection; whole-brick contiguity; hard cap; version bump; the level-0/level-1 probe subsets and reconstruction rule) and leaves field ordering, integer packing, and threshold values to the implementer, who sees the whole picture when landing.

**Grounding notes (verified against this tree).** `DEFAULT_PROBE_SPACING = 1.0` at `crates/level-compiler/src/sh_bake.rs:33`; the uniform grid derives from the world AABB in `probe_grid_layout` / `grid_dimensions` (`crates/level-compiler/src/sh_bake.rs:148-190,408`). `--sh-probe-spacing` CLI at `crates/level-compiler/src/main.rs:658-666`. `REQUIRED_STORAGE_BUFFER_BINDING_SIZE = 2 GiB − 8` (stopgap, documented load-bearing) at `crates/renderer/src/render/renderer_init_resources.rs:126-134`, requested at `crates/renderer/src/render/renderer_init_resources.rs:156`, pre-checked at `crates/renderer/src/render/renderer_init_resources.rs:189-198`. Direct compose bindings: subblocks 20 / offsets 21 / lights 24 / weights 26 (`crates/renderer/src/render/direct_sh_compose.rs:20-26`); the runtime `selection_weights` buffer is not PRL payload. The dev-tools footprint instrumentation (`ComposeStorageFootprint`, `crates/render-cpu/src/sh_compose.rs:26-63`) already logs the direct promotion bindings once per construction (`crates/renderer/src/render/direct_sh_compose.rs:366-370`). No adaptive/level/indirection concept exists anywhere in the SH code today — Tasks 3–5 are net-new on that axis.

## Wire format

The adaptive fields ride the existing `DirectShDeltaVolumesSection` (PRL id 41), whose v1 layout — version byte, `affinity_factor`, `affinity_dims`, `tile_dimension`, `tile_border`, CSR `affinity_offsets`/`affinity_lights`, flat f16 `delta_subblocks` — is documented in-source at `crates/level-format/src/direct_sh_delta_volumes.rs:14-27`. Version 2 mirrors v1's conventions exactly: little-endian throughout; integer widths and signedness follow the current section; the payload's first byte is the bumped `DIRECT_SH_DELTA_VOLUMES_VERSION`, and any other version rejects at parse with the existing named error. Constraints for the v2 additions (field order, packing, and exact encodings are implementer-pinned at landing):

- A **per-CSR-entry level**, integer-encoded with room for more than two values (levels beyond 0/1 are reserved for the multi-level follow-on, rejected at parse for now). Level 0 = 64-probe full brick, x-fastest in-cell order (v1-identical). Level 1 = 8-probe corner brick: in-cell local coordinates ∈ {0,3} per axis, x-fastest order among the 8, reconstructed trilinearly with per-axis weights `local/3`.
- A **per-CSR-entry pool offset** into `delta_subblocks`, in f16-half units, `u32`-representable at the maximum capped pool size. Offsets monotonic non-decreasing in entry order; entry byte size is a pure function of its level and `tile_dimension`; bricks are contiguous and never split; the final entry's end equals the pool length (exact coverage — no slack, no overlap).
- `affinity_lights` values remain selection indices (Invariant I4). `affinity_offsets` (cell → entry range) is unchanged from v1.
- Empty/absent encodings follow v1: no usable entries → the section is not emitted (the bake returns `None`, `crates/level-compiler/src/direct_sh_bake.rs:314-353`); a per-cell "no entry for this light" is simply the entry's absence from the CSR.
- Structural validation at parse mirrors v1's posture (`crates/level-format/src/direct_sh_delta_volumes.rs:86-215`): truncation, monotonicity, level validity, offset bounds, and exact pool coverage are all parse-time rejects; selection-index bounds remain the loader's job (`validate_direct_sh_delta`).
- The invariant the whole format serves: a world-position read resolves deterministically — probe → affinity cell → CSR entry range → (level, offset) — to one contiguous brick or an explicit absence, and summed pool bytes never exceed the declared cap.

## Open questions / risks

- **Does two-level surface-biased density clear the 128 MiB floor at dense settings?** The plan's gate. Required shrink is ~3× at 2.0 m spacing and ~10× at 1.33 m; coarsening buys 8× on coarsened cells plus whatever the drop class removes. If Task 1 projects over 512 MiB, stop and fork (Sequencing Phase 1); if between 128 MiB and 512 MiB, the slice may still proceed with the floor deferred — an owner call recorded at the gate, not silently made.
- **Seams at density boundaries.** Adjacent cells at different levels reconstruct differing delta values at neighboring probes; the discontinuity is bounded by intra-cell delta variation, which is exactly what the classifier keeps small — and Task 1's reconstruction-error measurement quantifies it before any bytes change, which is the strongest de-risking available short of shipping. Residual risk (a mis-chosen threshold) is watched by the manual-visual AC at density boundaries specifically.
- **Threshold choice.** Surface-distance class boundaries and the near-zero drop threshold are picked in Task 3 from Task 1's data, as compile-time constants (not author-facing knobs — the only knob this spec adds is the memory cap). If the spike shows proximity is a poor proxy for reconstruction error, Task 3 switches to the error-threshold policy directly; the format is policy-agnostic either way.
- **Cap defaults.** The two tiers (64 MiB bake knob from the hardware budget; 128 MiB loader ceiling from the WebGPU floor) are principled but untested against real dense maps; if the adaptive dense-stress result lands between them, the flagship map fails the default knob and the author must raise it deliberately — loud by design, but friction worth recording. Task 6 revisits both numbers with the measurement in hand.
- **Oversized-file exposure.** Non-test source: `direct_sh_bake.rs` 929 lines (split task 2), `sh_bake.rs` 1207 (not extended here — only `probe_grid_layout` is read), `sh_volume.rs` 1339 (not extended — Task 5 confirms no delta-payload edits land there), `direct_sh_compose.rs` 602 (extended in place, under the split-first threshold). The slice deliberately keeps the indirect path (`sh_bake.rs`, `sh_compose.rs` indirect pass, `sh_group` cache) untouched.
- **Fallback framing.** No `sh-delta-texture-array` spec exists in `context/plans/`; the texture-array migration is a *direction*, alive only as this spec's failure fork. Task 6 records whether it should ever be drafted. Expected answer on a passing slice: no — but for the right reason. A texture array is not a null option, because textures can carry BC6H where storage buffers cannot (Direction → Alternatives rejected); it is deprioritized because adaptivity removes the same order of bytes without lossy compression of a signed difference signal, and because the two are largely non-additive once the pool nears the hardware budget. If the gate fails, this is the live fork and its compression upside is the reason it is still worth drafting — do not record it as closed on the grounds that it "only relocates bytes."
