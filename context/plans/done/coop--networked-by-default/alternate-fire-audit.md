# Connected-client alternate fire source audit

Read-only source audit at branch `codex/coop-networked-by-default`, requested baseline `5fbd32328`. No repository edits, Cargo commands, experiments, commits, or delegation. Read architecture index first, routed networking/input/entity/development/testing contracts, and current brief index/research/plan. Source findings are distinguished from runtime reproduction below.

## Finding and confidence

**Proven source flaw:** applying an ordinary local-player movement snapshot repeats weapon tuning installation, and weapon installation unconditionally cancels an active Charging/Executing cursor. Nothing checks that the host tuning actually changed. A connected client's execution lifetime is therefore bounded by the next applied local-player entity record instead of the authored program and explicit lifecycle edges.

Exact chain:

1. `crates/netcode/src/client.rs:897` (FullBaseline) and `:995` (Delta) call `maybe_arm_local_pawn` whenever an applied record has `local_player: true`.
2. `maybe_arm_local_pawn`, `client.rs:1446`, always emits `outcome.armed_local_pawn = Some(...)` at `:1496`; this is deliberately also the movement-reconciliation seam, not a one-time arm event.
3. `client_receive_and_apply`, `crates/netcode/src/lib.rs:881–889`, calls `remote_materialize::materialize_armed_local_pawn` for that outcome on every such snapshot.
4. `crates/netcode/src/remote_materialize.rs:183` always calls `materialize_net_local_wieldable_inventory_from_tuning`. Movement has a `rebuild_movement` distinction; weapons have no corresponding change distinction.
5. `crates/sim/src/scripting/builtins/net_descriptor.rs:206` preserves the same-canonical local entity but loops every occupied tuning slot. The same-canonical branch calls `apply_net_wieldable_tuning` unconditionally at `:303`.
6. `apply_net_wieldable_tuning`, `net_descriptor.rs:355`, clones the component, calls `weapon.cancel_activation()` at `:366`, rebuilds a descriptor, validates it, then calls `weapon.refresh_from_descriptor(&descriptor)` at `:417` and writes the clone back at `:418`.
7. `WeaponComponent::refresh_from_descriptor`, `crates/entities/src/components/weapon.rs:503–519`, cancels again and reinstalls both activation programs. `cancel_activation`, `weapon.rs:368–372`, changes Charging/Executing to Idle.

This is not owner-private magazine/heat/cell projection legitimately rolling back prediction. It is **local pawn materialization during movement snapshot apply** accidentally invoking the descriptor-replacement lifecycle. Owner-private scalar slots themselves remain presentation/resource samples.

Normal snapshots occur at 30 Hz (`crates/netcode/src/host.rs:14–24`). The owned snapshot carries `last_processed_client_tick` (`crates/netcode/src/replication.rs:215–230`), so even a stationary participating pawn can produce routine movement-authority changes as commands resolve. This is not restricted to joining, model repair, a weapon grant, or a script reload.

### What it explains, and what it does not yet prove

- The shipped rifle's secondary is three shots with two 80 ms waits (`content/dev/scripts/reference-rifle.ts:16–24`), 9 base damage and ordinary per-shot ammo cost. At 60 Hz the waits compile to five ticks. A movement snapshot arriving after ordinal 0 but before ordinal 1 erases the client's remaining two due shots. The host's independent cursor still fires and pays for all three. No client HIT declarations exist for the erased ordinals, so the host cannot apply their target damage. This is a direct, internally complete explanation of the one-damage/three-ammo mismatch; it remains to be run through a discriminating production-receive regression.
- The shipped plasma secondary is press-triggered, min 200 ms/full 1000 ms, with damage/resource multipliers `1 + 9*charge` and size multiplier `1 + charge` (`content/dev/scripts/reference-projectiles.ts:29–40`). Its primary is a separate hold action at 130 ms recovery. A snapshot erasing Charging directly causes the reported meter flash/disappearance.
- Erasure also loses future release/cancel correlation: the next fixed-command producer reads `state.activation_cursor()` then calls `capture.set_active(active_token)` (`crates/postretro/src/frame_loop/mod.rs:671–684`). Once that is None, `ActivationInputCapture::command` cannot attach a later physical release to the former token (`crates/postretro/src/input/activation.rs:86–95`). Focus cancellation can likewise lose it after the erased cursor has been reseeded away. Thus the host can retain a charge the local player can no longer release normally; real commands keep its input timeout alive until another explicit lifecycle cancellation/charge expiry.
- **The reported regular plasma shot is not yet source-proven by this cause.** There is no generic secondary-to-primary fallback. `controller_activation_request` (`crates/sim/src/weapon/execution.rs:123–156`) starts Primary only if the primary button independently qualifies; secondary is press-only and its consumed flag survives refresh. The pure charge machine never auto-fires or treats neutral as release (`crates/combat-model/src/activation.rs:86–127`). A regression must assert the transmitted lane/token/buttons/release and final charged launch/damage. If the regular shot remains after the cancellation seam is corrected, inspect actual input activation events/bindings and local shot identity before changing semantics.
- Three fire sounds are consistent with the host authorizing three shots, but which peer heard the reported triple sound was not specified. Host remote FIRE emits `activate` per accepted shot (`crates/sim/src/sim/weapon_stage/commands/remote.rs:178–193`). Other observers get those cues; `crates/netcode/src/weapon_cues.rs:119–122` deliberately excludes the firing owner, which normally predicts its own sound. This source flaw alone does not establish why the firing owner itself would hear all three sounds after predicting only one shot. Keep that distinction in the playtest record.

## Other state and cost effects

The unconditional refresh is narrower than a full weapon reset:

- **Erased:** Charging/Executing cursor, including start token/pawn, accepted/last-real/last-advanced ticks, next step/due tick, ordinal and resolved charge. Later input capture then loses correlation; charge HUD becomes false/0. Frozen queued shots and already-contacted/live predicted projectiles are retained separately and are not reconstructed or rewound by this refresh.
- **Preserved for identical tuning:** cooldown/recovery remaining; reload/equip state and latched remaining/total timing; reload feedback stream and cursors; magazine; input press-consumed flags; activation clock/last tick; shells fired; bloom accumulator/idle timer. `refresh_from_descriptor` comment at `weapon.rs:534–538` explicitly preserves these while cancelling charge/execution. Therefore do not claim routine snapshots refill ammo or restart reload/equip countdowns.
- **Resources:** `weapon_resource.rs:133–155` preserves same-kind heat/cell live values, idle timers and overheat latch, clamping only to new bounds. A real resource-kind replacement intentionally creates fresh heat/cell, and heat/cell→ammo seeds magazine capacity. Connected clients do not own passive heat/cell updates or resource/reload prediction; HUD authoritative values come from correlated owner slots, not refreshed component-local defaults. Keep that contract.
- **Mixed descriptor components and ownership:** same-canonical refresh only writes Weapon; Health, Brain/Agent and canonical Inventory ownership survive. Changed canonical slot identity follows release/despawn/recompose. A repair must not substitute full entity recomposition for same-instance tuning or reintroduce held world participation.
- **Viewmodel:** current asset/seed follows Inventory and placement follows installed host tuning (`postretro/src/frame_loop/mod.rs:1976–2023`). No source evidence that identical refresh itself resets asset identity/placement. The affected charge/progress presentation is local HUD, and missing shot emissions can affect per-shot feedback independently.
- **Avoidable runtime work:** each routine local movement record loops up to ten slots and clones each live WeaponComponent, clones action programs into a fresh descriptor, preserves/clones local sound fields, validates, reinstalls Arc-backed compiled primary/secondary programs and registry-writes the component (`net_descriptor.rs:263–305, 360–418`; `weapon.rs:516–521`). Foundation compilation allocates at install (`combat-model/src/activation.rs:1–2`). Existing cloned runtime components share programs; repeated rebuilding defeats that design. Stop the work at the materialization/change seam, rather than just removing one cancel call.

## Coherent repair recommendation

Keep the existing single weapon machine, authorization, resource and lifecycle semantics. Separate **ensure a local instance exists** from **replace its installed host gameplay tuning**:

1. Routine local-pawn snapshot apply may arm/reconcile movement and ensure missing presentation/inventory. For an existing same-canonical local Weapon instance with unchanged host tuning, it must perform no descriptor refresh/program installation, no activation cancellation, and no Weapon registry write.
2. Use the existing installed host `tuning_generation`/applied-generation distinction at the private netcode glue (today movement-only), plus actual row equality/installed-semantic comparison. `TuningPayload` and `WieldableTuningPayload` already derive PartialEq (`combat-model/src/carried_loadout.rs:63, 155`), and host Control already sends only changed payloads (`netcode/src/lib.rs:1415–1429`). No per-frame descriptor hash/version framework is needed.
3. A changed **unrelated** slot or movement tuning must not cancel the active weapon. Only a genuinely changed gameplay row of the same live instance gets the existing validated `refresh_from_descriptor` cancellation; newly created instances always get full host tuning. An equal Control resend should be inert for existing weapon execution as well. Comparing normalized validated host gameplay fields against the live installed component is an alternative to retaining another whole payload; exclude live resources/cursors and preserved local presentation sound keys from that comparison. At normal unchanged snapshot cadence, gate before cloning/validating/compiling.
4. Preserve slot reconciliation: absent/new grants, changed canonical replacement, removal and stale IDs still follow current canonical ownership and generation-safe lifecycle. Both Control-first and baseline-first ordering work; a genuinely new local pawn/missing Inventory initializes from host slots even when the payload generation is unchanged. Holstered same-instance rows are preserved and changed holstered rows retune once, with their inactive recovery/resource rules unchanged.
5. Preserve **real** cancellation: switch/drop/reload/focus/death/disconnect/level change/actual descriptor replacement still cancel future work, without refund or reissuing paid shots. Never make `refresh_from_descriptor` globally preserve a cursor across actual program replacement, never keep a fake charge-HUD timer to hide the issue, and never generate missing damage on the host without a client declaration.
6. Preserve invalid-tuning atomicity. `apply_net_wieldable_tuning` currently mutates a clone and only commits after validation; moving its early cancel is not itself a partial live mutation, but do not introduce one. The broader installed-payload contract intentionally **invalidates** old host tuning on malformed/epoch-invalid Control (`netcode/src/lib.rs:493–505`; tests `o42_malformed_tuning_replacement_invalidates_previous_install` and `unknown_epoch_tuning_replacement_invalidates_previous_install`). Live Inventory/Weapon equip state remains untouched while prediction/placement gates become inert. Do not silently change that policy into keeping the old installed payload; retaining the old live component is distinct from continuing to trust the invalidated payload.
7. Demotion/unload/re-promotion clears existing endpoint generations/state (`endpoint.rs:771–783`) and re-creates instances. Any new installation bookkeeping must be identity-scoped and cleared there; no stale slot-only entry may skip tuning for a replacement/new pawn. Prefer existing generations and bounded row comparisons over new cache infrastructure.

This can be a private orchestration/idempotence fix plus focused tests, without wire format, protocol/epoch, SDK authoring, weapon descriptor, activation ordinal, resource-authority, or public breaking-API changes. If implementation adds parameters to exported materialization APIs, follow the repo's owner-confirmed API-break rule; the behavior does not require that choice. The named future `E16--persistent-firing-modes` consumer also needs captured execution preserved through unrelated updates; do not special-case rifle/plasma/modes or remove actual replacement cancellation.

## Why existing green tests miss it

1. `postretro/src/host_activations/conditioned_tests.rs` genuinely exercises conditioned transport, host input/authority, ClientWeaponFrame prediction, HIT and outcomes. Its `Fixture::transport` at `:530–628` drains Control and reliable Input outcomes, **not snapshot receive/materialization**. `Fixture::predict` at `:694–807` calls the fixed prediction path directly; `step` at `:1017–1022` composes predict/send/projectiles/host tick. Thus its full-charge and burst loss/hitch tests never execute the cancelling seam.
2. `netcode/src/activation_harness_test.rs:124+` uses `ClientActivationTiming` with a separately managed WieldableState; it proves queue/timing ordinals, not snapshot→materializer→WeaponComponent lifetime.
3. `sim/src/scripting/builtins/net_descriptor.rs` inventory merge/retune tests assert retained entity IDs, Health, magazine, cooldown and equip/reload timers (e.g. `:1640–1708` and the installed-action sound/override test `:2290–2388`). They omit an active Charging/Executing cursor across repeated identical materialization. Consequently they can truthfully pass those fields while execution is cancelled.
4. `postretro/src/client_weapon/tests.rs` deliberately tests real descriptor replacement/captured projectile correction (`:840+`), so cancellation there is expected. `reconcile.rs` tests Completed retaining a live client execution, but no simultaneous routine snapshot install destroys it first. Individual correct boundaries leave an untested composition.
5. Current brief's presentation conditioned tests use real snapshot receive for the atmosphere/target requirements but do not hold the shipped alternate-fire program across those receives. Synthetic weapons use different waits/scales; they do not pin the real dev rifle/plasma data.

## Focused proof to require before claiming a fix

A regression should first fail on the current source at the cancelling seam; no broad tests or weakened waits/resource asserts substitute for this.

- **Production receive cadence + shipped rifle:** obtain descriptors through real dev script install (including TS/Luau data parity if using existing fixture); join with actual tuning Control and local-pawn baseline. Drive a real AltFire action edge through ActivationInputCapture and fixed producer, then apply ordinary host-generated movement Deltas at the shipping 30 Hz cadence through `client_receive_and_apply` between all three shots. Include a render-only receive frame. Assert one token/secondary lane, ordinals exactly `[0,1,2]`, waits five ticks each, exactly three declarations, three host-authorized shots, magazine minus 3, and three accepted target damage applications totaling the actual resolved damage with spread controlled by a sufficiently broad target/valid aim. Count activate/impact presentation per intended peer. Repeat stationary and moving; snapshots must demonstrably be applied during execution.
- **Production input + shipped plasma:** hold AltFire beyond min/full while ordinary snapshots apply. Assert Charging and monotonic fixed-tick HUD progress remain, no semantic shot/debit/declaration before explicit release, release names the original secondary token, no primary start is transmitted, and exactly one scaled projectile/contact/damage. Full charge should use damage 100, cell cost 50 and visual size 3 for the shipped base values; minimum-boundary/early release and partial charge should derive expected scale from actual descriptor. Include render-only snapshots and same-frame press/release. If a regular shot still occurs, log/assert primary/secondary buttons, token lane, release tick, program identity and final resolved scale to distinguish input vs replacement vs outcome correction.
- **Lifecycle distinctions:** repeated identical Control, unrelated-slot grant and movement-only tuning change preserve active cursor/compiled program; actual changed same-canonical gameplay row cancels once, updates future program and preserves frozen issued shot semantics/resources/recovery. Switch/drop/reload/focus with no tick, owner death, removal, canonical replacement, and demotion/rejoin retain current real cancellation/teardown behavior.
- **Installation matrix:** Control-first vs baseline-first, missing/new local Inventory under already-installed tuning, new grant, removal, holstered changed/unchanged row, stale/generation-reused IDs, retained mixed Health+Weapon/behavior. Assert instance ownership/retained Health/resource/recovery/equip state as well as execution.
- **Invalid replacement:** retain existing fail-closed malformed/epoch tests; add invalid-row validation proving no partial live component mutation and no cancellation/program replacement before validated installation.
- **Cost:** no per-snapshot Weapon registry write or activation compilation/descriptor clone for unchanged installed rows; use a small targeted allocation/write observation only if an existing seam supports it. Avoid benchmark/test proliferation mirroring private fields.
- Run the repaired focused receive/weapon/conditioned suites, then affected review and required change checks. Rebuild actual playtest executables; previous test-ready binaries cannot validate source repairs. Preserve M1–M4 landing gates and add owner alternate-fire recheck on both host/client roles.
