# Co-op Client Movement Feel

## Goal

Restore smooth client-player movement in authoritative co-op. The host command queue currently discards the majority of a connected client's input on a clean link, causing constant micro-stutter, a jump that must be held ~0.2–0.5 s before it fires, and stepped rotation as seen by the host. Fix the host's input resolution so a client's on-time-but-slightly-late input is applied rather than dropped, then re-measure to decide whether any presentation-side smoothing remains warranted.

## Scope

### In scope

- **Fix A — host input playout buffer.** Change `HostCommandQueues::resolve_tick` so it does not advance the resolve cursor past a tick whose command has not yet arrived (within the hold grace), and so it maintains a small standing playout depth behind the newest received command. This is the primary, evidence-backed fix and it delivers the stutter, hold-to-jump, and (very likely) the host-side rotation fixes at once.
- **Re-measurement gate.** After Fix A, capture the `netdiag` counters (vsync-on and vsync-off) and decide, from data, whether a host-side presentation defect survives.
- **Fix B — host-side remote-pawn delay presentation (conditional).** If re-measurement shows the host still steps the client pawn's orientation after Fix A, give the host the same delay-buffered presentation the client already uses for remotes. Design carried here; implementation gated on the measurement.
- **Fix C — orientation sampling cadence (conditional).** If re-measurement shows the sending client's sub-60-fps render rate still starves orientation after Fix A, address the render-rate sampling of `facing_yaw`. Gated, and must argue divergence from the `input.md` §3 render-rate-look contract.

### Out of scope

- Splitting `main.rs` (11 161 lines) or `interpolation.rs` (1 428 lines). Fix A lives in `command_queue.rs`; Fix B adds a new `netcode` submodule with only thin `main.rs` wiring; Fix C touches the input/look sampling path (`main.rs`) and the `input.md` §3 contract. A split of these monoliths is its own work, not gated on this bug.
- Wire-format changes. The client already sends one `ClientMessage::Input` per fixed tick at 60/s; the send path is correct and untouched.
- Client-side prediction, reconciliation, and the interpolation buffer's internals — not implicated: the fault is fully explained host-side (`netdiag::send` shows a steady 60/s; the loss is entirely in the host's `resolve_tick`). Untouched, not re-verified here.
- The `--release` build skipping the scripts-build regeneration (a separate, unrelated launch-tooling bug).

## Direction

**Problem.** `resolve_tick` (`crates/postretro/src/netcode/command_queue.rs:397`) advances `resolved_cursor` and calls `drop_stale(expected)` on the gap path (`:490–491`), so when the client's command for the expected tick has not yet arrived — which, on a clean loopback, is most ticks, because the client's 60 Hz send and the host's 60 Hz resolve run ~1 tick out of phase — the host Neutral/Held-fills the tick, advances past it, and discards the real command as stale when it lands. The cause is *cursor advancement on an unfilled tick*, not loss, not a rate limit, not the catch-up trim (`trims = 0`, `cursor_lead ≈ 0` in the data; see `research.md`).

**Prior commitments.** The prediction/reconciliation and interpolation model in `context/lib/networking.md` is preserved: the client still predicts locally and reconciles against `last_processed_client_tick` (stamped from `resolved_cursor`, `netcode/replication.rs:142`). Fix A makes `resolved_cursor` trail the newest received tick by a small playout margin (~`INPUT_BUFFER_TARGET − 1` ticks in steady state, ~1 at target 2), so the client's ack lags ~1 tick more and its reconcile replay tail grows by ~1 tick — bounded and within the existing model. The existing gap policy (`INPUT_HOLD_TICKS = 3`), catch-up trim (`INPUT_BUFFER_MAX = 8`, `INPUT_BUFFER_TARGET = 2`), and reload recovery lane (`pending_reload_presses`, `preserve_due_reload_press`) are retained; Fix A changes *when the cursor advances*, not those constants' meaning.

**Divergence, stated.** Fix A deliberately supersedes two shipped commitments — this is the change, not an oversight. (1) `plans/done/M15--p3-movement-prediction-reconciliation/index.md:63–66,281–284` shipped an AC that *synthetic hold/neutral ticks advance the authoritative input cursor; later real commands at or below that cursor are dropped* — Fix A reverses this for the within-grace **Held** case: a held tick no longer advances the cursor, so a real command arriving within `INPUT_HOLD_TICKS` resolves `Real` instead of being drop-staled; the give-up **Neutral** after the grace still advances, preserving the absent-client guarantee. (2) `context/lib/networking.md` §"Host input command queue — gap policy and bounded playout" (the *Bounded playout buffer* bullet, ~lines 306–319) states the contract as *the cursor advances +1 per tick*, rationale *any backlog ... would become permanent latency* — Fix A no longer advances +1 on an unfilled within-grace tick and establishes a standing playout depth (buildup threshold ~`INPUT_BUFFER_TARGET`, ~1 tick in steady state after the first consume). That same bullet already permits the resolved cursor to sit *a small bounded buffer behind the newest received command* up to `INPUT_BUFFER_TARGET` (~33 ms), so Fix A's steady-state depth is **within** the documented tolerance; what changes is that the depth is established proactively (a playout floor) rather than only reactively (catch-up trim), and that the +1-per-tick rule yields during the hold grace. Warrant: the +1-per-tick-on-synthetic-ticks rule is the direct source of the ~75 % input loss under sub-tick phase jitter on a clean link (`research.md`). Task 1 updates `networking.md` §"Host input command queue" in the same change, per the contract-surface discipline (`context/lib/index.md` §2).

Fix C would touch the `input.md` §3 render-rate-look contract — an explicit divergence it must argue, which is why it is gated.

**Alternatives rejected.** (1) *Minimal change only* — stop advancing the cursor during the Hold grace, but keep resolving from the queue edge (no standing playout depth). This recovers late commands but, under a steady ~1-tick phase offset, still alternates Held/Real (~50 % Real) because each freshly-expected tick is again not-yet-arrived. Rejected as the sole fix: it halves the loss but does not close it. Fix A keeps this "don't advance on hold" behavior *and* adds the standing playout depth that gets steady-state resolution to ~100 % Real. (2) *Timestamp-based input reordering / client send-with-lead* — larger surface, touches the wire and the client, and buys little over a host-side playout buffer, which is the standard placement for absorbing receive jitter. Rejected as disproportionate. (3) *Raise the snapshot rate or extrapolate on the host* — addresses presentation, not the input-loss root; does nothing for the dropped commands. (4) *Align ingest with resolution in-frame* — drain pending client input immediately before each `resolve_tick` rather than once per render frame in the snapshot-apply stage (`main.rs:2446` before the tick loop at `:2492`), so the awaited tick is already enqueued without a standing playout margin. Rejected: the two 60 Hz clocks free-run with intrinsic sub-tick jitter — and at the observed 250–330 fps the host runs well under one fixed tick per frame (the *multiple fixed ticks in one frame* ordering row) — so per-tick ingest cannot remove the phase offset a playout buffer absorbs, and it does not help the accept-handshake backlog the existing catch-up trim exists for.

Foreclosures and one-way doors: Fix A commits to a buffered-input playout model and adds ~1 tick (~16 ms) of latency to *authoritative* input application in steady state; client prediction hides this locally, and it is tunable via `INPUT_BUFFER_TARGET`, so undoing or retuning is a constant change — not a one-way door. Fix B commits the host to delay-buffered remote presentation (adds presentation latency to how the host sees remotes, already true on the client side); localized and reversible.

## Tasks

### Task 1: Host input playout buffer

Rework the gap path of `HostCommandQueues::resolve_tick` (`crates/postretro/src/netcode/command_queue.rs:397`) so a slightly-late client command resolves `Real` instead of being drop-staled, and so the resolver maintains a small standing playout depth behind the newest received tick. Two behaviors, both in `resolve_tick` and the `ClientCommandState` it mutates (`command_queue.rs:167`):

(a) **Hold the cursor on a genuine late-arrival, not on the neutral-walk.** The cursor holds this tick — leave `resolved_cursor` unchanged, do **not** call `drop_stale(expected)`, and do **not** `take_exact` — iff all three hold: `take_exact(expected)` would find nothing, `held_ticks < INPUT_HOLD_TICKS` (grace not exhausted), **and** `last_resolved.is_some()` (a real command is being held, via `held_gap_sim_command`, resolving `Held`). This is the late-arrival wait: `expected` is retried next tick and its command, arriving within the grace, resolves `Real`. `held_ticks` still increments on each held tick, so the grace stays bounded. Every other gap resolution advances the cursor exactly as today:

- **Give-up** (`held_ticks` reaches `INPUT_HOLD_TICKS`): resolve `Neutral`, advance past `expected`, `drop_stale`, and clear `last_resolved` so a later real command at a higher tick resumes cleanly.
- **Neutral-walk** (`last_resolved.is_none()`, latch disarmed — the coast after a give-up, marching toward a stream that resumed at a far-future tick with commands still buffered): resolve `Neutral` and advance one tick per resolve. This is the depth-keyed design's deliberate resume path (a single far-future command must not trip catch-up; the cursor walks to it — `networking.md`). **Do not** strip advancement from this case when you move the cursor-advance off the hold path; only the hold-with-a-command-to-hold case suppresses it. Concretely, once the buildup latch (b) is disarmed, the cursor holds iff `take_exact(expected).is_none() && held_ticks < INPUT_HOLD_TICKS && last_resolved.is_some()`; every other gap resolution advances. The buildup latch is evaluated first (b), and while armed it holds regardless of this predicate.

The reload recovery lane (`preserve_due_reload_press`, `pending_reload_presses`) observes the resolved tick only on ticks where the cursor actually advances — thread `preserve_due_reload_press` through the `Real`, give-up, and neutral-walk paths, never the hold-without-advance path (a non-advancing hold keeps `expected` constant, so calling it there would re-test the same tick each hold and risk early delivery).

The grace is counted in resolve-ticks, not wall-clock. A multi-tick hitch frame runs several resolves after a single per-frame `ingest`, so it can burn the full grace before the next frame's `ingest`; a command that lands one frame late *during a hitch* is still drop-staled. Bounded loss on hitch frames is accepted — the standing playout depth (b) absorbs the common single-tick phase offset, not a multi-tick host stall. One consequence: during an outage the cursor now falls up to `INPUT_HOLD_TICKS` further behind newest than the old +1-every-tick hold, lengthening the resume neutral-walk by that bounded amount.

(b) **Maintain a standing playout depth via a one-shot buildup latch.** Add `building_playout: bool` to `ClientCommandState` (no new tuning constant, no new wire field). The field defaults disarmed (`Default`), so it must be **armed** explicitly on the stream-begin path (`resolved_cursor == None`); each give-up then recomputes it as `building_playout := pending.is_empty()` after the give-up's `drop_stale` — a give-up that clears the buffer re-arms buildup, one that leaves commands buffered disarms and lets the neutral-walk advance. It also **disarms** the instant `pending.len() >= INPUT_BUFFER_TARGET`. Precedence when armed: the grace give-up wins — once an armed hold reaches `held_ticks == INPUT_HOLD_TICKS`, resolve the give-up (advance, `drop_stale`, recompute the latch) rather than continuing to hold; the "hold regardless of the (a) predicate while armed" rule governs only the within-grace armed ticks. While armed, `resolve_tick` evaluates the latch **before** the exact-tick path and resolves `Neutral`/`Held` **without** consuming (`take_exact` is not called), without `drop_stale`, and without advancing the cursor — it withholds the first `Real` until the queue has built to `INPUT_BUFFER_TARGET`. Evaluating before `take_exact` is load-bearing: `take_exact` removes the command, so a buildup check placed after it would pop the awaited command and then resolve `Neutral`, and the buffer could never build. Once disarmed, the exact-tick path consumes the oldest buffered command as the first `Real`, and steady state runs one `Real` per tick. The buildup threshold `INPUT_BUFFER_TARGET` is the *disarm depth*, not the steady-state cushion: after the first consume drops one command, `resolved_cursor` trails the newest received tick by ~`INPUT_BUFFER_TARGET − 1` ticks (≈ 1 tick / 16 ms at `INPUT_BUFFER_TARGET = 2`) — enough to absorb the sub-tick phase offset that caused the bug. Task 2 measures whether that cushion needs raising.

**Depth, never tick-distance.** Readiness is keyed on `pending.len()` alone — the same depth-keying the catch-up trim uses, and for the same reason (`networking.md`: "the trigger is pending-queue depth ... not tick-distance to the newest command"). A single far-future command after a silence sits at depth 1 and keeps the latch armed; do **not** gate buildup on `latest_observed_reload.0 − cursor` or any newest-received-tick distance, which would read that one command as "buffer full" and reintroduce the silent-resume failure the depth-keying exists to prevent. (`latest_observed_reload` stays the reload lane's marker; the playout latch does not read it.)

**Buildup cannot hang, and cannot self-trigger a give-up.** Each armed hold increments `held_ticks` (even when `last_resolved == None`, so a fresh stream is bounded too) and stays subject to the `INPUT_HOLD_TICKS` give-up, so a client that sends one command then goes silent cannot pin the latch armed forever — it gives up, advances, and the pawn neutralizes (AC5). This requires the standing invariant `INPUT_BUFFER_TARGET < INPUT_HOLD_TICKS` (2 < 3 today), so a normal ~`INPUT_BUFFER_TARGET`-tick buildup completes before the grace fires. A mid-session underrun — a give-up that leaves `pending` non-empty — does **not** re-arm the latch, so a single late packet costs at most the hold grace, never a fresh buildup stall.

Keep the existing catch-up trim (`INPUT_BUFFER_MAX`) for the over-buffered/hitch case unchanged. The diagnostics already recorded in `resolve_tick` (`self.diag.record(...)`) stay and become the verification instrument for the ACs. The P-labeled rows in the Orderings table are the `command_queue.rs` unit-test matrix for Task 1 — write one deterministic ingest/resolve test per row (assert `source`, `client_tick`, and the resulting cursor); the integration re-measurement in Task 2 confirms the counters on a live session.

The existing `command_queue.rs` test module encodes the superseded semantics — advance-on-hold and an immediate first `Real` from a single queued command — so tests that ingest one command then resolve (e.g. `late_arrival_within_hold_resolves_real`, `resumed_input_after_gap`, `resume_after_silence`, `missing_tick_holds_then_neutral_advancing_cursor`, the reload-lane tests, and the hitch/startup lag-math tests) will fail, not merely need extension. Migrate them to the new behavior (pre-buffer ≥ `INPUT_BUFFER_TARGET` so the latch disarms before asserting, expect the buildup withhold and the hold-without-advance) as part of this change — do not "repair" a failing assertion to match old behavior.

Documentation to update in the same change so contract and code do not drift: `context/lib/networking.md` §"Host input command queue — gap policy and bounded playout" (the *Bounded playout buffer* bullet, ~lines 306–319) — the hold grace does not advance the cursor on a held command, the buildup latch establishes the playout floor proactively, and the +1-per-tick rule yields during the grace; and the in-code comments that still describe the +1-per-tick model — `command_queue.rs` module header and the `resolve_tick` / `INPUT_BUFFER_TARGET` doc comments, plus the `QueueEvent::lead` comment in `netdiag.rs` ("Positive means the cursor is ahead"), which now reads negative in steady state.

## Rough sketch

Fix A centers on the gap branch of `resolve_tick` (`HostCommandQueues::resolve_tick`, `command_queue.rs`). Today both the exact-hit path and the gap path end with `resolved_cursor = Some(expected)` + `drop_stale(expected)`. The change makes cursor advancement conditional: advance on a `Real` hit, on a `Neutral` give-up after `INPUT_HOLD_TICKS`, and on the post-give-up neutral-walk (`last_resolved.is_none()`); hold only on a within-grace `Held` that has a command to hold (`last_resolved.is_some()`). A one-shot latch `building_playout: bool` on `ClientCommandState`, keyed on `pending.len()` alone (never tick-distance) and evaluated **before** `take_exact` so the withheld command is not consumed, governs the initial/underrun buildup and gates even an available `Real` until depth reaches `INPUT_BUFFER_TARGET`. `held_ticks` already tracks the grace count; its reset points are the give-up and `Real` paths. No new tuning constant — reuse `INPUT_HOLD_TICKS`, `INPUT_BUFFER_TARGET`, `INPUT_BUFFER_MAX` (only the `building_playout` bool is added), under the standing constraint `INPUT_BUFFER_TARGET < INPUT_HOLD_TICKS`. Verification uses the existing `HostQueueDiag` counters.

## Open questions

- **Exact playout margin.** `INPUT_BUFFER_TARGET = 2` (~33 ms) is the natural reuse and matches the observed ~1-tick phase offset with headroom. If Task 2 shows residual `Neutral` under normal jitter, the margin may need to grow; if input latency feels heavy, 1. Owner tuning call, bounded by the AC that steady-state `neutral ≈ 0` **and** the invariant `INPUT_BUFFER_TARGET < INPUT_HOLD_TICKS` — raising the margin to 3+ requires raising `INPUT_HOLD_TICKS` in the same step, else buildup can self-trigger a give-up.
- **Fix B host clock source.** Task 3 assumes the host presents remotes at `current_tick − delay` off its own authoritative tick. If a wall-clock playout (as the client uses) turns out cleaner for cross-frame smoothness at high host render rates, that is an implementation choice for Task 3 — recorded here so it is decided, not discovered.
- **Does Fix A alone close everything?** The evidence says Fix A removes the dominant cause of all three symptoms, including rotation. Tasks 3–4 exist only if Task 2's measurement disproves that. This is deliberate: the spec does not pre-commit presentation work the data has not yet justified.
