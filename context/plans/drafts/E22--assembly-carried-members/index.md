# E22 Spec 1 — Assembly carried members (mover-carried dynamic light)

> **Status:** draft. First spec of Epic 22 (`../E22--kinematic-assemblies/`). Foundation + first consumer. Source-grounded seam map, lifecycle diagram, observer/ordering tables in `research.md`.
> **Related:** `context/lib/build_pipeline.md` §PRL section IDs (KinematicGeometry 43, AlphaLights 18) · `context/lib/entity_model.md` · `context/lib/rendering_pipeline.md` §4 · `context/plans/done/E17--rotating-movers/` (spin) · `context/plans/done/E21--bone-sockets-attachments/` (the attachment relation this generalizes).

## Goal

A dynamic light can be authored to travel with a kinematic mover: the mapper binds a `light_dynamic` / `light_dynamic_spot` to a mover, and at runtime the light rides the mover's pose — position, and for a spot on a **translating** mover its authored cone aim — staying locked to the moving geometry on host and connected clients alike. This is the first consumer that proves Epic 22's canonical member-of-an-assembly relation, built on the shipped kinematic mover substrate with no new wire traffic.

## Scope

### In scope
- A `carrier` KVP on the FGD `DynamicLight` base class binding a dynamic light to a mover by the mover's **`name`**.
- Compile-time resolution of `carrier` to the mover of that name, producing a carried-light **linkage** (light → mover + authored local offset). No-match, duplicate-name, and baked-light bindings degrade with a named warning (the light stays unbound); never a hard build failure (see Orderings).
- Emitting the linkage in `KinematicGeometry` (id 43), version 4 → 5, as a per-mover member-light list; back-compatible decode of v1–v4.
- Runtime: resolve the linkage at level load onto the spawned dynamic light, and compose the light's per-frame world **position** from the carrier mover's **interpolated** transform (`pos + rot·offset`, so a carried omni orbits a spinning mover), by generalizing the existing light-bridge follow hook. A carried **spot** on a **translating (non-spinning)** mover keeps its authored cone aim, which is correct because a non-spinning mover holds identity rotation.
- Client parity with no new wire: the carried light reconstructs from the mover pose the client already re-derives from replicated phase.
- A dev fixture map and edge tests (reverse, stop, completion, 0/2 ticks per frame, spinning mover for the carried omni, unresolved/baked bindings).

### Out of scope
- **The full `MapAssembly` container** and multiple member kinds. Spec 1 ships the minimal member-light **linkage** — the reusable relation — not a general assembly type. `MapAssembly` lands with spec 2 (`E22--group-recognition`), where `func_group` and heterogeneous members justify a container; introducing it now would be a stub no consumer exercises.
- **`func_group` / linked-group recognition.** Binding here is the explicit `carrier` KVP only. Spec 2 adds implicit grouping that projects onto the same linkage.
- **Non-light members** (`prop_mesh`, emitters carried by a mover). The linkage generalizes, but only the dynamic light is spec 1's consumer.
- **Instancing / shared templates** — spec 3.
- **Baked lights that move.** A baked light's contribution is baked static; it cannot move. A baked light bound to a mover is warn+ignored, never carried.
- **A carried spot's cone re-aim under a *spinning* mover.** A carried spot rides a **translating** mover in spec 1; on a spinning mover its position still orbits (position compose), but the cone aim is *not* re-rotated — the light bridge's dirty gate compares the followed **position** only (`cached_follow_positions`, `light_bridge.rs`), so an axial spot (constant position, rotating aim) would never re-upload its cone. Carrying aim under spin needs a dirty-on-aim extension to the bridge; deferred. Spec 1 warns at compile when a spot's carrier is a spinning mover.

## Direction

**Problem.** A dynamic light cannot travel with a kinematic mover today. Co-locating a `light_dynamic` with a mover in the editor changes nothing: the light compiles to a top-level dynamic light at its authored world origin (`research.md` seam map), disconnected from the mover, which then moves out from under it. The cause is the missing member-of-mover relation and the runtime pose composition it drives — not the discarded editor grouping (that is spec 2).

**Prior commitments.**
- *Kinematic substrate (Epic 17).* Movers live outside the static bake, one entity per mover, driven by `run_kinematic_mover_tick`, drawn at `interpolated_transform(id, alpha)`; client re-derives the mover pose from replicated phase. This spec adds a relation onto that substrate and changes none of it. Consistent.
- *E21 attachment relation.* E21 renders a child at `holder_interpolated_transform × socket_matrix`, follows the rendered pose, inherits visibility, re-derives on the client with no new wire, and deliberately carries no per-attachment **authored** data offset. This spec is the same relation with the holder pose being a mover `Transform` (E21's `RigidRest(Mat4)` runtime-pose case) and the child a live light entity (E21's explicitly reserved "entity-as-attachment" growth). The offset stays out of *authored* data — it is derived at compile as `light.origin − mover.origin`, the same origin-subtraction the mover geometry already uses — honoring E21's no-authored-offset stance; the derived offset *is* stored on the wire (12 bytes/member, see Alternatives / Wire format), a denormalization E21 does not need but the linkage does.
- *Source-format neutrality.* `carrier` is a canonical binding on the engine's dynamic-light archetype, resolved in the compiler; it names a mover by its engine-side `name`, not a TrenchBroom construct. No source vocabulary crosses into a shared stage.
- *Trigger→mover binding.* Triggers bind movers by `_tag` and command *all* matches — fan-out is correct for a command. A carried light rides exactly *one* parent, so it binds by the mover's `name` (the unique "stable mover name") and resolves to a single mover at compile time. Using `name` rather than the trigger `_tag` vocabulary is deliberate: it fits the 1:1 relation, gives the currently diagnostics-only `name` field a real consumer, and avoids overloading `_tags` (a light sharing a script-query tag with a mover must not silently become carried).

**Alternatives rejected.**
- *Reuse `follow_transform` as-is.* It reads the **same entity's** Transform (projectile-scoped) and is gated on the `follow_transform: bool` flag. A carried light's pose comes from a **different** entity (the mover). Rejected as-is; adopted as the hook to generalize — the carrier branch is checked first and is mutually exclusive with the projectile-follow path (a carried light keeps `follow_transform = false`).
- *A per-tick system that writes the light entity's Transform from the mover each tick.* Rejected: the light's visible pose must match the **interpolated** mover pose the geometry draws with, and a tick-written child Transform would need its own interpolation and could desync by up to a tick. Composing at upload time from the mover's interpolated pose is exact by construction (same `alpha`, same entity, same `interpolated_transform`) and needs no tick system (`research.md` design resolution).
- *Peel the light entirely into the mover record (section 43 carries full light params).* Rejected: it duplicates light-param encoding and forks the dynamic-light spawn path. Keeping the carried light a normal `AlphaLights` record plus a small linkage reuses all existing dynamic-light machinery; only the per-frame position is overridden.
- *Bind by mover `_tag` (mirror trigger `target_tag`), or infer from shared `_tags` with no KVP.* Rejected: the trigger tag vocabulary carries fan-out semantics (command all matches) a single-parent light does not want, forcing a uniqueness-suppression check; and any tag-based scheme overloads `_tags` — a light sharing an unrelated script-query tag with a mover would be silently carried (shared-tag *inference* additionally makes >1 shared tags ambiguous). Binding by the mover's unique `name` fits the 1:1 relation directly. The engine already chose a dedicated `target_tag` KVP over shared-tag inference for triggers, for the same overload reason.
- *Membership-only wire (store `alpha_light_index` alone; re-derive `local_offset` at load).* The offset is `AlphaLightRecord.origin − mover.origin`, both already in the PRL, so the wire could omit it. Rejected in favor of storing the derived offset: it keeps the linkage self-contained and the runtime resolution a pure copy (no per-light arithmetic against a second section at load), for 12 bytes per carried light. The version bump is required for membership regardless, so denormalizing buys nothing structural. Decided, not deferred.

## Acceptance criteria

- [ ] In a dev map, a `light_dynamic` whose `carrier` names a linear `kinematic_mover` renders at a fixed offset from the platform and tracks it across start→end→start; at rest the light sits at its authored position.
- [ ] The carried light's rendered position matches the moving geometry with no visible one-tick lag on a frame with **zero** fixed ticks and a frame with **two** fixed ticks (interpolation parity with the geometry draw — same mover entity, same `alpha`).
- [ ] The mover reverses (`ping_pong`) and completes (`once`): the light tracks through the reversal and holds at the terminus — it never snaps back to the authored origin.
- [ ] A carried **omni** `light_dynamic` on a **spinning** mover (E17-D) orbits the spin axis at its authored radius (position composes `pos + rot·offset` from the mover's interpolated rotation).
- [ ] A carried `light_dynamic_spot` on a **translating (non-spinning)** mover tracks the mover's position and holds its authored cone aim, at rest and in motion.
- [ ] A `light_dynamic_spot` whose `carrier` is a **spinning** mover → a compile warning naming the light and the spinning mover (cone re-aim under spin is not carried in spec 1); the light still carries position and compiles bound.
- [ ] `carrier` naming **no** mover → a compile warning naming the light and the missing name; the light compiles as a normal unbound dynamic light at its authored origin and the build succeeds.
- [ ] `carrier` matching **more than one** mover (duplicate mover `name`s) → a compile warning naming the light and the duplicate-named movers; the light compiles unbound.
- [ ] `carrier` on a baked `light` / `light_spot` / `light_sun` → a compile warning; the light bakes as a normal static light with the binding ignored.
- [ ] A blank or cleared `carrier` produces no warning and a normal dynamic light — never a parse error.
- [ ] A connected client renders the carried light tracking the mover identically to the host, and the app/wire protocol version is unchanged (no new replicated field).
- [ ] `KinematicGeometry` round-trips version 5 with member-light linkages; **a synthetic v1–v4 payload still decodes** (empty linkages), and `from_bytes` accepts version 5. Adding a carried light leaves `level_content_digest` unchanged.
- [ ] A carried light produces no baked lighting data (it is dynamic): one `AlphaLights` record, no static/animated bake-namespace entry.
- [ ] A carried light moved far from its authored origin stays correctly lit and culled: dynamic-light culling is influence-based (`influence.center` is relocated to the followed position), so the stale baked `leaf_index` is never read for the moving light, and the light does not blink out when the mover geometry is frustum-culled.

## Tasks

### Task 1: Thin vertical slice — omni light carried by a linear mover
Build the whole path end to end for one case: a `light_dynamic` (omnidirectional) bound to a non-spinning `kinematic_mover`, tracking it at runtime. **Compile:** add a `carrier` string KVP to the FGD `@BaseClass = DynamicLight` block; read it in `translate_light` (`format/quake_map.rs`) via the blank-is-default `authored` helper pattern — and read it for **all** light classnames, not only the `DynamicLight`-derived ones, so a hand-authored `carrier` on a baked light is detectable for the Task 2 warn-clear (the FGD only offers the KVP on the dynamic base, but `translate_light` reads `props` directly). Store it on a new `MapLight.carrier: String` field (`map_data.rs` — a new typed field; `MapLight` has no KVP bag). After the parse loop collects both `lights` and the movers (a post-loop pass, sibling to `resolve_kinematic_movers`), for each dynamic light with a non-blank `carrier` resolve it against the movers' `name` fields to the mover of that name and compute `local_offset = light.origin − mover.origin` (mover **spawn** rotation is identity — `MapKinematicMover` carries no authored rotation field, only spin authoring that begins at identity — so no inverse-rotation term is needed); record a `CarriedLightLink { source_light_index, mover_id, local_offset: [f32;3] }`. **Wire:** bump `KINEMATIC_GEOMETRY_VERSION` 4→5 (`level-format/src/kinematic_geometry.rs`); append to each `KinematicMoverRecord`'s encode/decode a member-light list of `{ alpha_light_index: u32, local_offset: [f32;3] }`, guarded `if version >= V5`, defaulting to empty for v1–v4 (mirror the v2/v3 append blocks); widen `from_bytes`'s accepted-version set to include 5. **Pack:** at the seam where both the source `MapLight` list and the `AlphaLightsNs` namespace are in scope (`pipeline.rs`, where `alpha_lights_ns` is built from `map_data.lights` **before** `encode_kinematic_geometry_section`), map each link's `source_light_index` to its **`AlphaLights` section position** using the `AlphaLightEntry.source_index` inversion the namespace already carries — this accounts for the `!bake_only` filter that drops baked-only lights from `AlphaLights` — and emit the per-mover member-light list. **Runtime:** decode the linkage into `LoadedKinematicMover.carried_lights`. Because lights spawn (`LightBridge::populate_from_level_with_influences`, `startup/lifecycle.rs`) **before** movers spawn (`spawn_loaded_kinematic_movers`, Segment B, `startup/lifecycle_world_cpu.rs`), carrier resolution is a **distinct pass after mover spawn**, not a parameter threaded into `populate_from_level`: immediately after `spawn_loaded_kinematic_movers` returns its `Vec<EntityId>` (order-aligned with `geometry.movers`), zip it with `geometry.movers` to build a `mover_id → EntityId` map, then for each carried link set `LightComponent.carrier: Option<LightCarrier { mover_entity: EntityId, local_offset: Vec3 }>` (`#[serde(skip)]` — a raw runtime handle that must not round-trip; note `follow_transform` is only the *routing-field* precedent, it is itself `#[serde(default)]`) on the already-spawned light entity, looked up by its `AlphaLights` index via `LightBridge::entity_for_map_index`. A `mover_id` absent from the map (a failed/partial mover spawn) leaves that carrier `None` (unbound at authored origin) — never bound to a misaligned entity. **Compose:** generalize `follow_transform_position` (`scripting/systems/light_bridge.rs`) so a light with `carrier: Some(..)` returns the carrier branch **first** (mutually exclusive with the `follow_transform` projectile path): `registry.interpolated_transform(carrier.mover_entity, alpha).ok().map(|t| t.position + t.rotation * Vec3::from(local_offset))` — the engine `Transform` has no `transform_point`, and movers never scale, so `pos + rot·offset` is the compose; `interpolated_transform` returns a `Result`, so `.ok().map(..)` mirrors the existing `Mesh` branch. `rot·offset` handles a spinning mover's orbit from the start. The bridge already writes that position into the `GpuLight` origin and the culling `influence.center`. Prove it in a dev map: a moving platform (`name "lift"`) carrying an omni `light_dynamic` (`carrier "lift"`); the light tracks the platform. Keep validation, spot handling, and the full edge suite for later tasks — this task's tests are a smoke check, a `KinematicGeometry` v5 round-trip unit test, **and a synthetic-v4-payload decode test asserting empty `carried_lights`**.

### Task 2: Compile-time resolution diagnostics and digest exclusion
Own the resolution edge cases in the post-loop carrier pass from Task 1, matching the compiler's warn-and-continue posture. A `carrier` naming **no** mover logs a warning naming the light (origin) and the missing name, and leaves the light unbound (a normal top-level dynamic light at its authored origin). A `carrier` matching **more than one** mover (duplicate mover `name`s) logs a warning naming the light and the duplicate-named movers, and leaves the light unbound (a light cannot ride two movers); spec 1 warns on the duplicate-name collision but does not add a general unique-`name` check (out of scope). A `carrier` present on a **baked** light (`light` / `light_spot` / `light_sun` — `is_dynamic == false`) logs a warning and clears the binding, so the light bakes normally (mirroring how baked `_cast_entity_shadows` is warn-cleared in `translate_light`). A `light_dynamic_spot` whose resolved carrier mover carries spin authoring (`spin_speed_deg_s != 0`) logs a warning that cone re-aim under spin is not carried in spec 1 — the light still binds and carries **position** (orbit), but its cone aim will not rotate; this is the scoped boundary made a real diagnostic (mover spin authoring is in scope at the resolution pass). A blank or cleared `carrier` is not a warning and not an error — the `authored` helper returns the default and the light is unbound. Separately, ensure the new member-light linkage is **excluded** from `level_content_digest` (`runtime_movers.rs`). Note the real mechanism: `level_content_digest` iterates `geometry.movers` (the runtime `LoadedKinematicMover`, not the wire `KinematicMoverRecord`) and hashes named fields by **field access** — an allowlist that reads `mover_id`, `name`, `origin`, `path`, spin, `carry_yaw`, vertices, indices and simply never reads block/event fields. So adding `carried_lights` to `LoadedKinematicMover` is auto-excluded by *not adding a read* — the exclusion is achieved by inaction, not by a named skip (the digest is not a doctrine denylist today; do not restate the imprecise "like the v3 event fields already omitted" as the warrant). Add unit tests for each degradation (no-match, duplicate, baked, spot+spinner warn), a test for the blank/cleared `carrier` (no warning, normal dynamic light), and a test asserting the digest is byte-identical with and without carried lights.

### Task 3: Carried spot consumer and cull correctness
Add the carried `light_dynamic_spot` consumer on a **translating (non-spinning)** mover and confirm cull correctness as any carried light moves. The spot's `cone_direction` is authored world-space and, because a non-spinning mover holds identity rotation, its authored aim stays correct with no runtime rotation — spec 1 packs `cone_direction` **as-authored** for a carried spot (no compile-side and no bridge-side direction transform; carrying aim under a spinning mover is deferred, see Scope). Position already tracks via Task 1's `pos + rot·offset`. Confirm the influence volume and cone still cull correctly as the light moves: the bridge relocates `influence.center` to the followed position, so name that influence-based path and assert a far-moved carried light is neither mis-culled by its stale baked `leaf_index` nor lost when the mover geometry is frustum-culled (the bridge iterates lights, not mover draws, and `interpolated_transform(mover)` is always available because the mover entity is always spawned). Tests: a carried spot on a translating mover tracks position and holds authored aim; a carried omni on a **spinning** mover orbits the spin axis at the authored radius; a far-moved carried light stays lit and correctly culled.

### Task 4: Dev fixture, edge suite, and client parity
Author the durable fixture and the full edge test suite (consuming Tasks 1–3). Fixture: a dev map with (a) a linear platform carrying an omni light, (b) a spinning mover carrying an omni light (orbit), and (c) a translating mover carrying a spotlight, with named stations for visual inspection. Tests per the `research.md` Orderings/pin table: pose tracking across reversal (`ping_pong`), stop, and `once` completion (holds at terminus, no snap); interpolation parity on a frame with zero fixed ticks and one with two ticks (light pose matches the geometry's `interpolated_transform` at the same `alpha`); reload / host level change (each carried light re-resolves after every mover-spawn path, before the first `LightBridge::update`); and **client parity** — a loopback/two-process check (or a client-path unit test over `client_predict_loaded_movers_tick` + the generalized bridge hook) asserting the carried light tracks the mover on a connected client with the app/wire protocol version **unchanged**, and that host and client light-vs-geometry never desync intra-client. Assert a carried light emits exactly one `AlphaLights` record and no bake-namespace entry.

## Rough sketch

- New FGD KVP on `@BaseClass = DynamicLight`: `carrier(string) : "Carrier mover name" : ""`.
- Compiler: `MapLight.carrier: String` (read for all light classnames); a post-loop `resolve_carried_lights` pass (resolving `carrier` against mover `name`) producing `Vec<CarriedLightLink { source_light_index, mover_id, local_offset }>`; pack maps `source_light_index → AlphaLights` position via `AlphaLightEntry.source_index` and attaches per-mover member-light lists.
- `level-format`: `KinematicMoverRecord` gains `carried_lights: Vec<MemberLight { alpha_light_index: u32, local_offset: [f32;3] }>`; `KINEMATIC_GEOMETRY_VERSION = 5`; `write_mover`/`read_mover` gate it on `version >= 5`; `from_bytes` accepts 5.
- Runtime: `LightComponent.carrier: Option<LightCarrier>` (`#[serde(skip)]`); resolution is a **distinct pass after `spawn_loaded_kinematic_movers`** (Segment B, `lifecycle_world_cpu.rs`), building `mover_id→EntityId` (zip movers × spawned vec) and setting carriers via `LightBridge::entity_for_map_index`; `follow_transform_position` generalized to a carrier-first branch. `LightCarrier { mover_entity: EntityId, local_offset: Vec3 }`.
- Compose: `interpolated_transform(mover_entity, alpha).ok().map(|t| t.position + t.rotation * local_offset)` for position; carried-spot `cone_direction` packed as-authored (no runtime rotation in spec 1).

## Wire format

`KinematicGeometry` (id 43) advances 4 → 5. Per-mover, after the v4 field group, append a member-light list: a length-prefixed sequence of `{ alpha_light_index: u32, local_offset: [f32; 3] }`, little-endian, matching the section's existing integer/vec conventions. Empty list encodes as length 0. Decoding v1–v4 yields an empty list (the established default-on-old-version pattern); `from_bytes`'s accepted-version set widens from `{1..4}` to `{1..5}`. `alpha_light_index` indexes the `AlphaLights` (id 18) section — the same positional index space `LightInfluence` (21) and `LightTags` (26) use. State the constraint, not the byte offsets: the implementer places the group after the v4 fields where both encoder and decoder gate on `version >= 5`.

## Decisions

- **Binding by mover `name`, KVP `carrier`.** A carried light rides one parent; `name` is the unique 1:1 identifier, gives the currently diagnostics-only field a real consumer, and avoids overloading `_tags`. Not the trigger `_tag` vocabulary (fan-out) — see Direction / Alternatives.
- **No-match / duplicate-name / baked binding → warn + unbound, never a hard error.** Matches the compiler's warn-and-continue posture; a valid map still results (unlike `switch`'s brush-count error, where the press volume is genuinely undefined). A duplicate-`name` match is a latent mover-authoring issue spec 1 warns on but does not police with a general unique-`name` check (out of scope).
- **Carried spots scoped to translating movers; spot-on-spinner warns (position carried, aim not).** The bridge's dirty gate compares the followed **position** only, so a carried spot with a constant position but rotating aim (axial on a spinner) would never re-upload its cone. Rather than add dirty-on-aim machinery, spec 1 supports carried spots on translating movers (where position always changes, so the as-authored aim rides along) and warns at compile when a spot's carrier spins. Carried omni on a spinner is fully supported (position orbit). Spinner-spot aim defers to a later spec.
- **Position compose is `pos + rot·offset`, not `transform_point`.** The engine `Transform` (`registry.rs`) is a plain `{ position, rotation, scale }` with no `transform_point` method; `interpolated_transform` returns a `Result`. Compose is `t.position + t.rotation * local_offset` behind `.ok().map(..)`, movers never scaling. `rot·offset` gives the spinning-mover orbit for free.
- **`LightComponent.carrier` is `#[serde(skip)]`.** It holds a raw runtime `EntityId` that must not round-trip; re-resolved at load. `follow_transform` is the routing-field precedent, but it is itself `#[serde(default)]` — do not copy its attribute.
- **Resolution is a distinct pass after mover spawn.** Lights spawn (`lifecycle.rs`) before movers (`lifecycle_world_cpu.rs` Segment B), so the linkage cannot be threaded into `populate_from_level`. A post-`spawn_loaded_kinematic_movers` pass builds `mover_id→EntityId` (zip movers × the returned `Vec<EntityId>`) and sets carriers via `entity_for_map_index`. It must run on every path that re-spawns movers+lights (reload, host level change), before that level's first `LightBridge::update`.
- **Store the derived `local_offset` on the wire (not membership-only).** Self-contained linkage, pure-copy runtime resolution; 12 bytes/light. Both origins are in the `.prl`, but storing avoids a cross-section read at resolution.
- **Positional `AlphaLights` index, computed at pack.** The linkage keys the carried light by its `AlphaLights` section position — the space `LightInfluence`/`LightTags` already use — mapped from source order via `AlphaLightEntry.source_index` at the pack seam (accounting for the `!bake_only` filter). The linkage ships in the same `.prl` as `AlphaLights`, so they cannot drift; no stable light id is needed.
- **Digest exclusion is by inaction (current allowlist), not a named skip.** `level_content_digest` reads named fields off `LoadedKinematicMover` by field access; `carried_lights` is excluded simply by not adding a read. This is presentation-only, so it must stay out of the multiplayer static-content fingerprint. (The digest is not a doctrine-conformant denylist today; converting it is out of scope.)
- **The carried light's baked cell assignment is harmless.** `AlphaLightRecord.origin` / `leaf_index` reflect the authored origin, but dynamic-light culling is influence-based and the bridge moves `influence.center` to the followed position, so the stale cell is never read for the moving light.
- **The light entity's own `Transform` stays at the authored origin.** The carried position is composed at upload via the carrier override; nothing reads a dynamic light's `Transform` for its position (mirrors `follow_transform`), so no per-tick Transform write is needed.
- **The carried light updates independent of mover render visibility.** The light bridge iterates lights, not mover draws; `interpolated_transform(mover)` is always available (the mover entity is always spawned), so the light stays correct even when the mover geometry is culled.
