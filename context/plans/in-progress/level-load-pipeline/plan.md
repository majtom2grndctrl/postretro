## Delegated answers
- **Pool size cap.** `LOAD_POOL_WIDTH_CAP = 2`; shipped width is `min(2, max(1, available_parallelism − 2))`, so a 4-core machine runs 2 and a 2-core machine runs 1. Tests construct the pool at width 2 whatever the cap. Reason: prep no longer outruns the parse (`research.md` §2.2), so width buys structure, not speed, and in the seam order the pool shares the CPU with the main thread, the upload thread and the four SH decode workers.
- **rayon or std pool.** A small engine-owned pool on `std::thread` + `Mutex`/`Condvar` queue, in a new module of `postretro` (load work is app-side; the renderer's upload thread is separate). Reason: rayon's pool has no per-task cancel or poll-and-join retirement, joins on drop (an event-loop-thread join the Cancellation rows forbid), and adds a runtime dependency against the tiny-binary northstar. Binary-size cost: the std pool adds no dependency; the release-binary delta is measured once for the whole brief at preflight (task 15) and recorded here.
- **Cache key.** blake3 over file content for every asset kind: the `.gltf`, each external buffer, and each referenced texture's `.prm` sidecar, plus every install-time parameter (import scale/pivot, material tier inputs) in a versioned key struct. Hashing runs on the pool. Reason: the existing `.prm` cache keys come from the bake and do not cover the glTF or its buffers, and path + mtime cannot prove "an edited file always misses". A hit still reads the files to hash them, but skips parse and upload, which dominate (`research.md` §2.1).
- **Phase weights.** parse 0.40, prep 0.15, upload 0.15, settling 0.30; named constants in the level-loader progress module. Each phase credits its own units (parse: bytes read; prep: tasks finished; upload: bytes written; settling: settle-set shortfall, as today). An empty phase credits its full share on entry so a near-empty level reaches 1.0. Reason: coarse and honest; lavapipe time is Settling-dominated but Metal is unmeasured, so the weights stay a tuning number reported with the Metal run.
- **Hand-out granularity.** Five ordered hand-outs: (1) SH stream manifest metadata (no cluster topology); (2) geometry + texture names and cache keys; (3) spatial: BVH, portals, cells, visibility, residency set, locator; (4) entities: data script, map entities, kinematics, triggers, teleporters, ghost links, environment volumes, push forces, reflection probes, fog, nav, cell draw index; (5) final: lights and every lighting section (SH volume, lightmaps, SDF, deltas, entity shadow lights) after the shadowmask drop and the `LoadedLighting` split, the finalized lightmap stream manifest, and the SH cluster topology after its install, then late validation's verdict. Lighting decodes before entities but rides hand-out 5 because the split rewrites it. Reason: hand-out 2 is what texture prep needs earliest; every section a parse-end step rewrites rides hand-out 5 (pin P25).
- **Chunked upload writes.** Yes: the upload thread submits its queued writes in batches of at most 32 MiB, each its own `queue.submit`, so no single main-thread present carries a world-texture-sized flush. Reason: bounds the Loading-frame stall the Manual row asks about; the size is a named constant reported with the Metal run.
