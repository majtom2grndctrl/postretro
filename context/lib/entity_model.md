# Entity Model

> **Read this when:** working on game logic, implementing entity types, loading entities from level data, or integrating entity state with renderer/audio.
> **Key invariant:** game logic owns all entities. Other subsystems borrow entity state read-only. Entities are component-tagged bags in a scripting registry; the engine ticks first-class components each frame.
> **Related:** [Architecture Index](./index.md) · [Development Guide](./development_guide.md) · [Audio](./audio.md)

---

## 1. Design Philosophy

Entities are component-tagged bags in a central registry. Every entity carries a `Transform` at minimum; additional components attach capabilities. The engine walks component columns each tick — no runtime type checks, no downcasting.

This is not a full ECS. There is no archetype storage, no query planner, no system scheduler. Component iteration is straightforward: iterate all entities carrying a given component kind and act on them. Favor readability and simplicity over maximum flexibility.

**Registry versus pool.** The registry holds what something must address individually: a hit, a replication update, an interpolation target, a script handle. Anonymous, disposable presentation lives outside it, so it never adds to tick cost or competes for registry slots. Particles are the case (§8).

**Component ownership.** The component vocabulary is engine-closed, for two reasons: hardware- and loop-level concerns (storage layout, per-tick systems a script VM can't drive at scale) and the engine's opinionated genre vocabulary — a retro shooter owns health, shields, and ammo as first-class nouns. Modders extend through declared data (descriptors, store slots, reactions), never new component kinds. Whether a capability is a dedicated component kind or a generic parameterized one (e.g. a shared scalar-stat kind serving both health and shields) is an internal storage choice — invisible to the script surface, which composes and queries components by name.

## 2. Entity Representation

### Common Data

Every entity carries a `Transform` (position, rotation, scale in world space). `Transform` is the only component guaranteed present at spawn.

Runtime cell lookup is transient. The camera is located each frame for portal traversal, and render collectors may locate an entity or particle position for visibility culling. Entities do not persistently track which cell they occupy.

### Components

Capabilities attach via component columns in the registry. Current engine components:

| Component | Purpose |
|-----------|---------|
| Transform | World-space position, rotation, scale |
| PlayerMovement | Capsule physics state for the player pawn |
| Immersion | Output-only: the fraction of the pawn's capsule its winning fluid covered on the last authoritative movement tick. Written by host movement; read only by the `player.immersion` slot (§7b). Never replicated |
| Light | Dynamic point-light parameters |
| BillboardEmitter | Particle emitter configuration |
| SpriteVisual | Billboard visual parameters |
| FogVolume | Runtime fog-volume parameters |
| Weapon | Descriptor-authored actions and tuning plus one live resource, shared recovery, reload, charging/execution, and input-edge state |
| AmmoReserve | Pawn-owned ammunition balances pooled by authored ammo type; reloads transfer from this reserve into the active weapon magazine |
| MeshComponent | Model handle (`model: String`) for rigid/static or skinned models, plus optional declared animation states and per-entity animation state; spawned via `prop_mesh` or a descriptor carrying a mesh component. Optional descriptor-authored `attachments` mount prop model handles at the model's named sockets (`resource_management.md` §7), rendered at a skinned holder's posed joint or a rigid holder's resolved rest matrix/socket transform — presentation-only (no collision, hit-zone, or gameplay-query participation; no netcode wire change), one authoring shape for skinned and rigid holders. Descriptor `shadowOnly` hides the mesh from the main view, so it draws only as a shadow and in the planar water mirror (`rendering_pipeline.md` §7.3a); it applies to the owning local-player view, and peer viewers render that player avatar forward. |
| Health | Hit points (`max`, `current`) plus optional direct-impact hitbox (one world-aligned AABB, fixed per archetype; its offset measures from the feet for a descriptor with `behavior`, else from the transform position, a movement pawn's capsule centre, §7b); declared via the `components.health` descriptor block. Health-bearing entities are damage targets. Hitscan rays and swept projectiles share target shapes from an authored AABB or zone-bearing skinned model (§7). |
| DefenseLayers | Host-owned defense layer stack in drain order (each layer's value and the parameters in force), health's own resistances, and the host tick of the last hit, which recharge counts from. Only an entity whose descriptor lists layers or a health `resist` carries it, so the per-tick layer step visits only those. Never replicated: a player's values reach their owner as owner-private slots (`scripting.md` §5) |
| KinematicMover | Engine-owned deterministic translating/spinning mover driver seeded from PRL `KinematicGeometry`; addressed as `getMapEntities("mover")` members, whose SDK handle builds declarative mover-command reactions. Also carries the mover's authored transition event addresses and sound keys for the app drain; the sound keys are presentation-only. |
| TriggerVolume | Engine-owned, serializable host-authoritative touch/use state for an invisible level-authored AABB. Named `on_fire` / `on_exit` reactions fan out effects; an exit fires only after that player's activation fired. Tracks occupancy; arming reopens Touch activation for already-standing players, while Use remains press-driven. |
| Touchable | Host-authoritative touch mode and sphere radius for a world item. Presence identifies the entity as a touchable world item. |
| Brain | Engine-internal enemy behavior: the entity's authored behavior state graph, the state it currently occupies, and its per-instance timers. Engine-owned evaluation, author-owned states and transitions (§7c). |
| Agent | Engine-internal navmesh path-following state for a moving enemy: the collision capsule seeded at attach time from the baked agent parameters, live velocity and ground reference (`GroundRef`, shared with the player: world, a mover, or airborne), the followed path plus its cursor, the mover gates and lift links it crosses and any planned ride, a destination, and mover state (an active ride, a walk clear of a pinning mover). No script surface (the `PlayerMovement` precedent). |
| Spawner | Map-authored enemy spawn point: the archetype name it materializes, how many enemies each firing creates, and the `spawned_tags` each spawned enemy carries (its own `_tags` never pass to spawns). Addressed as `getMapEntities("spawner")` members; a member's `fire()` spawns one batch from that spawner only. Stateless across firings; the resolved descriptor stays in the session spawn context rather than the serializable component. |
| ProjectileTrap | Map-authored, bodiless (no model, collision or health) trap naming one weapon descriptor; it fires from its origin along the view-frame forward of its map angles (§4). `fire` runs one execution of the weapon's primary action; a `fire` that meets a running execution or recovery is dropped. `start` repeats on an anchored schedule at an authored interval after an authored phase; `stop` cancels repeats and lets an in-flight execution finish. Addressed as `getMapEntities("trap")` members and by trigger commands. Host-only; started state and schedules belong to one level install and never replicate. Its runtime (the stripped weapon, the schedule, its own activation clock) rides the component, outside the registry's `Weapon` column, so weapon sweeps never reach it; a fixed-tick trap stage after AI and before steering drives it (`crates/sim/src/traps`). |
| EntityState | Per-instance modder-owned numeric fields. Every entity receives an empty component at spawn; fields are emergent — a name is created by its first write and an unset name reads as zero. No descriptor surface and no schema, so an entity may gain state mid-play without a respawn. |
| DeferredEffect | Per-entity queue of impact effects awaiting a later fixed tick, plus the terminal inert flag marking an entity bound for the frame-end removal pass. Every entity receives one at spawn, so deferring an effect never depends on a brain being present. Bounded per entity; overflow drops the newest request. |
| DescriptorProvenance | Which descriptor spawned the entity, through which spawn path, which components that descriptor owns, and which map KVP overrides landed. Descriptor hot reload and replication plan against it rather than re-deriving ownership. |

Type-specific data lives in the component. An entity is "a player" by virtue of carrying `PlayerMovement`, not by belonging to a typed collection. Other entity types follow the same pattern: enemies use an **Agent** component for navmesh path-following and collide-and-slide movement, plus a **Brain** component carrying the behavior state graph the AI tick evaluates (§7c). Doors, projectiles, and pickups should attach their behavior through components instead of typed collections.

**Weapon vocabulary.** One canonical weapon descriptor type — `WeaponDescriptor` (`crates/foundation/src/data_descriptors/types/combat.rs`; SDK `WeaponDescriptor`), authored as a `weapon` block on `defineEntity` and resolved by canonical name through the shared descriptor lookup (`find_descriptor`). No player-vs-enemy descriptor split and no branch on actor kind: a player-loadout weapon and an enemy attack resolve the same descriptor type. A restriction on who may wield a weapon, if ever added, is an attribute of the weapon — never a separate descriptor kind or an actor-type branch. Player pawns reference weapons through `components.inventory.loadout`; enemy attack entries may reference the same descriptor. Presentation follows the same rule: a weapon's sounds play whoever wields it. Projectiles retain their originating action, resolved shot identity, and effective fire/impact sounds. Delayed contacts never resolve through the shooter's current weapon (`audio.md` §4). Projectile traps are the one deliberate exception to the no-branch rule: a trap pays no ammo, heat or cell and never reloads, dry-fires or overheats. A trap takes projectile weapons only and refuses a charged primary action, having no held trigger to release; an unknown name, a hitscan weapon or a charged primary leaves it inert with one load warning. Its weapon resolves once per level install, so a hot-reloaded descriptor reaches it at the next install. Trap shots carry no attacker, direct or splash, and credit the weapon's own credit source, so a damaged enemy registers damage from an unknown source and never turns toward the trap.

**Weapon state.** Timed weapon states live in one component-level state machine: a new state is a variant plus its transition arms, never a new component field or boolean. Fire authorization is computed without consulting weapon state, so a preemption check and the real fire gate share one evaluation and cannot drift. State-dependent terms are applied by the caller around that shared verdict, not folded into it.

**Weapon activations.** Required `primary` and optional `secondary` actions share one execution, resource, and recovery gate. `press` starts once per fresh edge; `hold` requests another execution after completion and recovery. Secondary wins simultaneous fresh starts. An existing execution is never interrupted by another start, and blocked presses are consumed rather than queued. The one exception is a press refused only by the shooter's own pawn-state gate (a fire-blocking vault, `movement.md` §4): it is held and fires on the first open tick while the trigger stays held. Authors compose bounded shot/wait sequences; there is no burst opcode (`scripting.md` §11).

Charge belongs to an action, independent of resource kind. It requires `press`, freezes on explicit release, and never auto-fires at full charge. Release before the minimum cancels without debit; a normal sequence continues after button release. Switch, drop, a refused pawn fire gate, input suspension, disconnect, level change, and descriptor replacement cancel future work, and so does entering a fire-blocking vault. `charge.interruptedBy` is a closed map from interrupt source to whether that source cancels the charge while it is still charging. Every key is optional and defaults to `true`; an unknown source, a non-boolean or a non-object rejects content, through one check both runtimes share. `vault` is the only source today: `false` keeps the charge charging through the climb and fires its release once the climb ends (`networking.md` §Combat authority). Future sources (taking damage, NPC interactions) join the same map rather than adding fields. Death-sweep cancellation and the other lifecycle cancels are not charge interrupt sources. Zero-HP death sweeps cancel an undeclared pawn's charge; a declared pawn follows `fire`, so `fire: true` retains charge at zero HP (`scripting.md` §12). Switching, dropping and the other lifecycle cancels still cancel. A fresh reload press, when the life-state reload capability permits, cancels before the ordinary reload gate, even when reload cannot start; holding reload does not cancel repeatedly.

Every due shot samples current aim and freezes resolved combat and presentation tuning. Shots spend separately; waits and cancelled charge spend nothing. Accepted shots set action recovery, while later shots in the same execution bypass the start gate. Insufficient ammo/cell ends execution with one dry-fire cue and action recovery; heat lockout ends it silently. A threshold-crossing heat shot fires before cancelling remaining steps. Completion and cancellation preserve paid resources and recovery already owed. Authored visual size is independent of collision and splash radius. Authorized shots retain their captured values through later switching or content replacement.

**Dynamic accuracy.** Per-shot spread is a dynamic axis, not a fixed cone. Descriptor-tuned bloom, movement, and optional vertical bias compose the effective hitscan half-angle through one shared host/client calculation. Authored tuning replicates; bloom accumulator and idle timer remain live per-instance state across hot reload. Projectiles converge on the crosshair and never sample the cone. Each machine exposes its predicted neutral-degree result through local-only `player.spread` HUD state; the reticle maps it to a spread ring in script.

**Weapon resources.** The descriptor's `resource` is a tagged union of `ammo`, `heat`, and `cell`, and a weapon carries at most one. Each variant's numbers are authored inside the `resource` block and projected through `effective()` beside the flat stats. Heat and cell differ from ammo in three ways:

- **They update every fixed tick, independent of fire.** Heat cools and cells refill for every weapon instance, wielded or holstered, including while charging. Recovery freezes on inactive instances. The passive update runs once per tick on the authoritative path, before the active weapon's shot gate. Connected clients never run it; they read the replicated values.
- **Overheat is a latch on the heat resource, not a weapon state.** Switching away lowers the weapon, which would overwrite a state variant; a latch survives the round trip. The shot that reaches the threshold still fires. The latch then refuses pulls silently until heat returns to zero, cooling without the usual delay.
- **Their gates join the state-blind fire verdict beside the magazine check.** Overheated is a silent refusal. A cell that cannot pay for a shot dry-fires, exactly as an empty magazine does.

Heat and cell have no reserve, ignore reload input, and do not carry across a level transition: the carried loadout keeps magazines only, so a cell arrives full and an overheat clears. HUD state follows the health pattern of a raw value plus a companion max (`scripting.md` §5), and a local slot names the active weapon's resource kind so a HUD can pick its readout.

**Splash / area effects.** Splash is a `splash` block on `WeaponDescriptor`, beside the projectile block rather than nested in its travel tuning. Current use is projectile impacts; descriptors reject splash on hitscan weapons. A blast damages each visible live damageable volume in radius once through the damage chokepoint, using authored linear distance falloff and optional owner exclusion. Static world geometry and movers at the tick's pose occlude; other entities do not. A projectile whose centre starts a step inside a mover's hull, because the mover closed over it or it launched there, detonates where it is, and its blast reaches only the side it came from; one that only overlaps a mover's face meets it as it would a static wall. Host-authoritative results reach clients through replicated Health, and remote observers take the explosion burst from the reliable observer impact cue, which excludes the predicted owner. See [Networking](./networking.md) §Presentation events vs. replicated state and §Combat authority.

**Knockback.** Weapon hits carry an independent velocity-change payload. Direct hits use travel direction; splash uses the vector from blast center to damageable-volume center. Both support an authored upward blend. Splash force has its own distance falloff and owner multiplier: disabling self-damage still permits rocket jumping, and zero damage still permits a concussive blast. Splash replaces direct health damage; explicitly authored direct and radial pushes compose. Only live damageable players and navigation agents receive movement impulses. Health-only props remain stationary. Hit-zone multipliers affect damage only. Direct projectile tuning is captured at fire time; impact never re-reads the weapon. Response belongs to `movement.knockback` for players and `behavior.knockback` for enemies. See [Movement](./movement.md) §6.

**Defense layers and damage types.** Shields and armor are one engine noun (§1): an ordered stack of layers inside the `health` block, each an author-named kind the mod registers, drained before health by every damage producer. Every hit carries its producer's mod-registered damage type, or the mod's default when it names none, and the type scales its drain per pool. The engine owns each layer's value and its host-only recharge; the descriptor authors capacity, recharge and resistance. Layers follow health's lifecycle: spawn and respawn fill them, carry restores their values only when health carries, clamped to the arrival capacity, and `setHealth` / `grantHealth` leave them alone. Hot reload matches layers by name and keeps each kept layer's value, last good parameters and the last-hit stamp: a kept layer clamps at once to a lowered literal capacity, an added literal-capacity layer arrives full, an added expression-capacity layer fills at the next tick start, where the new parameters first evaluate, and a removed layer drops. Health stays the death authority: the latch, the sweep and liveness read health only. Per-entity state named `shield` stays author data the engine never drains. Authoring contract: `scripting.md` §2, §10.5, §11.

**Status effects.** A status is an engine noun beside defense layers: an author-named kind that deals damage over time, or none as a marker other policies read. A live instance is keyed by status and applier, the applying hit's damager or else its source id, so credit, stacks and time left stay per player in co-op. An entity holds at most 16 instances; a new one on a full entity replaces the one with least time left. One applier's applications to one target on one fixed tick count as one, so a shotgun's pellets or a rocket and its splash apply once. Damaging ticks run on the host in the status stage (§5) as ordinary in-tick hits: typed, through the damage chokepoint, crediting the applier and running impact policies. A marker's ticks never reach the chokepoint. An instance first ticks `tickMs` after it appears, then every `tickMs`; refresh and stack never move that phase, and a tick due on the expiry tick still lands. A target at zero health accepts no new instance and skips its due ticks, so another hit's authored death plays alone. An entity with no instance costs the stage nothing. Statuses are transient: the death latch, respawn, level change, same-map restart and rejoin clear them, carried state never holds them, and a save records none. Hot reload keeps instances by status name, drops a removed kind's, and applies changed parameters from the next tick without moving the phase. A fluid's status reaches player pawns only, since only pawns resolve fluid (§7). Authoring contract: `scripting.md` §2.

## 3. Entity Lifecycle

### Creation

Entities enter the world through two paths:

| Source | When | Examples |
|--------|------|----------|
| Level entity data | Level load | Player spawn, enemies, doors, pickups, triggers, lights |
| Runtime spawning | During gameplay | Projectiles, scripted actors |

Level-load entities are created once when the level is parsed. Runtime entities are created by game logic in response to player actions or game events. Anonymous particles and impact bursts use the separate presentation pool (§8).

### Update

All entities participate in applicable fixed-timestep game logic stages each tick. Once damage settles, a quiescent enemy (zero HP, or a despawn already queued) is excluded from AI and steering but may still participate in other applicable stages; as a corpse it keeps gravity, mover carry and displacement (`movement.md` §6). A dormant NPC runs AI and steering only on its tier's runs (§7c, Tick tiers). See section 5 for update order and model.

### Destruction

Entities are destroyed when:

- A scripted or engine bridge condition fires (emitter despawn, level unload).
- A scripted `despawn` effect reaches the end-of-frame removal pass. Health reaching zero only latches the entity and freezes non-player kill credit; it neither removes nor reports the entity. Successful scripted removal reports that frozen credit, while the player pawn instead remains present and emits one `playerDied` event at its first zero-HP latch.
- Level unloads (all entities destroyed).

Destruction is immediate: the entity's slot is cleared and its generation bumped (or the slot retired on generation overflow) in the same call that removes the entity. Callers must not hold entity IDs across points where destruction can occur.

**Held ownership.** Inventory membership defines whether an item is held, independently of its components and equip state. One canonical relation and a derived registry lookup serve replication, spatial targeting, AI actor/target selection, steering and mover blocking. All live slots count. Mutations and lifecycle cleanup keep the relation consistent; conflicting live ownership fails atomically. Holding preserves retained Health and behavior state and existing weapon execution/resource rules, except that an enemy's drawn attack execution is cancelled (§7c, Attack budget). Successful drop restores world participation. Releasing a held wieldable never moves the active weapon except to replace the one released: releasing the active weapon mid-switch moves to a live switch target, a dead target ends the switch on the weapon in hand, and a released weapon leaves idle. Single-player, host and a client applying a host-side drop share this rule. Explicit scripted Health mutation and lifecycle effects retain their semantics. Descriptor refresh never infers ownership from component presence.

Pawn-owned auxiliary entities share the pawn lifecycle. Retirement follows the
pawn's current inventory, including later pickups; items that were dropped or
acquired elsewhere survive. Destruction clears
ownership before entity-slot reuse. Local level teardown clears
the whole registry and active-wieldable handle together. Player damage does not
despawn the local pawn. These rules keep live weapon timers attached to their
reserve-owning pawn; reload is never cancelled as orphan cleanup.

## 4. Level Entity Data

Level files embed entity definitions: key-value pairs grouped per entity. Each group defines one entity with a `classname` key that identifies its type.

### Loading

The loader reads entity definitions and resolves each `classname` via a classname-dispatch table to an engine spawn handler. Recognized classnames produce an entity initialized from the key-value pairs (position, angle, flags, etc.).

Unknown classnames are logged as warnings and skipped. The engine does not crash on unrecognized entities — maps may contain editor-only or tool entities that have no runtime meaning.

### Key-Value Parsing

Entity properties arrive as string key-value pairs. The loader parses these into typed values (floats, vectors, integers, enums). Malformed values log a warning and fall back to defaults.

**Map declarations seed level state; descriptors tune archetypes.** Maps may declare initial level gameplay values at load, including world gravity, so basic content does not require a script. Maps may also place static regional gravity, push and fluid volumes, baked at compile time (§7, Environment Volumes); any further regional field needs its own amendment, and gas and haze stay with fog volumes. `force` on `push_volume` is one such amendment: a modifier that rides its volume's push and wins with it, scaling what bodies feel while particles and fluid surfaces show the nominal push (`movement.md` §6). Teleporter regions are another: baked like the rest, but armed and disarmed by script, so not static (§7). Ghost links are a third: baked regions scripts arm, presentation only (§7d). Level seams are a fourth: baked regions scripts arm that move players between maps (§7e). A map declaration cannot mutate gameplay after load or override per-archetype descriptor tuning. Weapon damage/range/action timing, player movement tuning, and future wieldable/ability tuning remain descriptor-owned. Scripts may mutate runtime values through their supported primitives, including on events. An archetype may need FGD presence to be map-placeable (a pickup's position), but never its tuning surface.

**Facing convention (engine-wide).** A map entity's yaw is the arrow TrenchBroom draws: Quake yaw 0 faces +X and turns counter-clockwise. The compiler keeps its sign (`build_pipeline.md` §Supported Map Formats), because the axis map (x, y, z) → (−y, z, −x) is a proper rotation. Camera and player forward is −Z; a model's front (glTF) is +Z. The half turn between them is applied at exactly one seam, `MapEntity::model_rotation_quat()`, which every model-bearing placement spawns from: props, spawners, descriptor-placed enemies, dummies and pickups, and loadout weapons. View-frame and frontless placements — player spawn and network slots, billboard emitters — spawn from `rotation_quat()`, and teleport destinations use the arrow's yaw directly. Copies a spawner releases fan out to the left of its arrow. A new spawn path picks its frame by the axis its entity treats as forward, never by negating yaw.

## 5. Update Model

### Fixed Timestep

Game logic runs at a fixed tick rate, decoupled from render framerate. Renderer interpolates between the last two game states for smooth visuals. An unperceived NPC with no target runs AI and steering at 2 Hz, each run stepping the ticks since its last. No authoritative tick is skipped: mover carry and pushes reach it every tick (§7c, Tick tiers).

### Update Order

| Order | Stage | Rationale |
|-------|-------|-----------|
| 0 | Transform snapshot | Copies current→previous transform for every already-live entity before any movement system runs. Entities spawned this tick skip the snapshot and initialize previous == current at construction (no pop on spawn). |
| 1 | Kinematic mover tick | Host pin pretest over player pawns and living agents (`movement.md` §6), then advances deterministic mover transforms and tick deltas, and records which watched movers are docked (the nav gate state every later stage reads), before player movement consumes mover collision/carry |
| 2 | Player movement tick | Input-driven; resolves capsule physics and position before anything reads player state. Teleporter arm/disarm queued since the previous tick has applied right after the transform snapshot, so every pawn reads one armed state. A teleport resolves after each pawn's movement step, so the trigger tick sees the arrival pose; authoritative `teleport` events dispatch once every pawn has moved |
| 3 | Trigger tick | Host evaluates touch-entry and use-overlap triggers after player movement; commands mutate mover phase for the next mover tick |
| 4 | Touchable tick | Host evaluates player-item touch overlap after triggers and before AI |
| 5 | Authoritative projectile flight | Advances existing gameplay projectiles after movement settles. Impacts route through the Health chokepoint before AI reads damage and attacker facts. |
| 6 | AI brain tick | Chooses each NPC's tier (§7c, Tick tiers), excludes quiescent brains, then selects targets on decide ticks, evaluates each admitted enemy's behavior graph, and applies the selected state's motion and action after player movement and projectile impacts settle (§7c) |
| 7 | Host camera callback | Host-side camera/aim work runs after movement and AI, before aim-dependent steering and weapon systems |
| 8 | Agent steering tick | After AI decisions and host camera work. Each living agent steers on its tier's runs (§7c) along its path, rides a lift, or walks clear of a mover that yielded to it, moving through mover contact and collision against static and mover geometry; corpses take motion alone. The mover blocking pass then judges players and agents at their settled positions (`movement.md` §6) |
| 9 | Weapon reload and activation tick | Advances passive resources and reloads, transfers completed reloads from pawn reserves, then consumes actions and per-shot aim; accepted shots may spawn impact effects and apply damage |
| 10 | Projectile launch finalization | Closes spawn grace for projectiles launched after the flight stage without moving them. They begin flight on the next fixed tick. |
| 11 | Status stage | Host and single player. Applies this tick's fluid statuses, then ticks every live instance. Follows every in-tick application, so a lethal tick latches and credits in the death sweep (§2, Status effects) |
| 12 | Death sweep | Processes entities whose health reached zero after same-tick damage |
| 13 | Assist accumulator | Host and single player. Evaluates pair values and advances held assists over settled positions and life states after same-tick damage and deaths; records completions into `TickEvents::assist_completions`, which the tick's player-event pass applies before its condition snapshot (`scripting.md` §12) |

Scripting bridges run later, outside the core simulation seam. Emitter, light and fog-volume bridges walk their configuration components. The emitter bridge writes particles into the presentation pool (§8); particle simulation updates that pool without spawning or rewriting registry entities.

The host camera follows the player pawn after movement and AI resolve. When no player pawn exists (no `PlayerMovement` entity), a fly-camera moves directly from input.

### Per-Entity Transform Interpolation

The renderer interpolates each entity's visual transform between the previous- and current-tick positions for sub-tick smoothness. The render-stage accessor `interpolated_transform(id, alpha) -> Transform` takes the frame alpha (0..1, from `frame_timing`'s `current_alpha`) and returns a blended transform: position and scale component-lerped, rotation shortest-path slerped. The stage-0 snapshot (previous = current) ensures entities spawned on the current tick render without popping. The mesh render collector (`mesh_render.rs`) is the first consumer; the accessor is general for future per-entity visual passes.

Decided, not yet built (`plans/ready/E17--mover-relative-rider-presentation`): the accessor returns the one presented pose every reader draws from. It gains a render-only per-entity correction, applied after the blend, that connected clients use to smooth mover corrections. Simulation reads of `Transform` never see it. A reader that takes the simulation pose for a drawing decision, such as a visibility cull, also covers the presented pose.

### Events

Movement, AI, weapon, and death events are collected across all catch-up ticks in stage buckets and drained after the tick loop completes. Movement, AI and weapon events travel as **emissions**: the event address paired with its emitter — an entity plus its origin at the tick, or an impact's contact set — and retained presentation provenance. Weapon shots carry their originating action and effective sound keys; enemy events carry their behavior graph and attack or entered activity. An entered activity with no `onEnter` still emits, with no address. Emissions are stamped where the event happens, so an emitter despawned before the drain still has a position. The drain fires each built-in and authored alias with the same emitter and plays descriptor sounds (`audio.md` §4, `scripting.md` §12). Death events use the sequence-aware drain path. Reactions observe the fully-settled post-tick world state.

## 6. Subsystem Interactions

### Ownership

Game logic owns entities exclusively. No other subsystem creates, modifies, or destroys entities directly. Server-authoritative replication preserves this: game logic applies server snapshots; netcode produces typed snapshots and never mutates the registry directly.

| Subsystem | Interaction with entities |
|-----------|--------------------------|
| **Game logic / bridges** | Own, create, update, destroy via the registry |
| **Renderer** | Borrows transform and visual-component data read-only for drawing |
| **Audio** | No direct entity access. The app drain turns emissions into anchored sound requests and answers audio's per-frame position queries from render-interpolated transforms, read-only; audio sees only opaque entity keys (`audio.md` §1). |
| **Input** | No direct entity interaction; input state flows through game logic |

### Cell Linkage

Runtime cells are visibility IDs, not entity ownership. `LevelWorld::locate_cell` maps a point to a cell for camera visibility, render-side entity/particle culling, and diagnostics. The entity registry stores no cell index and runs no per-entity cell update; a subsystem that caches entity cells owns its table and re-locates on every move (the AI tick scheduler's, §7c Tick tiers). BSP is compile-only scaffolding and is not part of the entity runtime model.

## 7. Collision

### World Collision

Entities collide against static world geometry. At level load, PRL static geometry is built into a `parry3d` trimesh held by `CollisionWorld`. Queries use `parry3d::query::*` free functions against this collider — no `QueryPipeline`. The one exception is the skin-distance capsule sweep movement and movers use: it runs through a small engine query dispatcher that keeps parry's BVH traversal for choosing candidate triangles but answers each capsule–triangle pair itself, by conservative advancement from the cast's start on exact closest points. A hit lands where the capsule first reaches the skin band and is dropped unless the rest of the motion would carry the capsule more than 0.5 mm into the band. Contract: a cast that starts outside the band, or at most 0.5 mm inside it, never ends more than 0.5 mm inside it. A tick-level contract sits beside it: a body whose own movement starts a tick clear of static geometry never ends that tick overlapping a surface by more than 0.5 mm. The cast contract bounds depth into the band per cast; the tick contract bounds surface overlap per tick (`movement.md` §1). Pairs the dispatcher can't answer exactly — not capsule–triangle, a degenerate triangle, or a capsule core piercing the triangle — use parry's cast. parry's own leaf cast is unreliable at the band boundary — tilted normals that bleed speed on flat floors, missed in-band starts that walk a capsule into a wall it rests against (dimforge/parry#452). Known limitation: a slide across a coplanar triangle seam that starts deeper than 0.5 mm inside the band hits the neighbour triangle's shared edge at a slightly tilted normal (about 4° from 1 mm deep); internal-edge handling is the follow-up fix. Static and mover casts treat `max_toi` as inclusive; parry's trimesh traversal drops a hit exactly at the limit. Combined static-plus-mover queries skip a mover before its narrow phase when its mesh-centred bounding sphere, built at load, cannot reach the query's swept sphere. The test carries rounding slack and passes non-finite input through, so the cull never changes a result. Static collision is built before any level-install mutation, so a mesh parry rejects fails the load and leaves the empty, already-unloaded world untouched. That route is defensive: parry 0.31 rejects a trimesh only for empty indices, which `CollisionWorld::from_level` pre-filters, and PRL decode validates the rest. Likewise a mover whose collision mesh parry rejects loads with no collider and a `[Loader]` warning, but kinematic-geometry decode already rejects empty mover geometry. Runtime cells and portals do not answer collision contacts.

**Skeletal hit zones.** The standalone entity-raycast facility resolves the nearest targetable entity for any ray. Targetable entities are Health-bearing damage targets with an authored AABB or zone-bearing skinned model, plus Mesh-only zone-bearing presentation targets used by connected clients for local hit detection. Mesh-only targets carry no `Health`, so they cannot take damage. Broad phase is the authored AABB for Health-only AABB targets and a derived model bound for zone-bearing ones. Narrow phase is the AABB slab test or, per tagged joint, a `parry3d` ray-vs-capsule test. Model→world uses full entity transform composition: scale, rotation, and translation plus mesh origin offset. Stateless meshes use authored rest pose for rendering, attachments, hit zones, and pose probes. Explicit animation components retain state-driven sampling. Gameplay capsules and probes intentionally omit presentation-only pose modifiers. A Health-bearing model with no usable zones falls back to its authored AABB; a Mesh-only target without usable zones is not targetable. The struck zone tag rides on `WeaponImpact.zone`.

**Radial entity overlap.** A one-to-many spatial query, sibling to nearest-entity raycast: given a world center and radius it returns every live damageable entity whose broad-phase volume intersects the sphere, each with its nearest point and distance. Caller-agnostic — no weapon, projectile, or splash knowledge. It reuses the raycast broad phase and shared liveness gate. Optional world occlusion, static geometry plus movers at the caller's poses, drops wall-hidden targets; a caller-supplied predicate handles exclusions. This is the first non-ray query-family member; future melee sweeps and area damage-over-time can reuse its candidate boundary.

### Entity-Entity Collision

Entity-entity collision uses simple bounding volumes: axis-aligned bounding box (AABB) or bounding sphere. Overlap tests are direct geometric checks, not spatial partitioning.

| Volume type | Use case |
|-------------|----------|
| AABB | Entities with box-like extents (player, enemies, doors) |
| Sphere | Entities where orientation doesn't affect collision (projectiles, pickups) |

Entity descriptors select the volume shape and fixed dimensions. Touchable items carry their descriptor-seeded sphere radius in `Touchable`; player-item overlap tests that sphere against the player capsule.

### Collision Timing

World collision resolves inline during each entity's movement — the entity slides along or stops at world geometry within its update step. Trigger-volume overlap runs after player movement, and touchable-item sphere/capsule overlap runs immediately after that trigger stage and before AI: only player pawns and stationary world items participate, so this narrower placement observes every relevant movement without delaying the touch to the next tick. Other entity-entity overlap tests run as a separate pass after all relevant entity updates complete. This prevents update-order-dependent collision results: every participating entity moves first, then overlaps are detected and resolved.

### Environment Volumes

Maps place static regional gravity, push and fluid volumes (`build_pipeline.md` §Custom FGD, id 52). They are non-solid: no collision, cell, portal, lightmap, SDF or navmesh role. `postretro-collision` answers every query over them: pure geometry over level data, no movement or entities. Each authored brush is a convex leaf — a plane set with bounds and a contents mask naming the fields its volume sets. Query indexes are built at level install, not baked, after static collision and before the level content digest publishes or the first tick runs. Installing another level replaces them whole; unload clears them. Queries take a contents mask and never see a volume whose contents miss it. Acceleration-only point queries may use bounded specialized indexes; candidate narrowing must preserve exact containment and independent field winners. Fluid and mixed queries retain the complete geometry index.

**One overlap rule per field.** A field's value comes from the winning volume among those that set it and are in reach; with none, the level default applies (level gravity, zero push, dry). The winner is the highest priority, then the smallest summed brush volume — so a pool inside a room wins without priorities — compared at 8 significant bits so near-equal sizes usually tie, then the earliest map entity. Fields resolve independently: a pool with no gravity inside a low-gravity room takes the pool's fluid and the room's gravity.

- **Gravity and push** reach is the body's position. Push yields two outputs: the winner's nominal push, and the felt push, nominal times the winner's force (default 1). Force never ranks a winner, so a force-0 push still carves its region.
- **Fluid** reach is the capsule's vertical segment, feet to head. A fluid volume is in reach only when it covers a positive length of the segment, so feet resting on the surface stay dry. Immersion is the segment's coverage by the union of every in-reach volume carrying the winner's fluid, so a pool split into several entities of one fluid reads whole, a different fluid never adds, and leaving through any face, bottom included, drops it.
- A non-finite probe resolves the defaults, dry. Resolution is deterministic and allocation-free; its result never depends on tree shape or visit order.

**Who resolves what.** Each body resolves at its own tick-start position, every tick.

| Body | Resolves |
|---|---|
| Player pawn | The full environment, felt push (`movement.md` §4, §6) |
| AI agent | Gravity only, clamped to its downward part. Agent collide-and-slide adds gravity every tick, grounded included, so upward gravity would lift it off the navmesh; in an upward-gravity volume it behaves as in zero gravity. Agents ignore push, never swim, and walk fluid floors |
| Projectile | Nothing; projectiles apply no gravity |
| Particle | Gravity and the nominal push at its post-step position, once per rendered frame; never fluid (§8). A force-0 river still carries foam |
| Fluid surface face | The nominal push 2 mm inside the face, at install and on every fluid-table or tuning refresh, for its drift (`rendering_pipeline.md` §7.3a) |

**Teleporter regions.** A `trigger_teleport` is a regional volume like those above — convex leaves, one entity's brushes read as their union (`build_pipeline.md` id 55), indexed at install — but not static. Each installs one entity carrying the `Teleporter` component (map-order index, source entity, armed state, `arrival_sound`, `on_teleport`), placed and tagged from its id-29 map-entity companion so scripts can find it. Armed state starts from `enabled_on_spawn`; scripts arm and disarm it on the host, applied at the start of the next movement tick (`scripting.md` §12), and it replicates (`networking.md` §Current contract). Mode picks the arrival: classic lands the body point on its `target` `teleport_destination` facing that destination's yaw; seamless carries the body's offset from a source-side `landmark` destination onto the target, turned by the yaw difference. Destinations are compiler-only and leave no runtime entity. Only player pawns resolve teleporters; agents, projectiles and particles never teleport. A pawn tests its body point, where gravity and push resolve, against armed regions it is not latched in, after its movement step, not at tick start. Among several, the smallest summed brush volume wins, overlapping brushes counted twice; there is no priority and no size quantization, so map order breaks only an exact tie of the computed sums, and near-identical regions rank by float rounding. The teleport ends the pawn's movement tick at the arrival pose. Relocation, arrival state and latches: `movement.md` §6 (Teleport).

**Hitscan splash facts.** A hitscan pellet reports each fluid-surface crossing strictly before its blocking hit as a fact: point, outward normal of the crossed face, fluid. A ray starting on a face never splashes there, a face shared by two brushes of one volume is no crossing, and two adjacent fluid entities give two. The fact is presentation: never replicated or hashed. Nothing consumes it yet.

## 7b. Player Movement Component

The dominant engine entity today is the player pawn. It carries a `PlayerMovement` component alongside its `Transform`. The component holds the capsule geometry, per-axis physics parameters (ground, air, fall), and mutable tick state (velocity, grounded flag, air-jumps remaining, active movement-state variant, air-dashes remaining, dash cooldown timer).

Movement is engine-internal. No script surface writes `PlayerMovement` — `getMapEntities` exposes map-placed kinds only; the movement system owns it exclusively. Scripts read one readonly projection per player: `player.swimming` from this component's movement state, and `player.immersion` from the separate `Immersion` component (`scripting.md` §5). Immersion is its own component because `PlayerMovement` is cloned into reconcile replay and merged from the wire; host movement writes it after each authoritative tick, and no state intent, replay or wire merge reads it. The camera follows the pawn's position each tick (eye-height offset above capsule center); yaw and pitch remain mouse-driven.

Movement design intent — the custom-kinematic foundation, the declarative author surface, the state-machine seam, and the FPS-flexibility band — lives in `movement.md`. This section covers only the component's place in the entity model.

**The body hangs from the live capsule's sole.** A pawn's transform is its capsule centre and its mesh is authored feet-at-origin, so the mesh origin offset drops the model by `halfHeight + radius` of the *live* capsule, not the standing one. Crouch, slide and a low life-state posture shrink the capsule with the feet planted, lowering the centre; an offset held at the standing size sinks the body into the floor and drops its cull point (the model origin) into the cell beneath, so the pawn vanishes. The fixed tick reseats every movement pawn's offset from its capsule right after Movement, before projectiles and weapons read hit zones, and the presentation pose pass reseats it again ahead of the foot probes (on a connected client that pass runs per frame and covers its predicted pawn). Draw, cull, hit zones and foot probes all read that one offset. A connected client's remote avatars carry no movement component, so they hang from the replicated live half-height presented with their pose and the descriptor radius. Between two samples the half-height blends with the transform, since a resize moves the centre linearly with it; stepping it would sink a crouching body through the blend. The host seat seats its delayed client-pawn bodies the same way and restores the live offset with the live pose (`networking.md` §Host-seat presentation).

**Lower-body facing and locomotion states.** A player's third-person body splits at the waist: the upper body faces aim, and the lower body faces travel, folded so it never points behind aim. Travel more than 105° from aim is a backpedal — the legs face against travel, toward aim, and backward states play. Travel within 75° of aim is forward. The band between holds the previous classification, so strafing while the aim sweeps does not flip the legs 180°; a pure strafe keeps whichever way the body was already moving, with about a 90° twist, since strafe clips and blend spaces are deferred. Stopping holds the classification too: a stopped body faces aim regardless, and a delayed presentation still drawing the last of the motion keeps its fold. The upper-body twist therefore stays within 105°. The engine selects player locomotion states by name, and only when the descriptor declares `walk_forward` or `walk`: the descriptor's `defaultState` when still; `walk_forward` (or `walk`) and `walk_backward` at walking speed; `run_forward` (or `run`) and `run_backward` when speed is nearer run pace. The run tier engages above the midpoint of `ground.speed.walk` and `ground.speed.run` plus 15% of their gap, and releases below the midpoint minus 15%; the active state is the memory. The midpoint, not walk speed, is the switch because walking while turning carries ground speed past the walk cap. A backward state that is undeclared, or whose clip did not resolve, plays its own tier's forward state — the visible signal that a backward clip is still owed. There is no cross-tier fallback, except that a run forward state whose clip did not resolve leaves the walk tier covering every speed; `run_backward` needs a run forward state beside it. Each state rate-scales against its own `travelSpeed`. The movement state, not speed, picks the crouch tier, since a crouch-walk and a slow stand-walk travel alike: `Crouching` plays `crouch_idle` when still and `crouch_forward` or `crouch_backward` when moving, never a run state, rate-scaled with `ground.speed.crouch` as the fallback reference; `Sliding` holds `crouch_idle` at rate 1 throughout. A missing or unresolved `crouch_backward` plays `crouch_forward`, and `crouch_idle` falls back to `defaultState`. The tier exists only beside a usable `crouch_forward`; without one, crouching and sliding select as standing does. Crouch states commit direction as walk and run states do; `crouch_idle` commits none. The jump sequence overrides every tier while it runs, and only in `Normal` or `Crouch` movement — swim, vault, dash and slide keep their own selection. A takeoff with the jump spent and vertical velocity above zero plays `jump_up` until the apex or the clip's end, then `jump_loop`; a fall without a jump keeps the ground stride until the pawn has been airborne 0.15 s (9 `air_ticks` at 60 Hz), so step-downs and ground-stick gaps never show a fall pose. An air jump after takeoff keeps `jump_loop`, and a launch without a jump (knockback, a push) falls into `jump_loop` after the delay. A takeoff needs a fresh airborne stretch: past the delay a spent jump still rising — an air dash or vault handing back mid-rise, a teleport arrival into the air, which spends the jump — falls rather than replaying `jump_up`; only a jump out of the water takes off however long the swimmer was off the ground. Airborne overrides posture, but a crouched landing returns to the crouch tier. A standing landing at or below `ground.speed.walk` plays `jump_down` until its clip ends, the pawn speeds past walk, or it jumps again; a faster landing goes straight to the stride. Jump states play at rate 1 and commit no direction. Without a usable `jump_loop` the sequence is absent; a missing `jump_up` takes off into `jump_loop`, and a missing `jump_down` lands straight into locomotion. A one-shot ends against its model clip's length, timed on the animation clock from when the selecting peer saw its motion begin; a clip whose length is unknown counts as played through. The classification and the jump phase are per-peer presentation memory on the mesh animation and never replicate (`networking.md` §Host-side remote-pawn presentation). Each peer's state selector is their only writer; where a peer selects no state for a pawn — a connected client's own pawn — the pose pass keeps the classification instead.

A player pawn is present only when the first resolving spawn names a movement descriptor. That spawn is the first `player_spawn` without `coop_only 1` whose `entity_class` is registered, else the first registered co-op-only one. Selection stops there: a class without movement spawns as a plain entity, and no later spawn is tried. When no pawn exists, the engine falls back to a fly-camera so maps are navigable without a player descriptor. A map with no `player_spawn` warns at compile and at load (a frontend backdrop logs it at info), and the compiler warns on Quake's player-start classnames, which nothing reads (`crates/level-compiler/src/parse/player_starts.rs`).

**Player spawn points.** A `player_spawn` is a place, never a pawn by itself. Single player and a co-op host materialize exactly one pawn at install, at the first spawn in map order without `coop_only 1` whose `entity_class` resolves (co-op-only spawns are a warned fallback); the host assigns each joiner the lowest free spawn in map order whose `entity_class` resolves, through the seat table (`networking.md` §Slot lifecycle). Selection lives in `crates/sim/src/scripting/builtins/player_spawn.rs`; the origin shift, which every descriptor spawn applies, is `spawn_origin_shift` in `data_archetype.rs`. A spawn's canonical origin is the **feet**: the `.map` front end moves `player_spawn` 24 units down to the bottom of its FGD box (Quake's player hull, `size(-16 -16 -24, 16 16 32)`), and spawn raises a movement pawn's transform by `halfHeight + radius` to the capsule centre, as AI placements already rise from feet. Nothing snaps or depenetrates a pawn at spawn, so a box sunk into the floor starts embedded. A `.prl` baked before this convention must be rebaked: an un-rebaked spawn keeps its authored origin, 24 units above the feet, so after the runtime rise the pawn starts 24 units above its floor and drops.

**Checkpoint spawn sets.** A `player_spawn` may carry a `checkpoint` key. Spawns sharing a name form that checkpoint's set, and the ordinary rules above choose within it. Once a `checkpoint(name)` step fires, or Continue arrives at one, arrival, respawn and late joiners use its set until the next level start; placements made against the previous set reset. A level start skips keyed spawns; when every spawn is keyed, it uses them all and warns. A checkpoint naming no spawn falls back to the level-start set and warns (`scripting.md` §5). A level seam's name is also a set name (§7e): a crossing, and Continue from one, select that set, and with none keyed fall back without the warning.

## 7c. NPC Brain Component

NPC behavior is an **authored hierarchical statechart**, not an engine-closed state enum. An NPC is any brain-bearing entity that is not a player pawn (`scripting.md` §12), ally or foe; every rule here applies to it. A graph declares named activities and ordered guarded transitions. Activities may be leaves or compose nested graph layers and stateless selector layers. A leaf selects motion, an optional action, and its animation. Transition guards are IR expressions (`scripting.md` §11) over a brain-local binding scope; the engine binds them when the graph is installed and evaluates them on every decide tick (Tick tiers, below).

**Ownership split.** The author owns which activities and layers exist, what each one does, the ordered guards between them, and — through an optional per-graph candidacy predicate — which of the candidates the engine offers are worth engaging. The engine owns everything else: which entities are offered as candidates at all, ranking and retention among the eligible ones, tick tiers and decide pacing, awareness meters, target-switch hysteresis, combat-slot resolution, steering, facing, damage application through the chokepoint, and the aggro gate. Motion and action verbs are closed vocabularies — an activity selects an engine behavior, it does not describe one.

The line between the two halves of targeting is **perceivable vs. worth engaging**. The floor decides what an enemy could possibly perceive — a question with one right answer, so it is correctness. Whether a perceivable pawn is worth attacking is taste: a blind grunt, a psychic boss, and an enemy that ignores the wounded are all valid designs. Candidacy can only narrow the offer set, never widen it.

**Smarter and dumber enemies author alike.** Intelligence comes from guards and options on one vocabulary, never a separate mechanism.

**One brain authoring surface.** `components.behavior` is the sole enemy-brain authoring surface. The descriptor materializes one retained graph component.

Invariants the evaluator upholds:

- **Guards evaluate on every decide tick.** Decide ticks are staggered 15 Hz pools, every 2 s for a dormant NPC (Tick tiers, below). No activity, animation, or cooldown latches an authored row to an activity or stance off. An authored commitment window is a guard over time in activity, never an engine mechanism. Rows to attacks, and the activities lowering generates from stances and attacks, carry engine gates (Stances and attacks, below).
- **Transitions evaluate outer-to-inner.** At each level, wildcard (`"*"`) rows precede the active activity's rows, each in declaration order; the first true row wins. A winning edge enters its target and descends through initial activities immediately. Newly entered activities do not evaluate transitions until the next decide tick.
- **Guards are read-only.** Per-entity state fields are written by impact policies and spawn seeding; guards only read them. That is how a hit-driven reaction and an authored wildcard transition compose without either knowing about the other.
- **Candidacy is per-graph eligibility; disengagement is per-activity policy.** The candidacy predicate is read-only and evaluated at most once per offered candidate, in ranking order: the scan stops at the first eligible hostile, then checks recent attackers for retaliation (an NPC without a target scans past it, up to its awareness meters' bound of 8). It never runs against the target already retained — dropping a retained target is what guards are for. It answers eligibility only, never rank: it produces a boolean, and ranking stays the engine's.
- **Peers are candidates; the engine may rank retaliation over distance.** The offered set includes brain-bearing enemies, not only player pawns, so an enemy can perceive a peer that damaged it. Ranking stays the engine's — candidacy is still boolean and narrowing — but the engine adds a **retaliation** term: a candidate whose recent accumulated damage exceeds an authored per-pair or per-archetype **tolerance** is preferred over the nearest hostile, tuned by authored scalars, never an authored ranking expression. The engine admits such an over-tolerance attacker to candidacy even when sentiment leaves the pair non-hostile — its own widening, not authored candidacy's. A retaliation-acquired target is engine-held against distance hysteresis until it is lost or a stronger over-tolerance provoker unseats it; standing down otherwise stays an authored guard.
- **Hostility is mutable per-entity state, not a fixed enemy/friend archetype.** The engine floor narrows fresh acquisition by it — a candidate is offered only when the evaluating enemy is hostile toward it — while dropping a target that turns friendly stays authored, per the split above. Hostility resolves from authored content: factions are named manifest data, and a directional per-pair **sentiment** scalar decides it — negative hostile, zero neutral, positive allied — seeded so unauthored content reproduces the prior faction-inequality rule (different faction hostile, same faction neutral) with zero authoring. The durable authored contract is the target-hostility fact a guard reads, not the numeric faction leaf beneath it: that leaf is an index into the sentiment table. The authored scalar is immutable baseline content. The AI reads a live sparse value over that baseline; authored reactions and impact effects move it, and author-tunable decay eases it back. The live value is host-authoritative, persisted, and replicated as state rather than content (`networking.md`).
- **Target selection holds no aliveness policy.** Aliveness gates the attack, not the choice of whom to attack. An enemy may select a corpse and be unable to hit it; disengaging from a downed target is an authored wildcard transition over target-side facts, not an engine rule. The authored death signal is the death sweep's latch rather than a health comparison — a health comparison cannot distinguish a corpse from no target at all, since target-side facts read zero untargeted.
- **Acquisition and stand-down are graph policy.** The engine holds no acquisition leash. A candidacy predicate, including a distance predicate, bounds fresh acquisition only; an ordered transition stands down a retained target. A graph without either policy pursues without limit by design.
- **Motion includes position goals, not only pursuit.** A motion verb may steer toward a fixed point — the enemy's home anchor, or the next point on an authored route — as much as toward the target. The home anchor is the enemy's spawn position, fixed for the brain's life and host-only; placing the entity authors its home, and runtime re-homing is a separate additive path. An activity that can select a position goal cannot declare an action or contain an action-producing layer. A resolved position goal is non-engaged: it holds no target and takes no combat slot, so movement leash and retreat compose as ordinary authored guards over the home-distance fact, not as engine policy.
- **Damage recency does not imply a spatial source.** Every landed hit resets recency, including contextless script damage. A separate latest-hit provenance fact says whether that hit supplied an attacker world position. Authored behavior must conjoin both before using damage recency to interpret shared last-known-position memory or directional bearing. The player's damage bearing takes the same shape — a bearing paired with a source-known flag (decided, not yet built; `networking.md` §Presentation events vs. replicated state).
- **Tiers are cost machinery and share no data path with authored relevance rules.** A tier reads target presence, the engine's per-player id-51 step, hits and the aggro gate; authored candidacy and guards never feed it. `@brain.acquisitionDue` reads true on decide ticks.
- **Bound guard programs are derived data.** They live in the evaluator, never on the component, so they are never serialized and never affect component equality. They rebuild from the retained graph whenever the entity is seen.
- **Animation is subordinate to graph state.** An unknown animation name warns once at spawn and keeps the prior animation at tick time; it never aborts the tick. A state that pursues without acting is a locomotion state: its animation is a travel cycle, so it yields to the graph's initial-state animation at a standstill. So does a nested leaf with no motion, action, layer, pose or attack mark of its own that plays its pursuing or travelling ancestor's clip: that clip is the ancestor's travel cycle. A nested leaf with its own clip (a windup, a recover) is a phase and plays it while still. That makes the initial state's animation the graph's rest pose, and authors should pick it accordingly.
- **A standoff bounds where a chaser rests.** Combat slots sit on rings at 0.75×, 1× and 1.25× the action's standoff. A chaser bound for its slot arrives only within the larger of the standoff and its slot's distance from the target, so it rests at most 1.25× the standoff out, never an arrival band beyond. Inside the slot's arrival band it presses on rather than stopping. A melee standoff at or under 0.8× the strike's reach therefore rests every chaser within reach. Nothing pulls a chaser inside its ring: slot scoring and crowding still spread a group, and a ranged chaser rests on its ring. Three cases bend the bound:
  - A route planned for where a moving slot stood, or one the planner snapped outside the bound, falls back to the band alone until the next replan (about half a second).
  - Once arrived, a chaser stays arrived until it drifts an arrival band past the bound, so crowding never flips it between moving and resting.
  - A chaser that cannot get closer (the navmesh and the collision world disagree there) arrives by the band once stuck recovery fires, until its slot moves.
- **Reachability is current, not static.** `targetReachable` is the verdict of the gated, ground-aware route query chase uses (`build_pipeline.md` §Navigation bake): false while a docked door cuts the only route, true once it leaves. A target reachable only across a lift reads true only while the lift is docked at the enemy's landing. A rider holds its boarding value until it steps off. AI, combat-slot scoring and steering read one gate generation per tick, and scoring rejects a slot whose capsule overlaps a docked mover. Known limit: a target standing on a mover resolves to the floor region under it.
- **Sight sees movers.** Every NPC line-of-sight test (perception, the fire gate, awareness meters, combat-slot scoring) sees movers at the host tick's pose. A closed door hides a target and stops the NPC's shots; an open gap does not. Slot placement stays static.
- **Selection and slot cost track what they inspect.** Each AI pass reads every pawn once, bucketed by faction, after the previous pass's apply; nothing carries to the next pass. An enemy inspects only buckets it is hostile to, plus its recent attackers, so registry size and allied crowds cost it nothing. A combat-slot batch grounds each slot, tests it against docked movers and routes it to its target once, shared by every enemy on that target. Sight from the slot and the enemy's own route stay per enemy: sight casts from that enemy's eye. Both are cost machinery: every enemy selects the same target and claims the same slot a per-enemy scan would.
- **Death is not a graph transition.** AI and steering exclude a quiescent enemy — zero HP, or a despawn already queued — as soon as damage settles; it moves on as a corpse that rides movers and never blocks them (`movement.md` §6). The later death sweep owns the death latch and frozen credit; an authored impact policy owns the death animation and despawn delay.

**Tick tiers.** The host picks each NPC's tier every tick, after projectile impacts settle and before AI (`crates/sim/src/npc_tiers.rs`). Rates are engine constants, never authored.

| Tier | Who | Decides | Acts |
|------|-----|---------|------|
| Engaged | Has a target, perceived or not | Staggered 15 Hz pool | Every tick |
| Idle | No target; perceived, `alwaysActive`, hit, aggro gate newly opened, or within 2 s of any of those | Staggered 15 Hz pool | Every tick |
| Dormant | None of those | Every fourth run (2 s) | Whole AI and steering tick at 2 Hz, each run stepping the ticks since its last; mover carry and pushes every tick (`movement.md` §6) |

- **Perceived** means inside some player's id-51 set within the AI lead (`build_pipeline.md` §Id-51 consumers): default 16 m, worldspawn `ai_wake_lead`, capped at `max_lead`. Every player pawn in play or down is a perceiver, the host's and clients' alike. Armed ghost links couple cells (`networking.md` "Ghosts constrain future relevance"). With no id 51, no perceiver, or every perceiver outside camera cells, every NPC is perceived. A visible gap is a residency miss: refine id 51, never add a PVS bake.
- **Moving up** happens on the tick the NPC becomes perceivable, gains a target, is hit or has its aggro gate opened. Its step is one tick: no catch-up movement, and facing turns one tick's worth. The AI credits the skipped span once. **Moving down** waits a 2 s hold.
- **Decide ticks** evaluate transition rows, selectors, combat-slot choice and engine-gated rows (a hold's release, a release's exit, `animationDone`). A row lands up to one interval (about 67 ms) after its guard becomes true. Acting between decides follows the last decide.
- **Elapsed time.** Timers, meters and clip time advance by elapsed time, never tick counts, so a skipped span counts once at any tier. A dormant run resolves each clip moment inside its step once; a repeating release's later passes in that step whiff.
- **Noticing.** An NPC without a target acquires a candidate only once that candidate's awareness meter fills (`awareness.fillMs`, default 1 s; `drainMs`, default 2 s; at most 8 meters per NPC). Two sightings in a row fill by the time between them; a first sighting fills nothing. A hit fills its attacker's meter at once. Closing the aggro gate empties every meter. A respawned pawn's previous life leaves no meter, attacker record or bearing. An NPC with a target ranks and switches by engine ranking, its meters frozen; a switch is a new acquisition.
- **Tactical range.** Past its tactical line (horizontal distance), an engaged NPC routes toward its target under `chaseTarget`, `strafe` and `reposition` instead of claiming a combat slot. It claims slots again 10 m inside the line. The line is `tacticalRange` (default 100 m), raised to the largest attack standoff plus 10 m with a warning at load and on each committed reload.
- **`alwaysActive`** keeps an NPC idle or engaged. A placed `always_active` key overrides the archetype.
- **Replan budget.** Steering's per-tick route-replan budget scales with the number of agents owed one, never below 4. Within each replan tier, paced agents go first, then higher NPC tiers.
- **Host-only.** Tiers, meters and decide ticks never replicate; clients draw NPCs from replicated state.

**Engaged motion and facing.** Two engaged verbs join the closed set. `strafe` orbits the target continuously: every tick it aims one 45° step ahead on a ring rotated to its current bearing, and reverses when that slot is unreachable, occupied or blind. `reposition` claims the best combat slot at least one spacing from its entry slot, within an `arc` measured from the target-to-enemy bearing at entry and a `minTravel` from its entry position, both fixed at entry; it re-scores around a moving target and never backs off. Flanking is a lateral arc: it reads the enemy's own approach, never the target's facing, which changes too often and lags for remote players. Each activity may choose `facing: "target" | "travel"`. Knockback never steers facing or picks a stride: a launched enemy holds its impact yaw unless its activity faces the target, and plays `jump_loop` after the player's fall delay. Under target facing an animation `X` resolves to `X_left`, `X_right` or `X_backward` by travel direction, else `X`; the host resolves the name, which replicates as ordinary animation state.

**Leap.** A third engaged verb, `leap`, travels to a landing spot and arrives on a clip moment. Only a leaf whose own attack fires `at` an event, once, may use it; never a selector.

- **Spot.** Fixed on entry, or on the first tick with a target: the attack's standoff short of the target on the line to the enemy, or the enemy's own position if already that close. Never re-aimed, so a target that leaves it is a whiff. It serializes with the clip clock. A spot off the navmesh moves along its line to the nearest walkable ground, target side first; with none, the leap warns once per entity class and stands.
- **Pace.** Until the moment, steering paces the agent to cover the route left in the whole ticks left, recomputed each tick and capped by the activity's `speed`. No arrival easing or arrival band: the last step lands on the spot. From the moment's tick, or any tick the latch closes (a launch) or the clock holds for a redraw, the leap stands, so one that falls short never lurches on.
- **Pushes.** Crowding and stuck recovery push a leaping agent at its base speed, so a top-speed leap never slides around a wall. Its route replans go ahead of other agents'.
- **Untimed moment.** A defaulted `hit` its clip lacks leaves no deadline: the leap flies at its cap and warns once per entity class and state. A named `at` its clip lacks resolves on the first tick, so the leap stands.
- **Faces** as a chase does. Agents move by a swept capsule, so even a top-speed leap stops at thin walls. Host-only: clients see the replicated position.

**Activity speed and stride rate.** An activity's optional `speed` multiplies the archetype's `moveSpeed` while it is the innermost active activity that sets one. The AI pass writes it onto the agent from its post-transition path, so it governs steering from the tick the activity is entered through the tick before it is left. It scales path steering (top speed, acceleration, arrival easing, separation and stuck recovery; a leap pushes at its base speed) but never knockback, a pin escape or a ride's walk. `moveSpeed` itself stays the base value. An enemy's playback rate scales on its graph's rate-scaled states: the locomotion state, and every state an activity plays under its own `chaseTarget`, `strafe`, `reposition` or `leap`, action or not, so a moving attack strides at its speed. Each scales against its own `travelSpeed`, else its clip's stride, else the base `moveSpeed`, clamped to 0.5–1.5x. Three per-state fields adjust this: `maxPlaybackRate` (≥ 1.5) raises that state's ceiling; `scaleWithSpeed: false` removes it from scaling; `playbackRate` (> 0, default 1, unclamped) is the fixed rate of any state the rule does not scale and is ignored on one it does. A travel variant (`<state>_left`, `_right`, `_backward`) inherits each of the three it leaves unset from its base state, resolved when the mesh descriptor is built. Production content keeps the 1.5x ceiling: legs flail past it. Clip time advances at the drawn rate, so clip moments land at clip time over the rate. Host and client derive the set, the base and the per-state fields from the descriptor, so nothing crosses the wire.

**Attack budget.** An attack starts only while its enemy holds a turn for it, so a group takes turns instead of piling on. The engine owns the mechanism; mods author the values (`scripting.md` §1).

- **Tokens.** A mod declares tokens, each with a default budget: how many may be drawn on one target at once, and how long a spent draw stays counted after its turn ends (`refreshMs`). Each attack draws tokens at a cost; an attack naming none draws the SDK's `defaultToken`, and an explicit empty list opts out. A grant needs room in every token drawn, for that pool and target; there is no partial grant. A profile overrides budgets per token.
- **Every target has its own allowance:** each player, NPC ally and infighting monster.
- **Refresh counts like a held turn** and starts however a turn ends, so interrupting an attack spends its refresh too.
- **Turns.** A turn is for one attack. An enemy never holds two turns that draw the same token, so its melee and ranged attacks overlap while two melee attacks take turns. An activity marked for an attack holds one turn across a windup–commit–recover chain; load rejects marks that disagree. An unmarked attack holds its turn through its execution and cooldown.
- **Arbitration** is host-only and deterministic, and sees every request and release of the tick before any attack fires. The longest wait wins and brain slot index breaks ties. The longest waiter on each token reserves its cost there (the whole token when its cost exceeds the limit), so a waiter drawing several tokens never starves while lighter attacks use the room it does not need.
- **Attack pools.** A map's `ai_attack_pool` names the profile its members use; enemies in no running pool use the default pool under the `default` profile. Pools run side by side. Membership is assigned by events: a start assigns the pool's tag holders, a start on a running pool re-assigns them, and a tagged spawn joins while the pool runs. Each enemy is in one pool, the latest assignment winning; a spawn matching two running pools joins the one started latest. A stop returns its members to the default pool and drops its refreshing counts. Running pools, their start order and each enemy's assignment survive serialization; turns, waits, reservations and refreshing counts are transient. Start and stop requests wait on the registry for the next pre-AI drain and are not serialized: a save system must drain them first or carry them.
- **Held enemies.** A held enemy leaves the AI set and its turns end. Held ownership keeps its weapon execution, but arbitration cancels any execution of a drawn attack whose holder holds no turn for it, so a dropped enemy never resumes a drawn burst. An undrawn burst may resume.
- **Reload.** A reload that drops a token an attack draws warns on that reload and ignores the draw. A load or reload that drops a profile a placed pool names warns, and the pool uses `default`.
- **Host-only, outside the co-op compatibility digest.** Clients never read the budget, and turns never replicate.

**Stances and attacks.** Stances and attacks are authoring vocabulary. Load-time lowering turns them into activities and sets their lowering-only fields itself (`pose`, `queue`, the hold's `releaseAfter`, the release's moment gate `afterMoment`, default-`at` marker `atDefault` and pass count `passes`, and the flinch route `staggerTo`); authors never write them (`scripting.md` §2). The runtime gains:

- **Pose.** Activities sharing a `pose` act as one: moving between them restarts no clip, plays no second sound, and keeps time in activity, `activityRoll` and `damageInActivity`. Entering from outside starts them fresh. A `"*"` or ancestor row into the current pose is skipped. A pose retains its target like an engaging activity. So does any activity marked for an attack.
- **Queued rows.** A row carrying `queue` requests its attack's turn from an unmarked activity while its guard passes, the target is within the attack's queue distance (`queueRange`, else `maxRange`), and the attack is off cooldown. The hit still needs `maxRange` at its moment; `engagementRadius` and `standoffDistance` keep defaulting from `maxRange`. A grant survives into the next evaluation, as a mark's does, and the row passes once the turn reads held. One request per enemy: a mark's outranks a queued row's, which outranks a pending unmarked attack. Rows into hand-written marks do not queue.
- **Release draw.** An attack's hold releases once its pose has lasted a hidden per-hold draw. No guard reads it, so branching on the roll never leaks timing (`networking.md` §Current contract, engine randomness).
- **Release exit.** A release behaves as an attack montage's strike section. Its own rows stay closed until its moment resolves, or with no moment until one pass of its clip, counted in clip time across variant restarts. A moment unreached within that pass whiffs, and an untimed named moment resolves on its entry tick. A release that ends having struck nothing, unless a flinch staggered it, starts its attack's cooldown as a hit would: the enemy committed, so a whiffed leap is not queued again at once. A release with `passes` (authored `repeat`, on a looping state, checked where an entity's mesh and behavior meet at load) starts its loop at clip time 0 on entry, not the drawn phase: host and client derive those states from the graph when the mesh materializes, and the clip clock, renderer and hit zones read one loop phase. That set is matched by state name and is not rebuilt by a behavior hot reload or a restore, so a reload that adds or removes `repeat` takes effect on the next spawn. Lowering keeps a repeating release planted (a steering one would restart its clip on each variant flip) and rejects a recover on its own state. It reopens its latch after each pass's moment, strikes once per pass under its one turn (a later pass skips the cooldown, which each hit restarts), and opens its rows once every moment resolved and its passes have played; a closed latch with passes owed (a flinch, a launch) cancels them. Once it has struck, a turn it loses (a target switch, a tick with no target) is not requested again, so the passes left whiff. The clock reaches at most one moment a tick, so passes shorter than a tick whiff, and a moment its clip cannot time strikes once; each warns once per entity class and attack when clips bind. An impact flinch during a release or recover plants the enemy, cancels its hit and any weapon burst in flight, plays its reaction through in clip time (capped by the default recovery in game time, from the first switch) and enters the attack's ending stance, never replaying the strike. The default recovery is an engine constant in `foundation`.

**Clip-timed attacks.** An attack may fire at a named moment in its clip (`action.at`, `resource_management.md` §7 clip events) instead of on entry.

- **Clip time is game time.** The brain accumulates clip time per AI tick for the animation its path selects, scaled by that state's playback rate. It never reads the animation clock, which is per frame and dev-scaled, so arbitration stays deterministic. This is the one exception to a single animation clock: presentation may lead or trail a moment by a frame, and without bound under the dev time scale. Activities sharing a state share its clip; a looping state starts at the enemy's drawn phase (a repeating release's at 0) and wraps. A travel variant switch restarts clip time, and so does dropping a held enemy: the drop attaches a fresh mesh. Clip time and the moment's latch serialize, so a restore resumes mid-swing. The accumulator and the moment check run on every tick the NPC acts; a dormant run resolves each moment inside its step once (Tick tiers).
- **One chance per entry.** The moment is checked after transitions, as attacks are. Every gate applies there; a failed gate is a whiff, and for a non-repeating release nothing fires later in that entry (a repeating release reopens its latch each pass; Release exit). Leaving first, entering a non-looping clip already past the moment, a knockback launch, or any switch off the path's animation other than a travel variant (an impact effect, a reaction) fires nothing that entry. Script reactions switch animations once per frame, so whether one cancels a moment can depend on how frames split ticks. A weapon attack starts its activation at the moment; the weapon's steps time the rest.
- **The mark is implied.** `at` holds its attack's turn from entry as `attackTurn` would, so the budget is asked before the swing plays. Load rejects `at` on a selector row or where the path selects no animation. A missing event warns when clips bind and fires as without `at`. A stance release narrows both: its defaulted `at` binds silently, and a named one resolves on its entry tick (Stances and attacks, Release exit).
- **Clip end.** `animationDone` turns true the tick after a non-looping clip reaches its duration, so a last-tick moment fires before an exit on it.

Graph evaluation is host-only. Clients consume replicated animation state and never evaluate guards.

## 7d. Ghost Links

Timelines are separate physical room copies joined by seamless teleporters. A **ghost link** lets a copy perceive the other: while armed, its members draw as translucent ghosts at the mapped pose in the other copy, and their sounds can play there. Room copies keep collision, hits, splash, AI perception and triggers isolated without any interaction filter. Ghosts are presentation only: they never collide, block, take hits or touch triggers.

- **Region.** A `ghost_link` brush volume over the source copy names a landmark inside it and a target in the other copy, both teleport destinations. The mapping is the seamless teleport's landmark → target transform, one function teleports and ghosts share, so a ghost and a seamless arrival from the same pose agree. A link is independent of teleporters. A two-way link is two volumes.
- **Eligibility is declared per layer, and links only narrow.**
  - A descriptor's `ghost` attribute marks an archetype that can ghost. It defaults to false for every descriptor, players included: the engine never branches on actor kind. A pawn ghosts with its third-person weapon.
  - A weapon's projectile block carries its own `ghost`, resolved from the firing weapon on every peer, a monster's projectiles included.
  - Movers have no descriptor: a link's `ghost_tags` names them by tag, per link.
  - Each link shows four member categories: players, non-player descriptor entities, projectiles and movers. A category never ghosts what the descriptor or tag did not opt in. The map sets a link's starting categories; scripts change them.
  - An impact belongs to a link when its shot's owner is a member, resolved from the shot id normalized as observer cues normalize it. An impact without a shot id belongs to no link.
  - The viewing player's own pawn, projectiles and sounds never ghost on that viewer's machine.
- **Resolved locally.** Each peer reads `ghost` from its own descriptors by the class each entity was materialized from, and resolves `ghost_tags` against its own movers, at install and on each committed reload, which re-resolves membership through the membership ramp. A level with links while no loaded descriptor sets `ghost` warns once at install. No membership fact rides the wire, and peers whose content differs see different ghosts. Per-instance tags on descriptor placements are unusable here: a connected client's copies of them carry no tags or map identity.
- **Per frame, from presented state.** An eligible entity is a member while its link is armed, its category is shown, and its presented point is inside the volume: the body point for a pawn, the origin for a projectile, the current bounds centre for a mover. The ghost draws at the mapped presented pose, so aim, pose modifiers and teleport cuts carry over. A ghost whose membership ends, despawn included, fades out at its last in-volume mapped pose, so a swap never draws a ghost between copies. An entity inside two armed links ghosts through each, one transform per link; a mover matching several of one link's tags ghosts once through it.
- **Not supported:** flipping `ghost` on one entity at runtime, and widening a link past its opt-ins.

Draw, limiter and audio contracts: `rendering_pipeline.md` §7.9, §7.8, `audio.md` §1. Replication: `networking.md` §Current contract. Script surface: `scripting.md` §2, §12. Author guide: `docs/ghost-links.md`.

## 7e. Level Seams

A **level seam** joins two maps: a player walks out of one into the other at the same place relative to the seam, facing and moving the same way.

- **Region.** A `level_seam` brush volume stands at the same place in both maps under one shared `name`. `target` names the next map's catalog id. Its landmark is a named teleport destination, else the bounds centre at yaw 0.
- **One inside test.** The upright player capsule against the union of the seam's convex brushes decides activation, arrival, latch and occupancy. A trigger's single bounding box would count the rooms beside a bent seam's bend.
- **Activation.** Touch or use, host and single player only. An undeclared pawn at zero health cannot activate it, as it cannot teleport; a declared pawn follows its state's `touch` and `use`. A disarmed seam never activates, and no seam activates in a frontend backdrop. Activation requests a classic level change, behind a loading screen; `mode` `seamless` does the same until a crossing without a loading screen is built (`boot_sequence.md` §9, Seamless level swap). Seams request at frame end, after the frame's last script drain, in one pick: the request queue keeps only the last load, so per-tick requests would let a later seam replace an earlier one. A `loadLevel`, `restartLevel` or any return to the frontend on the same frame wins. Among seams, the first activated in map order whose target the catalog knows wins; an unknown target warns once and requests nothing. A seam clears no pushed menu tree.
- **Arrival.** Unload reads each occupant's pose and motion relative to the landmark before teardown (`boot_sequence.md` §4). The seat's next pawn spawn takes it through the destination seam's landmark, under the teleport arrival rules (`movement.md` §6), at its own capsule size when that is not standing size. It spawns as the class of the start the seat would otherwise take and holds no start. A client's arrival rides the host's spawn-pose resolver to participation entry (`networking.md` §Slot lifecycle). Respawns never read it. The next unload, suspend, and a failed, cancelled or superseded load clear it. A blocked arrival, or a destination without the seam, falls back to a player start with one warning; a client's arrival is tested when it resolves and again at promotion. Seats outside the seam spawn at player starts.
- **Latch.** Every spawn and respawn latches the pawn against each seam its capsule overlaps, before any trigger tick sees it, so a two-way seam never bounces a player back. The latch clears when the capsule leaves. Arming keeps latches; a teleport takes none.
- **Event and occupancy.** The destination seam fires `arrive` once per arriving pawn, host-only, inside the first fixed tick after the spawn. A seam carrying a tag counts toward that tag's occupancy by its own inside test, armed or not (`scripting.md` §5).
- **Checkpoint.** A crossing is a checkpoint at the destination seam. The run records the seam's name, marked as a seam's, with seat 0's landmark-relative pose if seat 0 crossed. Continue spawns seat 0 there at rest, standing, its feet where they crossed, and fires `arrive`. The name also selects a spawn set (§7b).
- **Not supported:** non-player crossings, revisited-map state (crossing back loads the map fresh), and cross-map build checks.

## 8. Particles

Particles are anonymous presentation in a pool outside the registry. A particle has no entity id, no components and no script visibility, and is never replicated. Particle count never changes gameplay tick cost or gameplay spawn capacity.

**Producers.** The emitter bridge, a frame-time owner, writes the pool directly. Producers in the fixed tick or network ingest (impact bursts) queue plain-data requests on registry intake, drained into the pool at frame time. They never touch the pool, and the queue never reaches transport: each peer spawns its own bursts (`networking.md` §Presentation events vs. replicated state). Requests drain in raise order before emitter spawning; both producers feed the same frame's simulation and collection. Level unload and reload clear the pool and pending intake together.

**Simulation.** Rust, once per rendered frame on frame time, after the emitter bridge and before the light bridge: velocity, buoyancy and drag, curve-evaluated size and opacity, spin. Particles stay off the fixed tick; no per-particle script callbacks. Each step integrates position first, then takes gravity and push at the post-step position under the bodies' overlap rule (§7), never fluid. Buoyancy scales gravity; push is the nominal push, unscaled by buoyancy or force. A particle leaves on the step its lifetime ends, and every survivor steps exactly once. Pool order carries no meaning: the billboard pass is order-independent (`rendering_pipeline.md` §7.4).

**Emitter parameters.** A particle takes its emitter's curves, drag, buoyancy, sprite collection and tint at spawn and keeps them for life; a later emitter change reaches only later spawns. Parameters live in shared immutable blocks a particle references by index, never copied per particle. Blocks survive until their last particle expires; a later rewrite mints a new block only when a spawn succeeds. Spin is the one live value: a live emitter's spin rate refreshes its particles, so spin reactions turn existing smoke, and an orphan (emitter despawned) keeps rotating at the last rate. Reusing an entity slot cannot reconnect that orphan to a new emitter.

**Capacity.** A per-emitter cap of 4,096 and a global live budget of 65,536, shared by emitter and impact particles. Past either, new spawns drop with a rate-limited warning; live particles are never evicted. Gameplay registry capacity is independent. Steady-state spawning, stepping and expiry perform no per-particle heap allocation; level clear retains reusable capacities.

**Render collect.** Each rendered frame the collector culls each particle by its own position against the visible cells, buckets by its resolved sprite collection, and hands packed instances to the billboard pass. A conservative frustum pretest may skip a particle only when its whole rotated quad is outside; an offscreen centre alone never proves rejection. Gameplay projectiles remain individually addressed registry entities and share only the billboard collection path.

## 9. Non-Goals

- Full ECS (archetype storage, query planner, system scheduler)
- Entity inheritance hierarchies
- Per-entity script lifecycle callbacks (entity types don't have script attachment points; scripts manipulate entities through registered primitives)
- Client-authoritative entity state; deterministic-lockstep replication. Server-authoritative replication owns gameplay entities on the server; clients receive replicated component state.
- Entity serialization (save/load)
- Spatial partitioning for entity-entity queries (octree, grid), except combat-slot clearance's exact per-batch proximity query
- Physics engine integration (rigid body, joints, constraints)
