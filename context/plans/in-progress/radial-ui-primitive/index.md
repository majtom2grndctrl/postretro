# Radial UI Primitive (Ring / Arc)

## Goal

Add a `Ring` widget to the UI vocabulary: an anti-aliased annulus/arc **shape** whose geometric properties — radius, thickness, start angle, sweep — are each independently a literal or bound 1:1 to a state slot. It gives modders the first radial HUD primitive (reticle rings, arcs, expanding crosshairs) that the axis-aligned quad + text vocabulary cannot express. This is the deferred "Radial / ring / arc UI primitive" the roadmap names (Epic 13 deferred set). It is deliberately a *dumb shape*, not a value gauge: mapping a game-state value into a property's units (spread → px, cooldown → degrees) is a computed binding that belongs on the Behavior IR (Epic 14), spec'd separately — this primitive is that spec's first consumer.

## Scope

### In scope

- A `Ring` `Widget` variant + wire format: a fixed-size annulus-arc shape.
- Geometry authored per property, each `literal | bound`: `radius`, `thickness`, `startAngle`, `sweep`. A bound property reads its slot **1:1** in the property's own units (px / degrees), with an optional presentation tween on the bound ref.
- A static layout box (`diameter`) so bound draw values are appearance-only and never relayout.
- `fill` color and an optional full-circle `track` color.
- A CPU radial draw instance (`UiRingInstance`), a `UiDrawData` ring stream, a `UiPaintOp::Ring`, and an SDF renderer pipeline + shader (`ui_ring.wgsl`) slotted into the existing single-encode composition.
- SDK factories (TypeScript + Luau) `Ring(...)`, typedefs, the JS + Luau bridge arms, shared validation.
- A static reticle-ring demo in the dev mod.

### Out of scope — deferred to a successor spec

- **UI computed bindings via the Behavior IR** — resolving a bound value the IR derives from game state (`radius = map(player.spread, [0,1]→[12,60])`). This is the general home for value transforms (and likely subsumes `styleRanges` and `Bar::max`); an Epic-14 primitive-consolidation item, its own `/draft-plan`. Without it, no live slot is in UI-property units, so the *dynamic* consumers below are unblocked by that spec, not this one.
- **Bullet-spread / cooldown / charge gauges** — they need the IR mapping above (and, for spread, a gameplay producer that does not exist: no `player.spread` in `BUILTIN_ENGINE_STATE`). This spec ships the shape + binding hooks they will consume.
- Bindable `fill`/`track` colors, a value→color `styleRanges` on the ring, counter-clockwise winding, an in-ring text label, an `exitFade`. All additive follow-ups.
- Focusability/interaction (a ring is passive), and any change to `UiInstance`'s locked ABI or the `ui_quad.wgsl` pipeline.

## Direction

**Problem.** The UI widget vocabulary emits only axis-aligned quads (`UiInstance`: rect/uv/color/margin) and glyphon text through one shader (`ui_quad.wgsl`); there is no way to draw a ring or an arc. Radial HUD indicators — the observation that produced this — are unbuildable.

**Model — a shape, not a value visualizer.** A `Bar`'s `bind` prop encodes an assumption: the widget exists to visualize one number. That is wrong for a ring, which is a shape with several properties that vary independently and are often all static (a plain reticle ring binds nothing). So the ring has no privileged bound value: every geometric property is its own named prop, each `literal | bound`, generalizing per-property binding to the whole shape (each bound prop is the `SliderBind`/`SliderBindProp` shape — a `BindSource` plus an optional tween). A bound property reads its slot **1:1** — the widget performs no value transform.

**Prior commitments.** Honors "primitive surface is a contract" (`index.md` §2): a new kind updates SDK types, validation, and factories in one pass. Preserves the Goal-B locked wire format (byte-identical round-trip; additive fields skip-serialize). Keeps "renderer owns GPU" (shader/pipeline in `crates/renderer`). The one deliberate divergence from the `Bar` precedent — a second UI pipeline (SDF fragment fill) instead of the shared quad pipeline — is what the roadmap means by "a shader path beyond `ui_quad.wgsl`"; it slots into the `UiComposition`/`encode` single-encode contract as a new batch stream (diagrammed in `research.md`).

**Why 1:1 binding, and the IR seam.** The UI layer cannot compute per-frame (the VM drops; bindings are name→value). A bound geometric prop therefore needs its slot already in the property's units *or* a widget-side mapping. Baking a per-prop `from→to` range would work but would multiply exactly the pre-IR special case Epic 14's "primitive consolidation" exists to retire. So value mapping is placed on the Behavior IR as a **successor spec**, and this primitive stays a dumb 1:1 shape. The binding hooks are the seam that spec consumes.

**Alternatives rejected.** (1) The Bar-style privileged `bind`+`max`+`fillMode` value-visualizer — wrong frame for a shape with independently-varying, often-static properties (an earlier draft; see `research.md`). (2) A baked per-prop range — defers to IR (above). (3) Compose rings from many quads in mod code — no AA, no smooth arcs, dozens of quads; the roadmap calls for an engine primitive. (4) A pre-baked ring texture + `image` widget — fixed-resolution (against the AA-crisp-at-any-resolution model), no continuous arc/radius. (5) Extend the locked 64-byte `UiInstance` + `ui_quad.wgsl` — couples two primitives on one test-asserted ABI and the 9-slice path. (6) Ship a static-only shape with no binding — rejected: the hooks are cheap (reuse `drive_tween_f32`) and are the seam the IR spec lands on; omitting them forces a second breaking pass. (7) Defer the whole primitive and co-locate with the Weapon-Feel producer — foreclosed by the roadmap's "cross-cutting UI-layer work, reusable across features" framing.

**Foreclosures.** The durable commitments are the wire shape (`kind:"ring"`, its field names, the `literal|bound` scalar form) and the `UiRingInstance` ABI; removal later is content-breaking (pre-stable, acceptable). The first-in-codebase angle convention (0° = up, clockwise) is a foreclosure inherited by any future radial widget, not a re-litigable choice. The shader/pipeline are internal and cheap to change.

## Acceptance criteria

- [ ] A `ring` descriptor round-trips byte-identically through serde; `diameter`/`radius`/`thickness` are required, and every optional field (`startAngle`, `sweep`, `track`, `id`, `visibleWhen`, `role`) omits its key when absent/default (`startAngle` default `0`, `sweep` default `360`); each scalar property round-trips in both its literal (bare number) and bound (`{slot}`/`{local}`, optional `tween`) form.
- [ ] Raw JSON asset loads and both script bridges reject a literal that is out of range (`diameter`/`thickness`/`radius` non-finite or ≤ 0, `radius > diameter/2`, `thickness > radius`, `sweep` outside `(0, 360]`, non-finite `startAngle`) and accept the same fields in bound form (runtime-clamped, not load-validated). A valid ring from each frontend deserializes to the same `Widget::Ring`.
- [ ] With all-literal geometry, the collected draw data emits one ring instance for the shape (plus a full-360 track instance, sharing the shape's resolved radius/thickness, when `track` is set), with device-pixel radius/thickness and radians angles projected from the logical-reference values; a `sweep` of 360° renders a seamless ring (no wrap gap), a `sweep` < 360° an open arc.
- [ ] A geometric property bound to a numeric slot **or local cell** resolves **1:1** (the value is used directly in the property's units, no widget-side transform); changing the source changes the drawn shape; an out-of-range resolved value is clamped at draw, not rejected — `radius` clamps to `[0, diameter/2]` first, then `thickness` to `[0, clamped radius]`; a resolved `sweep` ≤ 0 (or `radius`/`thickness` ≤ 0) is a degenerate skip (no shape instance), and a resolved `sweep` > 360 clamps to 360 (seamless full ring).
- [ ] A bound geometric property with a `tween` eases its drawn value toward each new target (reusing the retained tween runtime); a bound-*value* change rebuilds the ring's draw list **without a taffy relayout** (`recompute_count` flat, `draw_rebuild_count` increments), and a settled frame rebuilds nothing. A `visibleWhen` flip toggles `Display` and **does** relayout (`recompute_count` increments, via `mark_dirty`), like every widget — the ring is appearance-only for value changes, not for visibility.
- [ ] `ui_ring.wgsl` parses and passes naga validation; the ring pipeline is created and a headless composition draws a ring batch at its painter depth (self-skipping when no GPU adapter is present); rings compose in painter order relative to quads and text through the single `UiComposition`/`encode` path (the per-layer encode loop stays unrepresentable, an opaque upper-layer quad occludes a lower-layer ring).
- [ ] The workspace builds: every exhaustive `Widget` match (`build_node`, `focus_meta`, `widget_visible_when`, `implicit_role`) and the exhaustive `NodeContext` match (`collect_node`) has a `Ring` arm; a ring is passive (id-only in `focus_meta`, `None` interaction).
- [ ] TypeScript and Luau `Ring(...)` factories accept each geometric prop as a literal number or a bound ref with an optional tween (the `number | BarBindProp` shape: a literal, or `BarBindProp`'s read-only bound arm `((ComputedRef<number> & { local?: never }) | LocalBindRef) & { tween?: NumberTween }`), emit a valid `{kind:"ring", …}` descriptor that round-trips to the canonical wire form, and the SDK typedef declares `RingProps` and `Ring`.
- [ ] The dev mod renders a static reticle ring (replacing or beside the current `"+"`), and the repo documents that value-mapped dynamic consumers (cooldown arc, spread crosshair) await the successor IR-bindings spec.

### Task 2: Per-property 1:1 binding + tween (CPU)

Make each geometric property bindable, entirely at the CPU tree level; no renderer change. Extend `NodeContext::Ring` so each geometric property is either a resolved literal or a bound driver (the `BoundScalar` source + its resolved `bind_scope`, a `last_resolved: Option<f32>`, and a `tween: Option<TweenState<f32>>`) — the per-property analog of the Bar's single-value driver. In `build_ring` (extending Task 1's file), resolve each `ScalarValue`: a literal is stored directly; a bound scalar seeds a driver (scope resolved like `build_bar`'s `bind_scope`, resolving both `{slot}` and `{local}` sources, tween born on first resolution). Add the `NodeContext::Ring` arm to `resolve_bindings` in `crates/ui/src/tree/ui_tree.rs` — note this match ends in a `_ => {}` wildcard (unlike the five compile-forced sites), so a missing arm compiles silently and rings would never ease; a tree test guards it. For each bound property, drive it 1:1 through a `drive_bar_binding`-shaped wrapper (branch on tween-present + a `Number` source → `drive_tween_f32` on the **raw** source value; else seed/hold — `drive_tween_f32` alone has no untweened/absent-source path), with no widget-side transform. Drive all four properties **unconditionally every frame** (each tween segment must advance regardless of the others) and combine their change flags **without short-circuit** (separate `let`s or `|`, never `||`), then flag `appearance_changed` only (a ring is a fixed-`diameter` leaf and must never mark itself dirty for relayout — Invariant "appearance-only"); this mirrors the `value_changed`/`max_changed` pattern in Bar's `resolve_bindings`. The tween targets the raw source value and `last_resolved` stores the **raw, unclamped** eased value; clamping is draw-only (so a `radius` easing past `diameter/2` draws clamped yet unsticks when it eases back). A bound tween advances against the frame clock even while the ring is `Display::None` (its node persists; only `Display` toggles), so `last_resolved` survives a hide and a re-shown ring reflects the current eased value — it does not pause, restart, or snap (matching Bar). In `collect_node`, read each geometric property's resolved value: the eased `last_resolved` when a bound driver has run, else — the fresh/first-frame path where `tween`/`last_resolved` are `None` (`build_draw_data`; most unit tests) — resolve the source 1:1 directly, mirroring Bar's `match (tween, last_resolved) { (Some(_), Some(d)) => *d, _ => bar_slot_value(...) }` fallback. Clamp at draw in order: `radius` to `[0, diameter/2]` first, then `thickness` to `[0, clamped radius]`; clamp `sweep`'s upper bound to `360` and treat a resolved `sweep` ≤ 0 as a degenerate skip (no shape instance); emit as in Task 1. Add tree tests mirroring `crates/ui/src/tree/tests/bar.rs`, covering the Behavioral pins: bound `sweep`/`radius` tracks its source 1:1 and a `tween` eases across frames (P2/P3), two bound props tween simultaneously without either stalling (P3), a `radius` easing past `diameter/2` and back returns unclamped (P5), `thickness` clamps against the clamped radius (P6), a resolved `sweep` ≤ 0 skips (P7), a `sweep`→360 target is seamless on the settle frame and that frame *is* rebuilt (P9), a bound-value change is appearance-only while a `visibleWhen` flip relayouts (P1/P2), a hidden ring's tween advances in the background (P10/P11), a fresh-path bound ring draws its source 1:1 (P12), a bound `sweep` resolving over-range (400) clamps to 360 seamlessly (P8), the track follows the eased radius (P16), and a `{local}`-bound prop resolves.

## Wire format

`ScalarValue` (new, `crates/scripting-core/src/ui/descriptor/values.rs`) is the reusable "literal-or-bound scalar" the ring's geometric props use; its untagged wire form is a bare JSON number (`Literal`) or a bind object carrying `{slot}`/`{local}` and an optional `tween` (`Bound`). It generalizes `BarMax` (which is literal-or-`{slot}`) with a `local` source and a tween — its bound arm is structurally `SliderBind` (a `BindSource` + optional tween); `BarMax`/`ColorValue` are the precedent only for the untagged, `Literal`-first ordering. It is available to future widgets wanting per-property binding.

`UiRingInstance` (CPU, `crates/ui/src/output.rs`) is a new `#[repr(C)] Pod` draw record byte-stable for app→renderer handoff, mirroring `UiInstance`'s discipline (a `size_of`/align assertion guards the ABI). It carries a device-pixel bounding rect, a linear-RGBA color, and the resolved radial geometry (center-relative outer radius, thickness, start angle, sweep — device px and radians). State the stride/size as the constraint; the implementer places fields. `GpuUiRingInstance` appends the painter depth, as `GpuUiInstance` does for quads.

| P2 | Bound-value change is appearance-only | `radius` bound, no tween; F0 source 10, F1 source 20 | F1: `recompute_count` flat, `draw_rebuild_count` increments |

| P5 | `radius` eases past `diameter/2` and back | `diameter=100`; retarget `radius` to raw 200 (drawn clamps to 50), then to 40 | Drawn radius clamps to 50 while raw > 50, then returns to 40 — proves `last_resolved` holds raw, unclamped |
| P6 | `thickness` vs clamped radius | `diameter=100`, `radius` eases to raw 200, `thickness=40` | Drawn radius 50; thickness clamps to `[0,50]`→40; annulus never inverts to a filled disc |
| P7 | Bound `sweep` resolves ≤ 0 | `sweep` source resolves to 0 or negative | Degenerate skip — no shape instance (track, if set, still draws when radius/thickness > 0) |
| P8 | Bound `sweep` over-range | `sweep` source 400 | Drawn sweep clamps to 360 → seamless full ring, no overshoot artifact |
| P9 | Tween toward exactly 360 | `sweep` tween (with `from`/retarget so an in-flight phase exists), target 360; sample in-flight before raw enters the snap band, then at settle | In-flight: open arc (< 360). Settle frame (`t≥1`): exactly 360, seamless, and the frame *is* rebuilt — because the raw eased `sweep` reaches its exact target (a raw change > `f32::EPSILON` from the prior frame); the within-ε-of-360 snap is draw-only and must NOT enter the change-detection compare (that would break the raw-`last_resolved` discipline) |
| P10 | Hide mid-ease, show later | `radius` tween; F0 births ease, F1 hide (`Display::None`), F2 (past duration) hidden, F3 show | F3 shows the background-advanced (settled) value — not a restart or snap; `last_resolved` survived |
| P11 | Slot changes while hidden | As P10 but F2 changes the source while hidden | On show, ring reflects the value eased toward the new source in the background |
| P12 | Fresh-path bound ring | `build_draw_data` (non-retained) with `radius` bound, source 25 | Draws radius 25 via direct 1:1 source resolution (no tween/`last_resolved`), not zero |
| P13 | First-frame `from` semantics | `radius` tween with `{from:10}` vs none, source 50, F0 | With `from`: F0 draws eased-from-10. Without: F0 snaps to 50 |
| P14 | Zero / sub-frame duration | `sweep` tween `durationMs:0`, then `< one frame` | duration 0: target reached on the start frame, no divide-by-zero; sub-frame: settles next frame |
| P16 | Track shares radius, ignores sweep/startAngle | `track` set, `sweep=90`; literal radius (Task 1) and eased radius (Task 2, folded into P5) | Track is full-360 sharing the shape's resolved `radius`/`thickness` (literal or eased); ignores `sweep`/`startAngle`; skips when radius/thickness ≤ 0 |
| P17 | Same-frame game write | Source written in Game logic, read in Render's `resolve_bindings` | Ring reflects the write in the *same* frame — no one-frame lag, matching Bar |
| P18 | Descriptor/theme rebuild resets ease | Ring mid-ease; F1 the tree rebuilds (`UiTree::from_descriptor`) | Tween state + `last_resolved` lost; a `from`-less bound prop snaps to the current source on the next diff — matches Bar |
| P19 | Paint-order tie-break | Two rings in one tree; each emits track then shape | Order follows the depth-first paint-stream walk (`from_layer_draws` monotonic `order`); within a ring, track draws behind shape |

## Script syntax examples

```ts
// Static reticle ring — no binding at all (the case a Bar-style model cannot
// express). A thin full-circle outline as a crosshair.
Ring({ diameter: 24, radius: 10, thickness: 2, fill: [0.8, 0.95, 0.98, 0.9] })

// A partial arc, all literal — e.g. a decorative 270° gauge frame with a dim
// full-circle track behind it. `sweep` < 360 leaves the arc open.
Ring({
  diameter: 96, radius: 44, thickness: 6,
  startAngle: 135, sweep: 270,
  fill: [0.1, 0.8, 1.0, 1.0],
  track: [0.1, 0.1, 0.1, 0.5],
})

// A bound geometric property — 1:1, no transform. `player.spreadRadiusPx` is a
// hypothetical slot ALREADY IN PIXELS; mapping a raw gameplay spread value into
// pixels is the successor IR-bindings spec's job, not this widget's. The ring's
// drawn radius follows the slot, eased.
Ring({
  diameter: 120, thickness: 2, sweep: 360,
  radius: bindState(player.spreadRadiusPx, { tween: { durationMs: 90, easing: "easeOut" } }),
  fill: [1, 0.2, 0.2, 1],
})
```
