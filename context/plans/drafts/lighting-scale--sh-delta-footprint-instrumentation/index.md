# Direct SH Delta Footprint Instrumentation

> **Status:** draft.
> **Track:** Lighting / build pipeline — measurement prerequisite, not a fix.
> **Related:** `context/lib/build_pipeline.md` (PRL sections, prl-build) · `context/lib/rendering_pipeline.md` §4/§7.1 (SH compose) · `context/plans/done/lighting--entity-direct-sh/` (the direct-SH feature this measures) · `context/plans/done/perf-animated-sh-light-culling/` (the sparse-CSR delta form).
> **Dependencies (this backlog):** No upstream dependency — this is the measurement foundation. Its delta-byte footprint output is consumed by `lighting-scale--adaptive-sh-probe-density`'s Task 1 measurement spike. It shares the `pack.rs` section-size logging surface with `compiler-log-hygiene`; coordination pinned: the id-27 per-section size line (Task 2) is part of the breakdown and follows its level, including any `compiler-log-hygiene` downgrade to `debug!`; Task 1's direct-delta summary and Task 4's SH-total aggregate are pinned `info!` and that spec's sweep must exempt them.

## Goal

A stress map compiled with dense settings baked a **1.22 GiB** direct-SH delta storage buffer — overflowing the engine's then 512 MiB self-imposed `max_storage_buffer_binding_size` and failing wgpu bind-group validation at load. The limit (`REQUIRED_STORAGE_BUFFER_BINDING_SIZE`, `crates/renderer/src/render/renderer_init_resources.rs`) has since been raised to a 2 GiB−8 stopgap that admits the buffer, but the stopgap is documented as load-bearing on above-spec hardware, with the tracked end-state a sparse layout under the 128 MiB WebGPU spec floor — so a 1.22 GiB delta payload remains the problem to shrink, not a resolved incident. Before choosing an allocation strategy, make the direct-SH delta footprint **visible at prl-build time**: which lights dominate the bytes, and how SH's share compares to the rest of the `.prl`. This is a logging-only measurement plan — no behavior, format, device-limit, or buffer-layout change. Its output unblocks a later allocation-strategy decision (footprint-gating vs. adaptive probe density vs. texture-array migration vs. chunking).

## Scope

### In scope

- A per-selection-light delta-byte histogram logged from the direct-delta bake, so map authors see which lights dominate the delta storage.
- A dedicated size log line for the indirect `DeltaShVolumes` section (id 27) in prl-build, matching every other emitted SH section.
- The existing `ComposeStorageFootprint` per-binding storage log wired into the direct compose path at runtime (the indirect path already has it).
- An aggregate "SH sections total vs. non-SH total" summary line in prl-build's section-size report.

### Out of scope (non-goals)

- **Changing the bake output.** No probe is added, dropped, culled, or re-valued. Baked `.prl` bytes are identical before/after this plan.
- **Changing the PRL format.** No new section, no version bump, no field added to any section struct.
- **Changing device limits.** `REQUIRED_STORAGE_BUFFER_BINDING_SIZE` (currently the 2 GiB−8 stopgap) stays as-is — this plan measures the footprint, it does not resolve it.
- **Changing the buffer layout / bind groups.** No binding added or moved on either compose path.
- **The allocation-strategy decision itself.** Footprint-gating, adaptive density, texture-array migration, and chunking are follow-up plans that consume this plan's measurements.
- **Per-frame or default-verbosity log spam.** Every added runtime log sits in a load-time / resource-construction path, never a per-frame render path. Every added detailed per-item breakdown (the delta histogram) is gated behind `-v/--verbose`, matching the house convention (`lightmap_bake.rs::log_stats`); at default verbosity each new bake log site emits at most one summary line. Normal (non-verbose) builds and runs gain no per-item or per-frame noise.

## Acceptance criteria

- [ ] Building `content/dev/maps/stress-warren-maze-crates.map` with `--lightmap-density 0.2 --sh-probe-spacing 1.33 --soft-shadow-samples 64` at info verbosity (`RUST_LOG=info`, no `-v`) prints a **single** direct-delta summary line — total delta bytes plus the top dominating light; Task 1's log site adds no other line at that verbosity. The full **per-selection-slot histogram** — one line per slot with at least one CSR entry, sorted descending by byte total, each naming the slot, its global light identity, CSR-entry count, and byte total — is emitted only under `-v/--verbose`.
- [ ] The histogram's summed per-slot bytes equal the emitted `DirectShDeltaVolumesSection`'s `delta_subblocks` byte length (`affinity_lights.len() × PROBES_PER_CELL × delta_probe_f16_stride(tile_dimension) × 2`), and the logged total equals that histogram sum. This is the checkable invariant that the accounting is complete and correct.
- [ ] prl-build prints a size line for the indirect `DeltaShVolumes` section (id 27) whenever that section is emitted, at the same log level as the other per-section size lines — id 27 is no longer the one emitted SH section with no size line.
- [ ] At runtime, loading a map with a direct-delta section logs a per-binding storage footprint for the direct compose path's PRL-baked delta buffers (`delta_subblocks`, `affinity_offsets`, `affinity_lights`) plus their total, and the log is unambiguously attributable to the DIRECT compose path (not confusable with the indirect path's existing footprint line). The line is emitted once per map load / compose-resource construction (`build_promotion_pass` under `DirectShComposeResources::new`, which is called only from the full-init and resource-rebuild paths), **not per frame** — matching the indirect path's existing once-per-load footprint log.
- [ ] prl-build prints one "SH sections total vs. non-SH total" `info!` summary line after the per-section size logs, summed over the emitted `sections` vec so every emitted section is accounted for.
- [ ] No change to compiled `.prl` output bytes and no change to runtime behavior beyond the added log lines. A byte-for-byte diff of a `.prl` compiled before and after this plan (same inputs) is empty.

## Tasks

### Task 1: Per-selection-light delta-byte histogram (direct-delta bake)

In `bake_direct_sh_delta_volumes_controlled` (`crates/level-compiler/src/direct_sh_bake.rs` — the `_controlled` body both entry points share; the un-suffixed `bake_direct_sh_delta_volumes` is a thin wrapper), compute per-slot stats immediately before the `Some(DirectShDeltaVolumesSection { … })` return. At that point the function holds `affinity_lights: Vec<u32>` and `selected: Vec<SelectedDirectLight>`. Each entry in `affinity_lights` is a **selection index** into `selected` — a CSR (cell, selection-slot) entry, NOT an AlphaLights or source-light id (pinned by the test `direct_sh_delta_affinity_lights_are_selection_indices`). Tally occurrences of each value in `affinity_lights` for per-slot CSR-entry counts; multiply each count by the per-entry payload `FORMAT_PROBES_PER_CELL × delta_probe_f16_stride(TILE_DIMENSION) × 2` bytes (= 64 × 144 × 2 = 18,432 for the default 6-texel tile — do not hard-code; `FORMAT_PROBES_PER_CELL` is already imported from `postretro_level_format::delta_sh_volumes`; the stride comes from the imported `FORMAT_DEFAULT_DELTA_PROBE_F16_STRIDE` or a new import of the `delta_probe_f16_stride` function). **Where the logging lives:** the bake has no verbosity state, and `selected` never escapes it — so the bake does not log the histogram itself. Return the stats alongside the section: a small `DirectDeltaBakeStats` — rows of `(static_index, csr_entry_count, byte_total)` sorted descending by byte total, plus the total byte count — populated from `selected[slot].static_index` (the light's position in the `StaticBakedLights` set — the stable global identifier) and, if cheap, the light's `origin` from `.light: &MapLight`. The `pipeline.rs` call site then logs: at any verbosity, one `info!` summary line — total delta bytes plus the top dominating slot; under `if args.verbose`, the full histogram, one line per slot with at least one CSR entry — matching how `lightmap_bake::log_stats` is actually gated (an `if args.verbose` at its `pipeline.rs` call site, not inside the baker), and keeping `compiler-log-hygiene`'s no-verbose-replumbing-through-bakers stance intact. If the label should also name the source `EntityShadowLights.light_indices` alpha value: `selected` is built by `selected_direct_lights` via a `filter_map` over `entity_shadow_lights.light_indices`, which discards the originating alpha index — extend `SelectedDirectLight` to carry it and populate it there; otherwise label by `static_index` alone, which `selected[]` already carries. The summed per-slot bytes must equal `affinity_lights.len() × per_entry_payload` (the AC-2 invariant) — log that total alongside the histogram.

### Task 2: Size log for the indirect DeltaShVolumes section (id 27)

In `crates/level-compiler/src/pack.rs`, add a size log line for the indirect `DeltaShVolumes` section, mirroring the existing `DirectShDeltaVolumes` (id 41) block (the `if let (Some(section), Some(bytes)) = (direct_sh_delta_volumes, …)` log). The section is already threaded and emitted: the param `delta_sh_volumes: Option<&DeltaShVolumesSection>`, its bytes `delta_sh_volumes_bytes`, and its emit at `append_optional_section(… SectionId::DeltaShVolumes …)`. It is the one emitted SH section with no line in the per-section size block (between the section writes and the trailing `Ok(())`). Add a guarded log line matching the `if let (Some(section), Some(bytes)) = …` pattern of the neighboring optional-section logs, **at the same log level as those neighbors** — this line is part of the per-section breakdown, so if `compiler-log-hygiene` downgrades the breakdown to `debug!`, this line goes with it; only Task 1's summary and Task 4's aggregate line are pinned `info!`. Report the byte length and a useful count (e.g. `affinity_lights.len()` CSR entries and/or `animation_descriptor_indices.len()` animated lights), placed adjacent to the other SH-section logs.

### Task 3: Wire ComposeStorageFootprint into the direct compose path

`DirectShComposeResources::new` (`crates/renderer/src/render/direct_sh_compose.rs`) is a dispatcher into `new_case1` (id-41 delta present) and `new_case2` (the section-45 animated-direct path); the three PRL-delta byte vectors (`subblock_bytes`, `offsets_bytes`, `lights_bytes`) are built in the shared helper `build_promotion_pass`, which both cases call. Construct and log a `ComposeStorageFootprint` (`postretro_render_cpu::sh_compose::ComposeStorageFootprint`) in `build_promotion_pass`, right after those vectors are built — one site, so the log fires exactly once per construction on either case; in Case 2 the promotion buffers may be empty and the footprint then reports zeros, which is correct and informative. **Footprint scope:** it measures the id-41 promotion-pass baked delta storage only. The direct path's Case 2 animated-add pass has its own id-45 buffers (`animated_direct_sh_compose.rs` builds its own `subblock_bytes`/`offsets_bytes`/`lights_bytes`) — those are excluded here; instrumenting them is a natural sibling addition but not this task. Two promotion-pass specifics: (a) `DirectDeltaComposeBuffers` carries no `animation_descriptor_indices` buffer, so set `animation_descriptor_indices_bytes: 0`; (b) `selection_weights` (bound at `BIND_SELECTION_WEIGHTS = 26`) is a **runtime** buffer passed in as `weights_buffer` — NOT part of the PRL-baked delta payload, so it is excluded (the footprint measures the baked delta storage, matching the struct's four fields). **Label plumbing:** `ComposeStorageFootprint::log()` hard-codes the string `"SH compose @group(1) storage footprint"`, which would mislabel the direct path (distinct pass, and the indirect path already prints that exact line from `ShComposeResources::new`). Make the direct log unambiguously the direct path — either parameterize `log()` with a caller-supplied label (updating the indirect call site to pass its current label) or emit a sibling direct-specific line — so AC-4 holds. The existing per-case lines (the "selected-light CSR" log in `new_case1` and the "Case 2 … animated-light CSR" log in `new_case2`) stay; the footprint is additive. **Frequency:** `DirectShComposeResources::new` is called only from `renderer_full_init.rs` and the `renderer_resources.rs` rebuild path — load-time / rebuild, never per frame; keep it that way. Do NOT add any logging to a per-frame compose/render path.

### Task 4: SH-total vs. non-SH-total summary line

In `crates/level-compiler/src/pack.rs`, after the per-section size logs and before the trailing `Ok(())`, add one `info!` summary line partitioning the emitted sections into an SH group and a non-SH group and reporting each group's total bytes (and their sum, which should equal the on-disk section-payload total). The SH group, enumerated exactly: `OctahedralShVolume`, `DirectShVolume`, `DeltaShVolumes`, `DirectShDeltaVolumes`, `AnimatedDirectShDeltaVolumes`, `EntityShadowLights`. `ShadowmaskAtlas` is lighting data but not SH storage — it counts as non-SH. Sum over the `sections` vec itself (partition by `section_id`, sum each blob's byte length): two emitted sections' byte locals (`map_entities_bytes`, `cell_draw_index_bytes`) are moved into `sections` rather than cloned, so a locals-only sum cannot account for every emitted section, while the `sections` vec holds every payload by construction — which also makes the sum-equals-payload-total check honest. State in the message which sections count as SH so the partition is auditable against the per-section lines directly above it. This line is one of the two pinned `info!` outputs `compiler-log-hygiene`'s breakdown downgrade must exempt (see Dependencies).

## Sequencing

**Phase 1 (concurrent):** Task 1, Task 2, Task 3, Task 4 — four independent, additive sites in four files (`direct_sh_bake.rs` + its `pipeline.rs` call site, `pack.rs` ×2, `direct_sh_compose.rs`). ## Rough sketch

- **Per-entry payload is a constant of the tile geometry.** One CSR entry = one 4×4×4 affinity cell = `PROBES_PER_CELL` (64) probes × `delta_probe_f16_stride(tile_dimension)` (144 halves for the default 6-texel tile) × 2 bytes = 18,432 bytes. The whole delta payload is `affinity_lights.len()` such entries. This identity is the histogram's accounting basis and the AC-2 cross-check. Confirmed constants: `AFFINITY_FACTOR = 4`, `PROBES_PER_CELL = 64`, `DEFAULT_DELTA_PROBE_F16_STRIDE = 144` (`crates/level-format/src/delta_sh_volumes.rs`).
- **Selection index ≠ global light id.** `affinity_lights[i]` indexes `selected[]` (the post-filter selected-direct-lights vec); `selected[slot]` resolves to a `MapLight` and its `static_index`. The bake already does exactly this resolution when it builds `delta_subblocks` (`let entry = selected[selection_index as usize];` in `bake_direct_sh_delta_volumes_controlled`) — the histogram mirrors that lookup for labeling.
- **Direct compose bindings (for the footprint).** PRL-baked delta storage in the promotion pass: `delta_subblocks` (`BIND_DELTA_SUBBLOCKS = 20`), `affinity_offsets` (`BIND_AFFINITY_OFFSETS = 21`), `affinity_lights` (`BIND_AFFINITY_LIGHTS = 24`). Runtime-only (excluded): `selection_weights` (26), `debug_override` (27). No `animation_descriptor_indices` exists in the promotion-pass buffers; the Case 2 animated-add pass's own id-45 buffers (bindings 22/23/25) are out of the footprint's scope. (`direct_sh_compose.rs`.)
- **Ballpark for the observed overflow.** 1.22 GiB ÷ 18,432 B ≈ 71k CSR entries — the histogram attributes those entries to their dominating lights, which is the number the allocation-strategy follow-up needs.
- **`.prl` byte-identity is the guardrail.** Every change is logging or logging-support plumbing — a stats struct returned from the bake, a label parameter on `log()`, optionally an alpha-index field on `SelectedDirectLight`; none touches emitted bytes, the section list, or any bind group. The AC-6 before/after `.prl` diff is the objective check that scope held.
