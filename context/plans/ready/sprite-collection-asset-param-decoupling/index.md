# Decouple sprite draw contract from texture asset

## Goal

Let one texture asset serve multiple consumers that draw it with different per-consumer look params. Today a "sprite collection" is keyed by the asset reference string, which fuses the shared asset to a single draw contract; two consumers of one asset that disagree on any look param currently collide, get skipped at registration, and render the wrong sprite at runtime. Introduce a synthetic **collection id** — `(asset, draw contract)` — as the render-time key, so distinct contracts over one asset become distinct collections that share the underlying GPU texture. This is the root-cause fix for the rocket-trail-renders-plasma bug (`research.md`).

## Scope

### In scope

- A `collection id` distinct from the asset reference, derived as a pure function of the draw-contract inputs, used as the render-time bucket key.
- Install registration keyed by collection id; GPU texture upload deduped by asset reference so one array backs every id that shares an asset.
- Replacement of the byte-identical conflict resolver (`resolve_sprite_collection_draw_contract`) with id derivation: differing contracts mint distinct ids instead of erroring, so no collection is ever skipped.
- Stamping the resolved id onto the particle render key at all four production `SpriteVisual` write sites (emitter/trail spawn, impact spawn, projectile-body host authoring, projectile-body presentation shared by host-observer and client).
- Host/host-observer/client agreement on the id for a given projectile, since `SpriteVisual` is re-derived per peer, not replicated.
- Revert of the shipped content workaround (`content/dev/scripts/enemy-rifle.ts`) so the fix ships proven against the original colliding content.

### Out of scope

- **Per-instance look params (approach B2 in `research.md`).** Rejected; see Direction.
- **Per-instance `tint` GPU channel.** `SpriteVisual.tint` stays CPU-only, as documented in the component. This work must not consume the one spare instance slot, so the tint channel remains free for later.
- **Authorable emissive/specular on billboard emitters.** Emitter-spawned particles keep emissive `0.0` and default specular, matching current install behavior; adding authored emitter emissive is a separate change.
- **New flipbook or cadence behavior.** Loop period keeps its current derivation and rendering; only its participation in the collection key changes.
- **Content that produces a specular collision.** No current producer sets `spec_intensity`/`spec_exponent` on a projectile or emitter sprite (both are forced to `None` on this path), so a specular collision is unreachable in content today. The id machinery still folds specular in generically; coverage is a unit test over synthetic contracts, not a content case.

## Direction

**Problem.** The render-time collection key is the raw asset reference (`SpriteVisual.sprite`), so it cannot distinguish two draw contracts over one asset. The install resolver reacts to the resulting ambiguity by requiring every consumer of an asset to agree bit-for-bit on the contract, erroring and skipping the whole collection on any mismatch; the runtime then falls back to the first-registered collection and renders its sprite. The cause is the fused key, not the resolver's strictness.

**Prior commitments.** `rendering_pipeline.md` §7.4 pins the billboard draw contract: `SpriteDrawParams.params.y` / `params2.y` are the sole specular inputs, `params.z` the loop period, `params.w` the emissive term — all read from a per-collection uniform; billboards are "batched by sprite collection — all particles sharing a collection issue one draw call." The vertex stage is at six of eight storage buffers with a headless test and a `Renderer::new` debug assert pinning ≤ 8; the instance stride is 32 B with one spare 4-byte slot. This design keeps every one of those commitments intact: the per-collection uniform, its field meanings, the one-draw-call-per-collection rule, the vertex-storage budget, and the 32 B stride are all unchanged. What changes is only the definition of a collection — from "one asset reference" to "one `(asset, contract)`" — and the addition of an asset→texture dedup beneath it. `SpriteVisual` is deliberately kept off the wire (`netcode/replication.rs`); this design honors that by deriving the id per peer rather than replicating it.

**Reversibility.** The id is derived per frame, per peer — never baked into PRL, never sent over the wire. Backing out (to per-asset keying, or a later pivot to B2) costs code only: no format migration, no content re-bake. This is the fact that most de-risks the direction.

**Alternatives rejected.** *Content policy — make the workaround the rule.* Declare "one asset reference carries one draw contract" and require content to duplicate the asset when a second contract is needed, the friction the shipped `enemy-rifle.ts` workaround dodged only by deleting its `smoke_puff` trail outright rather than duplicating the asset. Rejected: it is engine-fighting friction every modder re-hits against the modder-friendly northstar, and it scales VRAM with contract count — the exact one-array-per-asset invariant (INV 3) this design restores. *B2 — per-instance look params.* Push loop period, emissive, and the two specular params into `SpriteInstance`, keep one collection per asset, delete the resolver. It buys a single draw call per asset but is the wrong granularity: the four params are constant across an emitter's particles, so B2 replicates draw-contract state across every instance in the stream. It grows the 32 B stride to 48 B (+50 % instance bandwidth) and spends the one spare slot on contract-constant data, leaving less room for the genuinely-per-instance `tint` channel the component already anticipates. It also rewrites the §7.4 "sole specular input" contract and edits the hot shader in four sites. B1 keeps the params at their true granularity (once per contract), preserves the shader contract verbatim, and pays only a few extra draw calls — a cost §7.4 already absorbs ("no per-collection sprite cap"; collections number in the low single digits). *Stopgap — skip the loop-period check for single-frame collections.* Fixes only the observed case; silent on emissive collisions and multi-frame sprites. The content workaround already stops the bleeding, so there is no urgency that would justify shipping a known-partial fix.

## Field classification

Three granularities. The bug is that the middle tier is wrongly fused to the top tier.

| Tier | Fields | Lives in | Keyed / packed by |
| --- | --- | --- | --- |
| Asset-intrinsic | frame arrays (diffuse/spec/normal), frame count, slot mask, dimensions | GPU texture array + `SpriteDrawParams.params.x`/`params2.x` | asset reference (dedup target) |
| Draw contract | loop period (`params.z`), emissive (`params.w`), spec intensity (`params.y`), spec exponent (`params2.y`) | per-collection `SpriteDrawParams` uniform | collection id |
| Per-instance | position, age, size, rotation, opacity | `SpriteInstance` (32 B) | packed per particle |

The collection id names the pair (asset-intrinsic tier ⊕ draw-contract tier). The dedup makes many ids share one asset-intrinsic upload. The per-instance tier is untouched.

## Collection id

`derive_collection_id(asset, contract)` is a pure, injective function of the asset reference and the raw draw-contract inputs `{ lifetime: Option<f32>, frame_duration_ms: Option<f32>, emissive: f32, spec_intensity: Option<f32>, spec_exponent: Option<f32> }`. Float fields encode by bit pattern, preserving the current `to_bits()` equality semantics: two byte-identical contracts collapse to one id; any bit-level difference yields a distinct id. It folds the *raw* cadence inputs, not the frame-count-derived loop period, so no site needs the frame count to compute the id — the frame count enters only once, at registration, when each id's loop period (seconds) is computed for the uniform (unchanged from today).

Because the id is a pure function of inputs that both host and client hold (the shared `ProjectileDescriptor`, or the local `BillboardEmitterComponent`), every peer derives the same id without any table or wire field. Identical-id candidates are identical by construction, so registration needs no conflict arbitration — it groups candidates by id and registers one collection per id. The only surviving validation is the specular-exponent finiteness check, kept before registration.

The id is a `String`: the asset reference as a human-readable prefix, then a reversible bit-exact encoding of the contract float fields (each field's `to_bits()`, with `None` distinguished from any value). This makes it injective by construction — no two distinct contracts share an id — rather than probably-injective. A hash is rejected: a collision would silently fuse two contracts into one collection, reintroducing the wrong-params-on-a-shared-asset bug nondeterministically. A decimal encoding is rejected for the same reason: display rounding is lossy, so it would re-fuse contracts that differ below the printed precision. The asset prefix keeps the id useful in the unregistered-id and dedup warnings; staying a `String` keeps the `HashMap` keys and `SpriteVisual` serde unchanged.

**Terminology.** *Asset reference* names the texture (the dedup target); *collection id* names the `(asset, contract)` pair (the registration and render key). The bug was conflating them. New code and the promotion-time durable capture use the two terms consistently, so the failed model is not re-taught at the type level. The codebase's existing use of "collection" to mean the asset reference (the install grouping key, `register_collection`'s `collection` parameter) shifts to mean the collection id where it becomes the registration key.

## Acceptance criteria

- [ ] Two consumers of one asset with different loop periods (rocket trail `smoke_puff` lifetime 1.75 and enemy-rifle trail `smoke_puff` lifetime 0.45, workaround reverted) each render `smoke_puff` in single-player; neither falls back to another collection. The no-fallback routing (each trail resolves to its own registered id, no fallback warning) is the automatable proof; the on-screen pixel is a §7.4-style manual GPU check.
- [ ] Two consumers of one asset with identical contracts register exactly one collection (one draw call, one bind group).
- [ ] No collection is skipped when contracts differ (two differing-contract candidates over one asset register two collections) — unit-testable; the removed conflict-warn-`continue` path's non-existence is a grep/review gate.
- [ ] One asset shared by N collection ids uploads its GPU texture array exactly once — asserted via the Task 3 dedup seam; the "VRAM does not scale with id count" half is a review gate over that seam, not a runtime VRAM measurement.
- [ ] A projectile whose body or trail shares an asset with another consumer, but differs in contract, renders its own contract from all three vantages — host local shooter, host remote-observer, and client materialized copy — because all three derive the same id.
- [ ] A runtime sprite whose id was never registered at level load still routes to the default collection with a one-time warning (behavior preserved).
- [ ] Impact particles still render their own collection after the migration: the separate impact registration and `weapon/impact.rs::spawn_particle` derive the same id from the shared impact contract, so impact never falls back to the default collection.
- [ ] An invalid specular exponent (non-finite or ≤ 0) is still rejected before registration.
- [ ] `derive_collection_id` is injective and bit-exact over synthetic contracts spanning all four contract fields, including specular (which has no content producer today).

- Collector (read side): `scripting/systems/particle_render.rs` — `ParticleRenderCollector { buffers, sprite_to_collection, default_collection, warned_unregistered }`, `register_sprite` (id→id, first is default), `resolve_fallback` (origin of the wrong-sprite render), `pack_sprite_instance` (position/age/size/rotation/opacity + one pad; no contract params). - Write sites (stamp the id here): `scripting/systems/emitter_bridge.rs::spawn_one` (emitter/trail; has `{ sprite, lifetime }`, no emissive/cadence — implicit emitter contract), `weapon/impact.rs::spawn_particle` (constant collection; stable id from its fixed registration), `sim/weapon_stage/commands.rs::spawn_projectile` and `netcode/projectile_presentation.rs::attach_projectile_visual_components` (body; full `ProjectileBodyVisual::Sprite`, read past the `..`).
- Shader (unchanged): `shaders/billboard.wgsl` — `SpriteDrawParams` field meanings, `frame_idx` from per-instance age and `params.z`, six vertex-stage storage buffers.

`SpriteVisual` keeps a single render-key string (renamed `sprite` → `collection`, holding the id) plus the existing size/opacity/rotation/tint. Keep `derive_collection_id` in a location both install and the render/scripting write sites can call (a shared crate reachable from `postretro` and its systems); it takes only the asset reference and the raw contract inputs, so it has no renderer or GPU dependency.
