# Faction Sentiment as Game State

## Goal

Turn faction sentiment from immutable mod-init content into **mutable, decaying, persisted, replicated runtime game state**, and prove it with two consumers: an authored **reaction verb** (`setSentiment`/`adjustSentiment`) that story beats and player choices fire, and an **impact-policy effect** (`adjustSentimentToward`, chained on the damage-impact handles) that makes a backstab between sympathetic factions degrade their relationship — feeding the already-shipped sentiment-driven targeting so the degraded relationship erupts into a brawl. The engine owns the live sentiment table, its decay, its persistence, and its replication; mod authors own the events that move it and the rate it cools.

## Scope

### In scope

- A **live sentiment overlay** — an engine-owned mutable sparse table `(from_idx, to_idx) → current sentiment`, seeded empty (every pair at its authored baseline), holding only pairs currently diverged from baseline. Lives on `ScriptCtx` as its own `Rc<RefCell<_>>`.
- **Switch the AI read path** from the immutable baseline `FactionRegistry` to a live view that resolves overlay-over-baseline. Behavior-preserving while the overlay is empty.
- `setSentiment(from, to, value)` and `adjustSentiment(from, to, delta)` **consequential system-reaction verbs** (name-literal factions), fired from any reaction source — `levelLoad`, crossings, triggers, dialog-button `onPress` (a single-player player choice needs no new mechanism; in co-op a client-fired `onPress` has no host uplink in v1, so a sentiment-affecting choice must fire from a host-evaluated source — see Task 6).
- An `adjustSentimentToward` **impact-effect method** on the damage-impact handles — `impact.target.adjustSentimentToward(impact.source, delta)` and its source-chained mirror — receiver = "from" faction, argument = "to" faction; the engine resolves each handle's faction index at apply time and moves that directional pair by an author-supplied signed delta.
- **Author-tunable decay** easing each diverged pair back toward its baseline: a global default rate plus an optional per-pair `decay` override, seeded to zero (hold) so unauthored content never decays. A per-tick engine pass; entries reaching baseline are dropped.
- **Campaign persistence** of the diverged overlay, keyed by authored faction name plus collision-proof engine keys for the reserved player/default-enemy indices, surviving level unload and process exit and restored on load.
- **Co-op replication** of the overlay as host-authoritative shared state; clients converge on the host's live values; late joiners receive the current overlay.
- **Reference dev-mod content** exercising all of it: a story/trigger sentiment shift, an emergent backstab→brawl impact policy, a non-zero decay, and a persistence round-trip.

### Out of scope

- **Runtime faction *membership* change** (an entity switching factions mid-session). Unchanged from faction-crossfire's deferral; the per-entity `faction` field stays engine-mutable interim storage with no authored runtime faction-set verb.
- **Mutable tolerance.** Only *sentiment* is runtime-mutable here. The pair/archetype `tolerance` that gates retaliation (faction-crossfire) stays authored content; no `setTolerance` ships.
- **Authored faction durable identity.** Persistence keys authored factions by *name*. A faction renamed between sessions orphans its persisted sentiment, which is dropped with a warning (the ordinary malformed-value degrade path). Rename-stable authored faction keys — a later addition mirroring the store's `identity.json` mechanism — ship if a consumer needs them. The two engine-reserved faction indices use stable internal keys because they have no authored names.
- **A new author-readable sentiment fact.** `@candidate.sentiment` already exists (faction-crossfire); once the read path switches it observes the live value with no new fact. No new IR leaf is added.
- **Per-attack aggregate.** The emergent effect fires per *impact*; the `onDamage` per-attack rollup (roadmap Combat Feedback & Economy follow-on) is not required and not built here.
- **A general keyed-state primitive.** The overlay is a bespoke engine table, not a new author-facing keyed-map store type.
- **Sentiment value clamp.** v1 adds no authored `[min,max]` bound on sentiment: only the sign is load-bearing, and unclamped `adjustSentiment` overshoot stays correctly hostile/allied. An authored range bounding writes and decay is a later addition (`scripting.md` §1's "expose the axis") when a consumer needs it.
- **Non-linear decay.** Decay is linear (rate × `dt`, Task 4). An authored non-linear cool-off (e.g. an exponential curve) is deferred until a case demands it.
- **Reverse-pair write sugar.** Sentiment writes are directional and authors write both directions explicitly; a `setSentimentSymmetric(a, b, v)` convenience is left out of v1.

## Direction

**Problem.** Faction sentiment is authored once and frozen — `FactionRegistry` is built at mod-init and has no runtime mutator, and the AI reads it from an immutable `Ref<DataRegistry>`. So the relationship layer the game's fiction turns on (betrayals, alliances, grudges) cannot move: a story beat, a player choice, or an in-world betrayal can damage entities but can never change how factions *feel* about each other. The observation that produced this: faction-crossfire made sentiment *drive* targeting, which makes a mutable sentiment immediately legible as emergent behavior — but crossfire deliberately froze sentiment as content, leaving the game-state dimension unbuilt.

**Prior commitments.**
- Faction-crossfire (`context/plans/in-progress/faction-crossfire/`) scoped out "Runtime re-authoring of factions/sentiment" and kept sentiment riding the content-parity gate. **This spec is that deferred growth**, and it diverges on parity: once sentiment is mutable it is *state*, not content, so it replicates as host-authoritative state and leaves the content-parity hash (`mod_digest::hash_faction_registry`, over the baseline) untouched — the same split replicated mover phase already makes against static map content.
- `scripting.md` §11 impact-policy substrate: the effect set is "closed but extensible — a later spec that needs a new effect *adds* an arm." The `adjustSentimentToward` effect arm is exactly that addition; source-addressing is already exercised by `grantHealth`/`grantAmmo`.
- `scripting.md` §1: feel lives on a spectrum, engine seeds a default and exposes the axis. Decay rate and the per-pair sentiment deltas are the axes; the seeded defaults (zero decay, unchanged baseline) reproduce today's frozen behavior; a game that wants grudges to cool picks a rate through content.
- `scripting.md` §5/§12: mutable, persisted, replicated, host-authoritative state that authored reactions write. Sentiment matches that contract, but its faction-pair key is content-defined and (for the emergent case) a runtime value, which the static per-slot store cannot address — so it is an engine-owned table rather than store slots (see Alternatives rejected).

**Alternatives rejected.**
- **Live sentiment as durable store slots.** Reuses persistence/replication wholesale. Rejected: the store is strictly per-static-slot, so a faction-pair table forces one dotted slot per ordered pair; the emergent backstab can touch any pair and mid-session slot creation breaks the replication fingerprint, forcing all-N² pairs declared up front; decay is a sparse shrinking set that fixed slots cannot represent; and persistence demands `ownership == Mod` + a mint-identity ledger key that engine-synthesized pair slots cannot obtain. Grounded in `research.md` §"(a) vs (b)".
- **Mutate `FactionRegistry.relationship_overrides` in place.** Simplest write path. Rejected: decay-toward-baseline needs the baseline preserved, and in-place mutation destroys it. The baseline must stay immutable and the live value must be a separate overlay.
- **A bespoke `onFactionHarm` dispatch source for the emergent case.** Rejected by the owner: too specific. The impact-policy substrate already fires at the damage chokepoint with `source`/`target` tokens, so the emergent path is an *effect callable inside an ordinary impact policy* (`defineImpactEvent`), not a new event type.
- **Author-baked decay with a fixed engine rate.** Rejected per §1: it bakes one point on the spectrum. Decay is an authored scalar, seeded to zero.
- **Build the general keyed/dynamic-state substrate now, with sentiment as its first consumer** — a reusable author-facing keyed-map store type that would absorb this table plus any future pair-/key-addressed state. Rejected on proportionality and placement: the overlay is engine-owned authoritative state (like replicated mover phase), not mod-owned store state, so a *store*-shaped general primitive is the wrong home for it; and a general dynamic-state primitive is a large, unshaped design that would balloon this spec's scope for zero additional shipped behavior. The overlay is bounded and sparse (diverged pairs only), so its bespoke persist section and sync record stay small. If several engine-owned keyed-state tables later accrue (store slots, mover phase, this overlay), reconciling them into one substrate is a deliberate future consolidation — not a reason to over-build the first bounded consumer now.

**Placement.** The live overlay, its decay pass, its persistence section, and its sync record are engine-owned authoritative state. The authoring surface — the reaction verbs, the impact-effect method, the decay-rate scalar — is content (no rebuild). The AI's ranking/targeting ownership (§7c) is untouched; this changes only *which* sentiment value the existing filter reads.

## Acceptance criteria

- [ ] **AC1 — behavior-preserving empty overlay.** With no runtime sentiment writes, the full faction-crossfire and AI test suites still pass — behavior is preserved. The unit tests that call the renamed read fns (`is_hostile`, `target_offers`, `candidate_scope`) directly take the mechanical view-construction edit the signature change forces; no behavioral assertion changes, and the ~40 tests routing through `run_ai_tick_with_navigation` are untouched. The live view resolves every pair to its baseline value, and `is_hostile` / `@candidate.sentiment` / the offer filter behave exactly as against `FactionRegistry` today.
- [ ] **AC2 — reaction verb writes reach the AI.** After a `setSentiment("a","b", v)` reaction fires, the AI's next tick reads `v` for that directional pair (verified by a targeting outcome that flips when `v` crosses zero); `adjustSentiment("a","b", d)` moves the current live value by `d` (relative to the live value, not the baseline). An unlisted pair, written for the first time, reads its written value while its reverse pair still reads baseline (directional).
- [ ] **AC3 — verb is a consequential, host-authoritative reaction.** `setSentiment`/`adjustSentiment` classify as consequential (like `setState`), not presentation: fired from a trigger `on_fire` — or any source — they drain host-authoritatively at frame-end (the overlay is not a slot table, so even a trigger fire lands through the system-reaction drain, visible the next tick, not in-tick), and the write is host-authoritative: trigger, crossing, and `levelLoad` sources are host-evaluated, so their writes originate host-side and reach clients only through replication (AC7). A connected client's own local reaction fire writes nothing — a host-authority gate suppresses it (Task 6) — and, absent a client→host reaction uplink in v1, moves no shared sentiment.
- [ ] **AC4 — emergent impact effect.** An `impact.target.adjustSentimentToward(impact.source, delta)` effect inside a `defineImpactEvent` policy — the receiver handle is the "from" faction, the argument handle the "to" faction — when a damager of faction A hits a victim of faction B, moves the B→A live pair by `delta` (signed: negative degrades, positive bonds); the symmetric `impact.source.adjustSentimentToward(impact.target, delta)` moves A→B. Both faction indices are resolved from the two handle tokens at apply time; a hit whose `source` is absent (contextless damage) or whose source/target lacks a faction is a no-op. Verified for a same-faction hit and a cross-faction hit.
- [ ] **AC5 — backstab→brawl loop.** In the dev mod: two sympathetic-by-baseline factions, an impact policy that degrades A→B (and B→A) on harm, and a tolerance/sentiment configuration such that once the degraded pair crosses hostile, faction-crossfire's offer filter selects across the pair. A scripted A-hits-B backstab drives the pair hostile and A and B begin selecting each other as targets — the emergent brawl — with no engine stand-down rule.
- [ ] **AC6 — decay toward baseline.** With a non-zero decay rate, a diverged pair eases monotonically toward its baseline value over successive ticks and, on reaching baseline (within an epsilon), the overlay entry is removed (the table returns to sparse). Decay never overshoots baseline (a pair below baseline rises to it and stops; a pair above descends to it and stops). With the seeded zero rate a diverged pair holds indefinitely. A pair's decay rate resolves to its per-pair override when authored, else the global default.
- [ ] **AC7 — co-op replication.** A host-side sentiment change (reaction or impact effect) reaches every connected client so the client's live view matches the host's; a client that joins mid-session with a non-empty overlay receives the current diverged pairs. Clients hold no independent authority — the host's overlay is the source of truth, and the AI (host-authoritative) reads the host overlay.
- [ ] **AC8 — campaign persistence.** A diverged overlay saved on clean exit and reloaded restores the same directional pair values, across a level change within the playthrough. A pair that has decayed back to baseline is absent from the save (not persisted at baseline). A persisted pair whose faction name no longer resolves on load is dropped with a warning and does not abort restore.
- [ ] **AC9 — no double-application within a tick.** A pair written by both an in-tick impact effect and a frame-end reaction on the same frame reflects both writes deterministically (impact in-tick before the AI read, reaction at frame-end for the next tick), and two impact effects on the same pair in one tick apply in a defined order — neither is silently dropped.
- [ ] **AC10 — typedef surface.** The reaction verbs appear in the `postretro/ui` module surface and the impact `Effect` arm in the impact-policy surface; each added author-facing API — the `setSentiment`/`adjustSentiment` verbs, the `adjustSentimentToward` handle method, and the `decay` / `factionSentimentDecay` fields — carries short hover documentation in both SDK type surfaces (effect, value shape, the negative-degrades / positive-bonds sign convention, the seeded-zero decay default) per `scripting.md` §7; the committed typedef drift test and the impact-effect-arm-count / UI-function-inventory surface tests pass with the additions.

### Task 4: Author-tunable decay toward baseline

Add the per-tick decay pass and its authoring surface. Resolve a decay rate per pair: a global default authored on the manifest faction surface plus an optional per-pair `decay` on the authored sentiment entries (`FactionSentimentDescriptor` gains a `decay` field; `data_registry.rs` baseline resolves it like `tolerance`, and the manifest/SDK/typedef surface carries it — `sdk/lib/data_script.ts`/`.luau`, the sentiment-entry drain (`drain_faction_sentiments_js`/`_lua`, imported into `staged_manifest.rs`) for the per-pair `decay`, a new top-level manifest field plus its own drain for the global `factionSentimentDecay` default, the typedef template + regenerate). Seed the global default and every unauthored pair to **zero** (hold), so unauthored content never decays (AC6, and the behavior-preserving invariant). Invoke `FactionSentimentState::decay_step` once per authoritative tick from the fixed-tick loop in `simulate_tick` (`sim/mod.rs`), which a connected client skips entirely — so decay runs only on the host by construction and needs no explicit gate; the client overlay is a replication sink (Task 6) that converges on the host's post-decay set. Run it at the top of the tick's impact phase — before the pre-read impact stages (ready-hit ingest, projectile advance) as well as the AI read — under a `RefMut` released before the AI's immutable view borrow is taken, so decay eases the pre-write value and any same-tick impact then moves from the decayed value (the Orderings' decay-first ordering). The decay write and the AI read stay disjoint phases within the tick. Each diverged pair eases toward its baseline by its resolved rate × `dt`, clamped so it never crosses baseline, and is removed from the overlay when within an epsilon of baseline. A zero rate short-circuits (no accrual, entry unchanged) so the pass is provably inert for held content. A non-zero rate must always make progress toward baseline. Near baseline a per-tick step smaller than the baseline-removal epsilon still moves the pair, so it converges over successive ticks and is dropped once inside the epsilon band. But sentiment is unclamped (Scope), so the emergent brawl can drive a pair to a large overshoot magnitude where `rate × dt` falls below the value's floating-point ULP and a naive additive step is lost to rounding — stranding the pair above epsilon forever. Guarantee progress regardless of magnitude: accumulate the sub-ULP residue across ticks, or floor the effective step to the pair's ULP, so any non-zero rate eventually walks any diverged pair into the epsilon band and removes it. A small authored rate must never strand a diverged pair, whether near baseline or far from it (AC6). Test the far-from-baseline case, not only the near-baseline one. Test: a seeded diverged pair with a non-zero rate converges monotonically and is dropped at baseline; a zero-rate pair holds; per-pair override beats the global default (AC6).

### Task 5: Campaign persistence of the overlay

Persist and restore the diverged overlay across levels and process exit. Add a `faction_sentiment` section to `PersistedState` (`crates/postretro/src/scripting/state_persistence.rs`) as a map keyed by the directional authored faction *name* pair, with stable engine-reserved keys for player index 0 and default-enemy index 1, value the current sentiment. The reserved key namespace is forbidden to authored faction names, so identities cannot collide. Add collect (on the same clean-exit/periodic save path the slot sweep uses, gated by the existing `StateStoreLifecycle`) and overlay-restore functions: collect iterates the overlay's diverged pairs, maps each `(from_idx,to_idx)` back to its durable key, and writes the value; a pair at baseline is absent from the overlay so it is naturally absent from the save (AC8). Restore runs **once per session**, in the same restore pass as the slot sweep, gated by the existing `StateStoreLifecycle` (`should_restore_after_mod_init` / `mark_restore_completed`, which latches `restore_completed` after the first fresh-load restore) so it fires on the first mod-init commit of a load and **not** on the `replace_factions` commits an in-session level change routes through — Task 1's in-memory preserve owns those, and re-running restore there would re-apply the last on-disk overlay over the live one and clobber divergence accrued since the last save. Restore re-resolves each saved key to its current index and `set`s the overlay; an authored name that no longer resolves is dropped with a warning and does not abort the restore, matching the substrate's malformed-value degrade rule. The overlay restore is host/single-player only: unlike the per-owner slot restore, which the shared pass runs on a connected client too, the overlay is host-authoritative shared state that a joining client receives through Task 6's replication, not from its own disk. Skip the overlay restore when the endpoint is `NetEndpoint::Client`, so a client that happens to hold a local campaign save for this mod never writes divergence into its own overlay — every client-side overlay value arrives through replication (AC7). This keeps restore inside the host-authoritative writer set with impact, decay, and the gated reaction drain. Bump `CURRENT_STATE_VERSION` and handle the older-version file (no faction section → empty overlay). Test: save authored and reserved diverged pairs, restore, assert all round-trip; a decayed-to-baseline pair is absent; an unresolvable saved authored name is dropped without aborting; an older-version save file with no `faction_sentiment` section restores to an empty overlay without error (the `CURRENT_STATE_VERSION` migration path).

### Task 6: Co-op replication of the overlay

Replicate the overlay host→client as host-authoritative shared state. Add a dedicated sparse sync record carrying diverged pairs as `(from_idx: u16, to_idx: u16, value: f32)` (a new record type/section in the netcode state path — `crates/net/src/state_slots.rs` for the wire type and `crates/postretro/src/netcode/state_slots.rs` for host produce / client apply — kept separate from the per-slot `StateSlotDescriptor` schema, which does not fit a dynamic sparse set). The live overlay itself enforces the transport envelope before every write: faction indices must fit `u16`, values must be finite, and at most 4,096 pairs may diverge. Existing baseline relationships beyond that mutable envelope remain valid immutable content. Snapshot production caches the lowered pair vector by overlay mutation generation, rebuilding only after a write or removal. Bump `SNAPSHOT_VERSION` for the added snapshot record — per `networking.md` §Version gates it bumps when a change lands on the snapshot record itself, and this new record is one. The snapshot record is a bitcode wire type folded into the handshake `protocol_id`, so adding one bumps `WIRE_VERSION` too: every prior snapshot-record change did — mover replay provenance and the `blocked` phase each advanced both constants — and that `protocol_id` change is what refuses earlier peers at the handshake. `SNAPSHOT_VERSION` itself is not a handshake gate; it is validated at snapshot decode. The Input-channel `ClientMessage`/`ServerMessage` vocabulary is unchanged. Host: after the tick, emit the current diverged set (full-set baseline for a joining client; delta for steady state, reusing the existing baseline/delta/ack cadence). Client: apply the received set into its `faction_sentiment` overlay (all-or-nothing, like `apply_store_slot_batch`), so the client's `LiveFactionSentiment` view matches the host; a pair absent from a host delta because it decayed to baseline is removed on the client. Clients never write the overlay from local reactions, impact effects, or the decay pass — every overlay write is host-authoritative (AC3, AC7). The reaction drain (Task 2) and the overlay restore (Task 5) are the two overlay writers whose code path also reaches a connected client, so each is gated host-only rather than host-only by construction. The drain runs on a client because clients compose reaction descriptors for presentation — gate that write with `script_ctx.owner_slot_writes_enabled.get()`, the flag set false for a connected client at `session/mod.rs` from `NetEndpoint::Client` (already the command-apply guard on `trigger_commands.rs`'s `AddOwnerSlot` arm), reachable through the `ScriptCtx` the drain holds; a client's local `onPress` fire evaluates but writes nothing. This task owns that gate on the Task 2 reaction-drain arm (built in Phase 1, before this task); Task 5 owns the parallel restore gate that skips the overlay restore when the endpoint is `NetEndpoint::Client`. The Task 3 impact applier and the Task 4 decay pass, by contrast, run only inside the host's `simulate_tick`, which a connected client skips, so they are host-authoritative by construction and carry no per-site gate. Trigger, crossing, and `levelLoad` sources are host-evaluated, so their sentiment writes originate host-side and reach clients only through this replication. A client-local dialog `onPress` `setSentiment` has no host uplink in v1 — the Input channel carries no reaction command (`networking.md` §Channel model) — so it moves no shared sentiment; a sentiment-affecting player choice must be authored on a host-evaluated source, and a client→host reaction uplink is deferred. The overlay is state, not content, so it does not enter `mod_digest::hash_faction_registry` (parity is over the baseline only). Test (host + client harness): a host write appears on the client; a mid-session join receives the current diverged set; a decayed pair clears on the client; and a client-local reaction fire (a dialog `onPress` `setSentiment`) evaluates but writes no overlay entry — the host-authority gate suppresses it (AC3, AC7).

### Task 7: Reference content and integration proof

Author dev-mod content exercising every surface and lock it with an integration test. In `content/dev/scripts/` (composed through `content/dev/start-script.ts`, mirrored in Luau where applicable): declare two factions that are sympathetic (neutral-or-allied) by baseline but whose tolerance/sentiment configuration means a degraded pair becomes a selectable crossfire target (building on faction-crossfire's offer filter); an impact policy (`defineImpactEvent`) whose harm effect chains `impact.target.adjustSentimentToward(impact.source, <negative>)` and the source-chained reverse to degrade the pair both ways; a non-zero `decay` so the grudge cools; and a story trigger firing `setSentiment`/`adjustSentiment` for the scripted-beat and player-choice cases. Integration test asserting AC5 and the round-trip: a scripted A-hits-B backstab through the full fixed-tick projectile path drives the A↔B pair hostile on the impact tick, A and B then select each other (the brawl), decay eases the pair back toward baseline over subsequent ticks with no further harm, a `setSentiment` beat overrides it, and a save/restore across a level change preserves a diverged pair. The harness also proves AC9: two impact effects degrading the same pair on one tick both apply in impact-dispatch order with neither silently dropped, and a pair written by an in-tick impact and a frame-end `setSentiment` on one frame reflects both writes deterministically — the impact before that tick's AI read, the reaction visible on the next tick. This is the consumer that proves the foundation: if the authored verbs plus the impact effect cannot produce the brawl and survive a round-trip, an earlier task is wrong.

The reaction-verb wire spellings mirror the existing camelCase system reactions (`flashScreen`, `setState`); the impact-effect wire primitive string mirrors the existing effect arms (`grantHealth`, `slot.set`). The two authoring surfaces are deliberately distinct in name and shape: the reaction is a top-level, name-literal verb (`adjustSentiment("cabal","resistance", d)`, `postretro/ui`), while the impact effect is a chained handle method (`impact.target.adjustSentimentToward(impact.source, d)`, `postretro` impact effects) whose receiver is the "from" faction and argument the "to" faction — so the direction reads from the call site rather than from token argument order. ## Orderings

The overlay is mutable state written by two event kinds (reaction, impact) and a timer (decay), and read by the AI. Scenarios the implementation must resolve, cited by the Task 4/7 tests:

| Scenario | Ordering | Expected outcome |
|---|---|---|
| Projectile impact write vs AI read, same tick | Projectile impacts write in the projectile stage (`sim/mod.rs`), upstream of the AI read; the read view holds no overlay borrow at that point | The AI reads the post-write value on that tick — a projectile backstab can flip hostility same-tick (AC4, AC5) |
| AI-fired impact write, same tick | An AI attack applies `adjustSentimentToward` inside `apply_outcomes`, after the read and after the transient view `Ref` is released | The write lands with no borrow overlap; the AI observes it on the *next* tick, not the firing one (AC4, AC5, AC9) |
| Hitscan / mover-crush impact write, same tick | Local-weapon and mover-blocking impacts write after the AI read; ready-hit ingest (co-op remote authorized hits) and projectile advance write before it (`sim/mod.rs`) | Local-weapon and mover-crush land for the next tick; a projectile *or* a ready-hit-ingest impact is same-tick-visible — the two pre-read stages are ready-hit ingest and projectile advance, so a remote hitscan backstab flips hostility on the host that same tick, not only a projectile one (AC4) |
| Two impact writes to one pair, different stages | Projectile-stage and AI-apply-stage writes to one directional pair in one tick | Both apply in stage order; same-stage hits apply in FIFO dispatch order; none dropped (AC9) |
| Non-trigger reaction write vs AI read | `setSentiment`/`adjustSentiment` from `levelLoad`, a crossing, or a named fire drains at frame-end (consequential), after the tick | Takes effect on the next tick, not the current one (AC2) |
| Trigger `on_fire` reaction write vs AI read | A trigger `on_fire` `setSentiment`/`adjustSentiment` enqueues a system-reaction command that the frame-end system-reaction drain applies to the overlay after the authoritative tick returns. Unlike `setState`, whose in-tick trigger path writes the tick-context *slot table*, the overlay write is not a slot write and is not in the trigger binder's in-tick consequential-primitive set, so it never lands at the trigger stage — the drain owns it | Frame-end drain after the tick's AI read; the AI observes it on the *next* tick, exactly like a non-trigger reaction write. A trigger fire buys no same-tick visibility over a crossing or `levelLoad` fire (AC3, AC9) |
| Decay vs write, same tick | Decay runs once per tick upstream of the AI read; a write may also land that frame | Decay eases the pre-write value; a same-frame impact write then moves from the decayed value (deterministic: decay first, in-tick impact next, frame-end reaction last) (AC6, AC9) |
| Decay reaches baseline | A diverged pair eases to within epsilon of baseline | The overlay entry is removed; the pair reverts to baseline resolution and to absence from persistence/replication (AC6, AC8) |
| Adjust overshoots baseline via decay | Decay would step past baseline in one tick | Clamp to baseline exactly, then remove — never overshoot to the far side (AC6) |
| Write involving the player faction | `source` or `target` resolves to `PLAYER_FACTION_INDEX` (0), or a verb names no faction that maps to the player | The pair is written like any other index pair; the AI already treats player-vs-enemy via sentiment, so no special case — but the player pawn carries no authored faction name, so a name-literal verb cannot target it (only the impact effect, via the token, can involve index 0) |
| Contextless / faction-less impact | `dispatch.source == None`, or a recipient lacks the `faction` field | The `adjustSentimentToward` effect no-ops (no pair to move), matching the ledger's contextless-hit rule (AC4) |
| Save while a pair is decaying | Clean exit mid-decay | The current (mid-decay) value persists; restore resumes decay from it. A pair already at baseline is absent from the save (AC8) |
| Restore with a renamed faction | A persisted name pair no longer resolves against the loaded baseline | Dropped with a warning; restore continues for resolvable pairs (AC8) |
| Co-op join with non-empty overlay | A client joins after host-side divergence | The client receives the current diverged set as a baseline sync and its view matches the host (AC7) |
| Client-fired verb | A connected client's local reaction fires `setSentiment`/`adjustSentiment` | No local authority: a host-authority gate suppresses the client write (Task 6), and v1 carries no client→host reaction uplink, so a client-local dialog `onPress` moves no shared sentiment. Host-evaluated sources (trigger, crossing, `levelLoad`) originate all sentiment writes host-side and replicate to clients (AC3, AC7) |

## Invariants

| Invariant | Established by | Preserved / threatened at | Verified by |
|---|---|---|---|
| Baseline stays immutable; live = overlay-over-baseline | Task 1 (separate overlay type; view resolves overlay-then-baseline) | Any write path mutating `FactionRegistry.relationship_overrides` instead of the overlay would destroy the decay target | AC1, AC6 |
| Empty overlay is behavior-preserving | Task 1 (empty seed), Task 4 (zero default rate) | A non-zero default rate or a seed that diverges a pair without authoring | AC1, AC6 |
| No overlay borrow spans an overlay write within a tick | Task 1 (view `Ref` built for `compute::evaluate` and dropped before `apply_outcomes` runs `on_impact`), Task 4 (decay `RefMut` taken and dropped before the view `Ref`) | `on_impact` runs mid-tick at five stages (`sim/mod.rs`: ready-hit ingest, projectile advance, AI `apply_outcomes`, mover-blocking, local-weapon); an `adjustSentimentToward` applier takes a `RefMut` at any of them, and AI-initiated attacks fire it *inside* the AI call after the read. A view `Ref` held across the tick — or across `apply_outcomes` — is a RefCell double-borrow panic. The view borrow must not outlive the read that uses it | AC1, AC4, AC9 |
| Sentiment is state, not content; replicates, does not gate parity | Task 6 (host-authoritative sync; overlay excluded from the compat hash) | Adding the overlay to `hash_faction_registry`, or a client writing its own overlay | AC7 |
| Diverged set is sparse; at-baseline pairs are absent everywhere | Task 1 (remove-at-baseline mutator), Task 4 (decay removal) | A pair left in the overlay at its baseline value would persist and replicate needlessly and never decay-remove | AC6, AC8 |
| Decay eases toward baseline and never overshoots | Task 4 (clamp-to-baseline step + epsilon removal) | A step that crosses baseline, or a rate applied without `dt` scaling | AC6 |

## Script syntax examples

```ts
defineMod({
  factions: [defineFaction("cabal"), defineFaction("resistance")],
  sentiment: [
    // baseline: sympathetic (neutral), a slow grudge-cooling decay.
    sentiment("cabal", "resistance", { sentiment: 0, tolerance: 5.0, decay: 0.1 }),
    sentiment("resistance", "cabal", { sentiment: 0, tolerance: 5.0, decay: 0.1 }),
  ],
  factionSentimentDecay: 0,          // global default: hold (unauthored pairs never decay)

  // Emergent: a backstab sours the victim's faction on the attacker's; crossfire targeting does the rest.
  // The builder param IS the reusable handle — destructure it and chain effects off each party.
  events: [
    defineImpactEvent("factions:crossfire", { /* filter */ }, ({ target, source, amount }) => [
      { when: amount.gt(0), do: [
          target.adjustSentimentToward(source, read(amount).times(-0.01)),   // victim's faction → attacker's
          source.adjustSentimentToward(target, read(amount).times(-0.01)),   // and reciprocate, for a two-sided brawl
      ]},
    ]),
  ],
});

// Story beat / player choice — factions are author-time names.
onStateCrossing(getGameState().quest.betrayedResistance, { above: 0.5 }, [
  setSentiment("cabal", "resistance", -1),   // absolute flip to hostile
]);
// a dialog button firing adjustSentiment("resistance", "cabal", -0.3) is the same path.
```
