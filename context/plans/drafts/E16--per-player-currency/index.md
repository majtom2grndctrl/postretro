# Per-Player Currency (E16)

## Goal

Mod state has exactly one cardinality — global — so any mod-declared currency is team-shared in co-op. Give a store slot **per-owner cardinality**: an author declares whether a slot holds one value for the session or one value per player. `E15--seat-session-identity-roster` (shipped) already mints the owner identity this needs — a **seat** that survives level transitions and a disconnect-and-rejoin, keyed above the pawn and connection ids the engine addresses per-player state by today. This spec extends that seat's storage with per-owner slot values, and gives owner-addressed writes a way to reach one from an impact policy and from a reaction. The engine gains no currency, only the capacity to hold one per player.

Session-scoped. Saving a per-player value to disk and carrying it into someone else's session is `E16--per-player-persistence`, which sequences after this.

## Prerequisites

- **`E15--seat-session-identity-roster`** (shipped) — mints the `Seat` identity and the `SeatTable` this spec keys per-owner slot storage by: seat-to-pawn and seat-to-connection lookups, the disconnect hold window, and reclaim-by-player-id. This spec adds per-owner slot storage to that table; it mints no identity of its own.
- **`E16--resource-grant-chokepoint`** (shipped) — established source-addressed effect application: a planned command carries the token it addresses rather than assuming the dispatch target, and the bind guard becomes an expected-token checker. The owner-addressed `slot.add` here is the second consumer of both.
- **Epic 15 Phase 3.5** (shipped) — the owner-private replication scope, whose wire tracker already keys values by slot and owner, and which rejects `ownerPrivate` for mod stores today with the diagnostic "not supported for mod stores yet (no per-player authoring namespace exists)." This is that namespace.
- **`E16--impact-policy-substrate`** (shipped) — the `slot.add` effect this gives a target token, and the evaluate-then-apply snapshot model its reads obey.
- **`descriptor-identity-and-naming-sugar`** (shipped) — reserved the colon in authored impact-event ids for engine mod-qualification, and split a descriptor's durable identity from its authored name so a rename stops orphaning saved data. This spec's `defineImpactEvent` uses the single-segment authored id that change requires, and its new `perOwner` slots are declared through the final authoring surface that spec settled — so currency is authored once here, not migrated when identity lands.

## Scope

### In scope

- **Per-owner slot cardinality** — a mod slot declares `perOwner: true`; its record holds one value per shipped `Seat` instead of one global value. A per-owner slot's storage is keyed by that `Seat`, so a value survives a disconnect and a reclaim within the seat's existing hold window exactly as the seat's carried engine state does, and is dropped at hold expiry alongside it.
- **Owner-addressed writes** — a target token on the shipped `slot.add` so an impact policy can credit the damage source, plus a tag/activators-targeted reaction primitive so a trigger, crossing, or level-load reaction can credit a set of players.
- **Owner-addressed reads** — a policy reads a per-owner slot against an explicit owner token.
- **Publish paths** — host and single-player through the HUD slot publisher resolving the local seat; connected clients through the owner-private replication projection, which today serves one global value to every owner for a mod slot.
- **Reference per-player XP** in the dev mod, beside a shared counter, so the authoring choice is visible in one file.

### Out of scope

- **Persistence and the join seed** — `E16--per-player-persistence`. Both need decisions this spec should not smuggle: a connected client does not write the save file today (a shipped Phase 3.5 rule), and a client-to-host state write is a stated Phase 3.5 non-goal. Reversing either is deliberate work with its own Direction, and neither is needed for a per-owner currency to work within a session. Consequence, stated plainly: per-player XP survives a disconnect only within the seat's hold window; it does not survive past hold expiry, and does not survive to disk, until that spec lands. `persist: true` on a per-owner slot is rejected at load until then, not silently ignored — see Decisions.
- **Cross-device or account identity.** A seat is session-scoped, per `E15`. A player who disconnects starts the seat's existing hold; a rejoin within that window reclaims the same seat and its per-owner values, exactly as it does for engine-carried state. A rejoin after the hold expires is a new seat at declared defaults.
- **Source-addressed per-entity state.** Nothing here writes another entity's per-entity state, so `scripting.md` §11's same-entity seam is untouched and `E10--enemy-aggro-model`'s cut rationale stays intact.
- **Non-player owners.** Seats belong to players. An enemy's own counter stays per-entity state, which already ships.
- **Per-key / per-category slots.** `xpByWeapon.shotgun` needs a per-key mechanism that does not exist.
- **Client-authored writes and prediction.** The host is authoritative; a client receives values.
- **Engine-owned resources.** Health and ammo belong to `E16--resource-grant-chokepoint`.
- **Exact integer currencies past 2^24.** Slots are `f32`; a currency beyond ~16.7M silently rounds. `scripting.md` §5 already notes exact integer slots would need their own state-store and replication contract.
- **Per-client re-fire of `levelLoad` for a late promoter.** `levelLoad` fires once at install (`scripting.md` §12); a join-time per-player award is a different event source, demand-gated.

## Direction

**Problem.** A mod currency can only be a global store slot, so in co-op every player shares one pot. The cause is store cardinality — which is why the fix belongs to the store rather than the damage path. `E15--seat-session-identity-roster` already closed the identity gap underneath it: the seat is a player identity that outlives a level and a disconnect. This spec's only remaining cause to fix is that no store slot can be keyed by it yet.

**Prior commitments.**
- *The spelling was reserved for this.* Phase 3.5 allowed mod slots `network: "shared"` and rejected `network: "ownerPrivate"` in code with the diagnostic "no per-player authoring namespace exists." This supplies the namespace and unlocks the rejection.
- *The wire already has this cardinality.* The replication tracker keys values by slot and owner, and the owner-private resolver dispatches per-owner projections ahead of a global fall-through. Per-owner mod slots extend that shape: a declaration-driven lookup added ahead of the existing name-dispatch chain, not a replacement of it.
- *The store outlives level unload* (`scripting.md` §5). Honored by keying to the shipped seat: a per-owner value is addressed by something that outlives the level, so a per-owner slot obeys the same durability contract a global one already does. **Two earlier shapes of this spec violated this** — first backing a slot with a pawn-scoped field, then keying to the existing within-level player id — both invalidated by level unload. `E15--seat-session-identity-roster` shipped the durable key this spec needed; this draft extends that key's storage to per-owner slot values rather than minting a second one.
- *The seat already carries state across a disconnect.* E15's `SeatTable` holds a `CarriedState` per seat and restores it on reclaim within a hold window, dropping it only when the seat is released — at expiry, or when a live reclaim displaces a stale duplicate hold. A per-owner slot value rides the same window: it is neither cleared at disconnect nor restored by any new mechanism, because it stays keyed by the same `Seat` for the window's duration. Release, at both points `CarriedState` is already dropped, is the hook this spec adds.
- *Currencies are mod-owned* (`combat-events.md` §2). The engine gains cardinality, not XP.
- *Fan-out needs tag targeting.* `E16--resource-grant-chokepoint` established that the IR has no iteration, so reaching several recipients in one fire is only expressible through tag or activators targeting. The reaction write path is not optional here either.
- **Divergence, named:** `scripting.md` §12 states store slots are ambient and ambient refs do not enlarge a reaction's dispatch scope. An owner-addressed read binds an ambient store slot against an ephemeral dispatch token, so a per-owner read *does* enlarge the scope and cannot appear in a sourceless reaction. Deliberate: per-owner values have no meaning without an owner, and the alternative — an implicit owner — is a wrong-owner bug. Global slot reads are unaffected. `scripting.md` §12 wants this recorded at promotion.

**Placement.** Cardinality is a property of the slot, so it lives on the slot. The rejected alternative — backing a per-player slot with a field on the player's pawn — put cardinality in the impact layer, which made the currency non-persisting, readonly, and awardable only by dealing damage. All three fell out of the placement. The slot table stays in the entities floor crate; the key it now keys by, `Seat`, lives in `foundation` (`E15`), which `entities` already depends on, so no new crate edge opens. The seat *table* — the hold window, reclaim, and connection bindings — stays in the binary's `netcode` module where E15 placed it; this spec's per-owner storage lives beside the slot table it extends, addressed by seat value alone. Owner *resolution* — which seat a pawn belongs to, for effect apply, reads, and reactions — is read from the registry, not the binary-only seat table: entity-to-seat consumers sit in layers (impact-effect apply, an owner-addressed read's binding scope, reaction dispatch) that see a registry and an entity, never `SeatTable`. The registry already owns that association — `EntityRegistry::seat_for_pawn`, written through the single `SeatTable::set_pawn_binding` chokepoint — so this spec consumes it rather than building one.

**Alternatives rejected.**
- *Fusing cardinality into `network: "ownerPrivate"`* — one key meaning both "one value per player" and "replicated privately." Tempting because Phase 3.5 reserved that spelling and because the two coincide for the motivating case. Rejected: the axes are orthogonal, and fusing them makes a per-player slot the HUD never shows — host-side bookkeeping — inexpressible, along with any future shared-but-privately-delivered value. Phase 3.5 reserved a *spelling* for when a namespace existed; it did not decide the two concepts were one. Cardinality gets its own declaration and `network` stays purely about replication.
- *A slot as a view of a per-entity state field on the owning pawn* — an earlier draft, reworked after review. The value could not persist (components die with the level), could be earned only by dealing damage (per-entity state has one write site, inside an impact policy), and fused cardinality with backing.
- *Host issues reward deltas; the client accumulates its own total.* Better trust story, but reward policy evaluates host-side, so a policy reading a currency ("double past level 10") could not see it.

## Decisions

- **This spec mints no seat.** `E15--seat-session-identity-roster` already mints, re-binds, and reclaims the seat; per-owner slot storage keys by that shipped `Seat` and by nothing else. The engine's existing per-player state keeps using the id it uses today for its own consumers (trigger occupancy, use edges, alive players) — this spec does not rewrite those call sites.
- **`Seat` never appears in the authoring surface.** A script addresses an owner by token; the seat is resolved host-side. The key stays an engine-side detail, so `E16--per-player-persistence` can re-key per-owner records to a durable identity without touching a script. `byPlayer` is named for the identity a value belongs to, not for today's key — a seat is session-scoped, so a name built on it would have to change when that spec lands.
- **Owner resolution goes through the registry, not through `SeatTable`.** Impact-effect apply, an owner-addressed read's binding scope, and reaction-primitive dispatch each see only a registry and an entity, never `SeatTable`. The registry already answers this: `EntityRegistry::seat_for_pawn` resolves a pawn's current seat, kept current through the single `SeatTable::set_pawn_binding` write path and dropped on despawn. Every consumer resolves an owner the way it already resolves any other per-entity fact — this spec reads that association, it does not build one.
- **A per-owner slot value rides the seat's existing hold window.** A disconnect starts the seat's hold as it does today; a per-owner slot's storage is untouched during the hold, because it stays keyed by the same `Seat` throughout. A reclaim within the window resumes the same seat and the same values with no restore step, because nothing was ever moved. Expiry releases the seat and, alongside it, its per-owner slot values across every store; a rejoin after expiry is a new seat at declared defaults, matching `CarriedState`'s own expiry behavior.
- **Release clears per-owner storage from both places a seat is actually released.** `SeatTable::release_seat` is reached by hold expiry and, independently, by a live reclaim's stale-duplicate-hold cleanup — missing either leaks a seat's per-owner values forever, since seat numbers are never reused. Both call sites surface the seat they released; the caller, which holds the store handle `SeatTable` itself doesn't, clears that seat's per-owner entries across every store in the same call.
- **Per-owner storage is host-only.** A client holds no `SeatTable` and runs none of the host-only policies or reactions that use owner-addressed access. A client's local record for a `perOwner` slot is a plain scalar — its own resolved value, written by the existing snapshot-apply path — never a seat-keyed map.
- **Cardinality and replication are separate declarations.** `perOwner: true` selects per-seat storage; `network` continues to mean only how a value reaches clients. `network: "ownerPrivate"` requires `perOwner: true` — a single global value fanned privately to each owner is meaningless and is a load error. `perOwner: true` alone is legal and means host-local per-player state.
- **`perOwner` combined with `accumulate` is a load error.** An accumulate expression evaluates once per tick against a single value today; per-seat evaluation is a mechanism this spec doesn't build.
- **`perOwner` combined with `persist` is a load error, for now.** `persist`'s save path reads a slot's single scalar value; a per-owner record has none. Left unrejected, an author's `persist: true` on a currency slot would silently lose it every level unload — the worst version of the expectation gap this spec otherwise names plainly. The spelling is reserved the way Phase 3.5 reserved `ownerPrivate`: `E16--per-player-persistence` unlocks it.
- **Writes and reads are owner-addressed.** A per-owner slot's map is written and read only through an owner-addressed ref — the `ref.byPlayer(token)` form. **An access to a per-owner slot without `byPlayer` fails at bind, naming the slot and the offending policy or reaction**, rather than resolving to a default owner — an implicit owner is a wrong-owner bug that surfaces as one player's rewards landing on another. `byPlayer` on a global slot is equally an error. A failing descriptor is skipped, per shipped bind behavior — sibling policies and reactions still bind. A per-owner slot's retained scalar `value` — the local seat's projection, refreshed by the publisher or by client snapshot-apply — is a plain slot value like any other: `bindState` and the HUD publisher read it exactly as they read a global slot's value, and neither is owner-addressed access. The host's owner-private replication *projection* is the exception — it resolves each owner's seat-keyed entry (Task 4), not this retained scalar; reading the scalar there would serve the host-local player's value to every client.
- **`slot.add` gains a target token; its untargeted form is unchanged.** An absent token means the global slot exactly as today, so every shipped policy keeps working. This modifies a shipped effect arm rather than adding one — the widest blast radius here, and why the untargeted path must stay behaviorally identical.
- **A recipient with no seat is skipped with a warning.** An owner-addressed write resolving to an enemy, a prop, or a player mid-disconnect writes nothing and does not abort sibling effects. Distinct from the shipped silent skip for an absent or stale source, which stays silent — the warning is new, and only for a recipient that resolved to an entity with no seat.
- **An owner-addressed read whose token resolves to no seat returns the slot's declared default, and warns.** The §11 evaluator is total and must produce an `f32`, so a resolver miss — an enemy, a prop, a player mid-disconnect, or a pawn not yet seat-bound — yields the declared default rather than an undefined value or another seat's, symmetric with the write-side skip. Warned, not silent.
- **Reads observe the per-fire frozen snapshot**, like every other store read in a policy, so a gate never sees a write from its own fire.
- **No wire version change.** Per-owner values ride the existing owner-private replication path, and the replicated-schema fingerprint is content-derived, so adding slots costs no constant bump. The join seed — which would cost both the app-protocol and wire constants — is the other spec.
- **The UI is untouched.** Widgets bind by slot name and receive the local player's value; resolution happens in the publisher and the replication projection.

## Acceptance criteria

- [ ] A slot declared per-owner holds independent values for two players: crediting one leaves the other unchanged, in the same session.
- [ ] **A per-owner value survives a level transition** — after a level change or a single-player restart, a per-owner slot reads what it held before, exactly as a global slot does.
- [ ] An impact policy credits the damage source's own value; a reaction credits every activator that entered a trigger volume, and a tag-targeted reaction credits every matching player.
- [ ] A currency is awardable without dealing damage — a trigger volume, a crossing, and a level-load reaction each credit a per-owner slot. The level-load leg credits pawns live at install — the local player, and any already-spawned pawn; a client that promotes into an already-installed level misses that level's level-load award, because `levelLoad` fires once, at install. Re-firing it per late joiner is not a mechanism this spec builds.
- [ ] `network: "ownerPrivate"` declared without per-owner cardinality, `perOwner` declared alongside `accumulate`, and `perOwner` declared alongside `persist` each fail at mod-init with a diagnostic naming the slot. Per shipped store-declaration validation, this rejects the whole declaration set atomically — the manifest does not partially load.
- [ ] A bare read or write of a per-owner slot, and an owner-addressed access to a global slot, each fail at bind with a diagnostic naming the slot and the offending policy or reaction. Per shipped bind behavior, this skips only that descriptor — sibling policies and reactions still bind.
- [ ] A slot declared per-owner without a replication scope holds independent per-player values host-side and is not replicated.
- [ ] An untargeted `slot.add` on a global slot behaves exactly as before — the shipped dev-mod policies that use it are unchanged.
- [ ] An owner-addressed write resolving to a non-player entity writes nothing, warns, and leaves sibling effects in the same fire applying normally.
- [ ] An owner-addressed read whose token resolves to a non-player entity, or to a pawn with no seat yet, returns the slot's declared default and warns — never another seat's value, never an undefined one.
- [ ] A policy whose reward amount reads the same per-owner slot it credits observes the pre-fire value, not its own write — two hits in one tick accrue both increments.
- [ ] In co-op, each client's HUD shows only its own value; a second client's value never leaks across, including for a late joiner.
- [ ] A per-owner value survives a disconnect and a reclaim within the seat's hold window, unchanged; a rejoin after the hold window expires starts that per-owner slot at its declared default, and does not inherit the expired seat's prior values.
- [ ] A player holding two matching seats — a stale disconnected hold and a fresher one that wins reclaim — has the stale seat's per-owner values cleared at the moment the fresh one wins, not merely at expiry; the winning seat's own per-owner values are unaffected.
- [ ] Reference walkthrough: the dev mod awards per-player XP on a kill and increments a shared counter in the same policy; across two clients the XP readouts diverge while the shared counter agrees, and the only difference in the script is which slot each writes and whether that write is addressed with `.byPlayer(impact.source)`.

## Tasks

### Task 1: Per-owner slot storage on the shipped seat

Add a per-seat storage mode to the entities floor crate's slot table (`slot_table.rs`), keyed by the shipped `Seat` type (`crates/foundation/src/seat.rs`) rather than any new identity — `entities` already depends on `foundation`, so no new crate edge opens. A per-owner slot's record becomes a map from `Seat` to a value on the host, alongside the record's existing scalar `value` field, which the host keeps too: any read that doesn't address an owner — the UI snapshot, `bindState`, a crossing watcher — sees whatever the publisher last wrote there (Task 4), the local seat's projection. Only owner-addressed reads and writes touch the map. A client's local record for the same declared slot stays that plain scalar alone, since a client holds no `SeatTable` and never runs the host-only paths that access the map owner-addressed (see Decisions). The declared default serves any seat not yet written; a global slot's record is unchanged.

Resolving *which* seat a write or read addresses reads the registry, never the binary-only `SeatTable`: impact-effect apply, an owner-addressed read's binding scope, and reaction-primitive dispatch each see only a registry and an entity. `EntityRegistry` already carries the association — `seat_for_pawn(pawn)` over a `pawn_seats` map, written through the single `SeatTable::set_pawn_binding` chokepoint (reached by `bind_pawn`, `hold_disconnected_client`, and level-unload clearing) and dropped on despawn — so this spec consumes it and builds no mirror. `release_seat` deliberately does not touch that association: the pawn is already unbound at the hold edge, so the association is gone by release, and the per-owner *store* clear below keys by the released `Seat` value directly, not by a pawn lookup. Task 3's write paths and Task 4's read form resolve an owner by reading `seat_for_pawn` off the registry, the way any other per-entity fact is read.

Today the `levelLoad` fire runs inside `install_world_cpu` while `bind_pawn(Seat(0), …)` runs after it returns — a level-load award would skip-warn the local player. Add a pre-`levelLoad` hook to `install_world_cpu`, the `upload_mesh_models` shape, and move the existing `capture_player_spawn_placements` + `bind_pawn(Seat(0), …)` pair into the caller's closure — move the pair together, not the bind alone, since `bind_pawn` reads the placement `capture_player_spawn_placements` populates. Moving the pair before the fire populates `seat_for_pawn` in time, through `set_pawn_binding`; there is no separate mirror write. The pawn and the spawn-point products exist by the hook point, since the archetype sweep precedes the fire inside the installer's own ordering. The installer stays seat-table agnostic — the closure captures the table caller-side — and the post-install bind site is removed, not kept as a second writer. A remote pawn spawns at re-promotion, after install, and no bind-vs-dispatch ordering can reach it — see AC 4's scope.

Wire per-owner slot release to both places a seat is actually released, not just one: the expiry sweep in `release_expired_holds`, and the stale-duplicate-hold cleanup inside `admit_or_reclaim` when a live reclaim displaces an older held duplicate. Have `release_seat` surface the seat(s) it releases, and thread that up to the app-level callers that hold the store handle `SeatTable` itself doesn't — not a single caller. The expiry path surfaces through `release_expired_holds` → `finish_host_poll`, which has four production call sites; the reclaim path surfaces through `admit_or_reclaim`, which has two. Every one of those six sites must clear the released seat's per-owner entries; funnel them through one app-side clear helper so no path is missed. Clear each released seat's per-owner entries across every store at that call, not before. Do not clear per-owner slot values at `hold_disconnected_client` — the value stays associated with the seat for the hold window's duration by construction, since it is keyed by `Seat` and nothing removes that key until release. A reclaim within the window needs no restore step: `admit_or_reclaim` already rebinds the same `Seat` to the new connection, and the per-owner slot storage was never touched. Single-player has exactly one seat (`Seat(0)`, never held or released) and no path branches on player count. This same call site — the caller that clears a released seat's per-owner storage — is where `E16--per-player-persistence` will later capture a departing seat's values before they're dropped; keep the clear there rather than distributing it, so that later hook has one place to land. Assert the fourth Ordering pins row here.

### Task 2: Per-owner slot cardinality

Give the slot schema the declaration that selects Task 1's per-seat storage. A mod slot may declare per-owner cardinality; its record then holds a value per seat instead of one global value, with the declared default serving any seat not yet written. Storage mode follows role: host-side instantiation of a `perOwner` slot uses Task 1's per-seat map; client-side instantiation of the same declared slot stays a single value, exactly like a global slot, since a client never holds seat-keyed storage (see Decisions). Thread the declaration through the slot schema and the shared JSON bridge (`store_bridge.rs`) that lowers it, then through both SDK surfaces (`data_script.ts` and its Luau counterpart) and their generated typedefs, so a Luau and a TypeScript mod declare it identically. Keep cardinality and replication as separate declarations: unlock the shipped rejection of `ownerPrivate` for mod stores (`replication_scope_for` in the store bridge currently returns an error for it) but require per-owner cardinality alongside it, since a single global value delivered privately to each owner is meaningless. This task also adds the `byPlayer(owner)` accessor to the slot reference `defineStore` returns — the runtime method in `data_script.{ts,luau}`, its shape in the generated typedefs, returning an owner-addressed ref that `slot(...)` accepts and the store-read leaf resolves, and rejecting `byPlayer` on a global-slot ref. It lands here, before the Phase-3 fork, because both write and read tasks consume it; the added member must not leak into lowered widget binds.

Add the declaration-combination rejections that keep a slot's own declaration coherent — `ownerPrivate` without per-owner cardinality, `perOwner` combined with `accumulate`, and `perOwner` combined with `persist` — reported where the shipped slot-declaration validation already reports malformed schemas (`store_bridge.rs`, committed via `mod_init_exec.rs`). Shipped validation rejects a declaration set atomically at mod-init; this diagnostic follows that path rather than a new partial-load one — the whole set fails together, as every other malformed declaration already does. The access-agreement rejections — a per-owner slot accessed without an owner token, a global slot accessed with one — can't be checked here: they depend on a policy or reaction descriptor, which binds after mod-init and, for a level-local policy, doesn't exist until level install. Task 3 and Task 4 report those at bind, per shipped per-descriptor warn-and-skip semantics: a bad descriptor is skipped, not the whole manifest. The global path stays untouched: a slot without the declaration stores and reads exactly as today.

### Task 3: Owner-addressed writes

Make a per-owner slot writable from both paths, mirroring the dual `E16--resource-grant-chokepoint` establishes for grant. **Impact policy:** the shipped `slot.add` effect rejects any target today and lowers to a self-referential `Write` on a global slot; give it an optional target token at bind time, reusing the expected-token checker the grant spec generalizes rather than adding a third guard. A targeted add doesn't fit that `Write` shape — grantHealth/grantAmmo's targeted writes land on the recipient's own entity state, and a per-owner slot isn't entity state at all — so lower it instead to the existing `PlannedEffect::Command` shape with a new `ImpactEffect::AddOwnerSlot { slot, delta }` variant, intercepted in `apply_planned`'s `Command` arm before it would reach `apply_effect` — `apply_effect` sees only a registry and can't reach the slot table, so `AddOwnerSlot` is the one `Command`-shaped effect that doesn't route through it: resolve the addressed player's seat via the registry's `seat_for_pawn`, then write the delta into that seat's per-owner entry through `self.scope`'s `ScriptCtx` — the store handle the untargeted `slot.add` `Write` already uses, reached without `apply_effect`. Carry the delta, not a snapshot-evaluated absolute value, so two targeted adds to the same seat in one fire accrue instead of the second overwriting the first. An absent token keeps today's global `Write` lowering byte-for-byte. **Reaction:** register a primitive crediting a named per-owner slot for every target, accepting the activators token or a tag, so a trigger volume, a crossing, or a level-load reaction can award a currency — the only path reaching several players in one fire, since the IR has no iteration. The primitive is host-only at dispatch: a connected client also installs levels and fires `levelLoad` locally, so without a guard it would run — and, for a non-replicated `perOwner` slot, diverge — on every client as well as the host. A client-side fire is a silent no-op, not a warning. Both paths skip a recipient with no seat, warn, and continue; an empty recipient set is the no-warning row of the Ordering pins. Export the SDK builders for both, mirroring the shipped damage builder's activators-or-tag dual. Assert the first two Ordering pins rows here — the pin-1 test drives a level install with a level-load `addSlot` and asserts the local pawn is credited; remote pawns are outside the pin, per AC 4.

### Task 4: Owner-addressed reads and publish paths

Give a policy a way to read a per-owner value and the HUD a way to see it. **Read:** add an optional owner field to the existing store-read IR leaf, `serde(default)` and `skip_serializing_if`, so a plain read with no owner re-serializes byte-identical to today's leaf and every existing wire payload still parses unchanged. Enforce the `scripting.md` §12 exception at bind time rather than special-casing each call site: give the binding-scope trait a method for resolving an owned input that defaults to refusing it, and override that default only where an owner is meaningful — the scope an impact policy binds against. A sourceless reaction's scope inherits the refusing default and rejects an owner-addressed read at bind, for free; a bare read fails at bind the same way, per Task 2's access-agreement rule, skipping only that descriptor. The read resolves per fire through the registry's `seat_for_pawn`, off the same per-fire frozen snapshot the evaluator already applies to store reads. **Publish, host and single-player:** the HUD slot publisher republishes player slots each frame from local state, but over a hardcoded engine set (health, ammo, reload) — it does not enumerate mod slots. Add a pass that walks the slot table's `perOwner` mod records and writes each one's local-seat projection into the record's retained scalar `value`, the same field `bindState` and every other bare engine read already returns, following the existing no-value skip that leaves a slot at its previous value rather than resetting it. **Publish, connected clients:** the owner-private source resolver dispatches named projections ahead of a global fall-through, and a mod slot currently falls through to one global value served to every owner; add a per-owner projection ahead of that fall-through, resolving the resolver's existing `pawn: EntityId` through the registry's `seat_for_pawn` to a seat, then reading that seat's per-owner entry. ## Ordering pins

Concrete orderings the tasks must hold and the tests in Tasks 3 and 4 assert directly rather than restating.

| Scenario | Ordering | Expected outcome |
|---|---|---|
| Level-load reaction credits players | The pre-`levelLoad` install hook binds the local seat before the `levelLoad` fire inside `install_world_cpu`, so `seat_for_pawn` resolves the local pawn at fire time; the shipped post-install bind is too late and is moved, not duplicated | The award lands for every pawn live at install. A remote pawn spawns at re-promotion, after install, and no bind-vs-dispatch ordering can reach it — see AC 4's scope |
| Trigger fires with zero activators | An `addSlot` reaction receives an empty activator set (N=0) | Credits no one, emits no warning, sibling effects in the same fire apply normally |
| Late joiner's first owner-private snapshot | Seat is minted at admission, before the replication tracker's first per-owner ingest for that connection | The first delivered value is the slot's declared default (or the seat's current value), never another owner's value |
| Two held seats match one claim, both carrying per-owner values | `admit_or_reclaim` releases the losing duplicate inline, through the same release path Task 1 wires, before any expiry sweep runs that poll | The losing seat's per-owner entries are cleared in that same call; the winning seat's own per-owner values are untouched |
| Reclaim continuity through the replication tracker | A reclaim or repromotion re-registers the connection with the owner-private tracker, which dropped that client's state on the prior exit; the first produce after re-registration runs before any other read of that connection's per-owner values | Continuity comes from the seat-keyed per-owner store, never from tracker state — the first post-reclaim snapshot carries full baselines sourced from the store, not stale or missing tracker entries |
| Owner token resolved twice in one fire | A read resolves its owner at plan/seed time; the paired write (`AddOwnerSlot`) resolves at apply time; no in-fire effect re-keys the source pawn's seat between them (sibling despawns are deferred) | Both resolve the same `Seat`, so a read and a write of one owner token in a single fire always address the same seat, even if the target is retired later in the fire |

## Boundary inventory

| Name | Rust | Wire / serde | JS / TS | Luau |
|---|---|---|---|---|
| per-owner slot storage | entities floor-crate slot table, keyed by shipped `Seat` (`foundation`); host-side only, a plain scalar client-side | not replicated directly — see owner-addressed add/read rows | — (not author-facing) | — |
| seat resolution (consumed, not built) | `EntityRegistry::seat_for_pawn` — the shipped `pawn_seats` association, written through the single `SeatTable::set_pawn_binding` chokepoint; this spec reads it | not replicated | — (not author-facing) | — |
| per-owner cardinality | per-seat slot storage | slot declaration key | `perOwner: true` | same |
| replication scope | existing owner-private scope | existing scope tag | `network: "ownerPrivate"` | same |
| owner-addressed add (impact) | `slot.add` effect with a target token | effect args plus the addressed token | `slot(ref.byPlayer(impact.source)).add(delta)` — the shipped `slot(ref): NumberSlot` builder, widened to accept an owner-addressed ref | `slot(ref:byPlayer(impact.source)):add(delta)` |
| owner-addressed add (reaction) | reaction primitive | primitive name, `target?: "@activators"` or tag, args carry slot and delta | `addSlot(target, slot, delta)` | same |
| owner-addressed read | seat-bound store read | existing store input leaf, extended with an optional owner field; seat resolved per fire | `ref.byPlayer(impact.source)` | `ref:byPlayer(impact.source)` |

`ref.byPlayer(owner)` is one owner-addressed ref serving both roles: read it as a value, or pass it to `slot(...).add(delta)` to write — no separate read and write types. `byPlayer` selects; it never acts, so a ref gains no verbs and `scripting.md` §5's rule that helpers describe how a reference is used holds unchanged.

## Script syntax examples

```ts
// Proposed design — every currency here is declared by the mod. The engine
// ships cardinality, not XP.
const { state: progression } = defineStore("progression", {
  // One per player, replicated to its owner. Rides the seat's hold window;
  // session-scoped until the persistence spec lands.
  xp:        { type: "number", default: 0, perOwner: true, network: "ownerPrivate" },
  // One per player, host-side only — the HUD never shows it.
  killStreak:{ type: "number", default: 0, perOwner: true },
  // One for the session, shared by everyone.
  teamKills: { type: "number", default: 0 },
});

const reward = defineImpactEvent("reward", { tag: "enemy" }, (impact) => {
  const killed = impact.target.healthBefore.gt(0).and(impact.target.healthAfter.le(0));
  const bonus = impact.target.healthAfter.le(-40).select(50, 25);
  return [
    { when: killed, do: [
        slot(progression.xp.byPlayer(impact.source)).add(bonus), // per player
        slot(progression.teamKills).add(1),                // shared, unchanged from today
    ]},
  ];
});

// Awardable without dealing damage — the objective volume pays everyone in it.
// Tracer returns the builder's descriptor directly, like the shipped
// `grantAmmo(on.activators, ...)` pattern in combat-demo-reaction.ts.
onTriggerEvent({ tag: "objective" }, "enter", [
  defineReaction((on: TriggerEventParams) => addSlot(on.activators, progression.xp, 100)),
]);
```
