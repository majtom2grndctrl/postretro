# Player Revive and Assist

## Goal

Let mod authors build revive mechanics (Borderlands second wind, L4D teammate revive, a medic who revives faster) with author-chosen bonuses. The engine adds a teammate **assist** interaction, driven by its own `assist` input command, and life-state reads and effects on an impact's source. An assistable state's radius and hold time are literals or expressions over the helper and the target, evaluated on the host for each pair. `assist` ships an engine default, `hold` on Use's inputs, bound only in mods that declare `assistable`, so a novice author's revive works with no input authoring. The dev mod upgrades its down/bleed-out policy to full Borderlands. Builds on `E18--player-life-states` (Spec A, landed in `done/`): its life states, capability gates, verbs, name table and slots are the base this spec extends. `input-contextual-priority` later replaces the default's duration split with availability-ranked sharing and consumes this spec's candidate query.

## Scope

### In scope

- The `assistable: { radius?, holdMs? }` profile key on a Spec A life state. Each value is a literal or a Number expression over the helper and the target (`assist.helper`, `assist.target`); an omitted value takes its engine default (1.5 m, 3000 ms). Assistability is stamped per pawn as a bool and replicated on the pawn's movement state; the own pawn's `TuningPayload` profiles carry the key under a new `TUNING_PAYLOAD_EPOCH`.
- An interaction-pair binding scope with two roles (actor and subject), built for reuse by a later hold-to-interact. Assist binds it as helper and target.
- Host evaluation of each pair's radius and required ticks, and an owner-private pair table that tells each helper's client those values for every assistable candidate.
- A gameplay input command `assist`, its engine default (`hold` on `KeyE` / gamepad `west`, bound only while `assist` is relevant), a default activator per command, and its held bit on the wire.
- A host assist accumulator, with an owning-client prediction of the helper's own progress corrected at the acknowledged input tick, and a ramped display of received progress on the target's client. Target selection is a standalone pure query.
- Client retention of remote pawns' life-state id and `assistable` bool.
- Discrete player-event sources `assistReceived()` and `assistGiven()`.
- Two per-player Number slots: `player.assistProgress` (progress as helper) and `player.assistReceivedProgress` (progress of the assist being received).
- Impact-policy source read and effect: `source.inLifeState(name)`, `source.setLifeState(name)`.
- Dev-mod upgrade: teammate revive, second-wind self-revive on kill, XP bonuses, "Reviving" and "Being revived" HUD bars.
- Updates to `docs/scripting-reference.md`.

### Out of scope

- Phases 2–4 as listed in Spec A's Out of scope.
- **Contextual command priority**, including `assist` grouped with `use` on one key so a press does whichever is available. `input-contextual-priority` owns it, along with the E-key press-time resolution and its HUD prompt. It consumes this spec's candidate query.
- **Phase 3 presentation for assist:** a revive prompt showing the nearest assistable teammate.
- **Per-entity state (`@state.*`) reads in pair expressions.** `scripting.md` §11 requires the cross-entity state-read write path to be settled first. The roadmap carries it as a follow-up.
- **Pair facts.** The `@pair.` input prefix is reserved for facts about the pair itself and holds no names here. Distance is not one: a radius computed from distance is circular.
- **Not planned:**
  - Line-of-sight or facing requirements on assist. Optional profile keys can add them later.
  - Assist on non-pawn targets, and with them non-pawn sides in the pair scope. Deferred until a non-pawn consumer exists; it would need its own source (see Alternatives).

## Direction

**Problem.** Spec A lets authors down and respawn a player, but nothing lets a teammate bring a downed player back, and impact policy cannot read or change its source's life state. Revive mechanics therefore cannot be authored.

**Placement.**
- **Engine mechanism vs mod policy.** The engine owns the assist accumulator: who is in range, how long `assist` is held, and one completion per target. These run per tick over pawn positions and held input, which the IR cannot see. The mod owns every consequence: the state a revive enters, health, bonuses, cues. The mod also owns how far and how long a revive takes for each pair, as IR the engine evaluates; the engine owns the defaults, the caps and the accumulation rule.
- **Pair scope in scripting-core, not in assist.** The two-role scope sits beside the impact and player-event scopes, so a later hold-to-interact binds it with its own role tokens and reuses the accumulator step unchanged. Assist supplies only its tokens and its sides.
- **Host vs client.** Completion is host-authoritative. The helper's own progress bar is predicted on its client so host authority never shows up as latency. The prediction reads interpolated remote pawns, the remote pawns' life-state id and `assistable` bool (replicated on their movement state, below), the host's pair table, and the helper's own `use` capability. It reaches only the HUD's display map and is corrected toward the host. Success presentation plays only on host confirmation.
- **What the client knows about a teammate.** The host stamps each pawn's assistability as a bool onto its movement component and replicates it on the pawn's movement state, beside the life-state id that already rides there. A connected client keeps both fields for remote pawns, which it drops today. The numbers come only from the host: a pair expression can read either side's per-owner values, which a client does not hold for other seats, so the client never evaluates one. The host sends each helper's client a pair table, the radius and required ticks for every assistable candidate, and sends each target's client the required ticks of the assist it is receiving. The client's own pawn takes its `assistable` bool from its own profiles in `TuningPayload`, restamped like every other profile field.
- **Input resolution is client-side.** On a key shared by `assist` (`hold`) and `use` (`press`), as the engine default binds it, the client's activator resolution decides: holding past the hold threshold drives `assist`; releasing before it fires Use. The client sends only the resolved command. The host never turns `assist_held` into Use or Use into an assist. If host and client disagree about range, the assist does not progress on the host and no trigger fires.
- **Impact policy vs player events.** Second wind is a consequence of a kill, so it is authored where kills are: an impact policy that reads and sets the *source's* life state.

**Prior commitments.**

- **Life states, capability gates, `setLifeState`, `respawn`, `inLifeState` and the name table** (Spec A). Kept. `assistable` is a closed profile key added to Spec A's set. Unknown names in the new read and effect fail at bind the way Spec A's `inLifeState` does: the mod name table refuses the name (`resolve_life_state_id` for the read, `EntityScope`'s name check for the effect), and the policy is skipped with a warning. Spec A's I3 (the engine never changes life state on HP) gains `source.setLifeState` as an authored transition source.
- **The client restamps only its own pawn's profile, from `TuningPayload`; movement payloads for pawns without a local `PlayerMovementComponent` are ignored** (`IgnoredPayload::MovementWithoutLocalComponent`, Spec A). Diverges, narrowly. The client keeps remote pawns' `life_state` and `assistable` bool from the payload it already receives. Gates still never run on remote pawns. The divergence is needed because the helper's prediction reads its target's state. `TuningPayload` gains no field: the pawn's own profiles it carries include `assistable` because they serialize `LifeStateProfile`, so `TUNING_PAYLOAD_EPOCH` bumps (Wire format).
- **Player events are host-only, and `on.player` is legal only before `wait`** (`scripting.md` §12). Kept. `assistReceived` and `assistGiven` are discrete sources that bind the existing `on.player` at completion; no `wait` is involved.
- **Every player event is an edge over a condition, and a fire's writes are seen next tick** (`scripting.md` §12 Player events). Diverges, narrowly. The assist sources carry no condition. Their fires apply before the pass's condition snapshot, so that tick's conditions see their writes (O1). Completions apply in `players()` order of the target; each runs its `assistReceived` subscriptions, then its `assistGiven` subscriptions, each in composed order. Condition-edge events still read the snapshot and fire after it. The divergence is needed because a revive must land before a same-tick bleed-out condition reads `down`.
- **Command relevance is an exhaustive match over descriptors; while participating in co-op it also follows the installed host tuning** (`input.md` §Relevance, `derived_relevance`, `tuning_facts`). Kept. `assist` gains an arm: relevant exactly when some loaded descriptor declares an `assistable` profile key, or, in co-op, when a life-state profile in the installed host tuning does.
- **Shared keys (Steam rule): one short binding plus one `hold` per key in a context** (`input.md` §Shared keys). Kept. The engine default `assist` (`hold`) beside `use` (`press`) on `KeyE` / `west` is a legal pair today (`conflicts` in `input/binding_table.rs`), the same pattern as the dev mod's hold-Shift sprint beside tap-Shift dash. Kept as today: when a player's own layer binds Use on that input, `collides` drops the engine layer's `hold` there, and that player has no `assist` on the key until they bind it.
- **Engine default bindings are all `press`** (`default_bindings_for`, and `engine_slots` in `input/binding_table.rs`). Diverges, narrowly. Each command gains a default activator, `press` for every existing command and `hold` for `assist`, and both sites use it. The divergence serves "defaults for novices, controls for experts": an author who declares `assistable` gets a working revive with no input authoring, and an author who wants another key or activator overrides it in the `input` block. The cost is bounded by relevance: `assist` is unbound in a mod without `assistable`, so Use fires on press there exactly as before. In a mod with it, Use on `KeyE` / `west` fires on release before the hold threshold.
- **Client predicts only with host numbers** (`networking.md` §What gates). Kept. The client never evaluates a pair expression; it predicts from the host's pair table.
- **Descriptor-embedded expressions use exported constant handles, never callbacks** (`activation.charge`, `candidate.distance`). Kept. `assist.helper` and `assist.target` are constant handles; `assistable` takes no function.
- **Per-entity-state reads are same-entity until a cross-entity write path is settled** (`scripting.md` §11). Kept. Pair expressions read no `@state.*` input.
- **The candidate scope is the only per-pair evaluation context, and each scope's value-free twin binds inside the descriptor parsers** (`scripting.md` §11). Diverges, narrowly. `InteractionPairScope` is a second per-pair context, over two player sides rather than a fixed fact table. Its value-free twin binds after parsing, at the commit gates where store schemas and the life-state names exist; a rejection still fails loading with the authored key path. The divergence is needed because pair expressions read per-owner store values, and the descriptor parsers see no store schemas.
- **"Engine features per mechanic (a revive system, a lives system) put policy in the engine"** (Spec A, Alternatives rejected). Diverges, narrowly. The accumulator carries a small fixed rule set: nearest other pawn within its pair radius as target with ties to `players()` order, fixed-point progress that completes on the advancing tick reaching one whole, reset on release, target switch, or either pawn changing or re-entering a state, advance only on real-command ticks, one completion per target per tick, and a completion ending the hold until a real release. The divergence is needed because range and hold time over per-tick pawn positions and held input are invisible to the IR, so no authored policy can compute them. Everything a revive *does* stays authored.
- **"Death is modder policy derived from impact"** (Q3 archive, E16). Kept. Self-revive is an authored impact effect, never an engine rule.

**Alternatives rejected.**

- **Assist driven by held Use.** A Use press beside a downed teammate would also fire any Use-activated trigger or switch in reach, and the host cannot tell which the player meant. A separate command resolved on the client keeps the two apart.
- **Teammates' `assistable` from `TuningPayload`.** The payload carries the client's own pawn's profiles. Serving teammates from it, the client would also need each remote pawn's descriptor identity and life-state id, and would carry profile tables it mostly never reads; it still could not evaluate a pair expression that reads another seat's values. A per-pawn bool delivers assistability, and the host's pair table delivers the numbers.
- **No client prediction; the helper's bar shows the host's value.** The bar would start about one round trip late, against the smooth co-op presentation Spec A set as the governing preference.
- **No engine default; each mod binds `assist` itself.** A novice author who declares `assistable` would ship a revive no player can perform until they discover the `input` block, and every mod would repeat the same binding. The default's cost, Use on key-up, lands only in mods that declare `assistable`, and an author who wants Use on press rebinds `assist` in the `input` block.
- **Split each pair value into a target part times a helper factor.** It covers "medics revive faster" but not a value that depends on both sides at once (a medic reviving a medic), and it fixes the combination rule in the engine. One expression over both sides covers both, at the same host cost.
- **A callback form (`holdMs: (helper, target) => …`).** Descriptors carry plain data across the manifest boundary, and callbacks are legal only on top-level `define*` calls. Constant handles lower to IR like `activation.charge`.
- **Evaluate pair expressions on the client.** The client lacks other seats' per-owner values, so its result would differ from the host's whenever an expression reads one. The host's pair table costs a few bytes per candidate.
- **Summed f32 progress fractions.** Rounding could complete a tick early or late on one side only. A fixed-point accumulator with an integer increment gives host and client the same completion tick bit for bit.
- **A dedicated key in the dev mod.** Every gamepad face button already carries a gameplay command, and the free keyboard keys sit far from Use. L4D2, Back 4 Blood and Darktide all put revive on the use key.
- **One progress slot for helper and target.** Per-player slots are owner-private, so a target's client cannot read its helper's slot. A merged slot would also be ambiguous for a pawn that is helping while being helped. Two slots give each client its own reading.
- **A new `on.assister` token** for one `assisted()` event. A second dispatch token touches about a dozen hand-kept sites: SubjectToken, SequenceTarget, BoundTarget, DispatchScope's single event-player snapshot, `byPlayer` recognition in three installers, and five per-source rejection guards. Two discrete sources, each binding the existing `on.player` to a different pawn, deliver both bonuses with none of that.
- **Assist as a trigger volume attached to the pawn.** Trigger volumes are level-authored AABBs keyed by map identity. A pawn-carried one has no placement, tag, or install story.
- **A generic hold-to-interact mechanism with assist as its first target kind.** Pawn targets need the same accumulator either way. Assist stays player-on-player because no other hold-to-interact consumer exists. The parts that generalise cheaply are built generic in this spec: the pair scope takes role tokens and side kinds from its consumer, and the accumulator step takes evaluated pair values with no IR inside. Generalising later reuses both and `assistGiven` (which binds `on.player` to the helper), but `assistReceived` binds `on.player` to a target pawn, so a non-pawn target would need its own source. That is why non-pawn assist stays Not planned rather than deferred.
- **Second wind without impact-source effects.** The kill policy could write a per-player flag through `update(store.byPlayer(source), …)`, and a player event on `inLifeState("down")` plus the flag could revive. Without `source.inLifeState` the policy cannot restrict the flag to kills made while down, so the author must clear it on every down transition. The revive also lands a tick later than an in-tick `source.setLifeState`. Task 1 is cheaper for authors and faster.
- **Revive as an engine verb.** A revive is `setLifeState` plus `grantHealth` in an authored fire list; an engine verb would fix its health and state.
- **A respawn hook in `sim::respawn::drain`.** `drain` takes only the `ScriptCtx` and registry and cannot reach the session-owned accumulator state. The accumulator's elapsed check already sees every respawn into a declared state, since respawn enters it at elapsed zero.

**Foreclosures and one-way doors.**

- `assist_held` on `WireMovementInput`, the `assistable` bool on `WirePlayerMovementState` and the pair table and received required ticks on the local-pawn record take the next `WIRE_VERSION` (39 at `b6fc0c4`) and the next `SNAPSHOT_VERSION` (25), and `assistable` on `LifeStateProfile` takes the next `TUNING_PAYLOAD_EPOCH` (17). Pre-stable, each undone with another bump.
- SDK names (`assistable`, `assist.helper`, `assist.target`, `assistReceived`, `assistGiven`, `player.assistProgress`, `player.assistReceivedProgress`, `source.inLifeState`, `source.setLifeState`), the owner tokens `@assist.helper` / `@assist.target`, and the command ID `assist` become the modder contract; the command ID is also written into player bindings and manifests. Renaming any of them costs a pre-stable SDK break across both runtimes.
- The engine-owned numbers become modder contract too: the defaults (1.5 m, 3000 ms), the caps (16 m, 60 s), "a radius at or below 0 means this helper cannot assist this target", and the accumulation rule (a constant hold completes on exactly its required-count-th advancing tick). Changing a default changes every mod that omits the value.
- `assist`'s engine default is `hold` on `KeyE` / `west` until `input-contextual-priority` replaces it with its grouped default. A player who rebound `assist` keeps their binding across that change.
- Task 2a widens the per-player slot bitset (`EntityScope.warned_owned_engine`, capped at sixteen by a compile-time assert) to u32. The slot count is fifteen (`PlayerSlot::ALL` at `b6fc0c4`); the two progress slots take it to seventeen, so the widening is required for this spec to compile.
- An assist with no line-of-sight or facing requirement can be tightened later by adding optional profile keys. `@state.*` side reads and `@pair.` facts are additive inputs to the same scope. Nothing material is foreclosed.

## Acceptance criteria

### Descriptor and validation
- [ ] **AC1.** A life-state profile accepts `assistable` with `radius` and `holdMs` each a literal, a Number expression, or omitted, in both runtimes into the same lowered shape. `assistable: {}` is valid. An omitted `radius` lowers to 1.5 and an omitted `holdMs` to 3000. Loading is rejected, with the full key path (`components.lifeStates.states.<state>.assistable.radius` or `.holdMs`), for each case below:

  | Value | Rejected when |
  |---|---|
  | Literal `radius` | ≤ 0, > 16, or non-finite |
  | Literal `holdMs` | < 0, > 60000, or non-finite |
  | Expression, either field | Its root is not a Number; it names an unknown input, an unknown owner token, a per-entity state (`@state.*`) input, a `@pair.` input, a local-only player slot or either assist progress slot; it reads a per-player value with no owner (the message points to `byPlayer(assist.helper)` or `byPlayer(assist.target)`); it nests deeper than 32 or holds more than 256 nodes; or `inLifeState` names a state absent from the mod's name table |
  | `assistable` itself | It holds an unknown key |

  A connected client refuses a tuning payload whose profile carries a literal fault or an unknown key (non-finite literals are checked by calling `validate_life_states` directly, since JSON cannot carry them); it never evaluates or rejects a payload expression. A snapshot record whose pair table carries a radius that is non-finite or outside [0, 16], or whose pair table or received required ticks carry a count above the 60 s cap's count, fails validation. On every role, a pawn's movement component carries whether its current state declares `assistable`, restamped at every life-state write, and a connected client reads the same bool for a remote pawn.
- [ ] **AC2.** An impact policy whose `source.inLifeState` or `source.setLifeState` names a state absent from the mod's name table is skipped at bind with a warning naming the policy and the state; the mod's other policies still bind. At runtime, `source.setLifeState` on a source whose descriptor lacks that state, or declares no states, warn-skips.

### Impact source read and effect
- [ ] **AC3.** In an impact policy, `source.inLifeState(name)` holds exactly while the source pawn is in `name`. It is false for a non-player source, which reads no warning. `source.setLifeState(name)` applies to the source pawn in-tick with Spec A's `setLifeState` semantics: the next tick's gates read the new profile, elapsed time restarts, and the current state is a no-op. A live source that is not a player pawn warn-skips through `set_life_state`'s missing-state warning; an impact with no live source skips silently, as every source effect does.

### Assist
- [ ] **AC4.** Holding `assist` within the pair's radius (AC13) of another pawn whose current state declares `assistable` completes on the advancing tick whose progress reaches one whole (AC5). The completion fires every `assistReceived()` subscription with `on.player` = target, then every `assistGiven()` subscription with `on.player` = helper. Both fire in the player-event pass of the tick the hold completes, before that pass's condition snapshot. Completion itself changes no life state or health; only the authored fire lists do.
- [ ] **AC5.** Paired refuse/permit edges for assist:
  - **Refused:** out of range; target in a non-assistable state; the pair's radius at or below 0 (this helper cannot assist this target); helper's state has `use: false`; helper and target are the same pawn (a pawn whose state permits `use` and declares `assistable` never assists itself); release one held tick before completion.
  - **Permitted:** in range on an assistable state; `holdMs: 0` completes on the first held tick.

  Progress is fixed point in units of U = 2³² and accumulates per pair-evaluation pass. Each pass the pair's **required count** is n = `ceil(holdMs × 1000 / TICK_DURATION)`, with `postretro_foundation::TICK_DURATION` (16 667 µs) in microseconds, and at least one; its **increment** is `ceil(U / n)`. An advancing tick adds the current increment; the hold completes on the advancing tick whose progress reaches U. Reported progress is progress over U, capped at 1. For a constant `holdMs` up to 60 s the hold completes on exactly the n-th advancing tick. When a pair value changes mid-hold, progress keeps its fraction and the new increment applies from the next pass. Progress resets when the helper releases or switches targets, when either pawn changes or re-enters a life state (respawn included), and when the hold completes. After a completion the helper accumulates again only after releasing and holding `assist` anew. `player.assistProgress` reports the pawn's progress as helper, 0..1. `player.assistReceivedProgress` reports the progress of the assist the pawn is receiving, 0..1: the highest among its helpers, and 0 with none or while the pawn's current state declares no `assistable`, so a target revived in the pass reads 0 from that pass on (O50). A pawn helping while being helped reports both.
- [ ] **AC6.** Two helpers completing on one target in one tick produce one completion, for the earlier helper in `players()` order. The other helper's progress resets. Held `assist` survives a short input gap under the host's hold-then-neutral gap policy: gap-held ticks keep progress without advancing it, and only ticks driven by a real command advance it.

### Input command
- [ ] **AC7.** Absent a manifest `show` override, `assist` is listed and bindable exactly when some loaded descriptor declares `assistable` or, while participating in co-op, a life-state profile in the installed host tuning does; otherwise it is unbound, unlisted and never part of a conflict. While relevant, with no author or player rows for it, it is bound `hold` at the default threshold on `KeyE` and on gamepad `west`, and both glyphs draw that input. Every other command's engine defaults stay `press`. Bound to any key (`press` or `hold`, engine default or author row), holding the key past its activator's fire point sets `assist_held` on every command built while it is down, and releasing clears it. A binding-table rebuild while the key is down follows the existing rebuild rule. An `assist` binding the rebuild adds waits for a fresh press, so a key held across a relevance gain never sets `assist_held` and fires nothing on release (O52). An `assist` binding the rebuild removes lifts at once, and the next real command carries `assist_held` false as a release does (O53).
- [ ] **AC8.** With `assist` relevant and on its engine default, holding `KeyE` or gamepad `west` past the hold threshold drives assist and fires no Use-activated trigger or switch, with or without a teammate in range. Releasing before the threshold fires Use once. The pair raises no binding conflict. With `assist` irrelevant, Use on those inputs fires on press from the first gameplay frame, exactly as before this spec. A player row binding Use on `KeyE` drops `assist`'s engine `hold` there, as `collides` drops any lower-layer `hold`.

### Client experience
- [ ] **AC9.** The helper client's "Reviving" bar shows its own `player.assistProgress` on the first held tick, with no round-trip wait, whenever its pair table already holds the target, and advances every rendered frame at the rate the table's required ticks give. A target the table does not yet hold is not predicted; its bar waits for host samples (O43). If the host resets or never confirms (target moved, revived elsewhere, out of range on the host), the bar returns to 0 with no success cue. Success consequences (state, health, bonuses, their presentation) appear only after host confirmation; this clause and "no success cue" are a review gate plus the manual proof, since cues live only in host-run fire lists. After the first nonzero sample of each assist (a sample above 0 following a 0), which may step up from 0, the target client's displayed `player.assistReceivedProgress` never decreases between rendered frames unless a received sample is below its predecessor, and rises by at most twice the received slope (one increment of the host's received required ticks per server tick) over the frame's timeline advance.

The healer recipe shortens `holdMs` from a per-owner store read on `assist.helper`.

### Pair values
- [ ] **AC13.** Pair values are evaluated on the host, every accumulator pass, for each helper whose state permits `use` and each other pawn whose state declares `assistable`. An expression reads either side through `assist.helper` / `assist.target`: engine per-player slots, per-owner store values at that side's seat, and `inLifeState(name)`; it also reads global store values. A store write a fire list makes in tick N is seen by tick N+1's pass. Results and faults:

  | Result | Pair outcome |
  |---|---|
  | `radius` finite and > 16 | Clamped to 16 |
  | `radius` finite and ≤ 0 | This helper cannot assist this target |
  | `radius` non-finite, or a side value it reads is missing | Out of range; one warning per (descriptor, state, field), re-armed on reload |
  | `holdMs` finite and > 60000 | Clamped to 60000 |
  | `holdMs` = 0 | Completes on the first held tick |
  | `holdMs` negative or non-finite, or a side value it reads is missing | Progress kept, not advanced; one warning per (descriptor, state, field), re-armed on reload |

  Each connected helper's client receives its pair table (the radius, 0 when it cannot assist, and required ticks for every other pawn whose state declares `assistable`) on the snapshot that carries the life-state ids and `assistable` bools the table was evaluated against. Each connected target's client receives the required ticks of the highest-progress helper on it, ties by `players()` order, and 0 with none or while its state declares no `assistable` (O50). Both ride the target's own local-pawn record and reach its client on the next record after they change.

- **Fixed-point progress.** Progress is a u64 in units of U = 2³², not summed fractions. Each pass, the pair's required count is n = `ceil(holdMs × 1000 / TICK_DURATION)`, with `postretro_foundation::TICK_DURATION` (16 667 µs, the engine's fixed step) in microseconds, and at least one: the conversion `wait` enrollment uses (`sim/src/scripting_systems/reaction_scheduler/enroll.rs`, mirrored by `startup/reaction_validation.rs`), computed in f64. **One increment** is `ceil(U / n)`. A hold completes on the advancing tick whose progress reaches U, so `holdMs: 0` completes on the first held tick, and a constant n up to the 60 s cap completes on exactly the n-th advancing tick (I6), since n(n − 1) < U. Reported progress is progress over U, capped at 1. When n changes mid-hold, progress keeps its value and the new increment applies from that pass (O39). A pair whose `required_ticks` is 0 keeps progress without advancing it (O44). Host and client use the same functions, `pub fn assist::required_count(hold_ms)` and `pub fn assist::increment(required_ticks)`; the step takes `required_ticks`, never `holdMs`, so a client fed the host's integer computes the host's increment bit for bit.
- Progress resets per AC5. The state stores, per pawn, its life-state id and `life_state_elapsed_ticks` at the last pass. Elapsed advances once per host tick for every pawn in a declared life state, and entering a state, respawn included, sets it to zero. A pawn whose descriptor declares no states stays at zero, so the check compares its id alone; such a pawn can only be a helper, and a respawn mid-hold keeps its progress. When a pawn's id differs from the stored one, or it is in a declared state and its elapsed is not greater than the stored value, the accumulator resets that pawn's progress in both roles: its own progress as helper, and every helper's progress on it as target. This covers a respawn into the same state (O25) and a leave-and-re-enter between passes (O9), with no hook in `sim::respawn::drain`. The step's elapsed input is optional: with none, the check compares ids alone (Task 2b's client runner retains no remote elapsed). A pawn removed from the registry (seat harvest, O5, O19) drops its progress in both roles. A pawn that appears as a new entity starts from 0 (O20).
- Completions go into a `TickEvents` `assist_completions` list (precedent `trigger_exit_fires`), each carrying the target's life-state id and `life_state_elapsed_ticks` at record. One completion per target per tick (AC6): the earlier helper in `players()` order wins and the others reset, unlatched (O37). A completion ends the winning helper's hold by setting its latch (below): its progress resets to 0 and accumulates again only after `assist` is released and held anew (O4, O10). Only a real command with `assist_held` false counts as that release. A neutral command synthesized after the hold grace resets progress (O12) but leaves the latch set (O29).
- **One rule, two runners.** The accumulator is a pure `pub` step, `assist::step`, over the runner (host or client), the helper's id, position, `assist` level and capability, whether that tick's command is real, the candidates (each with id, position, current life-state id, `assistable` bool, `PairValues` and optional elapsed), the previous target and progress, the helper's latch, and each pawn's life-state id and optional elapsed at the previous pass. The latch marks an ended hold. With `assist` held and the latch clear, the step first chooses a target with `assist_candidate`, then resets progress to 0 when that target differs from the previous one or the reset rule above fires for either pawn. The first matching row then applies:

  | # | `assist` held | Command real | Latch | Target | Step |
  |---|---|---|---|---|---|
  | 1 | No | Yes | Any | Any | Progress resets to 0; the latch clears (a release) |
  | 2 | No | No | Any | Any | Progress resets to 0; the latch is kept (a neutral command after the hold grace, or a remote pawn with no resolved command; O12, O29) |
  | 3 | Yes | Any | Set | Not chosen | Progress does not advance. The host's stays at the 0 its completion left; the client's holds its current value until the correction settles it |
  | 4 | Yes | Any | Clear | None | Progress resets to 0 |
  | 5 | Yes | No (gap-held) | Clear | Chosen | Progress kept, not advanced (O11) |
  | 6 | Yes | Yes | Clear | Chosen | Progress advances one increment of the pair's current `required_ticks` (none when it is 0). On reaching U the host records a completion, resets progress to 0 and sets the latch; the client holds at U and sets the latch |

  The **step's reset** is a reset the step itself makes: rows 1, 2 and 4, and the reset before the table. The host's completion reset in row 6 is not one. The step returns the new progress, latch and target, the row it applied, whether the step's reset fired, and whether it completed.

  The host runs the step authoritatively, once per tick for each helper. Task 2b runs it on the owning client for its own pawn; rows 3 and 6 name the client runner's behavior for it. The accumulator keeps a per-helper row-6 record: whether its last pass ran row 6 without completing, and the chosen pair's `required_ticks` at that pass, whichever row it ran (0 with no target). Task 2b's listen-host and single-player display reads both, since its alpha term adds the increment that `required_ticks` gives; the snapshot builder reads the `required_ticks` for `received_required_ticks`. The step contains no IR: it takes evaluated `PairValues`, so a later hold-to-interact reuses it unchanged.

### Task 2b: Assist client presentation

This task builds the connected client's assist bars on Task 2a's surfaces, which it calls unchanged:
- `assist::step` (`sim/src/sim/assist.rs`), the pure accumulator step. It takes the runner (host or client), the helper's `assist` level, whether the command is real, the helper's capability, the candidates (id, position, life-state id, `assistable` bool, `PairValues { radius, required_ticks }`, optional elapsed), the previous target and progress, and the latch. It contains no IR. It returns the new progress, latch and target, the row it applied, whether the step's reset fired, and whether it completed. Its rows: 1, a release (reset, latch clears); 2, a non-real release (reset, latch kept; never on the client); 3, held while latched (no advance; the client runner holds its value until the correction settles it); 4, held with no target (reset); 5, gap-held (kept; never on the client); 6, held on a real command with a chosen target (one increment of the pair's `required_ticks`, none when it is 0; on reaching U the client runner holds at U and sets the latch). The **step's reset** is a reset the step itself makes: rows 1, 2 and 4, and the reset on a target switch or either pawn's state change before the rows. A candidate whose pair radius is 0, or which lies beyond its radius, is never chosen.
- **Fixed-point progress.** Progress is a u64 in units of U = 2³². `assist::required_count(hold_ms)` gives n, `ceil(holdMs × 1000 / TICK_DURATION)` with `TICK_DURATION` in microseconds, at least one; `assist::increment(required_ticks)` gives **one increment**, `ceil(U / n)`. Displayed progress is progress over U, capped at 1. The client never converts `holdMs`: it takes `required_ticks` from the host, so its increment equals the host's bit for bit.
- `ClientReplication::remote_assist_facts(entity_id)`: a remote pawn's retained life-state id and `assistable` bool, or nothing. Retained ids are compared only for equality.
- `ClientReplication::assist_pair_table()`: the host's pair table for the local pawn as helper, one `(EntityId, radius, required_ticks)` entry for every other pawn whose state declares `assistable` and whose network id the client has mapped. The client reads it from every accepted local-pawn record, and the host resends that record when the table changes. Radius 0 means this helper cannot assist that pawn; `required_ticks` 0 means held progress is kept, not advanced. Every assistable candidate has an entry, so a missing entry means only that it has not arrived yet.
- `ClientReplication::received_required_ticks()`: the `required_ticks` of the highest-progress helper on the local pawn, 0 with none or while the local pawn's state declares no `assistable`.
- The accumulator's per-helper row-6 record: whether its last pass ran row 6 without completing, and the chosen pair's `required_ticks` at that pass, whichever row it ran (0 with no target).
- The owner-private slots `player.assistProgress` (the pawn's progress as helper) and `player.assistReceivedProgress` (the highest progress among its helpers), which `ui_proxy` writes only off a connected client, and the local pawn's `PlayerMovementComponent` `assistable` bool, restamped from `TuningPayload`.

**Client step**
- **Where it runs.** The client step, its records, its follow state and the correction live in new module `crates/postretro/src/client_assist.rs`, not in netcode: netcode's forward prediction takes no `EntityRegistry` by design, and the step reads interpolated remote pawns from the registry. It runs inside the `predict` closure that `frame_loop` passes to `run_client_predicted_tick`, beside `predict_client_weapon_command`, with that tick's command and `input_tick`. `input-contextual-priority` reads its candidate inputs from this module. Its state clears where client prediction resets: beside the app's calls of `reset_level_scoped_client_state` (in `unload_level`) and `demote_client_state`, and when the apply outcome reports `armed_local_pawn`. No hold carries into a new level or onto a new pawn when an entity id recurs (O35).
- **Runner.** The owning client runs `assist::step` with the client runner once per forward-predicted tick, never during reconcile replay, for its own pawn as helper only, over interpolated remote pawns, the facts `remote_assist_facts` returns for them, and each one's `PairValues` from `assist_pair_table`. The client's commands are all real, so rows 2 and 5 never apply there. Reaching U latches the client as a completion latches the host, and the correction table's drop row latches it too, so a client holding on after a revive accumulates nothing on a second downed target until a release and re-press, whether or not its prediction had reached U (O28, O46). The client never emits completions. It passes no elapsed, so its step resets when a target's id changes but not when the target re-enters the same state; that reset reaches the bar through the host sample. Retaining elapsed would not help: remote movement payloads arrive once per `SNAPSHOT_TICK_INTERVAL`, so between payloads a target's retained elapsed would not advance and the elapsed rule would reset every predicted tick.
- **Host samples.** The host's sample is one owner-private Number on the state-slot channel and names no target, so a host target switch reaches the client only as a reset. For each accepted snapshot whose local-pawn record carries an acknowledged input tick (`acked_tick`, surfaced by `capture_local_reconcile` from `last_processed_client_tick`), netcode's `lib.rs` receive loop appends the pair (acknowledged tick, sample) to a new list on `ClientApplyFrameOutcome`. The sample is the committed `player.assistProgress` store value after that snapshot's state batch applies, read as `accept_timed_slot_sample` reads the weapon timers. The channel omits a value the client already holds, so a batch with no record for the slot still yields a sample (O30). A snapshot whose state batch was not applied, or that holds `player.assistProgress` for a baseline refresh, yields no sample. `client_assist` consumes the list in order after the receive step.
- **Abstention.** While `assist` is held and the latch is clear, a remote pawn whose retained `assistable` bool is set, which has no pair-table entry, and which lies within `ASSIST_MAX_RADIUS_M` and no farther than any target the step would otherwise choose makes the step abstain: it does not run, records nothing, and the display shows host samples (O43). When the entry arrives the step resumes and rebases from the newest host sample as the correction table's rebase row does, counting from that sample's acknowledged tick, so the bar does not drop. A pair-table entry with radius 0 is a known answer, not a missing one, and causes no abstention (O45).
- **Records.** The client records its progress, and the increment that tick's pair `required_ticks` gave (0 for a `required_ticks` of 0), at each forward-predicted tick on which the step runs with `assist` held and is not following. An idle tick records nothing. Records belong to one hold segment: the step's reset discards every record and ends follow, so a sample acknowledging a tick before the step's last reset finds no record (O14).
- **Correction.** Each sample is compared with the record at its acknowledged tick, never with the current prediction. The tolerance is the compared record's own increment, capped at U / 2. A hold whose required count is under two, `holdMs: 0` included, therefore still drops on a host reset or confirmation (O31), and a pair value that lowers the required count before a sample arrives never widens the tolerance for records made at the old rate (O48). A stalled pair records an increment of 0, so any difference rebases, onto the sample with nothing added (O58). The rebase row adds the current increment, since the ticks after the acknowledged one run on the host at the current value. Samples are compared in U units: a sample s counts as `round(s × U)`. Outside follow, the first matching row applies:

  | # | Sample vs the record at the acknowledged tick | Client action |
  |---|---|---|
  | 1 | No sample (state batch not applied, or slot held for a baseline refresh) | Keep the prediction |
  | 2 | No record at that tick (before the step's last reset, an idle tick, or pruned) | Keep the prediction (O13, O14) |
  | 3 | Sample 0, record above the tolerance (a host reset, a confirmed completion included) | Drop: the prediction becomes 0, the latch sets and the step enters follow; every record is discarded (O6, O46) |
  | 4 | Within the tolerance of the record | Keep the prediction |
  | 5 | Higher or lower than the record by more than the tolerance, sample above 0 | Rebase: the prediction becomes `round(sample × U)` plus the current increment for each advancing tick after the later of the acknowledged tick and the step's last reset, capped at U; records after the acknowledged tick are rewritten to the rebased values (O32, O42) |

  A record held at U meets a confirmation's 0 in row 3, so a confirmed hold returns the bar to 0 until the next press.
- **Follow.** Follow is a state of the client step, entered only by the correction table's drop row. That row sets the latch, because a host sample of 0 cannot tell a reset from a confirmation, and a confirmed host stays latched until a real release. While following, the step holds its progress at 0, advances nothing, records nothing and, being latched, chooses no target. A target switch on the client therefore never restarts the prediction, and the step leaves follow only through a real release or a host sample above 0 (O6, O28, O47). Follow replaces the correction table:

  | # | Event while following | Client action |
  |---|---|---|
  | 1 | No sample, or a sample of 0 | Stay at 0; keep following |
  | 2 | Sample above 0 | Rebase as in the correction table's rebase row, counting from that sample's acknowledged tick; stop following; the latch clears, since a host accumulating progress has no ended hold |
  | 3 | The step's reset (only a release, since a following step is latched) | Stop following; the latch clears with the release, and the step predicts from 0 under its own table |

**Display**
- The prediction never writes the slot store. Host samples land in the store as they arrive, so state crossings, conditions and store reads see only host samples (I2, O16). The prediction replaces `player.assistProgress` only in the UI display map that `App::build_ui_display_slot_snapshot` builds, the way `LifeStateDisplay` projects the life-state clock; a store write would be pulled back by a snapshot applied on a frame that runs no tick (O15). `build_ui_display_slot_snapshot` gains an `Option<client_assist::UiProjection>` parameter modelled on `life_state_display::UiProjection`, carrying the prediction, the step state and the increment the last forward-predicted tick advanced by on a connected client, or the host accumulator's per-helper row-6 record (the flag and its `required_ticks`) on a listen host or in single player, and the frame's render alpha. On every role the alpha term uses the increment of the last tick, never a pair table applied since. Its callers in `main.rs`, `loading_screen.rs`, `life_state_display.rs` and tests pass it.

- **Received progress.** The target client's displayed `player.assistReceivedProgress` never decreases between rendered frames unless a received sample is below its predecessor (AC9). `Ramp` is `pub(super)` in netcode's `state_slots/timed_slot_targets` module and runs on that module's sample timeline, so the projection lives there as its own stream beside the four weapon-fed ones, outside `NAMES`. It is a new type beside `Ramp`, which stays unchanged: `Ramp` ramps only after successive samples agree on a slope, so it would step on the first samples of every assist (O17). `accept_timed_slot_sample` feeds it the committed slot value from each accepted state batch with the snapshot's server tick, under the guards it already applies; `advance_timed_slot_targets` advances it, and `apply_timed_slot_targets`, which `App::build_ui_display_slot_snapshot` already calls, substitutes it in the display map. `reset_timed_slot_targets` clears it with the other streams.
- The stream's slope is known in advance: one increment of the received required ticks per server tick, `assist::increment(n)` over U, the rule Task 2a's step counts by. `accept_timed_slot_sample` takes that `required_ticks` as a new parameter, since it holds no registry, and never converts a `holdMs`. Netcode's `lib.rs` receive path reads it from `ClientReplication::received_required_ticks()`, which the same snapshot updated, so the slope always belongs to the helper whose progress the sample reports. The stream keeps an anchor (the newest sample s and its server tick t) and a displayed value. Its line at timeline time T is s plus the slope times (T − t), with T capped at t plus twice `SNAPSHOT_TICK_INTERVAL` server ticks, and at most 1. An anchor of 0 gives a flat line at 0: while no assist is received the display stays at 0 and never extrapolates. The first matching row applies:

  | # | Event | Stream action |
  |---|---|---|
  | 1 | Received required ticks of 0 or 1 | Show each sample raw; nothing divides by zero |
  | 2 | A sample above 0 after a sample of 0, or the stream's first sample | Show it at once (it may step up from 0) and anchor the line at it (O17) |
  | 3 | A sample below the previous sample (a helper released or reset, or a lower helper is now highest) | Show it at once and anchor the line at it (O18) |
  | 4 | A sample at or above the previous sample, whose line is at or above the displayed value | Anchor the line at it; the display keeps rising under the advance row |
  | 5 | A sample at or above the previous sample, whose line is below the displayed value (the host kept a gap-held tick while the stream extrapolated) | Anchor the line at it; hold the displayed value until the line overtakes it, never stepping down |
  | 6 | Timeline advance | When the line is above the displayed value, the displayed value rises toward it by at most twice the slope times the advance, then follows it; when the line is below, the displayed value holds |

- Success presentation (sounds, flashes) belongs to the authored `assistReceived` / `assistGiven` fire lists. Those run on host confirmation and route to each player's machine, so a prediction never plays one (AC9).

## Wire format

- **`WireMovementInput`** gains `assist_held: bool` beside `use_pressed`.
- **`WirePlayerMovementState`** gains `assistable: bool` beside `life_state`, true exactly when the current state declares `assistable`. `all_finite` is unchanged.
- **The local-pawn record** (the per-recipient record carrying `local_player`) gains, beside `last_processed_client_tick`:
  - `assist_pairs: WireAssistPairs`, a length-prefixed list of `(network_id: u32, radius: f32, required_ticks: u32)` entries sorted by `network_id`, one per other pawn whose state declares `assistable`. Radius 0 means this helper cannot assist that pawn; `required_ticks` 0 means held progress is kept, not advanced. An empty list means no assistable candidate. Entry count is bounded by the pawn count.
  - `received_required_ticks: u32`, 0 when no assist is received.

  Both are bitcode fields of the local-pawn record (`RawEntityRecord`, then `FullBaseline` and `Delta`), present behind one `has_assist_facts` flag, as `last_processed_client_tick` is present behind its own flag. They are authority metadata: `ingest_tick` refreshes them without minting a baseline, a change resends the owner's pawn at its held baseline as a moved resolved cursor does, and the client reads them from every local-pawn record it accepts, a held-baseline resend included. A record without `local_player` whose flag is set fails validation. Validation refuses a radius that is non-finite or outside [0, 16] and a pair-table or received `required_ticks` above 3600 (`required_count(60000)`). `postretro-net` declares both bounds itself, and a netcode drift guard pins them to the engine constants.
- `WIRE_VERSION` goes to the next value (39 at `b6fc0c4`).
- `SNAPSHOT_VERSION` goes to the next value (25 at `b6fc0c4`), with a history line, because `WirePlayerMovementState` and the local-pawn record ride the snapshot.
- `TUNING_PAYLOAD_EPOCH` goes to the next value (17 at `b6fc0c4`), with a history line.
- `TuningPayload.life_state_profiles` serializes `LifeStateProfile` itself, so the new `assistable` key, IR included, rides it with no payload code. `LifeStateProfile` denies unknown fields, so a reader on the old epoch rejects the payload: `TUNING_PAYLOAD_EPOCH` bumps, and `validate_life_states` refuses a literal outside its range. The payload carries only the pawn's own profiles; remote pawns' bools come from the movement state, and pair numbers only from the pair table.

## Script syntax examples

**Borderlands (dev mod, TS).** Spec A's policy plus revive, second wind and bonuses.

```ts
// player descriptor: Spec A's `down` gains (engine defaults: 1.5 m, 3000 ms)
assistable: {},

// player-death.ts, beside Spec A's goDown and bleedOut rows
players().on(assistReceived(), [revived]),  // on.player.setLifeState("alive"), on.player.grantHealth(30)
players().on(assistGiven(), [assistBonus]), // on.player.addSlot(progression.xp, 25)

// HUD: "Reviving" bar on player.assistProgress, "Being revived" bar on player.assistReceivedProgress

export const secondWind = defineImpactEvent("second-wind", { tag: "enemy" }, (impact) => {
  const { target, source } = impact;
  const killed = target.healthBefore.gt(0).and(target.healthAfter.le(0));
  return [{
    when: killed.and(source.inLifeState("down")),
    do: [source.setLifeState("alive"), source.grantHealth(40),
         update(progression.xp.byPlayer(source), (xp) => xp.plus(50))],
  }];
});
```

**L4D-style (Luau).** Only a teammate revives; no second wind, no bonus.

```lua
-- down = { ..., assistable = { radius = 2, holdMs = 5000 } }
players():on(assistReceived(), { revived })  -- on.player:setLifeState("alive"), on.player:grantHealth(30)
```

**Healer (TS).** A per-owner `heal` stat shortens the helper's revive; a target in a `downMedic` state can be revived from farther away.

```ts
export const stats = defineStore("stats", {
  heal: { type: "number", default: 0, perOwner: true, network: "ownerPrivate" },
});

// down profile
assistable: {
  holdMs: read(stats.heal.byPlayer(assist.helper)).times(-20).plus(3000), // above 60000 clamps; a negative result is a fault
  radius: assist.target.inLifeState("downMedic").select(3, 1.5),
},
```
