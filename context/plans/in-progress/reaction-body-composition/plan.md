- Path's SDK bullet names only `sdk/lib/**` → `sdk/types/postretro.d.{ts,luau}` are generated by `gen-script-types` (`scripting-core/src/typedef/`) and `sdk/type-tests/*.ts` check them with `tsc -p sdk/type-tests`. Planning around it by changing the typedef generator, regenerating both files, and proving the compile-time rejections as type-tests.
- Path "Split first" lists files past ~800 lines → non-test source today: `reaction_scheduler.rs` 758, `reaction_validation.rs` 581, `system_reactions.rs` 853, `light_membership.rs` 1555, `main.rs` ~12.7k; `data_script.ts` 836 and `data_script.luau` 1083 are whole-file. Planning around it by splitting only the file a task extends substantially, before that task, in its own behavior-preserving commit: `reaction_scheduler.rs` (the client role pushes it past 800) and `system_reactions.rs` (IR-binding walk) are expected. `light_membership.rs` gets a few lines and is not split. `main.rs` is kept to call-site wiring; if `dispatch_system_commands` must grow, it moves to its own module first.
- Path "`sequence_primitives_are_valid` consults `SystemReactionRegistry`" → threading the system registry into `validate_sequence_primitives` reaches 28 call sites, the staged mod-init commit among them. Planning around it by checking a `System` step against `SystemReactionKind::from_primitive_name`, which the parser already enforced; the sim test `registers_exactly_the_classified_system_reaction_kinds` keeps that list equal to the registered system primitives.
- Path "`drain_landings` installs the stored origin … each drain's deferred follow-ups carry that class and clock beside the origin" → the class and clock ride inside the origin instead: `FireOrigin::EveryMachine(MachineSource::{HostTimeline, HostMirrored, OwnState})`. `follow_up` keeps the source, so the `(name, FireOrigin)` follow-up channel and every `fire`-seeded child inherit it with no new field. The scheduler reads it from the fire context at enrollment; the `wait` control handler now receives the dispatching `ScriptCtx`.
- Path "Give capture a host-landing flag spanning both" → it is `ScriptCtx::landing` (`entities` `reactions/machine_local.rs`), a scope the scheduler enters for one landing's tail and follow-ups. The same scope carries the client landing mode (land, or converge for a late joiner), which `dispatch_sequence` and both primitive arms read to drop non-machine-local steps, so a `fire` target reached from a client landing passes the same filter.
- Running tests here needs `LANG` set (`LANG=en_US.UTF-8`): without a system locale, `ghost_link_twins_install_the_scripting_surface_with_zero_warnings` sees a locale warning unrelated to this brief.
- Path "Client tails … advanced by the connected-client tick" → today `scheduler.evaluate` runs only in the host tick loop (`frame_loop/mod.rs`, after the fixed tick), while `begin_frame` and `drain_landings` already run on every role (a disabled scheduler drains nothing). Planning around it by adding the client advance in the connected-client tick branch of the same loop, and leaving the two existing calls alone.
