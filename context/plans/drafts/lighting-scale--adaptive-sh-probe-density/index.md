# Lighting Scale — Adaptive SH Probe Density

> **Status:** draft. Spike-led thin vertical slice. **Gated on its own Task 1 measurement** — Tasks 2+ proceed only if the spike confirms the measured entry population distributes across levels and drops well enough to deliver a substantial bandwidth reduction and a bindable section.
> **Track:** Lighting / build pipeline — the storage-density root-cause lever behind the direct-SH delta's per-frame bandwidth and storage-buffer wall (measured scaling exponent ≈2.4–2.95 in probe density; Measured basis below).
> **Related:** `context/lib/build_pipeline.md` §Octahedral irradiance volume bake, §PRL section IDs (id 34/35 base atlases, id 27/41/45 deltas) · `context/lib/rendering_pipeline.md` §4 (Animated SH delta volumes / Baked direct for dynamic receivers / Promoted static lights), §7.1 step 5 (SH compose passes) · `context/plans/done/lighting-scale--sh-delta-footprint-instrumentation/` (the shipped measurement prerequisite whose recorded evidence this consumes) · `context/plans/done/sh-array-atlas/` (base-atlas D2→D2Array, landed) · `context/plans/done/perf-animated-sh-light-culling/` (the sparse-CSR affinity-cell delta form this extends, and its findings note) · `context/lib/experimental_spikes.md`.

## Goal

**Reduce the per-frame memory bandwidth of the direct-SH compose, measured against the recorded status quo — not toward a byte target.** The direct-SH delta (`DirectShDeltaVolumes`, PRL id 41) stores one dense 64-probe brick per `(affinity cell, selected light)` CSR entry, and the compose pass streams that storage every frame:

- The direct compose dispatches **every frame while any promoted light's weight is nonzero** — `direct_compose_should_dispatch` returns true whenever `active` (`crates/renderer/src/render/direct_sh_compose.rs:595-601`), and `active` is "any promoted weight > 0" (`crates/renderer/src/render/renderer_render_frame.rs:239-244`), matching `context/lib/rendering_pipeline.md` §7.1 step 5 ("while any weight is nonzero").
- It dispatches one invocation per composed-atlas texel (`crates/renderer/src/render/direct_sh_compose.rs:305-315`; bounds check `crates/renderer/src/shaders/direct_sh_compose.wgsl:131-139`), and `map_atlas_texel` maps **every** texel of each 6×6 tile, border texels included — there is no interior-only exclusion (`crates/renderer/src/shaders/direct_sh_compose.wgsl:54-85`).
- Each invocation loops its cell's CSR entries and reads 8 bytes per entry — two `u32` words through `unpack2x16float` (`crates/renderer/src/shaders/direct_sh_compose.wgsl:108-116`, loop at `crates/renderer/src/shaders/direct_sh_compose.wgsl:165-175`), skipping entries whose selection weight is zero (`crates/renderer/src/shaders/direct_sh_compose.wgsl:167-168`).
- Every `(entry, local probe, tile texel)` address is distinct, so across a cell's 64 probes × 36 texels = 2,304 invocations, each stored byte of each active-light entry is read **exactly once per frame**: 2,304 × 8 B = 18,432 B per entry — exactly the stored brick size.

**Per-frame delta read volume equals the stored payload, restricted to active lights.** Bytes removed from the pool are bytes removed from every frame's bus traffic; storage reduction and bandwidth reduction are the same lever, measured by the same number. At the measured configurations (all-lights-active, 60 fps upper bound — the zero-weight early-out reduces it in practice): 2.0 m spacing streams ~383 MiB/frame ≈ 24.1 GB/s, ~13% of a GTX 1060's ~192 GB/s rated bandwidth; 1.33 m streams ~1.22 GiB/frame ≈ 78.4 GB/s, ~41% of the card; the 1.0 m shipping default computes to ~2.40 GiB/frame ≈ 155 GB/s, ~81% of the card's entire bus — for one compose pass.

The mechanism: replace uniform per-cell storage density with **adaptive** density — full 64-probe bricks near surfaces, 8-probe corner bricks where the delta varies slowly, single-probe bricks where it is nearly flat, dropped entries where a light's contribution is negligible. Absolute byte thresholds are **constraints, not goals**: the 128 MiB WebGPU `max_storage_buffer_binding_size` spec floor decides whether an emitted section can bind on spec-floor hardware at all, and the 64 MiB bake-cap default prices the pool against the 3 GB-floor card (Hardware target section) — but success is a measured before → after reduction in per-frame delta traffic, compose dispatch time, and resident bytes, recorded in Task 6, never a number an agent loops toward. This spec leads with a measurement spike that decides whether the level/drop distribution delivers before committing the format change.

## Measured basis

Probe-spacing sweep on `content/dev/maps/stress-warren-maze-crates.map`, release `prl-build`, warm cache, 4 cores, `--lightmap-density 0.8 --soft-shadow-samples 64` held fixed so probe spacing is the sole variable (lightmap density does not affect SH probe counts — the delta payload is a pure function of CSR entries):

| `--sh-probe-spacing` | CSR entries | direct-delta bytes | total SH bytes |
|---|---|---|---|
| 2.0 m | 21,764 | 401,154,048 | 447,193,334 |
| 1.6 m | 41,070 | 757,002,240 | 841,864,606 |
| 1.33 m | 70,848 | 1,305,870,336 | 1,448,845,134 |
| 1.0 m (shipping default) | 139,909 | 2,578,802,688 | n/a — bake OOM-killed |

- **The harness is trustworthy:** the 2.0 m run reproduced the recorded instrumentation evidence (2026-08-04) byte-exactly.
- **Payload is exactly 18,432 B × CSR entries at every spacing.** 18,432 = `PROBES_PER_CELL` (64, `crates/level-format/src/delta_sh_volumes.rs:28`) × tile_dimension² (6² = 36 texels, border included — `DEFAULT_IRRADIANCE_TILE_DIMENSION`, `crates/level-format/src/octahedral.rs:7`) × `DELTA_TILE_TEXEL_F16_COUNT` (4, `crates/level-format/src/delta_sh_volumes.rs:31`) × 2 B (`DEFAULT_DELTA_PROBE_BYTES` = 288, `crates/level-format/src/delta_sh_volumes.rs:40`; per-tile stride fn at `crates/level-format/src/delta_sh_volumes.rs:313-315`). Entry count is the sole driver. The recorded largest light confirms the same identity: 528 entries × 18,432 = 9,732,096 B.
- **1.33 m measures 1,305,870,336 B = 1.216 GiB — the ~1.22 GiB incident is a reproduced measurement.** The incident's configuration paired 1.33 m with `--lightmap-density 0.2`; the sweep's 0.8 run lands the same bytes, confirming lightmap-density independence.
- **Scaling is ~n^2.4–2.95, flattening as cells saturate:** pairwise exponents 2.0→1.6 m k≈2.85, 1.6→1.33 m k≈2.95, 1.33→1.0 m k≈2.39. Cubic extrapolation from 2.0 m to 1.33 m overestimates the measured value by ~4.5%.
- **The shipping default is the worst case, not 1.33 m:** `DEFAULT_PROBE_SPACING = 1.0` (`crates/level-compiler/src/sh_bake.rs:33`) is 2× denser than the sweep's 1.33 m row. At 1.0 m the uniform payload is 2.40 GiB.
- **Recorded finding, out of scope:** the 1.0 m bake was OOM-killed at ~15.9 GB RSS (kernel-confirmed) after writing a 2.93 GB `.prl`. Host-RAM bake cost is explicitly not this spec's problem; no task or AC addresses it.

This spec's **dense measurement configuration** is `--sh-probe-spacing 1.33 --lightmap-density 0.8 --soft-shadow-samples 64` — the densest configuration with a recorded uniform baseline that completes on the measurement host. The 1.0 m uniform baseline is known exactly from the identity (139,909 × 18,432 B) even though the bake did not complete.

## Scope

### In scope

- **Task 1 spike (gate).** A bake-time, output-preserving analysis pass over the emitted direct-SH delta CSR: classify each emitted affinity cell by surface proximity, compute each brick's coarse-reconstruction error at **both coarse levels** from the already-baked probe data, and report the **projected** pool bytes — which, by the read-equivalence in the Goal, is also the projected per-frame delta traffic — under the level/drop policy, on the stress map at the dense measurement configuration. Changes no baked bytes. Gates everything below.
- **Three stored density levels per affinity cell + dropped entries, end-to-end through the live direct-SH delta path.** Level 0: full 64-probe brick (v1-identical). Level 1: 8-probe corner brick, trilinear reconstruction. Level 2: single-probe brick, broadcast reconstruction. Dropped: entry absent from the CSR. The 4×4×4 affinity brick is the existing primitive — the gap is a *per-cell level* + *per-entry pool offset indirection* + *cap*, not a new spatial structure. The rescope arithmetic that makes three levels the floor and rejects both two-level and an arbitrary-depth tree is in Direction.
- **Entry dropping as a co-primary mechanism, not a secondary.** Dropping is the only lever that removes compose loop iterations as well as bytes — a coarse brick still costs an entry iteration per invocation (and level 1's trilinear read issues 8 loads per invocation, trading DRAM traffic for cache hits), while a dropped entry costs nothing. Task 1 measures the near-zero population as a first-class classifier output, and Task 3's emission treats the drop threshold as a peer of the level thresholds.
- **An indirection** from CSR entry → (level, contiguous pool offset), carried in the id-41 section (version bump 1→2) and consumed by the direct compose pass — the Unity APV `ProbeBrickIndex` / Unreal VLM indirection-texture analog, collapsed to the affinity-cell CSR this engine already has.
- **A bounded pool / hard memory cap** on the adaptive delta pool bytes (the Unreal VLM *Maximum Brick Memory* analog, with fail-loud instead of Unreal's silent detail-brick culling). The bake fails loud with a named error when over cap; the loader independently re-validates and rejects, all-or-nothing.
- **Runtime integration on the direct path only:** the direct compose compute pass reads bricks through the indirection and reconstructs coarse cells' per-probe deltas; the composed direct atlas output is unchanged, so **no sampler shader changes** (warrant below, Rough sketch).
- **Logging discipline:** one-line footprint/level-histogram summaries at `log::info` in prl-build; per-cell detail behind `-v/--verbose`; runtime footprint once per load (dev-tools builds); nothing per-frame.
- **Task 6 findings note:** before → after per-frame delta read volume, compose dispatch time, and resident bytes, each with its ratio; the binding-floor consequence; and the fallback decision (is a delta texture-array migration still worth drafting).

### Out of scope (non-goals)

- **The indirect `DeltaShVolumes` (id 27) path.** Same CSR shape, would benefit identically, but the thin slice proves adaptivity on the **direct** delta — the dominant payload (401 MB of 447 MB SH total at 2.0 m; id 27 measured 37.5 MiB on campaign-test after the sparse-CSR work; note the indirect compose runs unconditionally every frame, `context/lib/rendering_pipeline.md` §7.1 step 5, so it is a real follow-on bandwidth consumer). Extending to id 27 is deferred breadth, recommended-or-not in Task 6. Nothing forecloses it: id 27 shares `AFFINITY_FACTOR`, `PROBES_PER_CELL`, and the CSR conventions (`crates/level-format/src/delta_sh_volumes.rs:18-40`), so the id-41 contract is directly transplantable.
- **Adaptive packing of the base SH atlases (id 34/35).** Already `texture_2d_array` (sh-array-atlas); their pressure was a 2D-dimension limit, not the storage-buffer wall. The base probe grid is consumed as-is. Foreclosure cost of deferring: none — the composed-atlas output shape is deliberately preserved (Invariant I1), so a later base-atlas change meets the same seam.
- **An arbitrary-depth subdivision hierarchy / coarser-than-cell merging** (APV/VLM brick trees whose nodes span multiple grid cells). The slice ships three stored levels *within* the fixed affinity grid; merging affinity cells into coarser nodes would change cell geometry (against Invariant I8) and the rescope arithmetic in Direction shows it is not needed: the three-level all-coarse limit already lands under the 64 MiB budget at the shipping default. The wire contract keeps the level field wide enough that more levels are additive (Wire format).
- **Per-cluster streaming / residency of bricks.** Separate epic. Priced: the pool stays CSR-per-affinity-cell with whole-brick contiguity, which is the cell-alignable shape a residency system would want; nothing here fights it.
- **Probe relocation / virtual offset** (moving bake sample positions out of geometry — DDGI relocation, APV virtual offset). Base probe positions are untouched; this spec changes which probes *store delta data*, not where any probe sits. The engine's shipped analog for bad probes is sampling-side: per-probe `validity` plus Chebyshev depth-visibility weighting (`context/lib/rendering_pipeline.md` §4 "Indirect", "Probe depth moments"). Priced: nothing here writes or forecloses probe positions; a relocation spec would touch `sh_bake.rs` probe placement, which this spec does not modify.
- **Runtime re-subdivision when lights move.** Selected lights are static-positioned; adaptivity is a bake-time spatial decision.
- **Lowering `REQUIRED_STORAGE_BUFFER_BINDING_SIZE`.** The stopgap is currently **2 GiB − 8** (`crates/renderer/src/render/renderer_init_resources.rs:126-134`), documented as load-bearing on above-spec hardware. Shrinking the requested constant waits until the indirect path (id 27 on large maps) is also confirmed under floor — Task 6 records the state.
- **Bake-time host-RAM cost.** The 1.0 m OOM finding (Measured basis) is recorded and explicitly not solved here — no task, AC, or scope addresses bake-host memory.
- **Probe/SH order and tile geometry changes.** `tile_dimension = 6`, `tile_border = 1`, the octahedral encoding, and the f16 tile payload are unchanged (`crates/level-format/src/direct_sh_delta_volumes.rs:32-33`, `crates/level-compiler/src/direct_sh_bake.rs:76-77`); only which probes are stored at what density changes.
- **Bake-time reduction.** Neutral-to-favorable side effect, not a goal.

## Direction

**Problem.** The direct-SH delta stores a dense 64-probe brick for every `(reached affinity cell, selected light)` pair regardless of whether the cell is open air where per-light direct irradiance varies slowly — and the compose pass re-reads every stored byte of every active light **every frame** (Goal). So payload scales as probe density^≈2.4–2.95 times per-light reach (Measured basis), and at the 1.0 m shipping default the uniform scheme computes to ~81% of a GTX 1060's entire memory bandwidth for one pass. Cause, not symptom: the 2 GiB−8 limit stopgap and the reproduced 1.216 GiB measurement at 1.33 m are both downstream of uniform per-cell storage density.

**Rescope arithmetic — why three levels, why not two, why not a tree.** The constraint side: binding at the 128 MiB WebGPU floor requires a 9.73× reduction at 1.33 m (1,305,870,336 / 134,217,728) and **19.2× at the 1.0 m shipping default** (2,578,802,688 / 134,217,728); the 64 MiB hardware-budget default requires 19.5× and 38.4×.

- *Two levels (64/8 probes) + drops:* coarsening's structural ceiling is 8× — in the degenerate all-coarse limit the pool is still **155.7 MiB at 1.33 m and 307.4 MiB at 1.0 m, over the binding floor with zero full-density cells**. Reaching the floor at the shipping default then requires drops to carry almost everything: with 5% of entries kept full, the byte fraction budget 1/19.2 = 0.052 forces coarse ≤ 1.7% and **drops ≥ 93%**; even at 2% full, drops ≥ 72%. Two-level-plus-drops is therefore a bet that ≥³⁄₄ of all entries are perceptually negligible — possible (the perf-animated findings measured 11.3% within-cell occupancy on the indirect path) but an extreme, spike-falsifiable assumption to build the format on.
- *Three levels (64/8/1 probes) + drops:* a level-2 single-probe brick stores one tile (288 B, 64× reduction) and broadcasts it across the cell. The all-L2 structural limit at the shipping default is 139,909 × 288 B = **38.4 MiB — under even the 64 MiB budget by construction, before any drops**. Realistic mixes need no extreme assumptions: e.g. 3% full + 10% corner + 60% single-probe + 27% dropped = 0.03 + 0.0125 + 0.0094 = 0.0519 → 19.3×, the shipping-default floor requirement. The far field of a broad-reach light — smooth but *not* negligible, exactly the population drops cannot touch — is what level 2 exists for. Marginal cost over two levels: one reserved level value the wire format already accommodates, one classifier threshold, and a broadcast reconstruction arm that is *cheaper* to read than level 1 (one 8 B load per invocation, same as level 0, vs. trilinear's 8 loads).
- *Arbitrary-depth tree / coarser-than-cell merging:* beyond 64× per cell, extra depth helps only where a region is smoother than "one tile per 4³-probe cell" — and such entries are near-zero candidates for the drop class anyway. The three-level all-coarse limit already clears the tightest constraint at the densest shipping configuration, merging cells would break the affinity-cell geometry invariant (I8), and Godot — the closest posture peer — ships no deep tree on its baked path at all (survey below). Rejected on arithmetic, not deferred on effort.

**Why drops are co-primary.** Per-frame cost has two components: bytes streamed and loop work per invocation. Coarsening cuts unique bytes 8×/64× but every surviving entry still costs an iteration in every one of its cell's 2,304 invocations — and level 1's trilinear read issues 8 loads per invocation (64 B issued against 8 B unique; the reuse is cache-served, so DRAM traffic still falls ~8×, but load-issue count rises). A dropped entry removes its bytes *and* its iterations *and* its loads. Dropping is the only lever that reduces instruction count along with traffic, which under a bandwidth objective makes it a peer of the level mechanism, not a bonus.

**Prior commitments.** (0) **Hardware target (owner, this spec forward): very performant on NVIDIA GTX 10-series, at least runnable on laptops.** This is stricter than the documented envelope — `context/lib/rendering_pipeline.md` §10 names the GTX 16-series (Turing) as the perf floor — and this spec diverges deliberately: Pascal 10-series is the binding constraint for its numbers (budget section below). Capture the widened floor in `context/lib/` at promotion, not during drafting. (a) The instrumentation spec (`context/plans/done/lighting-scale--sh-delta-footprint-instrumentation/index.md`, Goal) commits to "a sparse layout under the 128 MiB WebGPU spec floor" as the tracked end-state — that floor persists here as the binding-correctness constraint. (b) `perf-animated-sh-light-culling` locked `AFFINITY_FACTOR = 4` as a workgroup-coupled invariant and shipped the CSR + portal-reach clip this extends; its findings note measured **11.3% within-cell occupancy** on the indirect path and named a variable-stride fork as the latent optimization — this spec is that fork's direct-path sibling, with a level indirection instead of an occupancy bitmap. (c) Pre-release no-compat-shim policy (`context/lib/development_guide.md` §1.6): version bump, reject old sections, no migration. (d) The all-or-nothing direct-delta reject posture (`context/lib/build_pipeline.md` §DirectShDeltaVolumes) is preserved, not relaxed.

**Alternatives rejected.**
- *Per-light outlier culling / footprint gating:* killed by measurement — the largest light is ~9.3 MiB of 383 MiB at 2.0 m; the burden is structural, spread over many broad-reach lights.
- *Two-level scheme:* rejected as under-powered by the rescope arithmetic above — its 8× coarsening ceiling cannot reach the binding floor at either dense configuration without extreme drop rates.
- *Delta texture-array migration* (move `delta_subblocks` out of a storage buffer into a `texture_2d_array`, escaping `max_storage_buffer_binding_size`): rejected as the *primary* lever, but **not** because it saves nothing — that dismissal would be wrong, and the honest comparison matters if the gate fails. Moved as-is it only relocates bytes: VRAM, disk, and per-frame traffic keep their measured scaling, and the compose read gets more complex (texel addressing vs. the flat two-word load at `crates/renderer/src/shaders/direct_sh_compose.wgsl:110-116`). Its real attraction is that a texture can carry **block compression where a storage buffer cannot**, and this engine already ships BC6H for the irradiance atlas at ~8× smaller in VRAM (`context/lib/rendering_pipeline.md:95`) — a win of the same order as adaptive density, and one that cuts per-frame read traffic too. Two things qualify it, one of which is weaker than it looks: BC6H being RGB-only is **not** an obstacle, because every compose pass consumes `.rgb` only and never reads the fourth half (`direct_sh_compose.wgsl:173`, `sh_compose.wgsl:214`, `animated_direct_sh_compose.wgsl:215`), even though the format stores 4 halves per texel (`DELTA_TILE_TEXEL_F16_COUNT = 4`, `crates/level-format/src/delta_sh_volumes.rs:31`). The genuine obstacles are that deltas are **signed** (they ring negative — `direct_sh_compose.wgsl:169-173` — so it needs the `Bc6hRgbSfloat` variant, not the `Bc6hRgbUfloat` already in use) and that block compression is **lossy applied to a difference signal**, where error is more perceptible than on absolute radiance. So the reason to prefer adaptive density is that it removes bytes without a lossy-format gamble and without a second decode path — not that the alternative is worthless. The two are also **largely non-additive**: if adaptivity lands the pool near the hardware budget, compressing it further buys little against real quality risk. Note **no such spec exists in `context/plans/`** — the Task 6 decision is whether it ever needs drafting, not whether an existing spec is retired.
- *Occupancy bitmap with variable per-cell stride* (the perf-animated findings fork): stores only non-zero probes; finer-grained than level bricks but needs a per-cell popcount/prefix-sum on every shader read and has no notion of coarse *reconstruction* — it can only drop zeros, not thin slowly-varying regions. The level scheme subsumes its win where deltas are near-zero (drop the entry) and beats it where deltas are smooth-but-nonzero (coarse brick).
- *Silent degrade-to-fit* (Unreal's Maximum Brick Memory culls the most-detailed bricks until under budget): rejected — silent quality contraction violates the house fail-loud posture; the author gets a named error and chooses density or cap.

## Hardware target and memory budget

The owner's target binds this spec's numbers: **very performant on GTX 10-series, at least runnable on laptops.**

**Bandwidth reality (the objective's denominator).** The GTX 1060 6GB — the realistic volume target — has ~192 GB/s of rated memory bandwidth shared by every pass in the frame. The compose pass's measured per-frame delta traffic (Goal: reads equal stored payload of active lights, every frame while any promoted weight is nonzero): 2.0 m ≈ 24.1 GB/s at 60 fps (~13% of the card), 1.33 m ≈ 78.4 GB/s (~41%), 1.0 m shipping default ≈ 155 GB/s (~81%) — upper bounds assuming all promoted lights active, but the frame has to budget for the worst case. On laptop iGPUs sharing system DRAM the same traffic is a proportionally larger fraction of a much smaller bus. This is what "reduce bandwidth over status quo" prices: every byte the adaptive scheme removes is removed from this per-frame stream.

**VRAM reality.** The 10-series spans ~3 GB (1060 3GB, 1050) to 8 GB (1070/1080); the **1060 6GB is the realistic volume target**, the **3 GB parts and shared-memory laptop iGPUs are the floor**. The delta pool is one consumer among many: at the 2.0 m sweep row, *total* SH sections were 447 MB of which the direct delta was 401 MB — and baked-lighting residency also includes the lightmap atlases, the base id-34/35 atlases, the runtime-composed direct atlas (a second full-size `Rgba16Float` D2Array when promotion is active — created at `crates/renderer/src/render/sh_volume.rs:549-554`, format pinned at `crates/renderer/src/render/sh_volume.rs:1160-1180`), the shadowmask atlas, and the shadow pools, before any texture, geometry, or framebuffer byte. On the 3 GB floor, **total baked-lighting residency should stay under ~1 GB**, which prices the direct-SH delta pool at **tens of MiB, not hundreds**.

**Constraints, not targets (consumed by Task 4).** The engine-side loader ceiling stays **128 MiB** — the WebGPU `max_storage_buffer_binding_size` spec floor, a *binding-correctness* bound: it exists to guarantee an accepted section binds on any WebGPU-spec device, and is not a quality judgment. The bake-side `--direct-delta-max-size` default is **64 MiB** — ~2% of the 3 GB floor card, leaving room for the rest of the lighting stack; a map that needs more raises the knob deliberately (up to the loader ceiling) and the findings note records the tension. Neither number is a goal any task iterates toward: the bake emits what the classifier chooses and fails loud if that exceeds the cap; Task 6 records where the measured result landed relative to both, and revisits the numbers with measurements in hand.

**Pascal fp16 (consumed by Task 5).** Consumer Pascal (compute capability 6.1: GTX 1050–1080) executes native fp16 arithmetic at **1/64 the fp32 rate** — a hardware cliff, per NVIDIA's Pascal tuning guidance and community measurements (search-extract sourced). The current compose pass is already on the right side of it: `delta_subblocks` stays f16 **at rest** (no CPU expansion — `crates/render-cpu/src/sh_compose.rs:250` and the keeping-f16 round-trip test at `crates/render-cpu/src/sh_compose.rs:452`; raw u16 bytes uploaded at `crates/renderer/src/render/direct_sh_compose.rs:379-383`), and the shader converts on read via `unpack2x16float` — which returns `vec2<f32>` — so every arithmetic operation in `compose_main` is f32 (`crates/renderer/src/shaders/direct_sh_compose.wgsl:108-116,141-177`). **This is the contract: f16 storage, f32 arithmetic.** Task 5's coarse-brick reconstruction must keep it; do not introduce WGSL `enable f16` / native half arithmetic into this pass as an "optimization" — on the target hardware it is a 64× slowdown, not a win.

**Perf posture.** The compose pass dispatches **every frame while any promoted light's weight is nonzero** (Goal; `direct_compose_should_dispatch`, `crates/renderer/src/render/direct_sh_compose.rs:595-601`) — the adaptive read is per-frame hot-path work, not load-time-only work. The indirection adds one fetch per CSR entry; level-1 cells add an 8-tap trilinear reconstruction per texel (8 loads issued, cache-served, DRAM traffic still ~8× lower than a full brick); level-2 cells read one texel, the same issue count as level 0 at 1/64 the traffic; dropped entries cost nothing. Task 6 records the before/after dispatch time and names the adapter measured on; a 10-series measurement is preferred where available, and the findings note must say which class of GPU produced the number.

## Rough sketch

**Slice shape — thin vertical slice, spike-first.** The uniform→adaptive change is fundamentally a new indirection *contract* consumed across compiler, format, loader, and one compute pass; proving it once through the live direct path — the dominant payload and the per-frame bandwidth consumer — locks the contract with real data before any fan-out (id 27, streaming, per-probe occupancy). Specifying the full adaptive system up front is the monolith the roadmap's sibling-spec guidance warns against; the fan-out fork is decided in Task 6 on measured data.

**The primitive already exists; the gap is level + offset + cap.** `AFFINITY_FACTOR = 4` / `PROBES_PER_CELL = 64` (`crates/level-format/src/delta_sh_volumes.rs:25,28`; compiler mirror `crates/level-compiler/src/affinity_grid.rs:35`), the portal-reach clip (`decompose_affinity_for_lights`, `crates/level-compiler/src/affinity_grid.rs:134-187`), and the CSR (`crates/level-compiler/src/direct_sh_bake.rs:349-353`) are shipped. Unity APV and Unreal VLM are this brick + a per-region subdivision level + an index + a bounded pool; the slice adds exactly those three, collapsed onto the existing CSR.

**Where the win comes from — bytes and frames at once.** Every reached cell today stores 18,432 B per light (Measured basis identity), and by the read-equivalence in the Goal the compose pass streams exactly those bytes every frame per active light. A level-1 cell stores and streams 2,304 B (8×); a level-2 cell 288 B (64×); a dropped entry stores nothing, streams nothing, and — uniquely — removes its loop iteration from all 2,304 of its cell's invocations. The rescope arithmetic (Direction) shows the three-level mix reaches the shipping-default constraint envelope with unremarkable class fractions, where two levels required drops ≥72–93%.

**Measurement basis.** The four-spacing sweep (Measured basis) supersedes extrapolation: the 2.0 m row is byte-identical to the 2026-08-04 instrumentation evidence, the 1.33 m row reproduces the historic ~1.22 GiB incident as a measurement, payload is exactly 18,432 B × entries at every spacing, and the pairwise scaling exponents are 2.85 / 2.95 / 2.39. What is validated: per-cell storage density is the right *kind* of lever (structural, many-light, entry-count-driven). What is not yet validated: how the stress map's entry population distributes across the four classes — precisely Task 1's job on the dense measurement configuration.

**Contract discipline.** Per the style guide, this spec states constraints (per-entry level; entry→(level, offset) indirection; whole-brick contiguity; hard cap; version bump; the level-0/1/2 probe subsets and reconstruction rules) and leaves field ordering, integer packing, and threshold values to the implementer, who sees the whole picture when landing.

**Grounding notes (verified against this tree).** `DEFAULT_PROBE_SPACING = 1.0` at `crates/level-compiler/src/sh_bake.rs:33`; the uniform grid derives from the world AABB in `probe_grid_layout` / `grid_dimensions` (`crates/level-compiler/src/sh_bake.rs:148-190,408`). `--sh-probe-spacing` CLI at `crates/level-compiler/src/main.rs:658-666`. `REQUIRED_STORAGE_BUFFER_BINDING_SIZE = 2 GiB − 8` (stopgap, documented load-bearing) at `crates/renderer/src/render/renderer_init_resources.rs:126-134`, requested at `crates/renderer/src/render/renderer_init_resources.rs:156`, pre-checked at `crates/renderer/src/render/renderer_init_resources.rs:189-198`. Direct compose bindings: subblocks 20 / offsets 21 / lights 24 / weights 26 (`crates/renderer/src/render/direct_sh_compose.rs:20-26`); the runtime `selection_weights` buffer is not PRL payload. The dev-tools footprint instrumentation (`ComposeStorageFootprint`, `crates/render-cpu/src/sh_compose.rs:26-63`) already logs the direct promotion bindings once per construction (`crates/renderer/src/render/direct_sh_compose.rs:366-370`). No adaptive/level/indirection concept exists anywhere in the SH code today — Tasks 3–5 are net-new on that axis.

## Wire format

The adaptive fields ride the existing `DirectShDeltaVolumesSection` (PRL id 41), whose v1 layout — version byte, `affinity_factor`, `affinity_dims`, `tile_dimension`, `tile_border`, CSR `affinity_offsets`/`affinity_lights`, flat f16 `delta_subblocks` — is documented in-source at `crates/level-format/src/direct_sh_delta_volumes.rs:14-27`. Version 2 mirrors v1's conventions exactly: little-endian throughout; integer widths and signedness follow the current section; the payload's first byte is the bumped `DIRECT_SH_DELTA_VOLUMES_VERSION`, and any other version rejects at parse with the existing named error. Constraints for the v2 additions (field order, packing, and exact encodings are implementer-pinned at landing):

- A **per-CSR-entry level**, integer-encoded with room for more than three values (levels beyond 0/1/2 are reserved, rejected at parse for now). Level 0 = 64-probe full brick, x-fastest in-cell order (v1-identical). Level 1 = 8-probe corner brick: in-cell local coordinates ∈ {0,3} per axis, x-fastest order among the 8, reconstructed trilinearly with per-axis weights `local/3`. Level 2 = single-tile brick: the cell-mean delta tile, reconstructed by broadcast to all 64 probes.
- A **per-CSR-entry pool offset** into `delta_subblocks`, in f16-half units, `u32`-representable at the maximum capped pool size. Offsets monotonic non-decreasing in entry order; entry byte size is a pure function of its level and `tile_dimension`; bricks are contiguous and never split; the final entry's end equals the pool length (exact coverage — no slack, no overlap).
- `affinity_lights` values remain selection indices (Invariant I4). `affinity_offsets` (cell → entry range) is unchanged from v1.
- Empty/absent encodings follow v1: no usable entries → the section is not emitted (the bake returns `None`, `crates/level-compiler/src/direct_sh_bake.rs:314-353`); a per-cell "no entry for this light" — including a dropped entry — is simply the entry's absence from the CSR.
- Structural validation at parse mirrors v1's posture (`crates/level-format/src/direct_sh_delta_volumes.rs:86-215`): truncation, monotonicity, level validity, offset bounds, and exact pool coverage are all parse-time rejects; selection-index bounds remain the loader's job (`validate_direct_sh_delta`).
- The invariant the whole format serves: a world-position read resolves deterministically — probe → affinity cell → CSR entry range → (level, offset) — to one contiguous brick or an explicit absence, and summed pool bytes never exceed the declared cap.

## Open questions / risks

- **How does the stress map's entry population distribute across the four classes?** The plan's gate. The three-level scheme's structural range (1×/8×/64×/drop) covers the measured constraint envelope by construction (Direction), but whether the *classifier* assigns enough entries to the coarse and drop classes without visible error is empirical — exactly Task 1's job. The stop-and-fork condition is the hard constraint only (a projection that cannot bind at the 128 MiB floor), never a soft byte target.
- **Seams at density boundaries.** Adjacent cells at different levels reconstruct differing delta values at neighboring probes; level 2's broadcast is the flattest reconstruction and the likeliest seam source. The discontinuity is bounded by intra-cell delta variation, which is exactly what the classifier keeps small — and Task 1's reconstruction-error measurement at both coarse levels quantifies it before any bytes change, which is the strongest de-risking available short of shipping. Residual risk (a mis-chosen threshold) is watched by the manual-visual AC at density boundaries specifically, including level-2 cells.
- **Threshold choice.** Surface-distance class boundaries, the level-1/level-2 split, and the near-zero drop threshold are picked in Task 3 from Task 1's data, as compile-time constants (not author-facing knobs — the only knob this spec adds is the memory cap). If the spike shows proximity is a poor proxy for reconstruction error, Task 3 switches to the error-threshold policy directly; the format is policy-agnostic either way. The drop threshold deserves the most care: dropped entries are the co-primary lever, and an aggressive drop is the one class with no reconstruction at all.
- **Constraint tiers.** The two tiers (64 MiB bake knob from the hardware budget; 128 MiB loader ceiling from the WebGPU floor) are principled but untested against real dense maps; if the adaptive dense-stress result lands between them, the flagship map fails the default knob and the author must raise it deliberately — loud by design, but friction worth recording. Task 6 revisits both numbers with the measurement in hand.
- **Oversized-file exposure.** Non-test source: `direct_sh_bake.rs` 929 lines (split task 2), `sh_bake.rs` 1207 (not extended here — only `probe_grid_layout` is read), `sh_volume.rs` 1339 (not extended — Task 5 confirms no delta-payload edits land there), `direct_sh_compose.rs` 602 (extended in place, under the split-first threshold). The slice deliberately keeps the indirect path (`sh_bake.rs`, `sh_compose.rs` indirect pass, `sh_group` cache) untouched.
- **Fallback framing.** No `sh-delta-texture-array` spec exists in `context/plans/`; the texture-array migration is a *direction*, alive only as this spec's failure fork. Task 6 records whether it should ever be drafted. Expected answer on a passing slice: no — but for the right reason. A texture array is not a null option, because textures can carry BC6H where storage buffers cannot (Direction → Alternatives rejected), which cuts per-frame read traffic as well as bytes; it is deprioritized because adaptivity removes the same order of bytes without lossy compression of a signed difference signal, and because the two are largely non-additive once the pool nears the hardware budget. If the gate fails, this is the live fork and its compression upside is the reason it is still worth drafting — do not record it as closed on the grounds that it "only relocates bytes."
