# Seat, Session Identity, and Roster

## Goal

Give the engine a durable per-player key. Today every per-player address dies at a boundary: entity ids die at level unload, connection ids die at reconnect, and no identity is assertable by the player at all. This spec mints three separate identities — session, seat, player — and uses the seat to carry health, ammo, and loadout across a level change and back to a player who drops and rejoins.

## Scope

### In scope

- Host-minted session id, one per hosted run.
- Host-minted seat, one per admitted peer plus one for the local player, surviving level transitions.
- Client-asserted device-local player id, generated on first run, persisted with player options, and carried in the connect token.
- Engine-owned roster keyed by seat, published to clients.
- Seat-hold window and reclaim-by-player-id on rejoin.
- Carried per-player state: current health, ammo reserve across all ammo types, per-slot magazines, inventory composition, active slot, spawn placement.
- One shipped defect fix: placement assignments survive a close but are keyed by a client id the reconnecting peer no longer has, and the level unload drops them along with the round-robin cursor.
- Behavior-preserving splits of the four production files this spec extends.

### Out of scope

- **Per-seat scalar state slots and the `perOwner` mod-store authoring surface.** `drafts/E16--per-player-currency` owns them. This spec mints the key that surface will use; it does not build the surface. Nothing here needs it: the rejection in `replication_scope_for` (`crates/scripting-core/src/store_bridge.rs`) applies to mod-declared stores only, and this spec declares none — every engine slot it touches already has owner-private replication. The carried set stays a structured record because two of its six values, the ammo-reserve map and the inventory composition, have no slot representation at all — see Direction.
- **Lobby UI, join predicate, session-phase vocabulary.** The lobby spec of the Epic 15 band, not yet drafted. `plans/done/E15--session-lifecycle/index.md`'s "Authored join policy" bullet forecloses the join predicate; `plans/roadmap.md`'s "Lobby authoring surface" sub-bullet under Phase 3.75 owns the lobby UI and the session-phase vocabulary.
- **Authentication.** `context/lib/index.md:102` names anti-cheat a non-goal of this project's multiplayer; `research/coop-session-lobby.md:80-84` states the friends-group trust posture and says plainly that the player id "is not an authentication mechanism." The connect token is unsecured and its claim is forgeable. Two forward-compat constraints are honored instead — invariants I3 and I4.
- **Host migration and session-state serialization.** `plans/done/E15--session-lifecycle/index.md:78-80` opened the ledger without serializing it. This spec adds two entries to that ledger and keeps the roster rebuildable (I5); it writes no serializer.
- **A split of `crates/postretro/src/main.rs`.** Owner decision. This spec edits it in place rather than splitting it; a 9,967-line split is its own project.
- **Client-side health as a component.** A connected client's pawn has never carried `HealthComponent`; health reaches it only as a replicated slot. Carry stays host-side.
- **Two shipped ammo-display defects, both predating this spec and neither caused by the seat.** Switching to a weapon with no ammo resource leaves the previous weapon's ammo on the HUD, because `AmmoSlotProjection` stops ingesting rather than clearing and only the local host publisher has a `clear_hud_slot` path. And a connected client's local reload machine can `take` from its own stale `AmmoReserve` while a switch is in flight; the value is never displayed and the next snapshot overwrites it. Both belong to whoever owns HUD ammo replication.
- **Authored carry policy.** Carrying is unconditional here. Pistol-start, per-level resets, and any authored opt-out are policy, not mechanism — see Direction. The seam is named and kept to one call per spawn path; no descriptor field and no knob ship in this spec.

Two distinct types share the name `ReplicationScope`. They are not interchangeable and `entities` does not import net's; the mapping lives in the binary. Any task naming the type must qualify which one.

**`Seat` is the one identity that does not live in the net crate, and it must not acquire a second definition there.** `net` depends only on renet, renet_netcode, bitcode, and log — it is postretro-free by contract (`development_guide.md:28`) and cannot take a `foundation` dependency. `entities` may depend only on `foundation` (enforced by `layering_invariants_hold`, `crates/xtask/src/crate_graph.rs:496`). So no crate exists that both `net` and `entities` can name a shared type from. `foundation` is the only home from which the binary, `entities`, and any later floor-crate consumer can all name one `Seat`; the wire carries a bare `u16` and the net crate defines no seat type at all. Minting a `Seat` in `net` would force a duplicate in `entities` the first time per-seat storage reaches the floor slot table — the same split this table already documents for `ReplicationScope`, and the one I2 forbids.

`SessionId` and `PlayerClaimId` stay in `net`: they cross the wire and nothing below the binary names them.

Display names are UTF-8 `String` on the wire and are never used as a key.

## Wire format

Two new wire surfaces plus one net-to-binary field. One surface appends a variant to a shipped enum; whether that changes the enum's encoded layout is measured in Task 6, not assumed.

### Connect claim — connect-token `user_data`

Fixed 256 bytes (`NETCODE_USER_DATA_BYTES`), carried in `ClientAuthentication::Unsecure`, populated at `crates/net/src/transport.rs:764` where the client currently passes `None`. The host reads it with `transport.user_data(client_id)` on the `ClientConnected` edge in `collect_server_events` (`transport.rs:270-281`).

| Offset | Width | Content |
|---|---|---|
| 0..4 | 4 | Magic `b"PRSC"` |
| 4 | 1 | Format version, `u8`, currently `1` |
| 5..7 | 2 | Payload length, `u16` little-endian |
| 7..7+len | len | bitcode-encoded `ConnectClaim` |
| 7+len..256 | rest | Zero fill, ignored on read |

`ConnectClaim` derives native `bitcode::Encode`/`Decode` like every other wire type (`wire.rs:4`), holds `player_id: [u8; 16]` and `display_name: String`, and gains fields only by appending — bitcode tags positionally (`wire.rs:1048-1049`). `display_name` has no length bound of its own and the envelope is fixed at 256 bytes with a 7-byte header, leaving 249 bytes for the bitcode payload; pin `DISPLAY_NAME_MAX_BYTES = 200`, leaving 249 bytes less the 16-byte id and bitcode's length prefixes with room to spare. The encoder truncates on a UTF-8 boundary at that bound; the decoder rejects an over-long name as no claim. Both sides read the same constant — a mismatch produces a permanently anonymous seat with no error.

The magic prefix is load-bearing and not decoration. When a client passes `user_data: None`, renetcode fills the 256 bytes with **random** data rather than zeros, so an absent claim is indistinguishable from a present one without a marker. Magic mismatch, version mismatch, a length exceeding the remaining bytes, or a bitcode decode failure all mean *no claim*, and the host mints an anonymous seat that can never be reclaimed. This is the degradation path for a dev launch with no configured identity.

Endianness applies to exactly one field, the length prefix. No other multi-byte integer appears in the outer layout — the player id is opaque bytes and the payload is bitcode's own encoding — so there is one endianness decision, not a family of them.

This layout mirrors no existing section, because no existing section is a fixed-width transport field. The framing choice follows `ParityDeclaration` (`wire.rs:1110`) in using a bitcode struct for the payload, and adds the magic/version/length envelope only because the 256-byte field is fixed-width and pre-filled with noise.

### Session roster — `ServerControlMessage::SessionRoster`

A new variant **appended after `SwitchAccepted`** (`wire.rs:1260`), carrying `SessionRosterMessage { session_id: SessionId, your_seat: Option<u16>, view: RosterView }` — the session id rides every publish (AC-SESSION-1). `RosterView` is `Counts { participants: u16 }` or `Full { entries: Vec<RosterEntry> }`; the redaction tier is explicit in the type, never inferred from an empty list. `RosterEntry` holds `seat: u16`, `player_id: Option<PlayerClaimId>`, `display_name: String`, `connected: bool`. Seats travel as bare `u16` because the net crate cannot name the `Seat` type — see the Boundary inventory.

Admission is the privacy boundary. An admitted peer has passed a host decision and receives `Full`; everything below admitted receives `Counts` — how many players are here, and nothing about who they are (I9). Display names and player ids exist only inside `RosterEntry`, so the redaction is structural rather than a field-level filter a later edit can forget.

Conventions followed from the crate: variable-length lists are a `Vec` of a named struct, never parallel arrays (`ShotVerdictsMessage`, `wire.rs:1087`); an empty `entries` under `Full` is valid and means an empty roster; `Option` carries an explicit documented meaning — `your_seat: None` means the recipient holds no seat yet, which is every pre-admission recipient, and `player_id: None` means an anonymous seat. Fixed-size identity is a bare byte array, not a `Vec` (`ParityDeclaration.mod_digest`, `wire.rs:1111`).

### Delivery latency

`NetServer::update` calls `send_packets` once, at its end. Anything the binary queues after the poll returns — the roster publish, the snapshot batch — leaves on the next frame's `update`. Every "within one snapshot" claim in this spec means one snapshot interval after that flush, not from the tick that produced the value.

### What does not cross the wire

`CarriedState` — the seat's carried record — stays host-local. The net crate carries seat *ids* and never seat *contents*, which is what keeps it registry-blind (I8).

Ammo does not cross here either. Loaded magazine and reserve for the equipped weapon already replicate as owner-private state slots at snapshot rate, and the carry rides that existing path — see Task 8.

## Direction

**Problem.** The engine has no key that names a player for longer than one level or one connection, so every feature needing per-player state either dies at a boundary or is parked.

**Prior commitments.** The session-state ledger (`networking.md:149-153`) holds one entry, the connection, and says later specs add the seat and the roster to it — this spec is that addition. `plans/done/E15--session-lifecycle/index.md` carries an explicit out-of-scope bullet beside that same ledger citation — "Reconnect after a close. A closed connection stays closed. Demotion keeps a connection alive; a dropped peer relaunches" — which Task 7 reverses. The reversal is deliberate: the relaunching peer now rebinds a held seat rather than starting over. The admission/parity split turns on mutability (`networking.md:75-87`): the player id is *carried, never compared*, so it gates nothing and cannot convert a recoverable difference into a disconnect. `plans/roadmap.md:202` requires the roster be rebuildable from player ids alone; I5 honors it as far as it goes, re-minting every identified entry under a new host and naming the anonymous entry as the one case that cannot be. E17 said not to invent a heavyweight identity system (`plans/done/E17--trigger-command-surface/index.md:361-368`); I6 keeps its address intact and adds a parallel key.

*`networking.md:102` reads stronger than it is.* It says a client id is stable across a level change, "which is what later specs key player identity to." Client ids are wall-clock nanos minted per connection (`NetEndpoint::from_role`, `NetRole::Connect` arm, `netcode/mod.rs`), so that stability holds within one connection and not across a rejoin. This spec keys the *seat* to admission and the *reclaim* to the player id. The doc line needs narrowing at promotion.

*Why admission, not participation or connection.* Three edges were available. Participation is wrong because a level change drives every participant out of it, which is the churn I1 exists to escape. Connection is wrong because a seat number is never reused (AC-SEAT-1), so minting at connect lets anyone who can open a socket allocate seats without bound. Admission is the host's own decision point, it sits above the level-change demote floor, and it is where the roster's privacy boundary already falls (I9). One edge answers all three.

*Placement in the layer stack.* The seat **table** lives in the binary's `netcode/` module: it holds engine types, and `entities` is a compile chokepoint with six dependents including the whole render and UI stack that `development_guide.md:41` keeps domain logic out of. The nearest existing thing to a seat — `placement_assignments` (`netcode/lifecycle.rs:35-42`), a per-client map that survives a close but not a level unload — is already there. Session id and player id live in `net` alongside the other wire identities, mirroring `NetworkId` — a wire type whose allocator lives in the binary. For the seat **id type**'s placement, see the Boundary inventory.

*Carry is mechanism; whether a level carries is policy.* This spec makes the seat able to carry and makes carrying unconditional, matching the continuous-progression shape the campaign wants today. Pistol-start is a live design axis for a Doom-lineage shooter, and the repo's mechanism-versus-policy thesis is explicit — `plans/done/E16--impact-policy-substrate` builds a substrate holding no opinion about what a hit means. The opt-out seam is named rather than built: seeding reads the seat's carried record through one call per spawn path, so a policy that suppresses carry for a level suppresses that read. No authored knob ships here; adding one is a descriptor field and a check at that call, not a redesign.

**Alternatives rejected.**

*Key everything by the client-asserted player id and mint no seat.* One identity instead of three, trivial rejoin, a trivially rebuildable roster. Rejected because the player id is client-chosen and forgeable: making it the live key means a forged claim steals *live* session state rather than merely claiming a released one, and it makes admission stop being a host decision. The seat gives the host a value it controls. It also makes the id load-bearing everywhere, which is precisely what a later auth epic would have to unwind.

*Carry state through the existing `persist` save path.* Rejected on two shipped rules: a connected client does not write the save file (`should_save_persisted_state`), and client-to-host state writes are a stated Phase 3.5 non-goal. Persist is also machine-scoped where the carry is session-scoped — the wrong lifetime.

*Carry through per-seat state slots instead of a structured record.* The strongest rival, and the one that would also serve the currency spec. The state store has engine-global lifetime and is never cleared on level unload (`scripting.md:110`), so this path would delete the harvest hook and every harvest row in the Ordering matrix outright.

Rejected on shape. `SlotType::Array` does exist, so magazines fit, and health and active slot are `Number`. But `SlotValue::Array` is `Vec<f32>` — floats only. Inventory composition is a list of canonical *name strings* and has no representation at all, and the ammo reserve is a map keyed by ammo-type string, which no slot type expresses. Composition is the load-bearing value: without it the seat cannot rebuild a loadout, which is the carry's whole point. So a structured record is required regardless of what else moves into slots, and taking this path would also mean absorbing the `perOwner` authoring axis that `drafts/E16--per-player-currency` owns.

The seat still stands as the key a scalar per-seat axis will use when that spec builds one — same key, two shapes, one store each with no overlap in what they hold.

**Forecloses.** Fixing the claim in the connect token means it cannot change mid-connection — intended, and what makes it admission-stage-legal. The 256-byte budget forecloses a large profile payload; the envelope and a 16-byte id leave roughly 230 bytes, of which `DISPLAY_NAME_MAX_BYTES` claims 200. Monotonic non-reused seats foreclose a dense seat index; nothing wants one. Nothing here forecloses an authored carry policy: the seed path is one call per spawn path, and suppressing it is a check at that call.

**One-way doors.** None. The connect-claim layout is versioned and the version byte is checked, so a format change costs a protocol bump that admission already gates. Reclaim does not touch closed-slot terminality: a rejoining peer arrives on a fresh client id and never meets the closed entry, so the stale-packet guarantee stands and no shipped contract changes. `Seat`'s crate home is a door in practice rather than in principle — the type is trivial to move, but once consumers build against a net-crate seat, the duplicate-type shape is what gets extended; placing it in `foundation` now costs nothing. The carry inversion is fully reversible — deleting the harvest and seed hooks restores descriptor seeding.

## Acceptance criteria

Most criteria below are runnable tests. Four are not, and are marked **gate** — they are enforced by the compiler, by the type system, or by review, and no `cargo test` assertion expresses them. A gate still has an owner and still blocks the epic.

- [ ] **AC-CARRY-1** — A player crossing a level boundary keeps their current health, their ammo reserve for every ammo type they hold, each weapon's loaded magazine, their weapon loadout, and the weapon they were holding.
- [ ] **AC-CARRY-2** — A player at full defaults, a player mid-magazine, and a player at zero reserve all carry correctly; a player who crossed the boundary at or below zero health seeds the descriptor default rather than a dead pawn; a level that spawns no pawn leaves prior carried state unchanged rather than clearing it.
- [ ] **AC-SEAT-1** — The local player holds seat 0, every admitted peer holds a distinct seat above it, a peer below admitted holds none, and a released seat's number is never reissued for the life of the session. A peer admitted after a level change receives a spawn placement that no live pawn occupies and no held seat has reserved, whenever a free one exists; when live pawns outnumber placements the fallback reuses an index and logs the collision.
- [ ] **AC-SEAT-2** — A host level change does not release any seat, and every participant's seat is the same before and after.
- [ ] **AC-REJOIN-1** — A player whose disconnect the host has observed, rejoining within the hold window resumes with the health, ammo, and loadout they left with, and at their previous spawn placement when the rejoin lands in the same level; across a level change the placement is cleared and re-assigned by the normal assignment path.
- [ ] **AC-REJOIN-2** — A player who rejoins after the hold window expires starts at descriptor defaults, and the session continues without error.
- [ ] **AC-ID-1** — A client that generates an identity persists it on that run, including when a settings file already existed, and asserts the same identity on its next launch. A client whose identity cannot be loaded or written still joins successfully, is reported as anonymous, and on rejoin receives a new seat rather than reclaiming the old one — asserted at the `PlayerOptions` level, since `settings_path` reads the platform config directory and is not injectable end to end.
- [ ] **AC-ID-2** — A second client asserting an identity already held by a live participant joins with its own new seat, the existing participant is undisturbed, and the collision is logged.
- [ ] **AC-ID-3** — Reclaim succeeds only on an exact whole-identity match; a claim differing in any byte gets a fresh seat. I3's other half — that nothing parses, slices, orders by, or derives from the id's bytes — is a review gate over the reclaim path, not a runnable assertion.
- [ ] **AC-ROSTER-1** — The roster lists every seat with its connection state, survives a level change unchanged, and drops a seat when its hold expires.
- [ ] **AC-ROSTER-2** (gate) — No `RosterEntry` field is both host-minted and underivable from `player_id`. Enforced as a drift guard: an exhaustive match over `RosterEntry` with no wildcard arm, each field classified as client-asserted or host-re-derivable, so a new field fails to compile until classified. No host-migration code exists to run a rebuild against, and a rebuild test over a struct this spec authors would assert only its own construction.
- [ ] **AC-ROSTER-3** — An admitted peer receives the full roster; a peer that has not been admitted receives participant counts only, and no display name or player id reaches it. The structural half — that no message shape reachable below admitted can carry a name — holds because `RosterView::Counts` has no field to hold one, which the compiler enforces rather than a test.
- [ ] **AC-LEDGER-1** (gate) — The carried set is enumerated in one place using the exhaustive-match-no-wildcard pattern `networking.md:129` names, so adding a field without binding it fails to compile. The workspace has no `trybuild`, so this is verified by inspecting the pattern, not by a test that asserts a compile error.
- [ ] **AC-SESSION-1** — One session id is minted per hosted run, rides every roster publish, and is unchanged across a level change and a rejoin.
- [ ] **AC-LEDGER-2** (gate) — The seat and the roster appear as entries in the session-state ledger `networking.md:149-153` opened, alongside the connection. A documentation edit, delivered and checked in Task 6.
- [ ] **AC-E17-1** — Trigger occupancy, the Use interaction, and per-player use state behave exactly as before for both local and remote players across a level change.
- [ ] **AC-CLIENT-1** — Within one snapshot of a level change or a rejoin, a connected client's replicated `player.ammo` and `player.ammoReserve` match the host's authoritative values for the equipped weapon, and both re-target on a switch between two weapons that each carry an ammo resource. Active slot is excluded: no replication path carries it. Switching to a weapon with no ammo resource is the shipped HUD defect named out of scope and is also excluded.
- [ ] **AC-BUILD-1** — Each split file's tests pass with identical counts before and after, with no call-site path changes.
- [ ] **AC-HYGIENE-1** — Repeated connect and disconnect cycles do not grow this spec's own bookkeeping — the claim stash and the seat table — without bound. ## Tasks

### Task 1: Connect claim on the wire

Add the client-asserted identity to the connect token and read it host-side. Define `PlayerClaimId([u8; 16])`, `SessionId([u8; 16])`, and `ConnectClaim { player_id, display_name }` in `crates/net/src/wire.rs`, deriving native `bitcode::Encode`/`Decode` per that file's convention — no serde, and any future field is appended because bitcode tags positionally. Define `Seat(u16)` in `crates/foundation`, not in the net crate — see the Boundary inventory. Seats cross the wire as a bare `u16`; the net crate defines no seat type. Implement the 256-byte envelope: magic `b"PRSC"` at bytes 0..4, version `1` at byte 4, `u16` little-endian payload length at bytes 5..7, bitcode payload following, zero fill to 256. Pin `DISPLAY_NAME_MAX_BYTES = 200`. The encoder truncates `display_name` on a UTF-8 boundary at that bound; the decoder rejects an over-long name as no claim. Both sides read the one constant — a mismatch yields a permanently anonymous seat with no error. Provide encode and decode helpers where decode returns "no claim" for magic mismatch, version mismatch, a length exceeding the remaining bytes, or a bitcode failure — this matters because renetcode fills an absent `user_data` with **random** bytes, not zeros, so absence is only detectable by the marker. Thread an `Option<[u8; 256]>` parameter through `NetClient::new` (`transport.rs:750-756`, currently hardcoding `user_data: None` at `:764`) to all six call sites: `netcode/mod.rs:788`, `:3816`, `:3870`, `netcode/trigger_state_channel_harness_test.rs:298`, `net/src/harness.rs:280`, `transport.rs:1038`. `netcode/mod.rs:743` is not a call site; it is the doc contract on `NetEndpoint::from_role` and must stay consistent with the change. Host-side, read `transport.user_data(client_id)` inside the `ClientConnected` arm of `collect_server_events` (`transport.rs:270-281`) and stash the decoded claim on `NetServer` alongside the existing per-client side tables; the claim must be read on that edge and stashed, because renet_netcode drops the netcode entry when the connection tears down and it is not retrievable later. Add `disconnects: Vec<ClientId>` to `ServerPoll`, pushed from **inside `close_slot`**, once per slot. Read `slots.state(client_id)` *before* `slots.close()` and push only when the previous state was `Some` and not `Closed`: `close` returns `None` both for an already-closed slot and for the never-connected tombstone branch, so the return value cannot distinguish them, and a tombstone would otherwise emit an unbind for a client that never connected. `close_slot` is the one function every close reaches: the `ClientDisconnected` arm of `collect_server_events`, `reject`, `close_relay_connection`, and the deprecated fingerprint setter. Keying to the `ClientDisconnected` arm instead would miss `reject` entirely — it closes the slot into this poll's `pending_lifecycle` and queues teardown without any transport event, so the harvest would run with no unbind ahead of it. The accumulated vec is `mem::take`n into the `ServerPoll` at the same point `pending_lifecycle` is, in both `update` and `poll_handshakes` — taken any earlier, a reject-driven unbind slips to the next poll, behind its own harvest. The field is an id with no payload, so net stays registry-blind. Do not reuse the existing private `pending_disconnects`; that is the transport's own deferred-teardown queue, gated on an empty Control channel and drained by `apply_pending_disconnects`, and it means something else. The stash entry is removed at that same edge alongside `close_slot`'s existing removals of `parity_declarations`, `holding_diagnostics`, and `participation_epochs`, and the seat copies the claim at mint time so this removal is safe. `NetcodeServerTransport::user_data(&self, ClientId) -> Option<[u8; 256]>` and renetcode's `generate_random_bytes` fill for an absent `user_data` are both confirmed against renetcode 2.0.0, the pinned crates.io dependency. Net decodes the envelope into a `ConnectClaim` and holds it; the opacity I3 requires is about the player id's bytes, which nothing parses, slices, orders by, or derives from at any layer. Expose a read accessor for the binary. No seat, no roster, no carry in this task.

Source the id client-side in this task too, or the claim has nothing to carry and every shipped client is anonymous forever. Add it to `PlayerOptions` (`crates/postretro/src/options/mod.rs`): 16 random bytes generated when the field is absent, written back through the atomic save, and read at startup to populate the claim. No crate declares an RNG directly, but `getrandom` is already in `Cargo.lock` via `ahash` and `tempfile`, so a direct dependency on `crates/postretro/Cargo.toml` adds no new compile unit. Do not add it to `crates/net`, whose dependency list is a stated contract. Generate in `Session::build` (`crates/postretro/src/session/mod.rs`), not in `PlayerOptions::load`: `load` is deterministic today and four shipped tests plus `sanitize` depend on that. Persist on generation. The shipped save fires only `if !existed`, so a returning player — every install after first boot — would otherwise never write the id, and AC-ID-1 would pass on a fresh temp dir while failing in production. No new file and no new machine-scoped store — `settings_path` already resolves `<platform config dir>/settings.toml` and the save is already tmp-plus-rename. A missing or unwritable settings path is the anonymous degradation path, not an error: the client still connects, and the magic-marker envelope already handles the absent-claim case.

### Task 2: Seat table, session id, and the thin slice

Build the seat, mint it, and carry exactly one value end to end so the seams are falsified before anything fans out.

**Define the seat's three edges first.** The design needs three moments the shipped code does not expose under those names. Define them here; every later task keys to the edge, never to the function behind it.

| Edge | Observable it keys to | Why the obvious observable is wrong |
|---|---|---|
| Seat mint | `HandshakeOutcome::Admitted` in `ServerPoll.handshakes` | `SlotTable::transition` returns `None` for `Pending -> Admitted`, so admission emits no `SlotEvent` and there is nothing in `ServerPoll.lifecycle` to key to |
| Seat unbind | A new `disconnects: Vec<ClientId>` on `ServerPoll`, pushed from inside `close_slot` | `pending_lifecycle` receives an event only when `close_slot` returns `Some`, which `transition` produces only from `Participating`. A drop while `Admitted` — the level-load case Task 7 exists to serve — reaches the binary through nothing at all today. Keying to the `ClientDisconnected` event instead of to `close_slot` would miss `reject`, which closes without one |
| Seat harvest | A binary-side call placed immediately before each player-pawn despawn | No shipped event marks a pawn as about to die; two hooks across three call sites, named below |

`disconnects` is net's only new surface. It carries an id and nothing else, so I8 holds. The binary drains the poll in a fixed order — `disconnects`, then `handshakes`, then `lifecycle` — so an unbind is always visible to a same-poll reclaim and always precedes the harvest that describes it. The mint hook skips any client whose `slot_state()` is already `Closed` at drain time. `process_control_messages` walks a client's whole Control batch, so one poll can carry `Admitted` and then `Rejected` for the same client; without that check the seat is minted onto a closed slot, never unbound, and left `connected: true` for the session.

Create `crates/postretro/src/netcode/seat.rs` owning a `SeatTable`: a monotonic `Seat` allocator that never reuses a number, a map from seat to `Option<CarriedState>`, a map from seat to the currently bound `ClientId`, a map from seat to its live pawn, a map from seat to the claim it was minted with, a map from seat to its hold deadline, the round-robin placement cursor, and the session id minted once with the table. Every map lands here even where a later task is the first to write it, for the same reason `CarriedState` lands whole. Add `disconnects` to the running-frame drain guard in `crates/postretro/src/main.rs`, which today enters its block only when `handshakes`, `lifecycle`, or `switch_declarations` is non-empty. A poll carrying only disconnects would skip the block entirely, so the unbind, the hold clock, and the expiry sweep would never run on a quiet poll — exactly the abandoned-seat case AC-ROSTER-1 depends on. The table lives on `Session` (`crates/postretro/src/session/mod.rs`; its construction literal in `startup/lifecycle.rs` is exhaustive and must gain the field) beside `net_endpoint`, and reaches its consumers as a parameter: the spawn paths and the composition chokepoint take a carried record, never a borrow of the table, so nothing below `netcode/` learns the seat exists. The seat map's value is `None` until a harvest writes it, and a `None` record seeds nothing at any site, so every spawn path falls through to descriptor defaults. Without that `Option` a fresh seat is indistinguishable from one harvested empty — `active_slot: usize` has no absent state and an empty `AmmoReserve` reads the same either way — and AC-REJOIN-2's fresh-seat-at-defaults becomes unimplementable. `CarriedState` lands with its **full field set** in this task — `health_current: Option<f32>`, `reserve: AmmoReserve`, `wieldables: [Option<String>; WIELDABLE_SLOT_CAPACITY]`, `magazines: [Option<u32>; WIELDABLE_SLOT_CAPACITY]`, `active_slot: usize`, `placement: Option<usize>` — and a `HoldDeadline` newtype over the accumulated-time clock. No later task adds or reshapes a field. Only `health_current` is populated here — Task 5 fills the rest with behavior, not with new fields, so no later task reshapes a struct another is editing. Within `CarriedState` each field is written only when its source component is present on the pawn; a missing component leaves that field at its prior value. The seat owns its pawn binding, set at spawn and cleared at the unload harvest. The harvest resolves the seat **by pawn id**, never by the currently bound client id: a same-poll reclaim rebinds the seat to the new client during the handshake drain, before the old connection's `Closed` event drains, so a client-id lookup would miss the seat and lose the dying pawn's final state. The table lives in the binary because it holds engine types and because `entities` is a compile chokepoint that domain logic stays out of (`development_guide.md:39-41`). The `Seat` type itself comes from `foundation` (Task 1) and is not redefined here. Seat 0 is reserved for the local player, minted when the seat table is created, and appears in the roster with no claim of its own. The table is created with the session rather than with the network endpoint, so single-player and listen host both have one — otherwise `spawn_from_player_starts` seeds from a seat that cannot exist, and the host's carry needs a second mechanism, which is the duplicate-store problem I2 forbids. A connecting client mints no seat table; it holds only the `your_seat` the host sends it. Single-player has no drain site: `poll_world_less_transport` returns early without a `net_endpoint`. That is correct — no holds, no roster recipients — and the carry there runs entirely through the harvest and seed hooks. Mint every other seat on the mint edge above, binding it to that client id, and record the claim Task 1 stashed at that client's connect edge. **Mint at admission, not at participation** (I1) — see Direction, *Why admission*. It is also the edge Task 7 reclaims at and the edge the roster's privacy tier turns on (I9), so all three key to one place. Harvest keys to pawn despawn, not to level unload. Two hooks, two ordering constraints. The level-teardown harvest runs ahead of `clear_for_level_unload`, hooked in `unload_level` and in `App::suspended` **beside** their calls to `clear_net_level_parity` rather than inside it — that function early-returns when the session holds no `net_endpoint`, which is exactly the single-player case, so a harvest placed inside it never fires for a single-player level change and AC-CARRY-1 fails on the primary shipping path. The lifecycle harvest runs as the first statement of the `Closed | Demoted` arm of `host_handle_lifecycle`, ahead of `on_slot_closed`, which despawns the pawn and every inventory sibling wieldable before returning — and composition and magazines are read off those wieldables.

The lifecycle hook is a guard more often than a harvest. `clear_net_level_parity` demotes every *participating* slot — an already-`Admitted` slot produces no event, since `transition` returns `None` for `Admitted -> Admitted` — and those `Demoted` events do not drain until the next `NetServer::update`, by which point the teardown harvest has already run and the registry is cleared. So on every host level change the lifecycle arm meets a seat whose `pawn` no longer resolves: it must check the binding against the live registry and no-op otherwise, leaving the teardown record intact rather than overwriting it with empty. It does real work only on a mod-reload demote, where no teardown ran. The unload harvest clears the seat's `pawn` binding, because the pawn is about to die. The suspend harvest does not: `App::suspended` never clears the registry and never despawns, so every pawn stays live and the binding stays valid. Clearing it there would strand pawns that only the seat can still resolve, since `clear_net_level_parity` has already replaced `SlotPawns`.

The harvest is deliberately independent of `reset_level_scoped_host_state` replacing `SlotPawns`: the seat resolves its own pawn, so the client→pawn map's fate is irrelevant. Canonical names come off the entity through `DescriptorProvenance`, not the data registry, so `data_registry.clear()` does not bound it. Seed the harvested health back onto the pawn after spawn on the two paths that attach `HealthComponent` — `spawn_from_player_starts` and `spawn_net_slot_pawn` — as a post-spawn override rather than by threading into `attach_descriptor_components`; on both paths the seed lands after their call to `spawn_descriptor_instance`, which is where health actually arrives. `spawn_from_player_starts` loops over every `player_spawn` entity and spawns one pawn per entry, marking only the first with `PlayerMovement` as local via `mark_local_player_pawn`, guarded on `local_player_pawn().is_none()`. Seat 0's record seeds that pawn alone; the other player-start pawns take descriptor defaults. Do not add health to the connected-client path: that pawn has never carried `HealthComponent` (`remote_materialize.rs:143-199` attaches movement, inventory, mesh, and viewer role only), and its health arrives as a replicated slot. Keep E17's `PlayerId` untouched (I6). `host_handle_lifecycle` has two production call sites — the running-frame host arm and `poll_world_less_transport`, the latter driven from `run_loading_frame` and from Frontend/Splash — and a disconnect during a level load is observed only at the second, so both are hook targets for the mint and harvest handling this task adds. Sequenced after the splits so the edits land in the post-split files.

### Task 5: Full carried set

Extend the carry from health alone to the whole per-player set: current health, ammo reserve across every ammo type held, each inventory slot's loaded magazine, the inventory composition, the active slot, and the spawn placement. Enumerate `placement` alongside the rest of the carried set. `CarriedState` already carries every field this task needs; do not add or reshape one, or the concurrent roster task is editing a struct underneath you. The carried record reaches the composition chokepoint as a parameter, never by reaching back into `netcode/`. `compose_wieldable_inventory_slots` lives in `scripting/builtins/` and the seat table lives in `netcode/`; the function stays seat-blind and takes an optional carried loadout, and each caller resolves the seat before calling. Same shape that keeps `net` registry-blind, one layer up. Seed through the single composition chokepoint `compose_wieldable_inventory_slots` — all three spawn paths reach it, and it is the only writer of inventory *composition* (the `wieldables` array) and the only caller of `seed_weapon_reserve`. It is private, so no spawn path calls it directly: `spawn_from_player_starts` and `spawn_net_slot_pawn` reach it through `compose_wieldable_inventory`, and the client path through `compose_wieldable_inventory_from_slots`. The carried loadout threads through both wrappers. `compose_wieldable_inventory` has a no-loadout early return that writes a default `Inventory` and never reaches the chokepoint — a carried loadout must suppress that return, or the carry is silently dropped for any pawn descriptor with no authored loadout. `Inventory` as a whole has other writers: `apply_host_switch_declaration` (`netcode/mod.rs`) and the switch/lower path in `sim/weapon_stage/commands.rs` both write it, and `compose_wieldable_inventory` itself writes it on its own no-loadout early return. `active_slot` is separately written by `apply_host_switch_declaration` and the weapon-switch commands, and the carried-active-slot restore must not fight them. Two shipped gaps make this more than a hook. `active_slot` is currently *derived* — first populated slot wins, the `position(Option::is_some)` derivation in `compose_wieldable_inventory_slots`. Carry it as a parameter into the chokepoint, not as a post-composition override: an override has to be ordered against `apply_host_switch_declaration` and the weapon-switch commands, which is the fight this task must not pick. And `AmmoReserve`'s whole surface is `new`, `available`, `credit` (saturating add), and `take` — no iterator and no setter. Add a set-exact method rather than replacing the component wholesale; wholesale replacement inside a spawn path is the wider blast radius, not the narrower one. The missing iterator blocks harvest the same way: with nothing to enumerate, harvest must clone the whole component wholesale, which `AmmoReserve` supports — it derives `Clone` plus `Serialize`/`Deserialize` with no skipped fields, so whole-component replacement is available. Magazines restore by writing `WeaponComponent.magazine` (`weapon.rs:275`) per slot after composition. Carry nothing whose lifetime is bounded by the pawn instance: no cooldowns, no in-flight reload state, no movement runtime, no death latch, no kill credit. One rule covers all five, and the two that already declare it in source confirm the rule rather than standing alone — `pending_kill_credit` and `contributor_ledger` are `#[serde(skip)]` and documented transient (`entities/src/components/health.rs`). A reload in flight is bounded that way too: the magazine carries, the animation timing that would have filled it does not. Pin the death case AC-CARRY-1 leaves undefined: a carried `health_current` at or below zero clamps to the descriptor default on seed rather than seeding a dead pawn. The carried set must be enumerated in exactly one place using the pattern `networking.md:129` names working today — bind every field and name any skip, so a field added later and not bound is a compile error, not a runtime test (I7).

### Task 6: Roster and the session-state ledger

Build the engine-owned roster and publish it. The roster is keyed by seat and holds, per entry, the seat, the asserted player id if any, a display name, and whether that seat is currently connected. Its vocabulary is closed: it carries lifecycle facts the engine mints or observes, plus the display name the client asserted — and nothing else. **The roster must be reconstructible from the asserted player ids alone** (I5) — session id and seats are host-minted and cannot survive a host change (`plans/roadmap.md:202`), so no roster field may depend on a host-minted value that is not also derivable from its player id. Add the `SessionRoster` variant to `ServerControlMessage`, **appended after `SwitchAccepted`** (`wire.rs:1260`) because bitcode tags enum variants positionally and inserting anywhere else renumbers shipped variants. Adding this variant bumps the app-protocol (message-vocabulary) constant per `networking.md:379-391`; bumping it is a required step of this task. Whether it also bumps `WIRE_VERSION` is a measurement, not an assumption: `ServerControlMessage` has five variants today, and bitcode's discriminant width is a function of variant count. Round-trip the five shipped variants before and after appending the sixth and assert byte-identical encodings. A difference means the layout changed and `WIRE_VERSION` bumps too, independently, per that same section's Version gates rule. Roster changes mark a dirty flag; one publish per poll drain flushes it, after the lifecycle batch, to every slot whose state is `Pending`, `Admitted`, or `Participating` — never from the mutation sites themselves, or a single poll ships three rosters and two of them are intermediates. `Closed` is excluded deliberately: `apply_pending_disconnects` tears a rejected slot down only once its Control channel is completely empty, so publishing to it re-arms the channel every poll and the teardown never completes. An admitted or participating slot receives `RosterView::Full`; everything below admitted receives `RosterView::Counts` (I9). `participants` is the count of roster entries with `connected: true`, seat 0 included; a held seat is not counted. Publishing below participating is sound rather than merely tolerated: `NetServer::send_control` and `NetClient::drain_control` (`crates/net/src/transport.rs`) show a non-participating slot does receive control payloads — `send_control`'s own doc says control may be sent to an admitted or closed slot to deliver a hold or reject diagnostic, and `drain_control` returns payload-bearing frames regardless of epoch. So a client held for parity across a long level load watches a live roster instead of a stale one. The message carries `session_id` on every publish and the recipient's own seat so a client knows which entry is its own; a pre-admission recipient holds no seat yet and gets `your_seat: None`. Encode per recipient. `your_seat` differs for each, so a single encoded message reused across the fan-out ships one client's seat to everyone — the obvious optimization and the wrong one. Seat *contents* never cross the wire — the net crate stays registry-blind (I8, `development_guide.md:28` plus `crates/net/Cargo.toml`'s dependency list). Add the seat and the roster to the session-state ledger enumeration that `networking.md:149-153` opened with one entry (AC-LEDGER-2), and narrow `networking.md:102` — a client id is stable within one connection, not across a rejoin, so it is not what player identity keys to. Update `player_options.md` for the identity field Task 1 persists. Extend `layering_invariants_hold` (`crates/xtask/src/crate_graph.rs`) with an assertion that `postretro-net` has no internal dependencies, so I8 is enforced rather than merely warranted. It passes today; it is permanent protection, not evidence about this epic. Also fix the placement defect. `SlotPawns.placement_assignments` documents that it "survives a close so a reconnecting client lands on its prior spawn" (`netcode/lifecycle.rs:35-42`) — this part holds: `on_slot_closed` in `netcode/lifecycle.rs` removes only the `pawns` and `wieldables` entries and never touches `placement_assignments`, so the map does survive a close. The real defect is two-part instead. First, `assign_placement`/`placement_assignment` key by client id, while a reconnect mints a fresh client id in `NetEndpoint::from_role`, so the surviving entry is unreachable. Second, `reset_level_scoped_host_state` replaces `SlotPawns` wholesale at level unload, dropping the map, which is not a close. Move placement assignment onto the seat, where reconnect keys by seat rather than client id and level unload no longer drops it. Task 2 lands `placement` as a field on `CarriedState` and the cursor `next_assignment` on the seat table; assignment here keys by seat, and the client-id-keyed map plus its reset in `reset_level_scoped_host_state` are deleted, and the shipped test `placement_assignment_is_deterministic_and_survives_close` in `netcode/lifecycle.rs` is rewritten against the seat-keyed path. Leaving the cursor behind would assign placement 0 to the first post-level-change joiner, colliding with a seat that already owns it. Carrying it is not sufficient on its own: `assign_placement` issues `next_assignment % placement_count`, so a cursor at 2 entering a two-placement level collides just as hard. Replace the modulo with a scan that skips indices occupied by a live pawn **and** indices carried by a held seat, falling back to the modulo only when every index is taken. Held seats must reserve: a held seat owns no pawn, so a pawn-only scan hands its index to a joiner and AC-REJOIN-1 then puts the returning holder on top of them. Occupancy is measured in pawns, not seats: `spawn_from_player_starts` spawns one pawn at every `player_spawn` entry, so a scan over seats alone drops a joiner on top of a level-spawned pawn — the shipped collision this fix exists to end. Correct or delete the comment.

### Task 7: Seat hold and reclaim

Make a dropped player able to come back. Hold-start keys to the seat-unbind edge Task 2 defines — `ServerPoll.disconnects` — never to `SlotEvent::Closed`: `SlotTable::transition` (`crates/net/src/slots.rs`) emits `Closed` only from `Participating`, and a level change demotes every participant to `Admitted`, so a drop during a level load — the likeliest moment to drop — emits no lifecycle event at all. On that edge, mark the seat disconnected in the roster and start the hold window. A relay-added connection is not a special case. `close_relay_connection` calls `close_slot` like every other path, so a relay seat takes the hold like any other; the three binary-side relay harnesses must keep passing under that rule. Do not harvest here: the disconnect despawns the pawn, and Task 2 already hangs the harvest on pawn despawn, so this edge stores nothing itself. On a later admission whose stashed claim matches a held seat's player id exactly, rebind that seat to the new client id and restore its carried state; on no match, or on an expired hold, mint a fresh seat at defaults. If more than one held seat matches — a stale seat from an earlier drop plus a recent one — the most recently held wins and the loser is released immediately rather than left to expire (I1). **This decision happens at exactly one chokepoint** (I4) — the admission edge Task 2 already mints at, so a later auth epic replaces the claim's provenance there and touches nothing else — and matching is whole-identity equality only, never a parse or a partial comparison (I3, AC-ID-3). Advance the clock, evaluate expiry, and publish the roster at **one** site: wherever a `ServerPoll` is drained. One rule, two drain functions: the running-frame poll and `poll_world_less_transport`, which serves Loading, Frontend, and Splash. Both call the same routine; neither carries its own copy. The site releases any seat past its deadline, then drains the roster dirty flag last, so a release and the publish that describes it never split across frames. Accumulate the clock **once per frame, not once per drain**: a splash frame drains up to four times and the install-completion frame drains twice, each passing the same frame delta, so a per-drain accumulation multiplies elapsed hold time by the drain count and makes the window frame-rate-dependent. Order within the drain is fixed — reclaim is evaluated during the handshake batch, before the expiry sweep — so a rejoin landing on the deadline frame keeps its seat rather than losing it by a few microseconds.

Do not tie the clock to the sim tick. `unload_level` sets `BootState::Frontend` and the Frontend and Loading branches return before the tick loop, so a sim-delta clock freezes for the whole inter-level window — and a host that quits to the frontend and stays there would hold every abandoned seat, its placement, and its `participants` slot for the life of the process. AC-ROSTER-1's expiry would be unreachable. The poll site has neither problem, and it is the right measure regardless: a dropped player can reconnect on exactly the frames where the transport is polled, so those are the frames the hold should count.

The window ships as `HOLD_WINDOW: Duration = Duration::from_secs(30)`, a placeholder the manual verification gate replaces and whose lower bound that gate sets. Task 11's legs are written against it. Task 11 drives the clock with injected fixed delta. `crates/net/src/slots.rs` needs no change, and closed-slot terminality stays intact. Reclaim rebinds a seat to a **new** client id, and every production connection mints its id at exactly one site — wall-clock nanos, per connection, in `NetEndpoint::from_role`'s `NetRole::Connect` arm — so a reconnecting peer never presents an id `on_connect` has already seen. Relay-added ids come from harness callers rather than that site; they are never reclaimed, so they do not weaken the guarantee. `entry().or_insert()` inserts it as `Pending` normally, `transition`'s early return for a closed slot is never reached, and the never-connected tombstone population is never approached. The stale-packet guarantee is untouched and no shipped contract changes. Note that `close_slot` clears `parity_declarations`, `holding_diagnostics`, and `participation_epochs` (`transport.rs:503-508`), so a rebound connection re-establishes parity from scratch like any new connection — the seat carries gameplay state, not handshake state. Two live connections asserting one identity is not an error: the second gets its own fresh seat, the first is undisturbed, and the host logs it.

## Manual verification

Orchestration ends with a human pass. Automated coverage proves the mechanism works; this gate settles the one value the mechanism is indifferent to.

**Hold-window duration.** Host a session, drop a player mid-level, and rejoin. The window is long enough when it survives a client relaunch and reconnect at realistic speed, and short enough when an abandoned seat does not hold its spawn placement for the rest of the session. Set the constant to the value that pass produces and replace the placeholder. Reject any value at or below one frame: the seat releases on the first evaluation and no rejoin can land. The epic does not close until this runs.

## Rough sketch

`Seat(u16)` in `crates/foundation`. New wire types in `crates/net/src/wire.rs` (post-split, `wire/control.rs`): `SessionId`, `PlayerClaimId`, `ConnectClaim`, `RosterEntry`, `RosterView`, `SessionRosterMessage`, plus `ServerControlMessage::SessionRoster` appended last.

New module `crates/postretro/src/netcode/seat.rs`: `SeatTable { session_id: SessionId, next_seat: u16, seats: HashMap<Seat, Option<CarriedState>>, bound: HashMap<Seat, ClientId>, pawns: HashMap<Seat, EntityId>, claims: HashMap<Seat, Option<ConnectClaim>>, holds: HashMap<Seat, HoldDeadline>, next_assignment: usize }`. The seat stores the whole claim, not the id alone: the roster publishes a display name for a held seat whose connection is long gone, and Task 1's stash is removed at the close edge. `CarriedState { health_current: Option<f32>, reserve: AmmoReserve, wieldables: [Option<String>; WIELDABLE_SLOT_CAPACITY], magazines: [Option<u32>; WIELDABLE_SLOT_CAPACITY], active_slot: usize, placement: Option<usize> }`. The map's value is `None` until a harvest writes it, and a `None` record seeds nothing — that is what separates a fresh seat from one harvested empty. Seat 0 is the local player's, minted with the table. The whole `CarriedState` field set lands in Task 2 so later tasks fill behavior rather than fields. `next_seat` pins its exhaustion behavior: at `u16::MAX` the allocator refuses the mint and logs; the peer stays admitted without a seat. No number is ever returned twice.

Harvest hangs off pawn despawn — the `Closed | Demoted` lifecycle arm and the level teardown both `unload_level` and `App::suspended` reach — ahead of `clear_for_level_unload`. Seed applies inside each spawn path, after its `spawn_descriptor_instance` and composition calls, before the promotion seam reads the inventory, with the carried record passed in as a parameter rather than looked up. Route every seed through one call per spawn path so a later carry policy has a single site to suppress. The seed is a non-destructive read: the seat record is overwritten only by a harvest, never consumed by a seed, so a promotion that produces a fixture pawn with no `HealthComponent` or `Inventory` does not discard the carry. `AmmoReserve` gains a set-exact method for the seed and is cloned wholesale for the harvest; it derives `Clone` and unskipped serde, so the harvest side needs nothing new.

## Open questions

- **Hold-window duration.** Settled at the manual verification gate; see Manual verification. Ships as a constant rather than an authored knob because a knob is lobby-surface work.
- **Display name sourcing.** The id is generated and persisted (Task 1); the name beside it is not. Nothing today asks a player what to call themselves, and the lobby surface that would belongs to the Epic 15 lobby spec, not yet drafted. Until then the client always populates `display_name` from `PlayerOptions` and it is empty. The host never substitutes one: a host-minted name is not derivable from the player id, which I5 forbids.
- **`drafts/E16--per-player-currency` carries a stale decision.** It states that a disconnect releases the seat and drops its values, and that a rejoin is a new seat at defaults — reversed by Task 7, which holds the seat and restores it. That draft also argues against a standalone seat spec and places the seat in `entities`. All three need reconciling there when it unparks; none blocks this spec.
