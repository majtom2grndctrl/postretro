# Combat Presentation Substrate — Core, Damage Numbers, Enemy Status Bars

## Goal

A passive, capped presentation layer for combat-adjacent UI: renderer-local, world-anchored, pooled transient instances that reuse the shipped UI draw-list/theme/text machinery without the retained tree, modal stack, focus, hit-testing, or input dispatch. This spec builds the shared **core** (projection, pool, one-shot layout, per-instance facts, composition fold) and two surfaces on it: **floating damage numbers** (spawn archetype, authored as an impact effect) and **damaged-enemy status bars** (overlay archetype). Pickup prompts are a follow-on. The engine renders; the author decides what a hit *means* and what it *shows* — the combat "facts, not policy" line (`context/research/combat-events.md` §2) carried into presentation.

## Scope

### In scope

- **Core presentation layer.** A CPU-side pool of world-anchored transient instances (fixed cap, spawn, TTL, fade, evict-oldest); a CPU world→screen projection using the app camera; one-shot template layout (widget subtree → relative draw list); per-instance producer-stamped facts; a per-frame screen-space `UiDrawData` folded into the frame `UiComposition`.
- **Two archetypes, three verbs.** `definePresentationTemplate` (the reusable look), `present(template, {...})` (spawn from an impact policy), `defineOverlay({ over, template })` (fact-driven overlay). All under `postretro/ui`.
- **Damage numbers.** A `present` impact effect joining the existing presentation lane; single-player/host-local spawn, then co-op via a host-addressed unreliable presentation event routed to the damaging client.
- **Enemy status bars.** A `damagedEnemies` overlay source: dispatch-driven recently-damaged tracking (linger reset by each damage dispatch), with a per-frame read of `HealthComponent` (health track) and author-declared per-entity `@state` (shield track) for the fractions of already-tracked enemies; tween; evict on death. Co-op via host-pushed facts to the damaging client.
- **Theme/widget reuse.** Templates consume the shipped `UiTheme` and the `Bar`/`Text`/`Image`/`VStack`/`HStack` widgets, `styleRanges`, `visibleWhen`, `Switch` (SDK sugar), and value `tween`.

### Out of scope

- **Pickup prompts.** Follow-on spec: needs a net-new client-side local overlap pass (the touch pass is host-only), plus `awarenessRadius` and net-new `label`/`icon` descriptor fields. Named, not built.
- **Aimed-at enemy bars in co-op.** The host does not cheaply know a client's aim, so co-op enemy bars are **recently-damaged-by-me only**. Host/single-player may show an aimed-at bar; co-op does not. (`include: "aimedAt"` on the source is host/SP-only here.)
- **Client-side prediction of the shooter's own damage numbers.** The lean first cut is host-addressed for all numbers. Spawning client-locally off `resolution.hits` (`weapon/mod.rs:58`, populated at `main.rs:6217`) is a deferred feel-refinement, named not built.
- **Coalescing stacked hits** into a running total. Evict-oldest is the first-cut pool policy; per-target coalesce is a deferred opt-in.
- **Continuous distance facts**, tiered templates, per-tier mini-templates. Those are the pickup-prompt surface's needs.
- **Full `HealthComponent`/`EntityStateComponent` replication.** We push presentation *facts*, we do not replicate combat *state*. The replicated component set stays the shipped four kinds.
- **Reconciling a cosmetic.** A transient expires before a correction would land; the replicated HP slot is the source of truth.

## Direction

**Problem.** Combat produces facts the player cannot see: a hit's damage, a damaged enemy's remaining health. The impact-effect set is closed and has no path to presentation (`E16--resource-grant-chokepoint` deferred damage numbers here explicitly), and the UI layer only draws a single retained, screen-anchored tree bound to global slots — it has no transient, world-anchored, pooled instance. The cause is a missing *layer*, not a missing widget: the draw-list machinery exists but only one producer (the retained modal stack) is wired to it.

**Prior commitments.**
- *The engine emits facts; the author authors meaning* (`context/research/combat-events.md` §2). `present()` extends this to presentation — the engine renders, the author decides a hit shows a number. Reuses the shipped presentation lane in `evaluate_dispatch` (`impact_policy.rs:274`), where `PlayAnimation` is today the only member.
- *Renderer owns GPU* (`index.md` §2). All wgpu stays in `render/ui/`. The presentation producer is CPU-side and hands the renderer a `UiDrawData`, exactly as the retained tree does via `UiComposition::from_layer_draws` (`render/ui/mod.rs:296`); `push_focus_ring` (`mod.rs:1109`) is the precedent for a non-tree renderer producer.
- *Replicate state, present events* (this session's co-op transport decision; consistent with `networking.md` — presentation is host-local today). Durable per-player state (HP/ammo/XP) rides the shipped owner-private slot path; transient presentation rides a **new unreliable presentation message family** — its own vocabulary, not a `ServerMessage` variant (that type is doc-defined as the *reliable* Input-channel envelope, `wire.rs:1108`, the state lane; presentation is the event lane, and the substrate refuses to conflate them). It is addressed to one client and sent fire-and-forget on a dedicated unreliable `Channel::Presentation` (Task 5) via a `send_snapshot`-style addressed send (`transport.rs:628`), mirroring the *addressing* shape of the owner-private `send_shot_verdict` (`netcode/mod.rs:1749`) — not its channel and not its type.
- *Shields are author state* (this session; roadmap **damage application order** / **shields**). The enemy shield track reads author-declared per-entity `@state.shield` via the shipped direct accessor `registry.get_component::<EntityStateComponent>(id).get(name)` (`crates/scripting-core/src/ir/scopes.rs`, the `seed_target_from_registry` precedent) — no engine shield component, no unbuilt dependency.

**Divergence, named.** The sample assumed enemy bars read "already-replicated enemy health." They do not: `HealthComponent` (kind 10) and `EntityStateComponent` (kind 17) are absent from the replicated `ComponentPayload` set (`net/wire.rs:395`), which is the shipped four kinds. Deliberate divergence: rather than replicate combat state (heavy, and against the state/event line), the host *pushes* a damaged enemy's health/shield facts to the client that damaged it — the same addressed-event transport the damage numbers use. This scopes co-op enemy bars to recently-damaged-by-me, stated above.

**Alternatives rejected.**
- *Replicate `HealthComponent` to clients (a fifth `ComponentPayload`).* Gives every client every enemy's health continuously. Rejected: it replicates state to drive a cosmetic, floods the wire with data no client reads unless it is fighting that enemy, and crosses the state/event line the whole substrate rests on. The host-pushed-fact model sends only what a client is about to see.
- *Damage numbers as a replicated owner-private slot.* Reuses the per-player-currency path. Rejected: a slot is reliable, retained, and reconciled — the opposite of a transient the player reads for 900 ms and forgets. Unreliable fire-and-forget is correct and cheaper.
- *A standalone `defineDamageNumbers` binding instead of a `present` effect.* Rejected earlier in design: it re-subscribes the engine to the impact stream and re-derives the per-attacker routing the policy already carries, re-prescribing meaning the author owns.
- *A second retained tree for presentation.* Rejected: it drags in taffy dirty-tracking, modal stack, focus, and input — everything a passive layer must not have. The draw-list layer is reusable without any of it.

## Acceptance criteria

- [ ] A `present`-effect damage number appears at the hit location in single-player, rises, fades, and is gone by its `lifetimeMs`; its color follows the template's `styleRanges` by magnitude.
- [ ] The presentation pool never exceeds its configured cap: with more live instances than the cap, the oldest are evicted; no unbounded growth, no panic.
- [ ] A damage number spawned by a killing blow (the target despawns the same frame) still displays the correct value — read from the dispatch's captured `amount`/`health_after`, not post-despawn registry state.
- [ ] The presentation layer captures no input and takes no focus: (a) the presentation path calls no `export_top_focus_rects` (grep/review gate) and registers no focus/hit-test rects; (b) a presentation frame contributes zero focus-rect entries to the composition. (The layer emits draw data only, so input reaching game logic follows.)
- [ ] In co-op, a damage number for a hit dealt by client A appears on **A's** screen only — not the host's, not client B's. In single-player / on the host's own hit, it appears locally with no wire round-trip.
- [ ] A lost presentation event degrades silently: dropping the packet shows no number (or a stale bar value), never a stall, error, or reconnect. (Unreliable channel; verified by a drop-injection harness test.)
- [ ] An enemy status bar appears over an enemy once it is damaged, tracks its health fraction (tweened), lingers `lingerMs` after the last hit, and is removed when the enemy dies or the linger expires. A full-health enemy shows no bar when `hideAtFull` is set.
- [ ] The enemy bar's shield track renders from an author-declared per-entity `@state` value/max pair; an enemy whose evaluated `max` is 0 (no shield state) shows no shield track (`hasShield` false) and never a NaN. Vanilla/elemental/custom shields render through the same bar by pointing the pair at different state names.
- [ ] In co-op, an enemy bar appears on the client that damaged the enemy, shows that enemy's health/shield, and never leaks another enemy's or another client's values; a late joiner shows no stale bars.
- [ ] Template layout is correct for a multi-widget template: an enemy bar's `VStack[Bar, Bar]` stacks, and a two-`Text` row lays out horizontally, at the projected anchor, **with per-instance facts resolved into the draw list** (not an empty `cell_values`) — one-shot layout, no retained tree.
- [ ] World→screen projection culls correctly: an instance whose anchor is behind the camera or off-screen is not drawn (no wrap-around, no NaN).
- [ ] On a frame with zero fixed ticks, live instances still animate (TTL/fade/tween advance by frame time) and project to current camera; on a frame with multiple fixed ticks, a spawn from tick 1 and tick 2 both appear.
- [ ] Adding the presentation message family bumps `PROTOCOL_ID` (the vocabulary constant) and `WIRE_VERSION` (its byte layout), and leaves `SNAPSHOT_VERSION` untouched (presentation rides its own `Channel::Presentation`, not the replicated snapshot record); a peer built before the bump is refused at the handshake (no partial decode).
- [ ] The two pool budgets do not interfere: with the spawn ring at cap and the overlay map at `maxVisible` simultaneously, a new damage number evicts only the oldest spawn (never a bar) and a newly-damaged enemy past `maxVisible` evicts only the least-recently-damaged bar (never a number; ties broken by creation FIFO).
- [ ] Client fact-ingest handles adverse orderings (driven by calling the ingest directly in a chosen order — the client-side logic, not wire reordering): a stale `alive=true` after the `alive=false` death fact for the same enemy leaves the bar evicted (no resurrection over a corpse); an `alive=false` for a never-seen enemy creates no bar; two live fractions ingested out of order settle to the latest.
- [ ] In co-op, a damaged enemy whose author-declared shield recharges between hits updates its shield bar on the damaging client with no intervening hit; a frame on which the enemy's fact tuple is unchanged sends no packet; and — via test-gated `len()` accessors and a driveable TTL/prune advance — the host's per-(client,enemy) last-sent map (pruned on tracking-end) and the client's terminal-id set (TTL-expired) return to bounded size after a burst of kills, not growing with lifetime kill count.

## Tasks

### Task 1: World→screen projection

Add a shipped CPU world→screen projector for presentation anchors. Today billboards project GPU-side only, and the one CPU projector (`agent_overlay_world_to_screen`, `crates/postretro/src/agent_diagnostics.rs:93`) is `dev-tools`-gated and typed to `egui::Pos2`. Lift its logic into a non-gated, non-egui helper: given a world `Vec3`, the camera `view_projection: Mat4` (the app owns this as `RenderCamera.view_projection`, `crates/postretro/src/camera.rs:33`, via `Camera::view_projection()` `:156`), and the device viewport size, return `Option<Vec2>` device-pixel position — `None` when `clip.w <= 0` (behind camera), non-finite, or outside NDC bounds (the exact cull ladder at `agent_diagnostics.rs:103-117`), else `(ndc.x+1)*0.5*w`, `(1-ndc.y)*0.5*h`. This is a pure function with a unit test over known camera/point pairs (in-front maps to expected pixels; behind and off-screen return `None`). Place it in a non-gated module in `crates/postretro` (where the Task 2 producer lives), not behind the `dev-tools` gate `agent_diagnostics.rs` sits behind; it takes the camera matrix as an argument, so it needs no renderer internals (the renderer's `last_view_proj` is `pub(super)` with no getter — do not reach for it; the app camera is the source). No projection lives in the renderer's UI region, whose uniform is viewport-only (`UiUniform`, `crates/ui/src/output.rs:118`).

### Task 2: Pooled presentation layer + composition fold

Build the CPU-side presentation pool and wire its per-frame output into the UI composition. The pool holds a fixed-capacity set of live instances, each carrying `{ world_anchor: Vec3, spawn_time, lifetime, template handle, per-instance facts, motion/fade params }`; it owns spawn (append, evict-oldest at cap — never grow past the configured cap), age advance by **frame** time (so instances animate on zero-tick frames), fade, and expiry removal. The pool stamps each instance's `spawn_time` at intake-drain in the **frame-time clock** — the same clock TTL/fade/tween advance in — never a timestamp carried from the producing fixed tick (the Task 4 intake tuple carries no `spawn_time`); on its spawn frame an instance starts at `age = 0` and advances by that frame's `dt`, and evict-oldest breaks ties on equal `spawn_time` by intake FIFO order. The backing pool is **two disjoint budgets** sharing only projection and draw-assembly: a **spawn ring** (this task) bounded by its cap with evict-oldest, and (Task 6) a **keyed overlay map** bounded by `maxVisible` — a burst of damage numbers never evicts a status bar, and a full overlay map never evicts a number. Each frame it: projects every live anchor (Task 1) to device pixels, skips culled instances, asks Task 3 for each instance's relative draw list translated to the projected anchor, and assembles one screen-space `UiDrawData` (reusing `UiInstance`/`UiText`/`push_quad`/`push_text`, `crates/ui/src/output.rs:15,129` + `tree/draw.rs:229`). The renderer folds this `UiDrawData` into the frame `UiComposition` alongside the gameplay trees — extend the fold at `renderer_render_frame.rs:883-941` to include the presentation draw data (the retained-stack path builds `layer_draws` and calls `UiComposition::from_layer_draws`; add the presentation `UiDrawData` to that slice or a sibling `encode`, after scene / before the screen-effects resolve at `:962`). Name the app-side pool type `PresentationPool` (Tasks 4/6/7 cite it). The producers — Task 4's `apply_planned` intercept and Task 6's overlay refresh, both in `impact_policy.rs` with `&mut EntityRegistry` in scope but **no** handle to the app-side pool — push through an intake queue that **lives on `EntityRegistry`**, mirroring the dispatch queue: add `push_presentation_spawn`/`take_presentation_spawns` alongside `push_impact_dispatch`/`take_impact_dispatches` (`crates/entities/src/registry.rs`; the damage producer call site is `apply_damage_with_context`, `health.rs`). `PresentationPool` drains that registry-side queue each frame. The registry is the only object both the producer (registry-side) and the drain (app-side) share, so the queue cannot live on the pool struct — and producers still never touch renderer state directly. **Placement (Q2):** the pool (lifetime, per-instance facts, projection) lives app-side (`crates/postretro`), which already owns the render call, the camera, and (Task 6) the registry; the one-shot template **layout + lowering runs renderer-side** (Task 3 — it needs the renderer-owned `FontSystem`), fed each frame with the live instances' `(template, facts, projected anchor)`. This keeps wgpu and `FontSystem` in the renderer and combat/registry reads out of `crates/ui`. Until Task 3 lands, exercise the pool with a temporary hardcoded single-quad instance (a test seam Task 4 removes) so the projection→pool→fold→draw path is falsified before authoring exists. `render/ui/mod.rs` is 1244 lines — the fold addition is a few lines at the existing call site; do not restructure the pass.

### Task 3: One-shot template layout + per-instance facts

Lay out a presentation template's widget subtree once into a relative draw list, resolving per-instance facts, without the retained tree. A template is a widget subtree in the shipped vocabulary (`Text`, `Bar`, `Image`, `VStack`, `HStack` — the `Widget` enum, `crates/scripting-core/src/ui/descriptor/widgets.rs:28`). **Add a new tree-free one-shot layout+collect entry in `crates/ui`** — the lower-level taffy invocation is not exposed for reuse: `compute_layout_with_measure` lives only inside `UiTree::build_draw_data`/`build_draw_data_retained` (`ui_tree.rs`), and `collect_draw_data`/`collect_node` (`ui_tree_collect.rs`) are `pub(super)`, so the new entry must live in `crates/ui`'s tree module, not the renderer. Do **not** reuse `build_draw_data` (it hardcodes an empty `CellValues` and `time = 0.0`, silently dropping per-instance facts and never advancing tweens — it would satisfy "one-shot, no retained tree" and pass AC 10 while failing AC 1/7), and do **not** reuse `build_draw_data_retained` (the retained/`resolve_bindings` path, which also requires the renderer-owned `font_system`). The new entry builds the taffy tree (`build_node`, `build.rs`), runs `compute_layout_with_measure` with a `FontSystem` measure closure supplied by the renderer-side caller, and collects via a **`cell_values`- and time-threaded** `collect_draw_data` reusing the `push_quad`/`push_image`/`push_text` lowering (`crates/ui/src/tree/draw.rs`) — with **no** retained `UiTree`, dirty-tracking, modal stack, or focus/hit-test export. (`layout_gameplay_tree`, `render/ui/mod.rs:728`, is the retained path — `&mut self`, caches a `RetainedGameplayTree`, calls `resolve_bindings` — do not route through it.) **Placement:** because one-shot layout needs `FontSystem` (renderer-owned), the layout + lowering runs **renderer-side** (where the retained path's does), producing a template-local (origin-relative) `UiDrawData`; the app-side pool (Task 2) owns lifetime/facts/projection and hands the renderer each live instance's `(template, per-instance cell_values, projected anchor)`, and the renderer translates the origin-relative draw list to the anchor. **Per-instance facts:** a template's binds reference facts by name (`fact.number("value")`, `fact.number("healthFraction")`, `fact.bool("hasShield")`), and the value is a scalar the *producer* stamped for that instance — not a global slot. Resolve these through the tree-free per-instance resolvers — **not** the retained tree's `resolve_bindings`, which is a `&mut self` method on `UiTree` (`crates/ui/src/tree/ui_tree.rs`) that walks and mutates the retained tree it requires. The reusable resolvers are the free functions in `crates/ui/src/tree/draw.rs` (`resolve_text`, `resolve_panel_fill`, `bar_slot_value`) plus `drive_text_binding` (`bindings.rs`), which resolve against `(slot_values, cell_values)` with no tree. `cell_values` is the per-instance source — the G2 `localState` precedent, already threaded by `layout_gameplay_tree` — so supply each instance's fact bundle as that per-instance `cell_values` source rather than extending the global `slot_values` map (`UiRenderOutput.slot_values`, `crates/ui/src/output.rs`, is flat and global). Re-resolve facts every frame; re-run one-shot layout only when a fact that changes a node's measured size changes (a bound `Text`'s content width) — a fixed-structure template (`VStack[Bar,Bar]`) never re-layouts, only re-resolves fill fractions and advances `tween` (`TweenState<T>`, `crates/ui/src/tree/style.rs`). Templates consume the shipped `UiTheme` (`UiTheme::color/font/spacing`, `crates/scripting-core/src/ui/theme.rs:22`) the same way the focus ring does outside the tree walk, and `UiImageRegistry` (`render/ui/mod.rs:72`) for any image node. `styleRanges` resolves via the scalar resolvers in `draw.rs` (`style_text_value`/`style_value`); `visibleWhen` resolves via its predicate (`crates/ui/src/tree/predicate.rs`) — both as in the retained path.

### Task 5: Host→client presentation-event transport

Route a host-side spawn to the client that earned it, unreliably. The transport is a **new unreliable presentation message family**, not a `ServerMessage` variant: `ServerMessage` is doc-defined as the *reliable* Input-channel envelope (`crates/net/src/wire.rs:1108`), and presentation is the opposite — transient, unreliable, fire-and-forget — so conflating them crosses the state/event line the substrate rests on. Define a `ServerPresentationMessage` type carrying a **payload enum** whose first arm is `Spawn { template_id, anchor, value, facts }` and whose second, reserved arm is `OverlayFact { enemy_id: NetworkId, health_fraction: f32, shield_fraction: f32, has_shield: bool, alive: bool }` (Task 7 populates it — the field list is restated here because Task 5 pins the byte layout); **define both arms now** — the `OverlayFact` arm reserved-and-unused — so Task 7 adds no wire change and no second bump (a Task-5-era decoder that lacks the `OverlayFact` discriminant would otherwise error). **Versioning:** a new message vocabulary bumps `PROTOCOL_ID` (`handshake.rs:13`) and its byte layout bumps `WIRE_VERSION` (`:18`); `SNAPSHOT_VERSION` is untouched because it gates only `RawSnapshotMessage::validate` on the snapshot-record payload, not the channel envelope — the Snapshot drain (`drain_snapshots`, `transport.rs`) decodes each datagram at the `ParticipationFrame` envelope layer, which `WIRE_VERSION` governs — and the record itself is unchanged. One bump for the whole substrate; an older peer is refused at the handshake. **Vessel — decided: a dedicated unreliable `Channel::Presentation`.** Add a `Channel::Presentation` variant (the `Channel` enum is `u8`-keyed, `transport.rs`, so this is free) and a fourth `ChannelConfig` with `SendType::Unreliable` in `connection_config()`; `ServerPresentationMessage` is a tagged family on it, modeled on `ServerControlMessage` (`control.rs`). This is _the presentation channel_ the whole substrate rides (Task 7 and the Invariants name it). The alternative — a tagged sibling inside `ParticipationFrame` on `Channel::Snapshot` — is rejected on three source-grounded facts: (1) its only claimed advantage, saving a channel's memory, is a mirage: `CHANNEL_MEMORY_BYTES` (`transport.rs:39`) is renet's high-water *cap*, not an upfront reservation (the file treats `available == cap` as "empty", `:269`), so a fourth channel costs 0 bytes at boot and only holds memory if messages back up — and unreliable messages drop rather than accumulate; (2) `ParticipationFrame.payload` is a bare opaque blob carrying the `SNAPSHOT_VERSION`-validated record, so forking `drain_snapshots` would edit the shipped replicated-state decode for a transient cosmetic; (3) every channel today carries exactly one tagged family (`ServerControlMessage`/`ClientMessage`/`ParticipationFrame`), so a dedicated channel *is* the convention — and, being unreliable, it drops for a mid-joiner for free, needing none of `send_snapshot`'s participation-epoch bookkeeping. Address per-client with a `Channel::Presentation` send mirroring `send_snapshot`'s per-client addressing shape (`transport.rs:628`), without its epoch machinery. Adding the channel is part of `connection_config`, gated by the same handshake as the version bump. In Task 4's `apply_planned` intercept, resolve the presenter `dispatch.source` to its owning client via `CommandOwners::owner_of` (`command_queue.rs:63`): if it is the host-as-client's own pawn, spawn to the local pool as today; if it is a remote client, address the message to that `ClientId` and send nothing to anyone else; if `owner_of` is `None` (a non-pawn source — projectile, turret, or environmental damage, or `dispatch.source` is `None`), the number has no earning client, so spawn host-local only and never broadcast. Client-side: ingest `ServerPresentationMessage` in the unreliable-channel drain and spawn into the client's local pool. Loss is silent (unreliable) — a dropped spawn simply never appears; no ack, no resend, no reconcile. Verify with the latency/loss harness (drop injection): the number appears under clean conditions, is silently absent under drop, and never stalls the client. `net/wire.rs` (2728) and `netcode/mod.rs` (4781) are large; the new message type + one send arm + one ingest arm are localized additions, not restructures.

### Task 6: `defineOverlay` + `damagedEnemies` source + enemy status bar (host/single-player)

Build the overlay archetype and the enemy status bar, host-authoritative. **Authoring:** `defineOverlay({ over, template, maxVisible })` and the `damagedEnemies({ lingerMs, hideAtFull, shield? })` source descriptor under `postretro/ui`, with wire + Luau + typedef parity. This task also extends the `PresentationTemplate` descriptor (Task 4) with an overlay-only `worldAnchor { socket, offsetY }` field, carrying the same wire/Luau/typedef parity — Task 4's descriptor param list (`lifetimeMs`/`motion`/`fade`/`spawnScatter`) does not include it. The `shield` config is a **value/max pair** of IR expressions over a per-entity scope (e.g. `{ value: (e) => e.state("shield"), max: (e) => e.state("maxShield") }`) evaluated host-side per tracked enemy — a pair, not a single fraction lambda, so the engine can derive presence (`hasShield`) and guard the divide. **Host system — event-driven, not a state scan:** `HealthComponent` (`health.rs:314`) carries no last-damage timestamp, so a per-frame scan for "damaged within `lingerMs`" cannot be written and would be a poll-state model — the very thing the substrate rejects. Instead the overlay refresh is driven from the **same synchronous per-hit evaluation the `present` effect rides** — `evaluate_dispatch` / the `apply_planned` presentation lane, where each `InTick` dispatch is already in hand — **not** a second drain of the dispatch queue: `take_impact_dispatches` (`registry.rs`) is a destructive `mem::take` already consumed by the impact-policy runtime (`evaluate_pending_in_registry`), with no peek and no tee, so a second `take_` reader would starve it. Each such damage dispatch to a tracked-eligible enemy **creates or refreshes** the keyed **overlay** instance for its target `EntityId` and **resets its linger timer**. (This couples the overlay refresh to the impact-policy evaluation point — the price of not adding a queue fan-out; the per-frame fraction stamp below stays a separate game-logic pass.) A game-logic-stage system then runs **once per frame, after the frame's fixed-tick loop** (so an instance created in this frame's tick is stamped and projected the same frame, not a frame late), over the *already-tracked* set only. For each tracked instance it reads the current facts and applies eviction in the **same pass**: `healthFraction = current/max` (`HealthComponent`); a missing `HealthComponent` — a direct despawn drops it immediately, a scripted `mark_terminal_despawn` keeps it live to frame end — is treated as **evict**, never a default-0 read or panic; `current <= 0` likewise evicts in this pass, so a same-tick create-then-kill produces no rendered bar. The shield track is author-declared as a **value and a max** (`shield: { value: (e) => e.state("shield"), max: (e) => e.state("maxShield") }`), both evaluated host-side via the direct `@state` read (`registry.get_component::<EntityStateComponent>(id).get(name)`, `crates/scripting-core/src/ir/scopes.rs`): `hasShield = (evaluated max > 0)` — a single `get()` returns `0.0` for an unset name and offers no `has()`, so 'no shield state' is derived from the denominator, not the value — and `shieldFraction = max > 0 ? value / max : 0`, guarding the divide so no NaN reaches the bar. (`registry.iter_with_kind(ComponentKind::Health)` / `query_by_component_and_tag`, `registry.rs:888,857`, enumerate the tracked reads.) Overlay instances differ from spawn instances in lifetime: they are **keyed** (one per enemy, updated in place, not appended), linger on a per-instance timer reset by each damage dispatch, tween the health fraction (`TweenState`), and are evicted when the enemy dies (health `current <= 0` or despawn) or the linger expires. They are a **budget disjoint from Task 2's spawn ring** — a spawn overflow never evicts a bar — bounded by `maxVisible`, whose eviction key is **last-damaged time** (refreshed each hit), never `spawn_time` (evict the least-recently-damaged past the cap); ties on equal last-damaged time break by creation FIFO (mirroring the spawn ring), so host and clients evict deterministically. `hideAtFull` suppresses the instance while `current == max`. **Anchor** is a model-authored named point the template references by name (`worldAnchor.socket`): the posed head-socket world position is the **primary** path, the AABB-top offset the degrade. The posed path is a **thin getter to build** (~15–25 lines) over host-side, wgpu-free machinery that already exists (proven by the M10 hit-zone raycasts, the sim foot-probes, and E21 attachment rendering) — **no new per-frame pose pass**. Add `HitZoneStore::posed_socket_world(&self, registry, id, socket, anim_time) -> Option<Vec3>` on the store owned at `session.hit_zone_store` (`startup/lifecycle.rs`), composing: (i) socket→joint from `ModelHitZones.sockets` (E21 `SocketBinding::SkinnedJoint(idx)` / `RigidRest(m)`, `gltf_loader.rs`); (ii) the on-demand pose from `sample_world_pose_for_probe` (`hit_zones.rs:1137`, the game-side sampler over `model::anim` — the M10 on-demand pose path, not renderer state); (iii) model→world via `model_matrix(transform, origin_offset)` (`hit_zones.rs:1054`), then `offsetY`. Everything is in game-logic-stage scope (registry `Transform`/`MeshComponent`, the shared `anim_time`, the store). **Namespace:** `worldAnchor.socket` names an **E21 socket** (`ModelHitZones.sockets`), distinct from an **M10 hit-zone tag** (`joint_zones[].tag`); the getter checks `sockets`, else scans `joint_zones` for a matching tag. **Degrade to AABB-top** (mirroring `canonical_name`'s degrade-don't-refuse, never fail) when the socket is absent, or when the sampler returns `None` during a renderer-only smooth-interrupt snapshot fade (`hit_zones.rs:1160`): the fallback is host-readable via `HealthComponent.hitbox` (`{ half_extents, offset }`, `health.rs:25`; top = `position + offset + Y * half_extents.y`), or `ModelHitZones.derived_bound` for zone-only enemies. Projected by Task 1. This reuses Task 2's `PresentationPool` (extended with a keyed/overlay instance kind) and Task 3's layout/facts. Host/single-player only; Task 7 adds co-op. Aimed-at inclusion (`include: "aimedAt"`) is host/SP-only and optional here.

### Task 7: Enemy status bar — co-op fact push

Deliver enemy bars to the damaging client in co-op. Carry the enemy facts as the `OverlayFact` arm of Task 5's `ServerPresentationMessage` payload enum (Boundary inventory) — defined-and-reserved at the Task 5 bump, so this task adds no new message, no new variant, and no second `PROTOCOL_ID`/`WIRE_VERSION` bump. The payload is `{ enemy_id, healthFraction, shieldFraction, hasShield, alive }`, where `enemy_id` crosses as the replicated **`NetworkId`** (the host's `EntityId→NetworkId` allocator is monotonic and **never recycled**, `networking.md`; the client already holds the inverse `NetworkId→EntityId` map for rendering).

**Push cadence — on evaluated-fact change, per frame:** once per frame, **after the fixed-tick loop** (the same post-tick sample point as Task 6's stamp), the host evaluates each tracked enemy's fact tuple and sends a fact **only when it differs from the last tuple sent to that client** — addressed over the unreliable presentation channel (Task 5) to the client that damaged it, at most one fact per (client, enemy) per **frame**. On a multi-tick frame this is one end-of-frame fact, not one per tick, and a lethal frame sends a single `alive = false` with no preceding `alive = true`. On-*change*, not on-a-hit: health changes only on a hit, but an author shield **recharges between hits** (`scripting.md` §11 — a per-tick system, so `@state` advances on the tick clock and a zero-tick frame yields no change), and the evaluated-value compare catches that recharge where a literal on-hit trigger would leave the shield bar stale. An unchanged tuple sends nothing, so the overlay stays an *event* stream, not replicated *state* (a value that changed every frame would defeat the gate and is out of contract). The host holds a per-(client, enemy) **last-sent tuple**, pruned when that enemy's host tracking ends (death fact sent, or linger expiry) — bounding it to the live-tracked set × clients.

**Client ingest + terminal guard:** the client ingests facts into keyed overlay instances (keyed by the enemy's `NetworkId`), lingering/tweening/evicting client-side exactly as the host does, driven by arriving facts rather than a local registry read. Because the presentation channel is unreliable *and* unordered, a stale pre-death fact can arrive after the death fact, so the client keeps a **terminal-id set separate from the keyed map** (a removed instance cannot also remember its id). `alive = false` **marks the id terminal and removes any live instance — it never creates one**; ingest checks the terminal set before creating any instance, so a reordered `alive = true`, or an `alive = false` for a never-seen id, produces no bar over a corpse and no create-then-evict flicker. The terminal set is bounded by **TTL-expiry** past the channel's reorder horizon (a few hundred ms), then GC'd — not the session — since `NetworkId` non-recycling would otherwise grow it monotonically (the bounded `ContributorLedger` is the per-target-state precedent). A reorder between two *live* fractions (0.5 after 0.2) is a tolerated one-frame flicker the next fact corrects.

**Loss:** a dropped fact leaves the client's last value, and because the host suppresses resends of unchanged tuples, it persists until the next *value-changing* fact (which may skip the dropped intermediate value) — so the anti-orphan backstop is **client-side linger expiry**, not the `alive = false` death fact (sent once, and itself droppable; it only makes eviction prompt when it arrives). Recently-damaged-**by-me** only: the host pushes an enemy's facts solely to clients that damaged it, so a client never sees a bar for an enemy it has not engaged, nor another client's set. A late joiner has no prior facts and shows no bar until it damages something.

**Test seams:** the client fact-ingest is a plain function over `(fact, client state)` callable directly, so AC 15's adverse-ordering cases are ingest-order unit tests (not wire reordering); and expose behind `#[cfg(test)]` a `len()` on both the host per-(client,enemy) last-sent map and the client terminal-id set, plus a driveable TTL/prune advance, so AC 16's bounding is a runnable test rather than a review gate.

## Ordering pins

| Scenario | Ordering | Expected outcome |
|---|---|---|
| Killing blow, target despawns same frame | `present` captures its **value** at plan time (`plan_effect`, from the seeded scope, before the consequential lane's `SetHealth`/despawn) and reads its **anchor** from the registry at the `apply_planned` intercept (`plan_effect` has no transform); scripted `despawn` only stages end-of-frame removal (`mark_terminal_despawn`), so the transform is live through the presentation lane regardless of lane order | The number shows the correct value at the live anchor; no post-removal lookup |
| Fact arrives mid-tween (health/shield fraction) | New fraction retargets from the current interpolated value — no snap — over the full tween duration; `alive=false` skips the tween | Bar animates smoothly hit-to-hit; a zero-length authored tween snaps; facts arriving faster than the tween completes → last fact wins, intermediate fractions not guaranteed reached |
| Pool at cap, new spawn arrives | Task 2 evict-oldest before append | Oldest live instance disappears; count stays at cap; no growth, no panic |
| Frame with zero fixed ticks | Producer advances TTL/fade/tween by frame time and re-projects | Live instances still animate and track the camera; nothing freezes |
| Frame with two fixed ticks, a spawn each | Both `present` intercepts push to the intake queue; the producer drains both that frame | Both numbers appear |
| Overlay enemy dies | Task 6 evicts on `current <= 0` / despawn (same post-tick stamp pass); Task 7 pushes an `alive=false` fact, **terminal** for that `NetworkId` (recorded in the client's terminal-id set, separate from the keyed map) | Bar removed on host and (via the pushed fact) on the client; the terminal marker survives the instance's removal, so a later stale fact cannot resurrect it |
| Co-op facts arrive reordered (unreliable, unordered channel) | `alive=false` marks the `NetworkId` terminal and removes any instance (never creates one); ingest checks the terminal set before creating | A stale `alive=true` after death is dropped; an `alive=false` for a never-seen id creates no bar (no create-then-evict flicker); two live fractions out of order flicker one frame and self-correct |
| Multi-tick frame: enemy hit in an early tick, killed in a later tick | Host evaluates once per frame post-all-ticks, ≤1 fact per (client,enemy) per frame | One fact sent: `alive=false`, `healthFraction=0`; the intermediate `alive=true` never goes on the wire; client evicts |
| Spawn cap reached while status bars are live | Spawn ring and keyed overlay map are disjoint budgets | A new damage number evicts the oldest *spawn*, never a status bar; a full overlay map (`maxVisible`) evicts the least-recently-damaged *bar*, never a number |
| Overlay eviction, two enemies damaged in the same tick | Equal last-damaged time → break by creation FIFO | Deterministic eviction across host and clients; no HashMap-iteration-order nondeterminism |
| Overlay instance created in this frame's tick | Per-frame stamp runs after the fixed-tick loop | Stamped and projected the same frame (no one-frame-late/empty bar); a same-tick create-then-kill is evicted in that pass, so no bar renders for the killing blow |
| Per-frame stamp on a despawned tracked enemy | Absent `HealthComponent` (direct despawn drops it immediately; `mark_terminal_despawn` keeps it to frame end) | Treated as evict, never a default-0 read or panic |
| Shield recharge between hits | `@state.shield` advances on the tick clock (per-tick §11 system); change-detect samples at the same post-tick point | Recharge propagates a fact to the client; a zero-tick frame yields no change; an every-frame-changing value is out of contract |

| Presentation event dropped (unreliable) | No retransmit; host suppresses resends of unchanged tuples | Spawn: number never appears. | Two clients damage the same enemy | Host pushes that enemy's facts to each damager independently | Each sees the bar; neither sees the other's damage numbers |

## Open questions

Nothing open. Every prior and review-surfaced question is decided against the project's own commitments (lean / present-events-not-state, foundation-to-grow, spatial-data-from-the-model, host-authoritative): the transport is a new unreliable `ServerPresentationMessage` family on a dedicated `Channel::Presentation`, not a `ServerMessage` variant; the enemy-bar recency is event-driven from the per-hit impact evaluation, not a state scan; the spawn ring and keyed overlay map are disjoint pool budgets; the co-op fact stream pushes on evaluated-fact change (per frame) and guards the unordered channel with a terminal `alive=false` per non-recycled `NetworkId`; the shield track is an author-declared value/max pair (so presence and the divide-guard are expressible); one-shot layout runs renderer-side (it needs the renderer-owned `FontSystem`); and the enemy-bar anchor is the posed head-socket world position with an AABB-top fallback.

The two former build-time confirmations were investigated and are now **decided in source** (Task 5 / Task 6): (1) the presentation channel is a dedicated unreliable `Channel::Presentation` — the "extra channel costs memory" objection is a mirage (`CHANNEL_MEMORY_BYTES` is a high-water cap that starts empty), it keeps the `SNAPSHOT_VERSION`-validated snapshot decode untouched, and it matches the one-tagged-family-per-channel convention (`ServerControlMessage`); (2) the posed head-socket anchor is a ~15–25 line host-side getter over existing wgpu-free machinery (`HitZoneStore` + the M10 on-demand pose sampler + `model_matrix`), with the AABB-top fallback (`HealthComponent.hitbox`) host-readable in the same stage. The `EntityId`-reuse question was likewise resolved from source: `enemy_id` crosses as `NetworkId`, which the host allocator never recycles, so the terminal rule needs no runtime check.
