# E18 — Trigger-Event Dispatch Parameters (`TriggerEventScope`)

## Goal

Let a trigger-event reaction act on the ephemeral facts of the fire: *who* touched the trigger (`on.activators`), *which* volume fired (`on.trigger`), and how many bodies are on it (`on.occupancy`) — per §12 (`scripting.md`, where this event type is currently named "contact"; renamed here, see Rough sketch). Unblocks "damage whoever pressed the plate" and "disarm the plate that fired," authored once for any number of plates. Consumes the dispatch-param mechanism from `E18--dispatch-scope-params`; the key architectural move is that entity inputs never enter the IR substrate — `activators`/`trigger` ride the existing command-*target* channel (`BoundTarget`), keeping the IR purely numeric.

## Scope

### In scope

- **Activator identity at the fire site.** The trigger fire event already carries the crossing player (`TriggerEventFire.player: PlayerId`); resolve it to a pawn `EntityId` at dispatch (Local wraps the pawn; Remote resolves via `AuthoritativePlayer.pawn`) and thread a fire context — fired-trigger id, activator pawn set, effective occupancy — into the binding executor, which today keys only on `(trigger, edge)` and discards the player.
- **Sentinel command targets.** Two dispatch-time targets alongside tag and entity-id targeting: `"@activators"` (the fire's activating pawns — broadcast: the engine iterates the set in sorted order) and `"@trigger"` (the fired volume). `"@activators"` is legal in a `SequenceStep` id position and as a `PrimitiveReactionDescriptor` target; `"@trigger"` in a `SequenceStep` id position (arm/disarm steps). Resolved per fire by the executor; a syntactically legal but semantically mismatched sentinel/command pair executes with the shipped per-primitive warn-skip (as `applyDamage` on a health-less target already does).
- **`on.occupancy` numeric leaf.** `@occupancy` — the fired volume's *effective* occupant count (alive-filtered, the `E18--coop-activation-policy` predicate) at fire time: on an enter fire it includes the activator; on an exit fire it excludes them. Bound via a trigger-event vocabulary `DispatchScope`.
- **SDK surface.** `TriggerEventParams` (`activators`, `trigger` opaque target tokens; `occupancy` a `RuntimeValue`); free builders `damage(on.activators, amount)`, `armTrigger(on.trigger)` / `disarmTrigger(on.trigger)`; both runtimes, typedefs, drift check.
- **Script-side trigger-event observer.** Free function `onTriggerEvent({ tag }, "enter" | "exit", fire[])` returning a descriptor; carried on `setupLevel`'s manifest and `ModManifest.triggerEvents` with the same `levels` selector as crossings. Installs into the same binding table the brush `on_fire`/`on_exit` KVP path uses — the enter/exit dispatch gates widen so script-bound volumes with no KVP name still fire, and multiple sources on one `(volume, edge)` merge additively; both paths publish `TriggerEventScope` (a concept name — the trigger-event vocabulary of the sibling's `DispatchScope`, `[("@occupancy", Number)]`, not a new Rust type).
- **`"occupied"` is not an event.** The §12 table's third trigger-volume event is dropped: occupancy-conditioned firing is already covered by crossings over the `occupiedCount`/`occupants` ambient refs — one mechanism, not two. §12 updated at promotion.
- **Split-before-extend.** Relocate the command/target/execute half out of `trigger_bindings.rs` (1245 lines) before extending it.
- Tests: headless damage-the-presser, disarm-own-plate, occupancy param, install-time cross-source rejection; two-endpoint remote-activator damage.

### Out of scope

- **Non-player activators.** The trigger substrate tracks `PlayerId` only; AI/monster activators wait for the substrate to track them. `activators` is a pawn set, v1.
- **Per-activator sequence fan-out** (`on.activators.each((a) => seq([...]))` — §12 fork 3b). Broadcast targeting covers the driving cases; a fan-out opcode adds control flow to the loop-free IR and waits for a concrete case needing distinct per-activator *sequences*.
- **An `EntityRef` script value type.** `on.activators`/`on.trigger` are opaque author-time target tokens; no entity id is ever readable in script from dispatch, and they are never IR operands (`runtime.add(on.trigger, 1)` is ill-typed and has no wire form).
- **Entity inputs in the IR substrate** — no new `IrValue` kind, no entity-typed `BindingScope` channel. Targets are commands' business.
- **`levelLoad`/crossing sources publishing trigger-event inputs** — a `TriggerEventParams` reaction on those sources rejects at install (IR `@`-names reject via the sibling spec's published-input gate; sentinel targets via this spec's own subscription check, Task 2).
- Dynamic (script-spawned) trigger volumes as `onTriggerEvent` subjects — map-authored volumes only, matching the trigger substrate.

## Acceptance criteria

- [ ] Damage-the-presser: with a reaction `damage(on.activators, 25)` bound to a plate's enter event, the entering pawn loses exactly 25 HP and a second pawn standing elsewhere is untouched (headless).
- [ ] Broadcast-per-edge: two pawns entering the same plate on the same tick are each damaged exactly once (enter edges are per-player; each fire's activator set is that edge's pawn).
- [ ] Disarm-own-plate: two plates sharing one binding/address — stepping on plate A disarms plate A only; plate B still fires later (`disarmTrigger(on.trigger)`).
- [ ] `on.occupancy`: a reaction writing `on.occupancy` to a slot records 2 when two live pawns occupy the fired volume at fire time; a corpse on the volume is not counted; an exit fire excludes the leaver.
- [ ] Cross-source rejection: a `TriggerEventParams` reaction fired from `levelLoad` or a crossing is rejected at level install with a warning and never fires; other reactions on that source are unaffected.
- [ ] `onTriggerEvent({ tag }, "enter", [r])` fires identically to a brush `on_fire` KVP naming the same reaction — same fire context, same commands — including on a volume carrying no `on_fire`/`on_exit` KVP at all (script-only binding still fires; headless equivalence test).
- [ ] A brush-KVP-bound and a script-bound reaction on the same `(volume, edge)` both fire (bindings merge; no last-wins clobber).
- [ ] Degradation, identical in TS and Luau: a tag matching zero volumes warns and is inert; an unknown event string warns and drops the descriptor; an unknown `@`-spelling, a known sentinel in an illegal position (`@trigger` as a primitive target, `@occupancy` on any target/id), or a sentinel on a presentation-class step rejects at install; a primitive descriptor carrying both `target` and `tag` warns and is skipped.
- [ ] Two-endpoint: a remote player's pawn pressing the plate takes the damage on the host, and the client observes it via the shipped health replication; the local player is untouched.
- [ ] An `@activators`/`@trigger` sentinel command reached by a name-dispatched fire with no fire context (`onPress`/`onComplete`) warns and skips that command (headless).
- [ ] A remote activator absent from the tick's player list (exit fired by disconnection) yields an empty activator set: `@activators` commands no-op; `@trigger`/`@occupancy` unaffected.
- [ ] TS: passing a `TriggerEventParams`-typed reaction to `onStateCrossing`'s fire list fails `tsc --noEmit` (compile-must-fail fixture); `Reaction<{}>` is still accepted by trigger-event sources.
- [ ] Typedef drift check passes with `TriggerEventParams`, `onTriggerEvent`, `damage`, `armTrigger`/`disarmTrigger` in `postretro.d.ts` / `.d.luau`; a TS and a Luau fixture author an identical presser-trap producing identical wire data (the fixture's `fire`-list reactions carry explicit string names — a nameless reaction's body-hashed id differs per runtime).
- [ ] The binding executor split lands behavior-preserving: existing trigger-binding tests pass unchanged before the feature commits.
- [ ] Determinism: two identical headless runs produce identical damage ledgers and fire sequences for a multi-pawn presser scenario.

### Task 2: Fire context → executor; sentinel targets; `@occupancy`

The engine core. **Fire context — two build halves, pinned.** The occupant map is exclusively borrowed for the duration of `run_authoritative_tick_with_dispatch` (`crates/postretro/src/trigger_system.rs:140`), so the caller-side closure cannot reach it: the fired volume's effective occupant count is computed *inside* that method at the dispatch sites (`:262`/`:306`) and delivered by widening the dispatch closure's payload (occupancy alongside the `TriggerEvent`). The `ready/E18--coop-activation-policy` dependency (which lands first) relocates occupant tracking into its `Occupancy` struct, so these become `Occupancy` mutations, not the current inline `:205-223` map edits; the structural guarantee is what matters — every enter insert and exit removal for the tick is settled before the dispatch loop runs, so a dispatch-time `effective_occupants` read includes the entrant on an enter and excludes the leaver on an exit. The caller-side dispatch closure (`sim/mod.rs` now has two — the script-ctx path `execute_with_script_ctx` at `:182` and the literal `execute` at `:210`; the fire context threads through the script-ctx one, where the tick's players are in scope) resolves `TriggerEventFire.player: PlayerId` to the activator pawn set — `Local(EntityId)` is the pawn; `Remote(u64)` resolves through the tick's `AuthoritativePlayer { id, pawn }` list built at `sim/mod.rs:159-172`. The set is **ordered** (sorted) and broadcast iterates in that order — the determinism AC depends on it. Per fire the set is 0-or-1 pawn — the fire's own `TriggerEventFire.player`, empty if a remote is absent; broadcast-per-edge comes from the multiple per-player fires the tick already emits, never from aggregating a volume's entrants into one fire. The sort is a determinism and forward-compat detail, not multi-activator today. A remote activator absent from the tick's player list (an exit fired by disconnection) warns and yields an empty activator set: `@activators` commands no-op; `@trigger`/`@occupancy` unaffected. **Alive set:** the effective filter is needed *during* the trigger tick, so the alive set is built once at the top of each host tick, before `run_authoritative_tick_with_dispatch` — this both moves the coop spec's landed build point (top of the post-trigger occupancy aggregation) earlier in the tick **and** changes what it iterates: coop builds `alive_this_tick` from the *occupant* `PlayerId`s (safe only because it reads them post-settle), but an entrant this tick is not yet an occupant, so a top-of-tick build must instead populate `alive_this_tick` from the **full tick player list** (`AuthoritativePlayer`, `sim/mod.rs:159-172`) — otherwise a pawn's own enter fire would read an `@occupancy` that excludes it, breaking the enter-inclusion guarantee. Coop's post-settle aggregation reuses this superset unchanged, since it intersects with the occupant map either way. The earlier build point populates the coop spec's `Occupancy::alive_this_tick` field (or threads the set in as a new `run_authoritative_tick_with_dispatch` parameter alongside the occupancy payload), which the dispatch-site `effective_occupants(volume, &alive_set)` call reads. The invariant the move must preserve: `alive_this_tick` is populated before both the in-tick `@occupancy` reads here and coop's own post-settle aggregation that also reads it. The assembled context — fired trigger `EntityId`, activator pawns, effective occupancy — threads through the table's `execute_with_script_ctx` (`trigger_bindings.rs:303`; the base `execute` is `:272`, today `(trigger, edge, registry, slot_table)`) into command execution. **Sentinel targets:** The Rust descriptor widenings this bind depends on land in this task: `PrimitiveDescriptor` (`crates/entities/src/data_descriptors/types/reactions.rs:50`) gains the optional `target`, and `SequenceStep.id` (`:21`/`:22`) widens from `EntityId` to accept the sentinel strings (numeric vs string discriminates), with the per-runtime descriptor converters updated — `primitive_descriptor_from_js`/`sequence_steps_from_js` (`crates/scripting-core/src/data_descriptors/js/reactions.rs:85`/`:135`) and the Lua twins (`lua/reactions.rs:102`/`:158`), where `id` today parses as `EntityId` and gains a numeric-or-sentinel-string union and `PrimitiveDescriptor` gains optional `target`. Widening `SequenceStep.id`'s type ripples to every read: `bind_sequence_step` (which wraps `id` into a `BoundTarget::Entity`), the existing `SequenceStep` literals in tests, and the sequenced-registry dispatch (`dispatch_sequence`), whose registry keys on `EntityId` and so cannot receive a sentinel — the name-dispatch path must detect a sentinel `id` and warn-skip before that registry call, not resolve it. Add `Activators` and `FiredTrigger` variants to `BoundTarget` (Task 1's new module); `resolve` (today `&EntityRegistry`-only, `trigger_bindings.rs:434`) gains the fire context, threaded through `execute`/`execute_with_script_ctx` → `execute_non_store` → `resolve` on both paths, and maps the variants from that context to entity lists (broadcast: `Damage` on `Activators` applies the shipped per-entity damage dispatch to each pawn; `Arm`/`Disarm` on `FiredTrigger` targets the fired volume). The base literal `execute` (no fire context, `sim/mod.rs:210`) passes an empty context, so sentinel targets there resolve to empty and no-op. At bind time (`partition_direct_reaction` / `bind_sequence_step`), `"@activators"` in a step id or primitive target position and `"@trigger"` in a step id position produce the variants; a sentinel on a presentation-class step rejects at install with a warning (presentation steps drain app-side, where no fire context exists), and any `@`-spelling in a position where it is not enumerated legal — an unknown spelling, `"@trigger"` as a primitive `target`, or `"@occupancy"` in any target/id position — rejects at install with a warning rather than parsing as a tag. **Rejection is per subscription, not per registration:** a sentinel-bearing reaction registered in the composed named set is always legal — that is how the trigger path finds it. A *non-trigger source subscription* referencing it — a crossing `fire` entry, the `levelLoad` address — warns and skips that subscription at install: this install-time walk lives on the composed-reaction subscriber pass (`populate_level` + `rebuild_reaction_subscribers`, `crates/postretro/src/startup/lifecycle.rs:1127-1137`) and covers every non-trigger source that resolves reaction names, keyed on "a referenced reaction carries a sentinel in a target/id position"; a name-dispatched fire reaching a sentinel-bearing command at runtime with no fire context (button `onPress`, `onComplete` chains) warns and skips that command. This sentinel-channel check is owned here — the sibling's published-input gate covers only IR `@`-names (`@occupancy`). The runtime warn-skip lives on the named-dispatch execution path (`fire_named_event_with_sequences`, `crates/scripting-core/src/reaction_dispatch.rs:140`, added to this task's file list), which recognizes the sentinel `target`/id spellings and skips them when no fire context is present. The numeric `@occupancy` channel is symmetric: `@occupancy` lives only on the trigger in-tick bind site, so a reaction reading it that is reached through app-drain name-dispatch (`onComplete`, button `onPress`) hits a site whose scope carries no `@occupancy`, fails to bind there, and is skipped — no fire context, no evaluation. **`@occupancy`:** register a trigger-event vocabulary `[("@occupancy", Number)]` `DispatchScope` (sibling spec's Task 1 type — a `BindingScope` wrapping `StoreScope` with a fixed `@`-name vocabulary in the `MovementScope`-snapshot shape, seeded per fire before `eval_and_write`; grep the landed `crates/scripting-core/src/ir/scopes.rs` for the `DispatchScope` constructor and its seed call). The `StoreSlot` bound program's scope type widens from done ir-valued-reactions' `BoundProgram<StoreScope>` (live at `trigger_bindings.rs:132`, `BoundStoreValue::Ir`) to the trigger-event `DispatchScope` for **all** trigger-installed values — programs reading no `@`-input bind identically through its store delegation — bound once at install, evaluated in-tick with the fire context's count seeded.

### Task 3: `onTriggerEvent` observer — wire, manifest, install

Script-side trigger-event binding. Descriptor: `{ tag, event: "enter" | "exit", fire, levels? }`, where `fire` is an array of **reaction-name strings** — the SDK lowers reaction handles to their (auto-)id strings, so a referenced reaction must also be registered in the composed reaction set (same lookup and missing-name warn as the KVP path). SDK free function `onTriggerEvent(filter, event, fire, options?)` (filter is `{ tag: string }`, matching the trigger-volume query filter vocabulary; `options?` carries `{ levels }`, mirroring the crossing manifest's `levels` selector) returning the descriptor; carried on `setupLevel`'s returned manifest under a new `triggerEvents` key and on `ModManifest.triggerEvents` — the Rust `LevelManifest` struct and its manifest VM deserializer gain the `triggerEvents` field alongside `reactions`/`crossings` (consumed at `crates/postretro/src/startup/lifecycle.rs:1112-1131`) — composed at level install by the same `levels` tag-selector rules as reactions/crossings — purely additive; trigger-event descriptors are nameless, so descriptors identical across the full `(tag, event, fire, levels)` tuple from mod + level manifests dedup with a warn; descriptors sharing a `(tag, event)` but differing in `fire` merge additively rather than deduping. Install runs immediately after `build_trigger_bindings` (`lifecycle.rs:1141`), so brush-KVP bindings land first; resolve `tag` to the level's trigger-volume entities (the entity `_tags` grouping, as trigger diagnostics reads it) and append each fired reaction into `TriggerBindingTable` under `(volume, edge)`. **Merge, don't clobber:** today `bind_event` (`trigger_bindings.rs:226`) `.insert`s a `TriggerBinding { commands, residual: Option<..> }`, clobbering any existing entry. Merging requires (a) an append/merge entry point replacing that insert, (b) restructuring the singular `residual` handle so two sources' residual steps concatenate in install order, and (c) a public accessor exposing the table's `(volume, edge)` keys (the `bound_edges` set below is built from it). When a brush KVP and one or more `onTriggerEvent` entries target the same `(volume, edge)`, their commands and residual steps append into one `TriggerBinding` in install order (KVP first, then script entries in manifest order). **Widen the dispatch gate:** the enter/exit dispatch sites skip volumes with an empty KVP event name today (`trigger_system.rs:251`, `:295`); they must also fire when the binding table holds an entry for `(volume, edge)`: `run_authoritative_tick_with_dispatch` gains a `bound_edges: &HashSet<(EntityId, TriggerEventEdge)>` parameter, built from `TriggerBindingTable` before the call and passed at all three call sites (the `#[cfg(test)]` `run_authoritative_tick` wrapper at `trigger_system.rs:125` and the two `sim/mod.rs` dispatch closures at `:176`/`:204`), and each empty-name gate becomes "name-empty **and** `(volume, edge)` absent from `bound_edges` → skip." Such fires carry an empty `event_name`, appear in `report.fires` like any other, and the executor keys on `(trigger, edge)` and never reads the name; any name-keyed side path treats empty as absent. Execution, partition (consequential vs presentation), residual drain, and the Task 2 fire context are otherwise shared unchanged. A tag matching zero volumes warns and is inert (the shipped inert-degradation pattern). `"enter"`/`"exit"` are the only events — no `"occupied"`; the parser warns and drops a descriptor with any other event string, identically in both runtimes.

## Rough sketch

- **Terminology — "contact" renames to "trigger event."** §12 currently names this event type *contact*; that reads as physics-engine jargon (contact points) to anyone without that background. The author-facing family is renamed wholesale: `triggerEvents` manifest key, `onTriggerEvent` builder, `TriggerEventParams` SDK type, `TriggerEventScope` scope; the §12 event-type row renames at promotion — including its source-spelling column (`onTriggerEvent(...)` + the `triggerEvents` manifest key replace `world.query(…).on("enter"|"exit"|"occupied", r)`) and its published-inputs column (opaque command-target tokens replace `EntityRef[]`/`EntityRef`; the `occupied` event drops). Engine internals already use this vocabulary (`TriggerEvent`, `TriggerEventEdge`), so source, docs, and modder terms converge. Old term appears nowhere in shipped surfaces. This spec owns the contact→trigger-event rename and the `occupied`-drop §12 edits; the sibling `E18--dispatch-scope-params` promotion references the already-renamed row rather than re-editing it.
- **Two worlds, resolved.** Numeric dispatch inputs (`@occupancy`) are IR leaves through `DispatchScope` — same substrate as `@rising`/`@dt`. Entity dispatch inputs are **command targets**: the descriptor stores a sentinel spelling, bind produces a `BoundTarget` variant, and the executor resolves it from the fire context. The IR substrate stays two-typed (`Number`/`Bool`); no entity channel, no new leaf kind. This was the handoff's "biggest open substrate question" — answered by keeping entities out of the substrate entirely.
- **Why broadcast targeting suffices (v1).** The driving cases apply *one* command to each activator (damage) or target *the* fired volume (arm/disarm). Per-edge dispatch means the activator set is a single pawn today, so broadcast and fan-out are indistinguishable in practice; fan-out earns its IR control-flow cost only when a case needs per-activator *sequences*.
- **Future event sources (context for the naming).** Trigger events are one typed source among several: crossings are the universal condition observer (engine publishes counts as state; scripts watch crossings — the co-op occupancy pattern), `progress` already covers kill-ratio fires, and the combat-event substrate (`research/combat-events.md`) will likely add named or typed sources with their own scopes (`on.victim`, `on.killer` would reuse the sentinel-target channel). Each source keeps its own typed manifest key; there is deliberately no generic `eventObservers` bag — per-source keys are what make scope typing checkable.
- **Grounding (verified this session):** `TriggerEventFire { trigger, player: PlayerId, event_name }` (`trigger_system.rs:42`); edges detected per-player, vec built at `:211` and sorted at `:236`; the executor drops the player today (`bindings: HashMap<(EntityId, TriggerEventEdge), TriggerBinding>`, `trigger_bindings.rs:60`). `BoundTriggerCommand::Damage { target, amount }` already exists (variant at `:106`) — the presser case is a new target variant, not a new command. The damage chokepoint is `apply_damage_with_context` (`crates/entities/src/components/health.rs:319`); the reaction handler receives resolved `EntityId` slices (`crates/postretro/src/health/reactions.rs:47`). Entity-targeted steps already cross the FFI as `{ id: EntityId, primitive, args }` (`sdk/lib/entities/triggers.ts:26`, Rust mirror `crates/entities/src/data_descriptors/types/reactions.rs:21`) — the sentinel widens that id position.
- **Oversized-file flags:** `trigger_bindings.rs` 1245 → Task 1 splits it. `trigger_system.rs` 1695 — the coop spec's Task 1 already relocates occupancy out; this spec's edit there is the dispatch-closure fire context only (localized; no second split). `sim/mod.rs` edits are parameter threading.
- **Fire-context timing:** enter fires dispatch after the occupant-map insert and after the arm/disarm re-check (`trigger_system.rs:270-280`), so `@occupancy` naturally includes the entrant and honors same-tick disarms.

| fired-trigger target | `BoundTarget::FiredTrigger` | `"@trigger"` in a step `id` position | `on.trigger` via `armTrigger`/`disarmTrigger` | same | n/a |
| occupancy input | `DispatchScope` trigger-event vocabulary `("@occupancy", Number)` | `{"op":"input","name":"@occupancy"}` | `on.occupancy` (`RuntimeValue`) | same | n/a |
| trigger-event observer | trigger-event descriptor + install into `TriggerBindingTable` | `triggerEvents: [{ tag, event: "enter"\|"exit", fire: [reaction-name strings], levels? }]` on `setupLevel` return / `ModManifest` | `onTriggerEvent({ tag }, event, fire, options?)` (`options?` carries `{ levels }`) — handles lower to their (auto-)id strings | same | brush `on_fire`/`on_exit` KVPs remain the map-authored referrer |

Step `id` widens from `EntityId` to `EntityId | "@activators" | "@trigger"` (numeric vs string discriminates); `PrimitiveReactionDescriptor` gains optional `target`, mutually exclusive with `tag` (both present: warn + skip; Rust mirror `PrimitiveDescriptor`, Task 2). No new binary/PRL section.

## Script syntax examples

```ts
import { world, defineReaction, onTriggerEvent, damage, disarmTrigger, type TriggerEventParams } from "postretro";

// One-shot spike trap: hurt whoever pressed, then that plate never fires again.
// Written once; works for every plate tagged "trap". No string name — the const
// is the identity (name-as-address), so onTriggerEvent holds the reference directly.
const zap = defineReaction((on: TriggerEventParams) => damage(on.activators, 25));
const oneShot = defineReaction((on: TriggerEventParams) => ({ sequence: disarmTrigger(on.trigger) }));

export function setupLevel() {
  return {
    reactions: [zap, oneShot],
    triggerEvents: [onTriggerEvent({ tag: "trap" }, "enter", [zap, oneShot])],
  };
}
```
