- Found in review: the host's chained segments are frame-quantized. A re-parked or `fire`-seeded child enrolls at the frame-end drain, so on a host running several ticks per frame each segment lands up to (ticks per frame − 1) late, while the client's host-timeline mirror counts from the exact due tick. Owner asked for the approach that sets the engine up best long term: fix the host side. The host scheduler counts ticks and records each landing's due tick, and a child's countdown subtracts the ticks already elapsed since it (floor one tick). At one tick per frame nothing changes; a chain's timing becomes a function of the tick timeline, not frame rate. A trigger, teleport or player-event tail's first segment still starts at the frame-end drain, where those sources dispatch; making dispatch tick-exact is out of scope.
- Found in review: Decisions "Late joiner. Lateness is judged against the host tick at which this client revealed instead: at the first reading, `host time − local level time`, fixed once per level. A client live before the due tick lands the beat, late by its reading latency; a real late joiner still converges. `scripting.md` §12 takes this wording at landing.
- Found in review: a reading that finds several due segments now lands them in (due tick, id) order, re-expiring each landing's own re-parks and `fire` children before the next, so a late joiner converges to the host's final state across tails.
