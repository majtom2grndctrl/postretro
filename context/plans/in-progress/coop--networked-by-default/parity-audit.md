# PostRetro host/client presentation parity audit

Audit baseline: branch **codex/coop-networked-by-default**, supplied HEAD **5fbd32328**. Workspace: /Users/dhiester/Projects/Personal/postretro. Assessment date: 2026-10-11. Read-only source assessment; no source or plan edits, Cargo commands, builds, tests, commits, or rendered playtest were performed by this reviewer. The existing brief is test-ready, not landed.

## Outcome

The reported health-bar difference is real and follows the current audience contract: the host enrolls enemies damaged by host, NPC, or absent sources; each client enrolls only enemies damaged by that client. The recent shared-damage-number amendment deliberately did not change that rule. Making bars shared needs an explicit owner amendment, followed by one shared, bounded authoritative selection path; broadcasting the present private per-client records would retain several avoidable consistency and performance problems.

The alternate-fire failure is more urgent. Routine owner snapshots rematerialize an unchanged weapon and cancel its active burst/charge cursor. This is a gameplay correctness defect, not merely a missing effect. Fix it and prove the ordinary receive/materialization path preserves an in-progress action before landing the current brief.

The broad audit also finds missing observer sound families, missing NPC aim pose inputs, and incomplete animation timing. Most descriptor world presentation, active remote weapon attachment selection, and projectile body/trail/light replication already have dedicated paths. Smaller gaps involve projectile visual age, optional pawn/held-item presentation components, and participation cleanup. These warrant focused work, not a replacement replication architecture.

Evidence labels below distinguish **reported** player observations, **source-proven** producer/consumer mismatches, **predicted** visible consequences requiring a playtest, and **intended/deferred** differences. A source audit can inventory every relevant feature family without proving pixel/audio equivalence for every authored map, asset, frame rate, network condition, and renderer.

## 1. Live weapon execution is destroyed by unchanged snapshots

The normal local-pawn record surfaces an ArmedLocalPawn at [client.rs:1496](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/client.rs:1496). The receive integration calls local-pawn materialization ([lib.rs:883](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/lib.rs:883), [remote_materialize.rs:183](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/remote_materialize.rs:183)). Even when an existing inventory slot has the same canonical weapon, [net_descriptor.rs:303](/Users/dhiester/Projects/Personal/postretro/crates/sim/src/scripting/builtins/net_descriptor.rs:303) reapplies tuning. That function calls cancel_activation unconditionally at line 366, then refresh_from_descriptor at line 417, which also cancels at [weapon.rs:504](/Users/dhiester/Projects/Personal/postretro/crates/entities/src/components/weapon.rs:504).

The owner's subsequent predicted due shots are advanced from this cursor ([client_weapon/frame.rs:135](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/client_weapon/frame.rs:135)); charge HUD values also read it ([ui_proxy.rs:459](/Users/dhiester/Projects/Personal/postretro/crates/sim/src/scripting_systems/ui_proxy.rs:459)). Thus one ordinary intervening snapshot can erase remaining burst shots or charging. Meanwhile host execution can keep spending ammunition and publishing observer fire sounds. The alternate-fire investigator independently traced the same chain. This explains the reported three debits/sounds versus one client declaration and the charge flash. The exact claim that the eventual plasma shot uses primary rather than a low-charge secondary requires the separate investigator's final trace; this audit does not infer shot identity from appearance.

The completed [alternate-fire investigation](alternate-fire-audit.md) additionally proves that input capture is reseeded from the erased cursor ([frame_loop/mod.rs:671](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/frame_loop/mod.rs:671)), so later release/cancel can lose the original token and leave host charging. It preserves uncertainty about the apparent regular bolt/audio. The current refresh preserves resource state, recovery/reload/equip timers and several other runtime fields; the demonstrated destructive change is specifically Charging/Executing. Existing tuning generation plus per-row semantic equality is sufficient to distinguish real changes without recompiling or rewriting ordinary unchanged Weapon components, and an unrelated slot's tuning change must not cancel the active weapon.

**Durable correction:** give instance creation/descriptor replacement and routine snapshot reconciliation distinct lifetimes. Unchanged effective tuning must not reset execution, recovery, reload, bloom, or input-edge state. Cache a validated tuning identity/revision per materialized weapon or make the same-canonical path explicitly idempotent; retain cancellation for a real replacement or a defined incompatible tuning change. Do not merely suppress all later materialization: reacquire, restored inventory, newly populated slots, and genuine tuning changes must still apply. This is an implementation correction, not a request to change authored burst/charge policy.

**Acceptance:** interleave normal snapshot receive, local-pawn materialization, and owner command advancement between every shot of a three-shot secondary; exactly three declarations, host-authorized shots, debits, and intended cues result. Hold/release plasma through repeated snapshots and prove action identity, scaled shot, charge progress, and cancellation on actual switch/death/hold. Exercise same archetype in distinct inventory instances and reacquire. A standalone activation-executor test would miss the defect.

## 2. Enemy bars need an audience decision and a coherent state model

Host selection is explicit at [impact_policy.rs:802](/Users/dhiester/Projects/Personal/postretro/crates/sim/src/impact_policy.rs:802): damage enrolls in the local pool only when the source is not a remote-owned pawn. This includes NPC and absent sources. The caller supplies that ownership predicate at [frame_loop/mod.rs:1143](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/frame_loop/mod.rs:1143). Client enrollment is the converse: [presentation.rs:264](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation.rs:264) requires a damage source resolvable through MovementOwners and enrolls only that recipient. NPC-on-NPC bars therefore have no client recipient.

This matches the current written carve-out: [brief Decision 13:114](/Users/dhiester/Projects/Personal/postretro/context/plans/in-progress/coop--networked-by-default/index.md:114) and [AC23:175](/Users/dhiester/Projects/Personal/postretro/context/plans/in-progress/coop--networked-by-default/index.md:175) expressly leave overlay eligibility, caps, and linger unchanged. Shared damage-number routing at [presentation.rs:417](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation.rs:417) cannot fix health-bar enrollment.

There are additional consistency problems if the owner simply changes recipients:

- Host tie-breaking uses local EntityId at impact_policy.rs:809; remote enrollment uses NetworkId at [presentation.rs:328](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation.rs:328). Equal-time damage near the cap can select different enemies.
- The host refreshes linger from each damage fact. The receiver infers a fresh damage edge from decreasing fractions at [presentation.rs:683](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation.rs:683). Equal fractions or reordered samples do not mean the same thing. Receive time and host damage time are different clocks.
- last_sent is updated before the unreliable send ([presentation.rs:288](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation.rs:288)); there is no acknowledgement or periodic repair for an unchanged tuple. A dropped enrollment may never appear; a dropped health update stays stale until another changed tuple. Current facts have no revision/damage time.
- A fact arriving before its entity baseline is retained only briefly, bounded by a 0.5-second pending TTL (presentation.rs:37–41, 151–183). Large or delayed baselines can outlive that window. The host does not know it must resend the unchanged fact.
- Per-recipient tracking currently scans the live map for each fact and for each capped admission ([presentation.rs:279](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation.rs:279), :318). Copying the same shared combat selection into P private maps needlessly multiplies state and work.
- Host local overlay time advances with presentation intake ([presentation_pool.rs:88](/Users/dhiester/Projects/Personal/postretro/crates/sim/src/sim/presentation_pool.rs:88)); skipped rendering can differ from the independent network tracker clock. A shared selection should not depend on a peer rendering a frame.

**Recommended contract for owner review:** a recently damaged enemy is a shared combat observation, regardless of attacker. The host chooses one bounded roster of at most K eligible NetworkIds using host damage tick plus NetworkId as a stable total order, records last-damage generation/time and expiry, and publishes health/shield/alive revisions. The host consumes these same facts for its local pool. Each peer decides how to render that roster using its own camera and display preferences; own-player health, hit confirmation, XP, rewards, and screen effects remain private according to their existing contracts.

Treat the roster as **bounded expiring state**, not a series of unreliable guesses. Use the existing snapshot/repair mechanisms or a small revisioned roster protocol with explicit periodic repair, expiry, and terminal ordering. Preserve a compact semantic state rather than replicating widget positions or inspecting all enemies for every recipient. Facts received before a baseline must recover after it arrives; stale records must not resurrect a dead/despawned target.

**Owner decisions required:** shared eligibility; a globally shared K versus per-viewer relevance selection; whether a newly admitted client sees the still-live roster; and the exact linger/expiry policy. Recommended defaults are shared K and current live roster on admission, with expiry based on original host time. This gives honest current combat state without replaying old numbers or sounds. If the owner instead wants bars to be disposable events with no admission state, document that visible parity under loss/late join is intentionally weaker. A per-viewer nearest/visible K is a different product behavior and requires explicit relevance inputs; it should not be smuggled into a consistency fix.

**Bounds:** selecting once costs O(D + K) per dirty combat batch with bounded ordering/admission work (or O(D log K)); state is O(K), plus the normal per-connection delivery bookkeeping. Sending to P participants is necessarily O(PK) at a full refresh, but selection and health extraction need not be repeated P times. Set a byte/event rate budget and refresh cadence; do not promise a numeric bandwidth reduction without measuring actual serialization and P/K. Keep pending records, terminal retention, and reconnect state explicitly capped and cleared.

**Acceptance:** host, client A, client B, NPC, and absent-source damage select the same roster and fractions on all participants; K+1 simultaneous hits choose identical IDs; repeated hits refresh identical expiry, including damage with no net fraction decrease. Loss, duplication, reorder, fact-before-baseline, delayed baseline, death-before-baseline, render stalls, restart, Holding, and re-promotion cannot leave permanent stale bars or resurrect retired state. Verify the chosen admission policy separately from the no-replay damage-number policy.

## 3. World sounds are only partially networked

The host frame drains mover, movement, AI, weapon, observer, and owner-predicted requests into audio at [frame_loop/mod.rs:1197](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/frame_loop/mod.rs:1197). Connected clients run movement prediction rather than the host simulation ([frame_loop/mod.rs:730](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/frame_loop/mod.rs:730)), so they do not independently produce the remote event families.

Actual local producers include weapon dry/reload/overheat mappings at [sound_events/descriptors.rs:48](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/sound_events/descriptors.rs:48), jump/land at :154, AI activity/attack sounds at :178, and mover KVP resolution at [sound_events/movers.rs:39](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/sound_events/movers.rs:39). The observer publisher selects only weapon activate and impact ([weapon_observers.rs:42](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/weapon_observers.rs:42), :92). Its AI path requires a shot identity at :65; successful contact attacks have no shot identity ([ai/apply.rs:269](/Users/dhiester/Projects/Personal/postretro/crates/ai/src/apply.rs:269)). The wire cue kind has only Activate/Impact ([wire.rs:166](/Users/dhiester/Projects/Personal/postretro/crates/net/src/wire.rs:166)).

Consequently clients miss other participants' movement and non-shot weapon lifecycle sounds, AI activity-entry/contact-attack sounds, and mover KVP sounds. Authored equivalents using forwarded playSound may work, which makes the feature depend on the authoring route rather than the audible event. This is source-proven routing absence; audibility still depends on a descriptor actually declaring the sound and on distance/mixer limits.

Own-player reload/overheat cues currently derive from correlated host slot samples rather than an immediate local event. They can be delayed/coalesced: several shells in one sample sound once, and a short lifecycle entirely between samples may not produce its full local sequence. This is documented existing behavior in audio.md, distinct from the proven observer omissions. Improving it should retain authoritative resource correction and prevent prediction/confirmation duplicates.

**Recommendation:** complete a bounded authoritative world-cue seam building on frozen weapon cues. Normalize the missing producer events once, freeze sound key and origin before destruction, attach an event identity and participation lifetime, and route to observers with explicit owner prediction exclusion. Resolve assets and spatialization locally. Host and clients should consume the same logical cue, while a listener's own pawn keeps its intended own-pawn treatment. Do not mirror arbitrary gameplay reaction execution onto clients to get sound.

The existing cap of 64 weapon cues per message, 32 contacts per cue, and 256 bytes per authored name ([wire.rs:160](/Users/dhiester/Projects/Personal/postretro/crates/net/src/wire.rs:160)) provides useful precedents, not a complete global work/rate budget. Bound per-tick cue count/bytes, pending/dedup retention, malformed input, and overflow priority. Keep a cosmetic flood from starving control/HIT traffic; decide delivery semantics deliberately rather than silently changing the existing reliable weapon channel. No history of transient sounds is needed for late join. Persistent loops, if introduced later, need start/stop state, not replayed start events.

**Acceptance:** a two-client fixture triggers every descriptor sound field and mover edge on host/client/NPC sources. Every eligible listener hears one cue; the predictor hears one own cue; activity/contact attacks without shot IDs still work; entity disappearance retains captured origin/key; admission never replays old sounds. Check sound requests and anchors in automated tests, then audible spatial behavior in the platform playtest.

Scripted presentation already has an audience-aware five-command bridge ([presentation_commands.rs:19](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/presentation_commands.rs:19)). It intentionally serializes an entity anchor as a captured point (:27), reconstructed as a contact (:99). A moving long one-shot can therefore follow its entity on the host but remain at its fired point on clients. That is a known consequence of the chosen frozen-origin contract, not a reason to broadcast private HUD. If author requirements need tracked sound anchors, extend the world-cue contract with optional stable identity and origin fallback.

## 4. NPC pose and animation state are not complete presentation state

The host's pose update uses Brain.acquired_target to compute aim pitch/yaw at [sim/mod.rs:1240](/Users/dhiester/Projects/Personal/postretro/crates/sim/src/sim/mod.rs:1240). Remote descriptor copies correctly have no Brain. The connected-client pose path supplies remote-player aim maps ([main.rs:4882](/Users/dhiester/Projects/Personal/postretro/crates/postretro/src/main.rs:4882)), and NPC snapshot materialization derives locomotion playback but not NPC target aim ([snapshot_apply.rs:90](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/snapshot_apply.rs:90)). A model using aim modifiers can therefore look level/forward on a client while the host aims up/down or toward a target. This is a code-predicted visual gap; the magnitude depends on model modifiers.

Only current_state is serialized for mesh animation ([replication.rs:291](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/replication.rs:291)). Client apply switches that state ([client.rs:2590](/Users/dhiester/Projects/Personal/postretro/crates/netcode/src/client.rs:2590)); transition entry time is stamped locally ([transitions.rs:78](/Users/dhiester/Projects/Personal/postretro/crates/entities/src/components/animation/transitions.rs:78)). Thus a late joiner entering an already-running nonlooping death/action animation starts it late/from its own entry, and an authoritative despawn can truncate it. Short state transitions between snapshots can be missed. Same-state snapshots are a no-op; there is no evidence of routine same-state animation restarting, so do not conflate this with the weapon-cursor defect.

**Recommendation:** replicate the minimal host-derived visual pose scalars needed by NPC modifiers, not the Brain/target or full skeleton. For meaningful nonlooping/action animation, add entry revision plus host start/elapsed time; use existing synchronized/interpolated time so unchanged state is idempotent and a late joiner joins at current age. Preserve locally derived locomotion where exact phase is not required. Bound payload per actor, update only changed state, and establish quantization tolerance rather than requiring identical rendered bones at different interpolation times.

**Acceptance:** an NPC aiming at elevated and lateral targets yields equivalent presentation pose inputs/sockets at matched simulation times; state transitions carry stable entry identity; delayed baseline joins a death animation at its current age; repeated unchanged records do not reset it; missing/unsupported animation assets follow the established fallback. This expands the current state-name guarantee and needs a focused actor-presentation AC, not a silent rewrite of the completed descriptor-world task.
