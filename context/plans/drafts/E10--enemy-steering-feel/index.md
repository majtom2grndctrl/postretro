# E10 — Enemy Steering Feel (acceleration, turn-rate, arrival easing)

> **Wave:** E10 enemy-AI follow-up (refinement of the shipped `M10--enemy-ai-behavior` / `M10--pathfinding-path-following` foundation). **Deferred / larger** — the meatiest of the manual-test refinements. Surfaced in play-testing as "movement reads like a chess piece moving onto squares, not an immersive FPS chase."
>
> **Composes with:** enemy facing/orientation, the velocity-driven locomotion-animation spec (`E10--enemy-locomotion-animation`), and the existing separation pass. Steering-feel is independent at the code seam — consumers read `velocity` through the unchanged `path_state` surface; no API change is required when smoothing lands. Landing after facing/locomotion only improves visual polish. Note: the one-tick lag (`run_ai_tick` precedes `agent_steering::tick`, both in `sim::simulate_tick` — `sim/mod.rs:67`, `:75`) already applies to facing, so the smoothed velocity reaches facing/animation one tick later — acknowledged, not a same-tick guarantee.

## Goal

Give navigation agents believable locomotion dynamics — accelerate up to speed, ease into a stop, and turn at a bounded rate — instead of teleport-style instantaneous velocity that snaps to full `move_speed` toward each waypoint and snaps direction at every corner. The path itself is already string-pulled by the funnel; this is about how the agent *moves along* it.

## Background (the cause)

The steering tick sets horizontal velocity fresh and instantaneously every tick:

- `agent_steering::goal_velocity` (`crates/postretro/src/agent_steering.rs:461-493`) returns `(to_target / dist) * agent.move_speed` toward the current waypoint — **full speed in one tick**, and exactly `0` the moment there is no path or the agent has arrived. No acceleration, no deceleration, no arrival slowdown.
- `tick` (`agent_steering.rs:226`) adds `separation(...)`, clamps the combined horizontal vector to `move_speed`, then calls `collide_and_slide(...)` with that horizontal `desired` plus the vertical (gravity) component, and stores `agent.velocity = result.velocity`.
- Because the target direction jumps discretely as `waypoint_cursor` advances (`goal_velocity` lines 469-478), and speed is always full or zero, the agent visually snaps heading at waypoints and starts/stops abruptly — the "chess piece" feel. `AgentComponent::velocity` already persists across ticks, but the steering tick overwrites it with the post-collision `result.velocity`, so it cannot double as the pre-collision smoothing state — this spec adds a dedicated `steer_velocity` field for that (see In scope).

## Scope

### In scope

- **Acceleration / deceleration.** Acceleration governs the *magnitude* of the smoothed path-following velocity only: step `steer_velocity`'s speed toward the goal speed by at most `accel * dt` per tick (an acceleration limit, units/s²), instead of assigning the target speed directly. Direction is set by the turn-rate-limited heading (below), not by this step. Ramp up from rest and ramp down when the goal speed drops. Separation is NOT part of this accel-limited target — it is added on top afterward (see Composition). **IMPORTANT — integration-state source:** do NOT use `AgentComponent::velocity` as the integration state. In `tick` today, `agent.velocity` is overwritten by the post-collision `result.velocity` (agent_steering.rs:383), which diverges from the pre-collision desired whenever the agent grazes a wall — breaking AC1's monotonic-ramp guarantee. The integration state is the smoothed PRE-collision path-following velocity (heading and speed; separation excluded), carried across ticks in its own field (a new `AgentComponent` field, `steer_velocity: Vec3`); the persisted heading is derived from `steer_velocity.xz`. AC1's monotonic ramp is asserted over this pre-collision smoothed velocity (or on a collision-free fixture), so wall-grazing collision clamping does not falsify it.
- **Arrival easing.** Scale the goal speed down within an arrival band of the *final* waypoint so the agent eases to a stop rather than cutting from full speed to zero.
- **Turn-rate limiting.** Heading is first-class integrated state, derived from `steer_velocity.xz` and persisted across ticks. Each tick, rotate the PERSISTED heading toward the target direction (toward the lookahead/goal point) by at most `max_turn_rate * dt` (rad/s), then set `steer_velocity`'s direction from that rotated heading — so the agent curves toward a new waypoint direction over a few ticks instead of snapping. (At rest `steer_velocity.xz` is below the XZ-length floor and no heading exists; bootstrap it to the target direction that first tick, then rotate on subsequent ticks.)
- **Lookahead / corner anticipation.** Aim the turn-rate clamp at a short lookahead point a named `LOOKAHEAD_DISTANCE` along the remaining path corridor, not only the current waypoint center, so heading starts to rotate before a visible corner. This does not reshape the path. The target stays on the existing funnel path/corridor and falls back to the current waypoint when no lookahead segment exists. `LOOKAHEAD_DISTANCE` is a named tuning constant with a stated unit basis (a multiple of the capsule radius, mirroring `ARRIVAL_RADIUS_FACTOR`) and a non-degeneracy constraint: long enough to lead the corner (> `ARRIVAL_RADIUS_FACTOR * radius`, the waypoint-reached radius — distinct from the arrival-slowdown radius — so it reaches past the waypoint the agent is dismissing) yet short enough to stay in-corridor (below a typical corridor segment length, so the lookahead point does not skip past the next corner). **Disable convention:** `LOOKAHEAD_DISTANCE == 0` falls back to the current waypoint (no lookahead) — the toggle AC4 exercises.
- **Composition, preserved invariants.** Keep the separation push, the `move_speed` clamp, gravity/vertical handling, the collide-and-slide harness, determinism (fixed tick), and the replan/path-preservation behavior from `M10--pathfinding-path-following` intact. `steer_velocity` is XZ-only (`y = 0`); the smoothed velocity feeds facing and locomotion-animation selection. Normative order of operations in `tick`: (1) compute the target direction (toward the lookahead point when present, else the current waypoint) and the goal SPEED (with arrival easing); (2) rotate the persisted heading (from `steer_velocity.xz`) toward that target direction by at most `max_turn_rate * dt`, and set `steer_velocity`'s direction from the rotated heading; (3) step `steer_velocity`'s speed toward the goal speed by at most `accel * dt` (magnitude only); (4) add the separation push ON TOP of the smoothed `steer_velocity` (so separation un-stacking stays prompt and is NOT throttled by the accel or turn-rate clamps); (5) clamp the combined XZ vector to `move_speed`; (6) collide-and-slide with `desired = steer_velocity.xz + separation` (clamped) as the horizontal component plus the unchanged vertical (gravity) component. Note: `steer_velocity` carries only the smoothed path-following velocity — separation is added transiently to form the collide-and-slide input and is never folded back into `steer_velocity`, so the persisted heading stays free of separation jitter.
- **Tuning surface.** Acceleration, max turn rate, arrival-slowdown radius, and `LOOKAHEAD_DISTANCE` as named steering parameters (module constants in the steering precedent of `ARRIVAL_RADIUS_FACTOR` / `SEPARATION_STRENGTH`, derived from the capsule / `move_speed` where natural). Non-degeneracy constraints, so AC1/AC2/AC3 stay testable: (a) the speed ramp spans >= 2 ticks; (b) the arrival band must sit OUTSIDE the existing hard-stop, and its effective deceleration span must last >= 2 ticks. `goal_velocity` today sets `arrived = true` and returns `Vec3::ZERO` once the final waypoint is within `arrival_radius = ARRIVAL_RADIUS_FACTOR * radius` (= 1.5 * radius, agent_steering.rs:47, :482). If `slowdown_radius <= arrival_radius`, the entire easing region sits inside the hard-stop, the easing branch is dead code, and AC2 can never observe deceleration. So require `slowdown_radius >= 4 * arrival_radius` (i.e. `>= 4 * ARRIVAL_RADIUS_FACTOR * radius`) — this keeps the easing band entirely outside the hard-stop AND bounds the residual speed at the hard-stop boundary, `(arrival_radius / slowdown_radius) * move_speed`, to an ABSOLUTE `<= 0.25 * move_speed`. Also size the band so its EFFECTIVE deceleration span lasts >= 2 ticks: `(slowdown_radius - arrival_radius) >= 2 * move_speed * dt`. **Arrival decision (zeroed at `arrived`):** when `arrived` fires the goal speed is ZEROED instantaneously (the `<= 0.25 * move_speed` residual is dropped in one tick, bypassing the accel ramp-down) — the deliberate design is smooth deceleration through the band down to a small tail, then an instantaneous hard-stop to zero at the destination, so there is no destination overshoot. Do NOT remove the hard-stop: the `arrived` semantics are relied on elsewhere; the radius ordering plus the zero-at-`arrived` rule is the correct fix. (c) a reference corner turn spans >= 2 ticks at `max_turn_rate` on the test fixture (`corner_angle / (max_turn_rate * dt) >= 2`), so AC3's heading actually rotates over the corner rather than snapping in one tick.

### Out of scope

- Player movement (this is enemy/agent locomotion only).
- Path **post-smoothing** beyond the funnel string-pull (spline/corner-cut of the waypoint list). Keep it out of immediate scope unless Task 3 measurement shows turn-rate plus lookahead still leaves visible corner snap.
- Walk/run animation blending or speed-scaled playback rate.
- Promoting steering tuning to per-archetype descriptor fields (`components.ai` / a new steering block) — kept as engine constants here; descriptor promotion is a follow-up if modders need per-enemy feel.
- Dynamic obstacle avoidance beyond the existing inter-agent separation; flocking; pursuit prediction / lead-targeting.

## Acceptance criteria

- [ ] **(Task 1)** An agent starting at rest with a path does **not** reach `move_speed` in a single tick: its horizontal speed ramps up over multiple ticks and converges to `move_speed` (runnable unit test on the steering tick asserting speed at tick 1 < `move_speed` and a monotonic ramp toward it). The fixture must place the agent OUTSIDE the arrival band on a path segment long enough to reach `move_speed` before arrival easing kicks in — otherwise the ramp never completes and convergence is untestable. Sub-assertion (write-back discipline): on a wall-grazing fixture, `steer_velocity.xz` speed stays monotonic across the ramp while the post-collision `agent.velocity.xz` diverges from it — proving the integration state is the PRE-collision `steer_velocity`, never `result.velocity` (agent_steering.rs:383).
- [ ] **(Task 1)** An agent approaching its final waypoint **decelerates** within the arrival band — horizontal speed decreases as it nears the destination instead of holding full speed until a hard zero; the deceleration is observed over multiple ticks (the effective deceleration band `slowdown_radius - arrival_radius` spans >= 2 ticks of travel at `move_speed`, per non-degeneracy constraint (b)). The horizontal speed on the last tick BEFORE the `arrived` hard-stop fires is a small ABSOLUTE fraction of `move_speed` — `<= 0.25 * move_speed`, guaranteed by `slowdown_radius >= 4 * arrival_radius` — so the hard-stop zeroes only a low-speed tail rather than cutting from full speed to zero (runnable unit test asserting the speed profile over the final approach across multiple ticks AND that the pre-stop speed is `<= 0.25 * move_speed`).
- [ ] **(Task 2)** Every tick after the agent has a heading (the first-tick bootstrap out of dead rest — where a zero-magnitude `steer_velocity` has no heading to rotate from — is exempt), when the goal direction changes sharply (a waypoint turn or a re-plan), the agent's actual XZ **motion heading — the direction of `steer_velocity` — rotates by at most `max_turn_rate * dt` per tick** (not merely the goal-toward-waypoint direction): because heading is first-class integrated state, the persisted heading is what the clamp rotates and what sets `steer_velocity`'s direction, so the emergent motion heading is bounded and direction is not snapped (runnable unit test asserting the bounded per-tick change of `steer_velocity`'s heading across a corner; the corner fixture must satisfy `corner_angle >= 2 * max_turn_rate * dt` — Scope constraint (c) — so the turn spans >= 2 ticks and the clamp provably engages rather than the bound holding trivially on a shallow corner).
- [ ] **(Task 2)** On a two-segment corner fixture, lookahead targets the path ahead of the current waypoint while staying on the existing corridor/funnel path, so heading begins rotating before the waypoint handoff; with lookahead disabled (`LOOKAHEAD_DISTANCE == 0`) or unavailable (no lookahead segment remains), the target-direction helper falls back to the current waypoint and heading is turn-rate-limited toward that (runnable unit test on the target-direction helper covering both the lookahead and the `LOOKAHEAD_DISTANCE == 0` fallback paths).
- [ ] **(Task 2, full composition)** The combined path-following+separation velocity still never exceeds `move_speed`; agents still separate (do not stack into one body) — separation is added ON TOP of the smoothed `steer_velocity` (after the accel and turn-rate clamps) so un-stacking remains prompt and is not throttled by either clamp, then the combined XZ vector is clamped to `move_speed`. The clamp-engagement test fixture must build a PRE-CLAMP combined vector that provably exceeds `move_speed` (a full-speed `steer_velocity` heading plus an ORTHOGONAL separation push), so the `move_speed` clamp actually engages rather than passing vacuously against a sub-`move_speed` combined vector; and a promptness test must show two overlapping agents gain measurable XZ separation within N ticks where N is far below the accel-ramp time (constraint (a)), distinguishing "separation added on top" from separation wrongly routed through the accel limit. gravity/grounding still resolves through `collide_and_slide`; zero-length XZ direction is guarded by the existing XZ-length floor (cite the `yaw_rotation_toward` at `crates/postretro/src/scripting/systems/ai.rs:106` / `MIN_XZ_LEN_SQ` at `:110` precedent); the accel and turn-rate integration multiply by `dt` (`accel*dt`, `turn_rate*dt`), so a zero `dt` yields a zero step — no guard needed; arrival-band speed scaling (`dist / slowdown_radius`) is dt-free by construction and is unaffected; the goal-velocity and `move_speed`-clamp path do not divide by `dt` and need no dt guard (runnable unit tests / preserved existing steering tests stay green).
- [ ] **(Task 2, full composition)** The steering tick remains deterministic under the fixed tick (identical inputs → identical motion); the smoothing integration reads only the agent's own persisted (pre-collision) `steer_velocity` and the frozen position snapshot — never a neighbor's mid-tick-updated velocity — preserving the order-independence the separation pass already guarantees; the replan budget and path-preservation tests from `M10--pathfinding-path-following` (located in `crates/postretro/src/agent_steering/tests.rs`) remain green.

## Tasks

### Task 1: Acceleration / deceleration + arrival easing
Add `steer_velocity: Vec3` to `AgentComponent` as the pre-collision smoothed path-following integration state (heading derivable from `steer_velocity.xz`; separation excluded). Step its speed MAGNITUDE toward the goal speed under an acceleration limit (`accel * dt`), leaving direction to Task 2's turn-rate clamp. **Task 1/Task 2 seam:** refactor `goal_velocity` to return the eased goal SPEED scalar (magnitude only), NOT a direction×speed vector — the target direction is Task 2's concern. Add arrival-band speed scaling to that goal speed: within `slowdown_radius` of the final waypoint scale the goal speed linearly by `dist / slowdown_radius` (clamped to `<= 1`), where the named constant `slowdown_radius > arrival_radius = ARRIVAL_RADIUS_FACTOR * radius` (constraint (b): `slowdown_radius >= 4 * arrival_radius`). When `goal_velocity` sets `arrived`, ZERO the goal speed for that tick (do not accel-ramp it down) so the hard-stop stays instantaneous and there is no overshoot. **Write-back discipline:** write the PRE-collision integrated value back to `agent.steer_velocity`; never assign `result.velocity` to it (agent_steering.rs:383 — separation is added transiently and is never folded back into `steer_velocity`). Touches `AgentComponent`, `goal_velocity`, and the velocity-assembly in `tick`. **Construction plumbing:** initialize `steer_velocity` to `Vec3::ZERO` in `AgentComponent::new` (crates/entities/src/components/agent.rs:104) — the sole field-listing constructor that `from_nav_params` and `attach_agent` delegate to. The existing construction test `new_seeds_geometry_and_starts_at_rest` (agent.rs:184) must add a `steer_velocity == Vec3::ZERO` assertion for the new field.

### Task 2: Turn-rate limiting + lookahead target
Bound the per-tick rotation of the PERSISTED heading (derived from `steer_velocity.xz`) toward the target direction, and set `steer_velocity`'s direction from the rotated heading — so the clamp acts on the integrated heading, not a per-tick-recomputed goal-toward-waypoint heading (which would make the clamp inert). Derive the target from a short lookahead point (`LOOKAHEAD_DISTANCE`) along the remaining path corridor when available; otherwise use the current waypoint. Construct the lookahead point by walking `LOOKAHEAD_DISTANCE` of arc length forward along the remaining corridor waypoints; size `LOOKAHEAD_DISTANCE` as a multiple of the capsule radius in the band `> ARRIVAL_RADIUS_FACTOR * radius` (past the waypoint being dismissed) yet below a typical corridor segment length (so it does not skip the next corner); `LOOKAHEAD_DISTANCE == 0` disables lookahead and falls back to the current waypoint (AC4's toggle). Bootstrap the heading to the target direction when `steer_velocity.xz` is below the XZ-length floor (at rest). Touches the same velocity-assembly path in `tick`; composes with Task 1's magnitude step into one horizontal `steer_velocity` before separation and `collide_and_slide`.

### Task 3 (spike, no ACs): Corner-feel comparison
Entry gate: manual review against `content/dev/maps/campaign-test` or an equivalent hand-built corner fixture. Compare (1) turn-rate-only targeting the current waypoint and (2) turn-rate plus lookahead targeting along the path corridor. Only evaluate spline/corner-cut path post-smoothing if both modes still leave visible corner snap. Deliverable: a written go/no-go recommendation, so the phase has a defined output even when it ships nothing.

## Rough sketch

- Add `steer_velocity: Vec3` to `AgentComponent` as the pre-collision smoothed path-following state (NOT `agent.velocity`, which is overwritten by post-collision `result.velocity` and would break the monotonic ramp). In `tick`: compute the target direction (lookahead point, else current waypoint) and the goal speed (arrival-eased); rotate the persisted heading from `steer_velocity.xz` toward that direction by at most `max_turn_rate * dt` and set `steer_velocity`'s direction from it; step `steer_velocity`'s speed toward the goal speed by at most `accel * dt`; then add separation on top, clamp the combined XZ vector to `move_speed`, and pass `steer_velocity.xz + separation` (clamped) plus the unchanged vertical component to `collide_and_slide`. Vertical velocity handling is unchanged.
- Arrival easing: in `goal_velocity`, when on the final waypoint within an arrival-slowdown radius, scale the returned goal SPEED scalar by `dist / slowdown_radius` (clamped `<= 1`) so it tapers to a small tail at the destination; at `arrived` the goal speed is zeroed outright (not accel-ramped) to keep the instantaneous hard-stop.
- Turn-rate: derive the persisted heading from `steer_velocity.xz` (the integrated state, not the per-tick goal-toward-waypoint direction) and the target heading from a short lookahead point along the remaining path corridor; rotate the persisted heading toward the target by at most `max_turn_rate * dt`; guard the zero-length case with the XZ-length floor — at rest (`steer_velocity.xz` below the floor) bootstrap the heading to the target direction rather than rotating, so no `NaN`.
- New constants mirror the existing steering-constant style (`ARRIVAL_RADIUS_FACTOR`, `SEPARATION_STRENGTH`): an acceleration as a multiple of `move_speed` per second, a max turn rate in rad/s, an arrival-slowdown radius `slowdown_radius >= 4 * arrival_radius` (`= 4 * ARRIVAL_RADIUS_FACTOR * radius`; exceeds the waypoint-reached `arrival_radius` so the easing is not dead code behind the hard-stop, and bounds the hard-stop residual to `<= 0.25 * move_speed`) whose effective span also satisfies `(slowdown_radius - arrival_radius) >= 2 * move_speed * dt`, and a `LOOKAHEAD_DISTANCE` as a multiple of the capsule radius (> `ARRIVAL_RADIUS_FACTOR * radius`, the waypoint-reached radius, below a corridor segment length). `LOOKAHEAD_DISTANCE == 0` disables lookahead (AC4's toggle).
- **Split-before-extend (RESOLVED):** `agent_steering.rs` is 547 lines (production code; tests live in `agent_steering/tests.rs`), well under the ~800 threshold — no pre-split needed. Task 1 and Task 2 land in place.
