# Impact Policy Substrate + Per-Entity State Keystone (E16)

## Goal

The engine owns IMPACT — the single point where damage is applied. Build the substrate that turns impact into a policy surface: a dispatch source at the damage chokepoint, the per-entity modder state keystone (IR-bindable), the effect set, the `defineImpactEvent` authoring surface, and the engine-side evaluator. The substrate is death-agnostic — it holds no opinion about what a hit *means*. A policy domain supplies the meaning: **death is the first** (`E16--impact-death-lifecycle`, a thin policy spec on top of this one); the coming enemy-behavior-state system is the second, on the same substrate. The keystone's `EntityScope` binding depends on the impact dispatch (per-fire target seeding), so the keystone cannot stand below the dispatch — the foundation is the whole impact-policy machine *including* the keystone, built once, complete, so `EntityScope` never needs retrofitting into the evaluator later. This realizes the roadmap's Combat Feedback & Economy `onImpact` / `CombatScope` substrate.

## Scope

### In scope
- **Impact dispatch source.** A new §12 dispatch source fired at the damage chokepoint, publishing an ephemeral dispatch scope: number/bool IR facts (damage amount, pre-impact health, **unfloored** post-impact health, max health) plus two **command-target tokens** (target = damaged entity, source = damager). The one net-new engine event.
- **Per-entity modder state (the keystone).** A per-instance, modder-owned, name-keyed number state on an entity, exposed to the IR as a new binding scope: readable as an IR leaf, writable as an IR output. Host-authoritative.
- **New effects.** `despawn({afterMs?})`, `setHealth(value, {afterMs?})` (absolute; the death spec layers kill-detection re-arm onto this chokepoint), `setState(name, value)`, `playAnim(clip)`, `slot.add(delta)` — plus the deferred-effect component that owns their deferral (ordered queue, inert flag) and the end-of-frame removal pass despawn feeds.
- **Authoring surface.** `defineImpactEvent(id, filter, policy) → ImpactEvent` blessed handle — `id` is an author-assigned namespaced string, the stable/portable identity used for override linkage; `handle.override(filter, policy)` cross-scope refinement; the `NumberRef`/`BoolRef` IR skin over the shipped `runtime.*` builder with `.and/.or/.not/.select` sugar. `Effect` is the **closed** impact-effect set (`despawn`/`setHealth`/`setState`/`playAnim`/`slot.add`), not the general reaction surface.
- **Engine-side policy evaluator.** The runtime that binds each policy's gated-group IR to an impact fire, evaluates it, resolves base+override, and dispatches effects (Task 5).

### Out of scope
- **Death semantics.** 0 HP made inert, the kill-report rework, resurrect re-arm, and the reference death policies are the death spec (`E16--impact-death-lifecycle`), this substrate's first consumer. This spec changes no engine death behavior: the death sweep and its auto-removal are untouched here.
- **Crediting the source (rewards).** `grant(...)` — awarding xp / score / ammo / health to the damager — defers to Epic 16's **`resource-grant chokepoint + dev-mod reference`** item (Combat Feedback & Economy). Per-player resources also need a replication story (below). The impact scope still publishes `source` as a command-target token so the seam is charted; no v1 effect targets it.
- **Per-entity state replication.** Per-entity modder state is host-authoritative only. State that must reach clients uses a shared global store, as today. No per-entity/per-owner replication channel.
- **Opening the AI FSM state set.** The engine FSM keeps its closed locomotion states (idle/alert/attack/death). No author-declared AI states, no replacement of the transition core. Modder overlay states (stagger/downed) live in per-entity state, invisible to the FSM.
- **General deferred-effect scheduler.** Only the per-effect `afterMs` countdowns for `despawn`/`setHealth`. No generic timer/queue for arbitrary effects.
- **Spatial `zone` filtering.** Overrides narrow by an additional tag, not by a spatial region. No zone-membership subsystem.
- **Healing via the damage path** and non-impact health observation (regen, low-health UI) — unchanged, separate surfaces.

## Decisions

Pinned semantics (no TBD). The death-specific decisions — FSM coexistence, resurrect & kill re-arm, kill-report-off-despawn — live in `E16--impact-death-lifecycle`.

- **Entity references are command-target tokens, not IR leaves.** The IR carries only number/bool. `target`/`source` cross as opaque command-target tokens in the dispatch scope — mirroring trigger events' `on.activators`/`on.trigger` — consumed by EntityScope binding and by every effect writer, never as `resolve_input` number leaves.
- **Gated-group evaluation: INDEPENDENT.** Within one policy, every `{ when, do }` group whose `when` holds fires; effects within a group all fire. The author guarantees exclusivity for mutually-exclusive states (the death spec's lifecycle fixture uses `.and(state.eq(...))`). Forced by the override fixture: a base group and an added group sharing the same `when` must BOTH fire — first-match would drop the second.
- **Base + override: whole-policy REPLACE, LAST-REGISTERED (load order) wins.** For one `ImpactEvent` identity, an entity runs exactly one variant — the last-registered override whose filter matches. `defineImpactEvent`/`override` builders run once at load (not per fire), so precedence is **registration/load order, not runtime execution order**: within a manifest, `events[]` array order; across scopes, level-scope after mod-scope (§2 composition). "Most-recently-executed" everywhere in this spec means exactly this load-order last-writer. Filters narrow by an additional tag (an entity may carry several tags); authors scope overrides so it is clear where a modified rule applies and where it does not. Reuse is authoring-level: the override calls the base policy function and spreads its result. Base and override never both fire for the same entity.
- **Identity: explicit author-assigned id.** `defineImpactEvent(id, …)` takes an **author-assigned namespaced string id** (e.g. `"salvage:crate-break"`, like a store's dotted name) as its identity — NOT a content-derived hash. Base↔override linkage must survive the VM drop (JS object identity does not cross the FFI) *and* the runtime boundary (a Luau level may override a QuickJS mod's base), and it must be **stable under policy edits**. A content-derived FNV id fails all three: 32-bit collides; JS and Luau derive *different* ids from the same content, so cross-runtime override silently cannot link; and editing a base policy *changes* its derived id, silently orphaning every override that pointed at it — fatal for a refinement mechanism. An explicit string is portable across runtimes, stable across edits, collision-controlled by author namespacing (which closes the cross-mod-collision hazard by construction), and greppable/nameable in errors (`override targets unknown event "salvage:crate-break"`). This mirrors the store precedent (`defineStore("salvage", …)`), which impact events resemble far more than the anonymous `defineReaction` — both are cross-scope, cross-runtime, referenced-by-name surfaces. `override` links to its base by that id (the handle carries it within a runtime; the id string is the durable cross-runtime link); the engine merges base + overrides by string-equal id, no engine-side hashing. Because the id is author-given, the filter plays no part in identity — distinct events simply get distinct ids.
- **Producer contexts (both charted, app-drain stubbed).** Damage reaches the chokepoint from two producers: in-tick weapon fire and the app-drain `applyDamage` reaction. v1 implements impact dispatch + in-tick consequential evaluation for the **in-tick producer only**. The app-drain producer is charted at the same seam but its policy evaluation is a deliberate **no-op stub** in v1 — no policies run for app-drain-sourced impacts (DoT/environmental). Charting the seam now (rather than the whole mechanism) avoids an API footgun when that damage lands and its deferred next-tick evaluation is built. This is not "evaluated one tick late"; it is "not evaluated in v1."
- **Effect arms.** Consequential effects (health/state/store writes, despawn) evaluate in-tick, host-authoritative. Presentation effects (`playAnim`) are **also in-tick** — a synchronous `switch_animation_state` write, not an app-drain command. Cross-arm order (consequential before presentation) is fixed within the fire by Task 5's per-arm dispatch loop, not author-controlled. Each impact fire fully applies its effects to live state before the next impact on that entity is dispatched (per-fire, not per-tick-batch), so an emergent counter cannot double-count two same-tick hits.
- **Effect surface: closed impact-effect set.** A policy's `Effect` is a **closed union** of exactly the five impact effects — `despawn`, `setHealth`, `setState`, `playAnim`, `slot.add` — NOT the general `PrimitiveReactionDescriptor | Reaction<{}>` reaction surface (a WALL spike convenience). The evaluator implements exactly these; a closed type keeps the surface honest (no policy that type-checks and then no-ops) and matches the engine's deliberate closed-vocabulary pattern (`ComponentKind`, the 15-op `IrNode`, the `LogicalState` FSM). It loses no authoring power: `setState` + `slot.add` carry *all* author-defined semantics (any per-entity field or modder store — score, xp, quest flags, stagger), so the meaning still lives in the policy, not in an open effect palette. Closed-but-**extensible**: a later spec that needs a new effect (the economy epic's `grant`) *adds* an arm to the set, rather than leaving a hollow wide type standing.
- **Despawn ordering.** A `despawn` (even with no `afterMs`) only MARKS the entity; removal runs at end-of-frame (Task 3). Because `playAnim` is an in-tick write and despawn defers removal, a same-group `playAnim("shatter"`, or the death spec's `"death"`/`"gib")` still targets a **live** entity — the switch applies without error. With a bare `despawn()` removal runs this same frame before render, so the switch lands but zero frames render the clip; visible playback across render frames needs `despawn({ afterMs })`. `afterMs` extends the removal delay further.
- **`healthAfter` is unfloored.** The impact fact carries the true pre-`.max(0.0)` value (may be negative); the stored health component still floors at 0 for the HUD. This makes a death policy's kill (`healthAfter.le(0)`) and gib (`healthAfter.le(-40)`) both expressible.
- **Level gates re-fire on a persisting entity; transitions use the `healthBefore` EDGE.** The impact fires on every hit and a gated `when` is a LEVEL predicate: `healthAfter.le(0)` stays true while an entity persists at 0 HP (through a despawn window or a resurrect delay), so a bare-level death gate re-runs on every subsequent hit — restarting anims and **double-counting** `deaths.add`. Express a once-on-transition rule as the EDGE `healthBefore.gt(0).and(healthAfter.le(0))` (both facts are published for exactly this). A level gate is still correct where firing from *any* state is intended — e.g. gib a downed corpse, `healthAfter.le(-40)`. The engine cannot know which a gate wants and there is **no blessed `died()`** (deliberately — a level predicate like `healthAfter.le(0)` can't universally mean *died*, since a Quake-style zombie persists at 0 HP by design), so the author picks; the death spec's fixtures demonstrate both (grunt/imp/zombie-down use the edge, zombie-gib uses the level). This is the API's central authoring rule.
- **Manifest composition.** `events` composes with the §2 rule: mod-scope `events` are global; level-scope `events` add on `setupLevel`; the standard `levels` selector applies. Composition is additive first, then identity-merge resolves base+overrides.
- **Single dispatch consumer; cross-event order.** The impact dispatch source has **exactly one** consumer — the Task 5 evaluator. The source fires for every producer, but a fired-but-unread scope (the app-drain stub) is provably inert: no second subscriber exists to run a policy on it, which is what keeps the "no policy on app-drain" AC true even as the seam is charted. Two **distinct** `defineImpactEvent`s both matching one entity each fire their own policy independently, in registration (load) order; cross-event conflict resolution beyond store LWW is **out of scope for v1**.

## Acceptance criteria

- [ ] A damaging (in-tick) hit on an entity matching a `defineImpactEvent` filter runs its policy; IR facts evaluate against the real pre/post health of that hit.
- [ ] Per-entity state: a policy calling `setState("hits", ...)` causes a subsequent impact on the *same instance* to read the written value and branch; a second instance reads its own independent `0` (unset per-entity state reads total-zero).
- [ ] A `despawn()` removes the entity at end-of-frame — a same-group `playAnim` still targets a live entity (the switch applies without error); `despawn({ afterMs: N })` removes it ~N ms later (only `afterMs` keeps the entity alive across render frames, so the clip actually renders).
- [ ] Breakable fixture: each impact on a crate accrues `state("hits")` on that instance; the hit that reaches the threshold fires the shatter group **exactly once** (the gate reads the pre-effect snapshot, so the same-impact `setState` cannot shift it), switches to `"shatter"` on the still-live entity, bumps the store counter, and despawns. No health fact and no death machinery is involved — the substrate stands alone.
- [ ] Override: an override narrowing by an extra tag changes the policy for that subset only; the base still runs for entities the override doesn't match; no entity runs both. When two overrides match, the last-registered (load order) wins.
- [ ] Identity is the author-assigned id: editing a base policy's body does not change its identity or break its overrides; an override in one scope links to its base by the same string id (including across the QuickJS/Luau boundary).
- [ ] `Effect` is the closed five-arm union — a policy cannot reference a general reaction the evaluator doesn't implement (type/review gate: the SDK `Effect` admits only `despawn`/`setHealth`/`setState`/`playAnim`/`slot.add`).
- [ ] Independent gated groups: a single impact fires all matching groups (e.g. a store-write group and a despawn group together).
- [ ] Boolean composition: a policy using `.and(...)` type-checks and evaluates as the shipped `select` composition. (The evaluate-as-`select` half is runnable; "no `and`/`or` opcode introduced" is a review/grep gate — a negative-existence check against `IrNode`, not a runnable test.)
- [ ] App-drain-sourced impacts (`applyDamage`, DoT, environmental) run **no** policy in v1 — the dispatch/evaluation seam is charted but stubbed; only in-tick (weapon-fire) impacts run policies. (Depends on Task 1's producer discriminator; the "no policy runs" assertion is a review gate plus a store-counter check that the app-drain path fired nothing.)
- [ ] `events` compose additively across scopes: a mod-scope entry applies globally, a level-scope entry adds on `setupLevel` (standard `levels` selector), and base+override identity-merge resolves after composition.
- [ ] The spike files (`breakable.spike.ts`, `proposed.d.ts`) type-check against the *shipped* SDK after the authoring surface lands — as do the death spec's fixtures, which import this folder's `proposed.d.ts` via `postretro/proposed`.

## Tasks

### Task 1: Impact dispatch source
Fire a new dispatch source at the damage chokepoint (`apply_damage_with_context`), after the decrement, publishing an ephemeral dispatch scope with **four number IR facts** (all numbers; there is no bool fact) bound by these exact wire spellings — `@impact.amount` (damage), `@impact.healthBefore` (pre-impact health), `@impact.healthAfter` (unfloored post-impact health — the `current - amount` value *before* the `.max(0.0)` floor; split the existing single statement so the unfloored value is captured, then floored), `@impact.maxHealth` (max health) — plus **two command-target tokens** — `@impact.target` (damaged) and `@impact.source` (damager, from the `DamageContext.attacker` param in scope at the chokepoint — there is no `HealthComponent.last_attacker` field) — carried in the scope like trigger events' `on.activators`/`on.trigger`, NOT as number leaves (the IR has no entity type). **These six wire spellings are the cross-task bind contract: Tasks 4 and 5 must reproduce them verbatim, or `resolve_input` silently fails on an unknown name.** Register the number facts in the reaction dispatch model (scripting §11-12) so a policy binds them by name via `resolve_input`. The fire site already has `payload` (amount), the `context: DamageContext` (`attacker`), and the health component (pre/post/max) in scope — no new plumbing beyond reading them and splitting the floor statement (`updated.current = (updated.current - payload.amount).max(0.0)` → capture the unfloored `current - amount`, then floor).

`apply_damage_with_context` is the single funnel for all producers — weapon fire (`crates/postretro/src/sim/mod.rs:803`, in-tick), enemy melee (`crates/postretro/src/scripting/systems/ai.rs:835`, in-tick), and the `applyDamage` reaction (`crates/postretro/src/health/reactions.rs:74`, app-drain) — and today carries no producer arm. Add one pinned carrier: a **`producer` field on `DamageContext`** (`InTick` | `AppDrain`), set by each call site (both weapon-fire and enemy-melee sites → `InTick`; the `applyDamage` reaction → `AppDrain`), and carry it onto the fired impact-dispatch event as a named engine-internal field. It is NOT an IR fact and NOT `resolve_input`-bound — it is an evaluator gate, invisible to policies, distinct from the six `@impact.*` wire names (Boundary inventory lists it as an engine-internal carrier). The chokepoint captures the facts and fires the dispatch source for every producer, but Task 5 reads `producer` and evaluates policies **only for `InTick`** — the app-drain seam is charted while its evaluation is a no-op stub (Decisions: Producer contexts; AC "App-drain-sourced impacts run no policy"). Do not add policy evaluation here (Task 5) — this task only makes impact an observable, bindable event and carries the `producer` discriminator.

### Task 2: Per-entity state component + EntityScope (keystone)
Add a per-instance, name-keyed number state carried on entities, modeled on the store `SlotValue` vocabulary (a number value) but keyed per `(entity, name)` rather than by global dotted name. Storage: a new closed `ComponentKind` variant holding a small name→number map (the `HealthComponent.zone_multipliers` string-keyed-number-map is the structural precedent), created **empty at spawn** — **no declaration surface in v1**. A field springs into existence on first `setState`; an unset `state(name)` reads the IR total-zero (`0`), exactly as `StoreScope::read` does (`scopes.rs:256-257`). This keeps per-entity state **ECS-emergent**: any scope can graft a new state field onto an entity its author never anticipated — the substrate for mutable roles/allegiance (friendly↔hostile, quest-giver↔enemy), the deliberate opposite of a pre-declared closed schema. (Deferred: declaring *nonzero* spawn defaults; when added it must be an OPTIONAL, non-closing declaration — never a field whitelist — so the emergent-write path is never foreclosed. See Open questions.) Expose it to the IR as a new `BindingScope` (`EntityScope`): `state(name)` resolves to an IR input leaf, `setState(name, value)` to an IR output. Pin the reserved wire spelling `@state.<name>` for that leaf (Boundary inventory) so it routes to `EntityScope`, never to `StoreScope` — a bare non-`@` name in a dispatch scope delegates to `StoreScope` (`scopes.rs`) and would collide with a global store slot of the same name. Build `EntityScope` as a **layer over the impact dispatch scope** (which already layers over `StoreScope`, `scopes.rs:172-206`), yielding one composite `BindingScope` that routes by prefix: the four `@impact.<fact>` names → dispatch facts, `@state.*` → EntityScope, bare name → store (the `@impact.target`/`@impact.source` tokens never appear as IR leaves — no accessor emits them, Task 4 — so the fact router never sees them; the split depends on that). A policy IR reads both `@impact.healthAfter` and `@state.stagger` in one tree and `bind()` takes exactly one scope — so **this task owns constructing that composite**; it is what Task 5 binds each policy against. Crucially, follow the **`DispatchScope` per-fire idiom (bind once, refresh per fire), not `StoreScope`'s bind-once-against-a-stable-table**: bind the `state(name)` handle once, but supply the *current target entity id* as per-fire ambient state (like the `@`-seeded dispatch inputs), because one policy is bound once yet fires against a different target each impact. Note the shipped `DispatchScope::seed(name, value)` carries only `IrValue` (Number/Bool) — an `EntityId` cannot flow through it (`scopes.rs:144`) — so `EntityScope` needs a **new per-fire target-id channel** that mirrors seed's bind-once/refresh-per-fire pattern but is a distinct ambient input, NOT the `IrValue`-only `seed()`. Plumbing: the per-fire target id comes from Task 1's target command-target token. The `state(name)` **read path serves gate reads from the same per-fire frozen snapshot the dispatch facts use**: state values are captured at fire time — before any of this fire's effects apply — so a gate never observes this fire's own `setState` writes (Task 5's evaluate-then-apply model). Host-authoritative; no replication.

### Task 3: Effects (despawn, setHealth, setState, playAnim, slot.add)
Implement the effects as command-buffer instructions targeting the impact's command-target tokens (Task 1). Own all deferral with a **new dedicated deferred-effect component** (not `BrainComponent`, so non-brain entities defer too), holding: an **ordered queue** of pending entries `{ kind, countdown_ms, value? }` (`value` carries a deferred `setHealth`'s absolute amount; `despawn` needs none), plus a per-entity **inert flag**. Tick it host-authoritatively in the game-logic stage at a **fixed position AFTER the damage chokepoints that enqueue entries** (weapon fire `sim/mod.rs:803`, enemy melee `ai.rs:835`) — so an `afterMs` entry enqueued during this tick's impact takes its first decrement on the NEXT tick, making first-decrement timing deterministic (the placement `death_despawn_remaining_ms` uses). Decrement each entry's `countdown_ms` by `dt_ms` (copy that proven idiom) and apply entries in **insertion order** as they reach 0: a `setHealth` entry writes immediately; a `despawn` entry does **not** remove inline — it **marks the entity for the end-of-frame removal pass** (below) and **cancels all remaining queued entries** (the entity is bound for removal). This is the ordering contract; the breakable fixture never queues multiple entries, but the death spec's zombie — a pending resurrect `setHealth` vs. a later gib `despawn` — is the live case it must resolve.

Removal itself runs in a dedicated **end-of-frame removal pass that executes AFTER the post-catch-up-loop presentation/reaction drain in `App::redraw`** (the `pending_*` event drains + system-command drain at `crates/postretro/src/main.rs` ~:2041–2118; `simulate_tick` has already RETURNED at `sim/mod.rs:313`, so this drain is not in the tick) and **BEFORE render** (`render_frame_indirect` ~main.rs:2861). It runs **per-frame** after that drain — never per-tick and never inline in the game-logic stage; a multi-tick catch-up frame must remove only once, after the drain, not mid-loop. Because `playAnim` is an in-tick write, the entity is already live when the switch runs; this pass then reaps it at frame end (AC "same-group `playAnim` targets a live entity"; Decisions: Despawn ordering). Both an immediate (no-`afterMs`) despawn and an elapsed-countdown despawn feed this one per-frame removal pass. The game-logic countdown tick and the end-of-frame removal sink are distinct stages; do not fuse them. The death spec's kill-report task hooks this pass (report-on-removal); build the pass with that single downstream sink in mind but do not implement it here.
- `despawn({ afterMs? })`: set the target's **inert flag** (so the AI tick early-outs — see below), **cancel all other pending deferred-effect entries** for that entity, and **mark it for the end-of-frame removal pass**. The cancellation applies to BOTH despawn paths (immediate and elapsed-countdown), not only the queued one — so a gib `despawn()` cancels a pending resurrect `setHealth` the moment it marks removal, making the **terminal removal** outcome independent of the intra-stage tick order (which the spec does not otherwise pin — the intermediate HP trajectory, e.g. a one-tick resurrect flash, stays order-dependent; only terminal removal is pinned). With no `afterMs`, it is marked this frame (removed at this frame's end-of-frame pass, after the presentation drain, so a same-group in-tick `playAnim` still targets a live entity); with `afterMs`, enqueue a `despawn` entry with that countdown — when it elapses in a later game-logic tick it cancels the queue and marks the entity for that **frame's** end-of-frame pass (per-frame, not per-tick). Add the AI-tick **inert early-out**: an entity whose inert flag is set skips steering/attack/animation-request this tick (steering hold) — general quiescence for any entity bound for removal, so a killed brain stops engaging during its death-anim window and the modder's `playAnim` is not overwritten by an FSM animation request. (How this coexists with the brain FSM — no `LogicalState::Death` entry, the `death` state no longer HP-reachable — is the death spec's FSM-coexistence decision; the death spec's 0-HP-inert task relies on this early-out.)
- `setHealth(value, { afterMs? })`: a new absolute-set chokepoint on the health component (write `current`, clamp to `[0, max]`): the floor mirrors `apply_damage_with_context`'s `.max(0.0)`, and the upper cap mirrors `refresh_from_descriptor`'s `current.min(max)` (`health.rs:277`) — `apply_damage` itself only floors. `afterMs` enqueues a `setHealth` entry carrying `value` on the deferred-effect component. (The death spec extends this chokepoint to re-arm kill detection — clearing the `death_handled` latch and the pending kill credit; not built here.)
- `setState(name, value)`: an EntityScope IR output (Task 2).
- `playAnim(clip)`: presentation, an **in-tick synchronous write** (not an app-drain command). Route through the **id-targeted** `switch_animation_state(registry, id, name)` seam (`animation.rs:425`, which mutates `MeshComponent` synchronously in-tick), not the tag-resolving `setAnimationState` reaction; `clip` names a **declared animation state** on the entity's `components.mesh` (the seam errors on an undeclared state), not a raw clip. Cross-arm "consequential before presentation" order is enforced by Task 5's per-fire dispatch loop, not by an app-drain queue. Fixture strings (`"shatter"` here; `"death"`, `"gib"`, `"down"`, `"falter"`, `"glory_kill"` in the death spec) presume those states are declared on the entity.
- `slot.add(delta)`: an SDK-side builder that lowers to a self-referential IR output `Add{ read(slot), delta }` on the same store slot — no new evaluator opcode; document the read-modify-write-races-LWW caveat.

### Task 4: Authoring surface (defineImpactEvent + override + IR skin)
Promote the WALL into the real `postretro` SDK (the WALL `proposed.d.ts` has collapsed to a re-export shim; the shipped `postretro` types are the surface now). **Two review corrections land here** (Decisions): `Effect` is the **closed** impact-effect union — `despawn`/`setHealth`/`setState`/`playAnim`/`slot.add`, NOT `PrimitiveReactionDescriptor | Reaction<{}>` — and `defineImpactEvent` takes an explicit author-assigned `id`. `defineImpactEvent(id, filter, policy)` is a pure builder returning a branded `ImpactEvent` handle (mirror `defineStore`: pure, no FFI, registered only by returning it through a manifest `events` child). `id` is an **author-assigned namespaced string** (e.g. `"salvage:crate-break"`) — the event's stable, portable identity (Decisions: Identity), NOT an FNV-derived hash: an explicit string is portable across the QuickJS/Luau boundary, stable when the policy body is edited, and collision-controlled by namespacing. `handle.override(filter, policy)` links to its base by that id — the handle carries it within a runtime, and the id string is the durable cross-runtime link. Lower a returned `ImpactEvent` (base + its overrides) into the manifest as a descriptor the engine (Task 5) merges by string-equal id — no engine-side hashing. The policy builder receives an `Impact` occurrence whose accessors return IR refs (`NumberRef`/`BoolRef`) and whose methods return effect descriptors; add the `NumberRef` op-set mirroring `runtime.*` and `BoolRef` `.and/.or/.not/.select` desugaring to `select`. The accessors lower to Input nodes with the exact pinned wire spellings — Task 1's `@impact.*` (`impact.amount` → `@impact.amount`, `impact.target.healthBefore/healthAfter/maxHealth` → `@impact.healthBefore`/`@impact.healthAfter`/`@impact.maxHealth`) and **Task 2's** `@state.<name>` (`impact.target.state(name)` → `@state.<name>`). `target`/`source` are opaque command-target tokens (no IR-leaf accessors; `source` has no v1 methods — grant is deferred). A policy returns `EffectOrGroup[]`. Once the surface ships, `proposed.d.ts` collapses to a re-export shim of the now-shipped `events`-bearing manifest types (as its header comment anticipates), so the fixtures' `postretro/proposed` imports — this folder's and the death spec's — resolve to shipped exports and type-check unchanged — that is the sense of "type-check against the shipped SDK."

### Task 5: Engine-side impact-policy evaluator
Own the runtime that turns a registered `ImpactEvent` descriptor into per-fire behavior. On an impact dispatch (Task 1): resolve which event variant applies to the target — merge base + overrides by author-assigned id, last-registered (load order) winning for the target (Decisions), whole-policy replace. Bind each surviving policy's gated-group IR against the **single composite binding scope Task 2 constructs** (routing `@impact.amount`/`@impact.healthBefore`/`@impact.healthAfter`/`@impact.maxHealth` → dispatch facts, `@state.<name>` → the target's EntityScope, bare → store); `bind()` takes exactly one scope, so this composite — not two separate scopes — is the bind target. Pin the execution model as **evaluate-then-apply per fire**. For one impact fire the evaluator first evaluates ALL group `when`s **and** every effect's operand reads (bare top-level effects included) against one **impact-time snapshot** — the per-fire frozen state/health values captured at fire time, before ANY effect of this fire (bare or gated) has applied — THEN applies every effect in order. The snapshot extends the dispatch facts (already frozen at fire time) to per-entity STATE: a `state(name)` read is served from the snapshot, not live from the component, so a bare top-level `setState` — the fixture's `t.setState("hits", hits.plus(1))` — is invisible to every `when` in the same fire, exactly as an earlier group's `setState`/`setHealth` is invisible to a later group's gate. The author's mutually-exclusive `when`s must be decidable from this pre-effect snapshot; the breakable fixture's threshold gate and the death spec's imp state machine rely on it. Then, for every group whose gate held (independent evaluation), dispatch its effects (Task 3) in the fixed consequential-before-presentation order. Each fire fully applies its effects to live state before the next impact on that entity is dispatched (per-fire, not per-tick-batch), so two same-tick hits cannot both read stale state and double-fire the emergent counter. This is where the manifest `events` "lowers into" a chokepoint-registered predicate + effect dispatch. Bind-once/eval-per-fire, reusing the §11 evaluator; no live VM. Implement the in-tick producer path; **gate evaluation on Task 1's producer discriminator** — evaluate only when the producer is in-tick; the app-drain producer early-outs before policy resolution (a no-op stub at the same seam — v1 runs no policy for app-drain-sourced impacts; Decisions: Producer contexts).

## Sequencing

**Phase 1 (foundational):** Task 1 — the dispatch source + command-target token channel everything downstream binds to.
**Phase 2 (sequential):** Task 2 (per-entity state + EntityScope) — consumes Task 1 (the target token for per-fire seeding).
**Phase 3 (sequential):** Task 3 (effects) — consumes Task 2's EntityScope write-binding.
**Phase 4 (sequential):** Task 4 (authoring surface + descriptor) — consumes Task 1's dispatch scope and Task 2's `@state.<name>` spelling (the accessors lower to both).
**Phase 5 (sequential):** Task 5 (evaluator) — consumes Task 1's scope+tokens, Task 2's binding, Task 3's effects, and Task 4's descriptor.

The death spec (`E16--impact-death-lifecycle`) sequences entirely after this spec.

## Resolved design notes

- **Per-entity state schema declaration — DECIDED: implicit-on-first-write, total-default-`0`.** v1 has no declaration surface: a field exists on first `setState`, and an unset `state(name)` reads `0`. Because unset and reset-to-`0` both read `0`, `state(name).eq(0)` is **not** an is-unset test — it cannot distinguish "never written" from "written back to 0"; an author who must detect unset should reserve a sentinel (e.g. start counting from 1). Rationale: keep per-entity state ECS-emergent so an entity can gain roles/allegiances its author never declared (mutable friendly↔hostile, quest-giver↔enemy) — a pre-declared closed schema would make those transitions structurally impossible (the Face-McShooty rigidity class of bug). Consistent with the store model (implicit, type-zero, LWW). **Deferred (cohesively):** declaring *nonzero* spawn defaults (e.g. an optional `components.state` block paralleling `components.health`) — it must stay **non-closing** (never a field whitelist) or it re-imports the trap. **Downstream, not this epic:** wiring the AI-engagement side to *read* per-instance state (per-entity hostility changing who an enemy engages) is the enemy-behavior-state work this keystone sets up — same seam as the tag-wide aggro limit (`E16--impact-death-lifecycle` Out of scope).
