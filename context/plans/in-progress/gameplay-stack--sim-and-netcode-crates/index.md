# gameplay-stack--sim-and-netcode-crates

Brief · resumable — ordered phases (partition → boundary-prep → sim → netcode) that span sessions, with manual co-op proof last · Epic `gameplay-stack-decomposition` (M2) · reads: `context/lib/development_guide.md` §Workspace · `context/lib/scripting.md` §13 · `context/lib/networking.md` §Crate boundary and ownership, §Weapon placement is content · `context/lib/testing_guide.md` §3, §4 · read at 3acc6d6

## Problem

Developer-raised, anticipated need. `crates/postretro` is one bin-only crate of ~222K LOC, so every edit recompiles all of it: touching `startup/`, `input/` or `main.rs` rebuilds the fixed-tick gameplay cluster and netcode, and touching gameplay rebuilds the rest. The cause is that no crate boundary exists — `development_guide.md` §Layering invariants records the fixed-tick systems as binary-bound through collision, and M1 sank the shot-authority and carried-loadout types that made the `scripting ↔ sim ↔ netcode` cycle uncuttable. When this is done, the fixed-tick core, collision and the scripting host are `postretro-sim`; `netcode/` is `postretro-netcode` above it; the binary keeps orchestration and presentation; an edit to binary-only code rebuilds neither crate; and sim's harness-reaching tests keep their files, bar those whose helper names a sim type.

## Decisions

- **Both crates land in one stride.** Sequencing is unchanged — sim exists before netcode sits above it — only the packaging is. Split across milestones, netcode stays bin-only while sim exists, so sim's tests that reach netcode harness types (`sim/weapon_stage.rs`, `sim/touch.rs`, `sim/determinism_tests.rs`, `scripting/systems/ai_tests.rs`, `impact_effects.rs`) would relocate to the binary and reach sim through a widened public API. Combined, they stay put — bar the sim-type exception below, which costs a handful of callers rather than five files.
- **`postretro-sim` dev-depends on `postretro-netcode`; `postretro-netcode` depends on `postretro-sim`.** Cargo permits this because dev-dependencies bind only test targets, and `development_guide.md` §Workspace already records that a dev-dependency edge does not enter the layering.
- **The cycle carries a type across it only when that type lives below both crates.** `cargo test -p postretro-sim` compiles sim twice — the lib netcode links, and the test target — so a sim-defined type handed to a netcode function is two distinct types (`E0308`, "multiple different versions of crate"). Verified both ways on a scratch workspace at this shape. `produce_owned_snapshots` names only `EntityRegistry` and netcode's own types and crosses fine; `ingest_hit_declaration_for_test` takes `CollisionWorld` and `HitZoneStore`, both sim-resident after the move, and does not. Its callers in `sim/weapon_stage.rs` and `scripting/systems/ai_tests.rs` move to `postretro-netcode`, whose test target sees one normal compilation of each — they exercise a netcode entry point, so that is where they belong.
- **Test helpers reached across a crate boundary ship behind a `test-support` feature, never `#[cfg(test)]`** — a dev-dependency compiles the other crate without `cfg(test)`. Precedent: `postretro-entities` and `postretro-combat-model` `test-support`, `postretro-net` `dev-tools`. Sim's tests reach netcode's `produce_owned_snapshots` (it crosses fine); the binary's tests reach sim's `run_local_weapon_fire_for_test` and `weapon::tests` builders. `ingest_hit_declaration_for_test` gains no widening — its callers move to netcode, so it stays `pub(crate)`.
- **Tests that reach binary-only code move to the binary or drop the reach; nothing sinks to serve a test.** An item sinks only when its dependencies already sit below it, and its tests follow it. Which is which is Path.
- **What moves.** The `scripting ↔ sim` cycle becomes intra-crate and legal; netcode's edges into sim become down-edges.

| Crate | Takes | Workspace deps | Externals |
|---|---|---|---|
| `postretro-sim` | `sim`, `collision`, `nav`, `weapon`, `movement`, `kinematic_mover`, `agent`, `agent_steering`, `combat_positioning`, `trigger_system`, `trigger_bindings`, `trigger_commands`, `trigger_pools`, `impact_policy`, `impact_effects`, `spawner`, `health`, `grant`, `fx`, `sprite_collection`, `alloc_probe`, `frame_timing`, `presentation_pool` + `presentation_projection`, `scripting` minus the frame-path bridges | `entities`, `foundation`, `scripting-core`, `combat-model`, `net`, `model`, `render-data`, `level-format`, `level-loader` (collision builds from `LevelWorld`), `lighting` (`script_primitives`) | glam, parry3d, serde, serde_json, log |
| `postretro-netcode` | `netcode/` minus the App-composition drains | `sim`, `net`, `entities`, `foundation`, `scripting-core`, `combat-model`, `model` | glam, parry3d, thiserror, serde |

- **These stay binary-side and are not open questions:** `runtime_movers` (feeds collision at load/spawn but every caller is `startup/`, `session/`, `capture/`, `main.rs`), the four `*_diagnostics` modules (each reaches `crate::render`), `content_hash` and `mod_digest`.
- **Sim is the renderer's sibling over `entities`, not its dependent.** Its deps are the wgpu-free CPU crates the renderer also sits above; a `lighting` or `level-loader` edit will rebuild gameplay, and that cost is accepted. Netcode's `render-cpu`, `visibility` and `lighting` references sit in `projectile_presentation.rs`'s test module and become dev-dependencies.
- **The manifest cuts inside `scripting/systems/` at the fixed-tick / frame-path seam.** Modules that feed `render-cpu`, `postretro-ui`, `visibility` or App-side input stay in the binary; the fixed-tick handlers move. They sit under `scripting/systems/` by the handler-wiring convention of `scripting.md` §13, not because they simulate. Which module falls which side is source-derived — see Path.
- **Plain records sink so neither crate names a render-stack type.** `render_cpu::mesh_pass::ClipMetadata` (name + duration; the clip-table install path in `mesh_anim`) sinks to `postretro-model`, where the glTF loader already computes it. `postretro_renderer::PresentationDrawInput` (the pool's emitted record) sinks to `postretro-foundation`, where `PresentationTemplateHandle` and `PresentationFacts` are defined and from which `entities` re-exports them. The crates that owned them re-export; `presentation_pool` then moves whole, since `impact_policy` and netcode's client presentation both drive it in production.
- **Netcode's App-composition drains move to the binary.** `client_drain_control` and `apply_client_switch_resolution` in `netcode/endpoint.rs` take `&mut App` / `&mut Session` and are netcode's only production reach into the binary root besides weapon placement. They move with their call sites; netcode exposes what they call.
- **`resolve_weapon_placement` sinks to `postretro-foundation`** with `legacy_weapon_placement` and `BASE_OFFSET`; sim (`weapon_stage/commands.rs`) and netcode (`netcode/mod.rs`) both call it in production, and foundation already defines `WeaponPlacementDescriptor` and documents the legacy fallback. This is one layer deeper than `networking.md` §Weapon placement is content frames it; the rule follows the data it resolves.
- **`frame_timing` moves into `postretro-sim` whole.** Its accumulator defines the fixed tick, reaction scheduling converts ms→ticks against `TICK_DURATION` in production, netcode's cadence tests drive `FrameTiming`, and nothing in it reaches the binary. `postretro-net::timesync::DEFAULT_MICROS_PER_TICK` carries the same period for transport timesync; that duplication predates this work and stays.
- **Spawn windup stops sharing netcode's constant, value unchanged.** `spawner.rs` reads `netcode::MAX_DELAY_MICROS` — the interpolation delay ceiling, netcode policy — as a 250 ms attack windup. Sim declares its own windup constant at 250 ms; a netcode test asserts windup ≥ ceiling, the rule `plans/done/E10--enemy-multi-attack/` records as `cooldown.max(MAX_DELAY_MICROS / 1000)`. An equality pin would be a false invariant.
- **`alloc_probe` moves with its tests, and sim declares the `#[cfg(test)] #[global_allocator]`.** The attribute must annotate a crate-root static; the binary's static goes, having no remaining users.
- **`gen-script-types` and `mint-identity` become ordinary bins of `postretro-sim` over its lib.** Their `#[path]` re-compilation of `scripting` submodules existed because the binary had no lib target (`main.rs` says so); with a wgpu-free lib to link, it is double compilation. Invocations become `cargo run -p postretro-sim --bin …`; the committed-typedef test messages and xtask's `mint-identity` wrapper follow.
- **Visibility widens only where a boundary is crossed.** `pub(crate)` becomes `pub` for items another crate reaches — the `simulate_tick` seam among them — and nowhere else.
- **This legalizes a cycle M3 must undo; no M2 guard tracks its cost.** Once `scripting ↔ sim` is intra-crate the compiler stops flagging new AI↔sim edges, and AI is the churn locus, so M3's inversion price grows unmeasured until M3 opens. Accepted: the epic's Execution model re-grounds M3 against the live tree when it opens, re-enumerating the `ai → sim` edge set — a standing M2 drift guard would only turn that silent growth into a failing test, at the cost of a golden-set update on every legitimate AI→sim edge on the churn locus. Splitting sim now would be M3's work pulled forward against the epic's sequencing.
- **Runtime perf holds; only dev-build inlining changes.** Release builds optimize across crates (`lto = "thin"`), so the sim↔netcode crate boundary inlines as the intra-binary module boundary did — E19 and M1 crossed the same kind of boundary with no runtime regression. Dev builds lose cross-crate inlining at the seam: the iteration cost this epic buys, not one it takes. No new hot-path dispatch — the pool moves as a concrete struct, not behind a trait.
- **Non-goals.** The AI edit loop does not improve here: netcode depends on sim, AI lives in sim until M3, and Cargo rebuilds every dependent of a changed crate — what lands is the binary-only loop. No behavior, wire, scripting-semantics or SDK-typedef change. No combat-logic consolidation into `postretro-combat-model`. No crate for the frame-path bridges. `input` and `camera` stay binary-side whole — only tests reach them from the cluster.

## Acceptance

### Automated
- [ ] `cargo build --workspace`, `cargo test --workspace`, and `cargo build -p postretro --features dev-tools` pass.
- [ ] `layering_invariants_hold` passes; the regenerated `crate-graph.md` passes `crate-graph --check` and lists both new crates.
- [ ] `cargo tree -p postretro-sim -e normal` shows no `wgpu`, `winit`, `glyphon`, `postretro-renderer`, `postretro-render-cpu`, `postretro-visibility`, `postretro-ui` or `postretro-netcode`; `mlua`/`rquickjs` appear via `scripting-core`.
- [ ] `cargo tree -p postretro-netcode -e normal` shows `postretro-sim` and none of `wgpu`, `winit`, `glyphon`, `postretro-renderer`, `postretro-render-cpu`, `postretro-visibility`.
- [ ] Sim's test targets link netcode; its library does not: `cargo build -p postretro-sim` compiles no `postretro-netcode`, `cargo test -p postretro-sim --no-run` does.
- [ ] Rebuild isolation: after a warm build, touching a binary-only file recompiles neither crate; touching a sim file recompiles sim, netcode and the binary; touching a netcode file recompiles netcode and the binary, not sim.
- [ ] No moved module remains as binary source: `netcode/` and the modules the manifest hands to `postretro-sim` are gone from `crates/postretro/src/`. A grep gate — `cargo tree` cannot see a dead duplicate.
- [ ] No test is lost: `cargo test --workspace` runs every test it ran before, plus the windup guard this brief adds. Every test that changed file is named in the plan of record.
- [ ] The M15 Phase 0 determinism harness passes unchanged.
- [ ] `gen-script-types` leaves `sdk/types/` byte-identical; the committed-typedef test passes and names the new command.
- [ ] The xtask `mint-identity` wrapper invokes the `postretro-sim` bin and mints a mod's TypeScript sidecar; `sdk/` resolves at the unchanged manifest-relative depth.
- [ ] Weapon placement resolves identically at both ends of the precedence chain: an unauthored weapon yields the legacy offset with zero rotation; an instance-authored weapon overrides every lower tier.
- [ ] A newly spawned enemy still cannot attack for 250 ms; one whose cooldown already exceeds that keeps the larger value.
- [ ] A test fails if sim's spawn windup drops below netcode's interpolation ceiling; raising the ceiling above the windup trips it, raising the windup above the ceiling does not.
- [ ] The allocation-guard tests still arm under sim's allocator: a deliberate allocation inside a guarded window fails them.
- [ ] Every `pub(crate)` → `pub` widening has a caller in another crate.

### Manual
- [ ] `cargo run -p xtask -- run content/dev/maps/campaign-test.prl` plays identically: movement feel, enemy engagement, weapon fire, triggers, movers.
- [ ] Animated meshes play their clips and hit zones register on a moving animated enemy — the clip-table install path changed hands.
- [ ] Lights, fog, emitters, particles and damage overlays present correctly — the bridges stayed behind while the systems feeding them moved.
- [ ] A `--features dev-tools` launch starts and its debug panel draws.
- [ ] A co-op session with a connected client joins, replicates, reconciles, and survives a host level change.

## Path

Non-binding.

- **First slice: partition `scripting/systems/` in place and sink the records, before either crate exists.** Staying binary-side: `light_bridge` (reaches `postretro-renderer`), `mesh_render`, `fog_volume_bridge`, `emitter_bridge`, `attachments`, `particle_render`, `presentation_cells` (each reaches `render-cpu`, `postretro-ui` or `visibility`), `input_mode` (App-side input) — production callers all binary-side. Moving: `hit_zones` (a `simulate_tick` parameter) and `mesh_anim` (the render-free `animate_entity` it calls). Move the staying modules to a binary-side module and land `ClipMetadata` and `PresentationDrawInput` in their leaves. This is green on the existing tree and falsifies the riskiest assumption — that fixed-tick and frame-path halves separate cleanly. Today only `hit_zones → mesh_anim::animate_entity` crosses; if severing surfaces more, the seam is not where this brief claims.
- **Then boundary-prep, still on one tree:** `frame_timing` and `presentation_pool` relocation, the placement sink, the windup constant, the App drains up, the `fx` re-export paths in `scripting/reactions/{mod,registry}.rs`, the `test-support` features, and the test reaches below. Sim's integration-test directory is the fallback if a moved caller proves to test sim alone, at the cost of widening what it reaches.

- **Then both transplants, sim first, each wholesale.** `plans/done/E19--renderer-gpu/` moved its subtree in one cut so `super` paths survived; a partial cluster does not compile, so staging buys checkpoints that cannot be green. Netcode follows immediately — the dev-dependency that keeps sim's tests in place needs it.
- **Seams by symbol:** `sim::simulate_tick` / `simulate_tick_with_presentation_aim` are fully data-injected (`plans/done/M15--p0-headless-sim-seam/`) — sim's natural public face. `scripting_systems` is re-rooted through `#[path]` in `main.rs`; inside sim it becomes an ordinary module. `PresentationDrawInput` is re-exported from `renderer::render`, so the sink is a `pub use` there.
- **Manifests:** both crates declare `dev-tools` (trigger debug logging, `TriggerBindingTable::is_bound`, netdiag positions) and the binary forwards it as it does for `net` and `renderer`; sim enables `script-ffi` on `entities` and `lighting`. Sim dev-deps: `level-compiler` (nav bake contract), `script-compiler`, `ui` (typedef surface test), `test-log-capture`, `proptest`; netcode dev-deps: `net` with `dev-tools` (the packet conditioner), `render-cpu`, `visibility`, `lighting`. Bins keep `sdk/` at the same manifest-relative depth.
- **Strongest rival for the pool:** a sim-defined overlay-ledger trait the binary's pool implements. Rejected because netcode's client presentation drives most of the pool's surface in production; the record sink is a struct move and a re-export.
- **Strongest rival for the stride:** one fused `postretro-gameplay` crate now, split into sim and netcode at M3 beside the ai carve-out. It would delete the dev-dependency cycle, the `test-support` surface and every cross-boundary test question, and by this brief's own non-goals it delivers the same binary-only win today. Rejected because `netcode → sim` is already one-way after M1: fusing would legalize a second cycle on top of the `scripting ↔ sim` one, and M3 would owe two inversions instead of one. The epic rejected a mega-crate at M1's scope on a different argument — that an AI edit still recompiles netcode — which does not distinguish the two shapes here.
- `main.rs` this work only removes from — never adds to. At promotion: `scripting.md` §7 names the new `gen-script-types` command, `development_guide.md` §Target shape records both crates as built.
