## Layer home

The roadmap put layer values in per-entity `@state`. Source:
- `EntityStateComponent` is a schema-less f32 map. Every entity has one. A typo'd name reads as 0.
- Only impact-policy `setState` (on the target) and `adjustSentiment` write it. It has no per-tick writer, and reaction `setState` writes store slots, not entity state.
- It does not replicate. The only path to clients is the overlay's host-sampled `shield_fraction` / `has_shield` on `WireOverlayRoster`.
- `defineStore` rejects `perOwner` + `accumulate`, so recharge cannot live in the store per player either.
- Owner-slot `slot.set` in impact policies binds only to `@impact.source`, so a player's own shield cannot reach their HUD through the store.

## Damage chokepoint

- Every damage source calls `apply_damage_with_context`:
  - weapon impact (hitscan, projectile, splash, and host-validated client hits) via `apply_weapon_impact_damage_with_source`, which applies `zone_multipliers` first;
  - NPC contact via `AiHost::apply_damage`;
  - script `applyDamage` (`DamageProducer::AppDrain`);
  - mover crush (`kinematic_mover/blocking.rs`);
  - traps through the projectile path. Not traced end to end.
- Order inside the chokepoint: subtract, floor, `set_component`, contributor ledger, brain perception, `push_impact_dispatch`. Policies run in `evaluate_pending_in_tick_impacts` after `publish_health_from_registry`, `InTick` only.
- Damage also lands outside the tick: `host_flush_pending_hit_declarations` after the tick, and AppDrain at frame end. The last-damage stamp must therefore come from the chokepoint, not from a stage. The chokepoint has no tick counter today.

## Handle naming

- **Precedent.** `BindingNameSugar` (`apply_binding_name_sugar`, `crates/script-compiler/src/lib.rs`) inserts the binding identifier of a module-level `const`, `let` or `var` declarator, exported or not, as a string first argument into `defineStore`, `defineImpactEvent` and `definePresentationTemplate` when the callee is the bare identifier and the call has one argument fewer than the named form (`plans/done/descriptor-identity-and-naming-sugar`). An aliased import or a `Postretro.`-qualified call is not sugared. It runs before bundling, on every authored script, level scripts included, and never on the prelude. Called with the name still missing, the SDK throws `BINDING_NAME_SUGAR_DIAGNOSTIC`, whose text names only `defineStore` / `defineImpactEvent` (`sdk/lib/data_script.ts` / `.luau`); `sdk/lib/ui/presentation.ts` keeps its own copy for `definePresentationTemplate`. Tests live beside it in `lib.rs`, including one that leaves `defineStore(computedName, …)` alone.
- **TS only.** Luau source runs raw, so Luau passes the name explicitly, and its `defineStore` errors when the name is omitted. TS `defineStore` also accepts the explicit name, so `defineDefenseLayer("shield")` and `defineDamageType("shock", matrix, options?)` keep that form beside the sugar.
- **Names travel with handles.** A store ref carries its dotted name from creation, so a level VM re-runs `defineStore` and references slots without `defineMod`: `content/dev/scripts/closet-reveal.ts` imports `./closet-store`, and `closet-reveal.luau` re-declares the store only for its slot refs. Layer and type handles follow it: each crosses as `{ kind, name }`, so a content-derived reaction id (`autoReactionId`) tells two layers apart, and a bare string or a handle of the other kind is recognizable as a bad reference. It is caught where an unregistered name is caught on the same surface: at load on a descriptor or the mod manifest, at install on a reaction, impact policy or condition, at tree build on a UI binding, and at overlay install on an overlay callback, where `bind_damaged_enemies_overlay` already rejects a malformed overlay and it is skipped with a warning. One rule per surface keeps `.damage` symmetric: `{ type: shield }`, `{ type: "shock" }` and an unregistered type all drop that reaction, where a load failure for the first two would let one bad reaction take down the mod while the third only drops itself.
- **Wire shape.** The SDK's ref convention: what crosses the FFI is a value's enumerable fields, and helpers stay off the wire. `storeRef` (`sdk/lib/data_script.ts`) freezes `{ slot, kind }` and defines `byPlayer` non-enumerable; `impact.source` and the assist sides carry a non-enumerable `__wire`; an impact event handle carries `kind: "impact"`. The Luau `storeRef` keeps the same table fields and serves `byPlayer` through its metatable's `__index`. Component descriptors reach Rust through `conv::js_to_json` and `serde_json::from_value` (`data_descriptors/js/entity.rs`), and `#[serde(tag = "kind")]` enums already parse descriptor data (`foundation`'s `data_descriptors/types/combat.rs`, `activation.rs`, the latter with `deny_unknown_fields`). So one serde enum tagged on `kind` is the only definition of a handle reference, both SDKs build its input, and identical descriptors follow by construction. A bare string fails that parse. The other `kind` parses, as the enum's other variant, so each surface then checks the variant it expects and rejects the other `kind` right after the parse, the bad-reference case each surface already rules on.
- **The new definers' rule.** The precedent is arity-based, and both new definers take an optional trailing options argument, so arity alone cannot tell `defineDamageType(matrix, options)` from `defineDamageType(name, matrix)`, or `defineDefenseLayer(options)` from `defineDefenseLayer(name)`. The rule keys on an object-literal first argument instead: `defineDamageType` with one or two arguments and `defineDefenseLayer` with zero or one. A computed or string first argument is the explicit form and passes through, as `defineStore(computedName, …)` does. The cost: a matrix held in a variable is not sugared, and the SDK raises the diagnostic.
- **Name grammar.** Names are `grantAmmo`'s grammar (`validate_ascii_identifier`, `[A-Za-z0-9_.:-]{1,64}`) without `.` and `:`. A layer named `shield.capacity` would collide with layer `shield`'s `player.defense.shield.capacity` slot and its `@defense.shield.capacity` input. A TS binding containing `$` passes the sugar and then fails the grammar at load.
- **Duplicates fail load.** Fluids and ghost styles warn and drop a later duplicate. Registration lists are authored once, in the manifest, so a duplicate name is a typo, and a silent drop would hide which declaration a descriptor's reference reaches.
- **Rejected: key-derived names resolved by identity.** Naming each handle by its `defineMod` key, and resolving references by object identity, breaks twice. `setupLevel` runs in its own short-lived VM (`scripting.md` §2) and never calls `defineMod`, so a handle a level script imports is never registered. Luau's `require` keeps no module cache (`luau_require.rs`, `scripting.md` §2), so every `require` of the defenses module makes new tables, and only the start-script's set would be registered.
- **Counter-precedent.** Ghost styles and fluids keep explicit name fields because map files reference them as strings (`scripting.md` §2). Here the one map-file reference, FGD `crush_damage_type`, names the same binding name, so it needs no separate field.
- **Rename cost.** Renaming a binding renames the type or layer. An FGD value naming the old type warns once per level load and crushes as if the KVP were absent (the default type, or untyped without one), and a renamed layer renames its `player.defense.<name>` slots and changes the state-schema fingerprint.
- **Factions.** `defineFaction(name)` keeps its explicit string. Adopting binding-name sugar is a roadmap follow-up.

## Matrix and resist

- **Three levels, one job each.** The matrix is the mod-wide game rule per pool kind ("shock is strong against shields"). A layer entry's `resist` is equipment ("this shield is shock-warded"). `health.resist` is the body ("a fire imp's flesh shrugs off burn"); on an unlayered entity it is entity-wide resistance, the Quake path. A pool's multiplier is matrix × that pool's resist, and nothing else multiplies it.
- **Why pool-local.** An entity-wide resist would be a hidden third multiplier on every pool: a shock-warded shield would also ward the flesh under it, and a fire imp's flesh resist would also thin a shield it carries. Pool-local keeps each multiplier where its author put it. The cost: making a layered entity immune to a type everywhere takes one `resist` entry per pool (R-P11).
- **Expressions.** A resist value is a layer parameter, so gear raises a store slot the expression reads, with the same scope, clamps, fault rules and tick-start timing as capacity (R-P35). Its omitted default is 1, the fallback before any good value.
- Raw-remainder spillover keeps a type's bonus on the pool it targets: shock's ×2 against shields never carries over to the flesh beneath.
- With raw-remainder spillover, a layer above zero at ×0 never empties, so it absorbs all raw that reaches it and drains nothing. Drains by earlier layers stand (R-P31). That is what 0 means arithmetically; treating it as a bypass special-cased the arithmetic and left no way to say "this layer stops this type". Bypass is a different intent, so it gets its own literal.
- Resist 0 composes with that rule: the product is 0, so `resist: { burn: 0 }` on a shield makes it absorb every burn hit while above zero and pass nothing, and once it is empty it is skipped (R-P34). `health.resist` 0 deals no health damage. A `"bypass"` layer has no multiplier for its resist to scale, so it stays bypassed (R-P30).
- `health: "bypass"` would pass the hit to no further pool, the same result as `health: 0`; rejecting it keeps one spelling per result.
- A blocked hit has a positive raw amount, so it restamps and resets brain recency, and its points dealt are 0, so it credits nothing (R-P29). The same rules govern the resist-0 immune hit (R-P11).

## Default type

- **Why a default.** Untyped damage at ×1 everywhere cannot express "physical damage does ×0.8 against armor" unless every source is typed, and many are typed only by omission: an NPC melee without `damageType`, a crusher without `crush_damage_type`, a bare `.damage(n)`. `defineMod({ defaultDamageType })` names the type those sources deal, so one type's matrix covers them.
- **Why optional.** Without it, untyped damage stays ×1 on every pool with no resist, so every mod that predates this brief keeps its results (the parity rows).
- **Why the dev mod sets it and still types its weapons.** The dev mod declares `ballistic` (`{ armor: 0.8 }`), sets it as the default, and types every weapon explicitly anyway, so each gun keeps its type if the default ever changes and the explicit form stays exercised. The default then covers only the sources that cannot or do not name a type.
- **Why the plasma bolt and rocket get their own types.** `plasma` and `explosive` let the existing arsenal exercise the matrix (plasma strong against shields and weak against armor, explosive strong against armor and flesh and weak against shields) without new content, and the rocket's splash, its only damage (splash replaces direct health damage, `entity_model.md` §Components), rides the weapon's type, so one dev weapon covers typed splash.
- **Unknown FGD type.** An unknown `crush_damage_type` warns and counts as absent rather than failing load, because level content is not mod vocabulary.
- **Observable.** `@impact.type.<name>` is true for the default type on a hit whose producer named none, so a policy cannot tell a defaulted hit from an explicitly typed one. That is intended: the default is a type, not a fallback mode.

## Damage over time

The roadmap's `status effects / DoT` item owns statuses, as an engine per-tick component whose ticks emit through the combat-events chokepoint. The brief leaves two doors open: `defineDamageType`'s reserved options argument, and `.damage(amount, options?)` as an options object. It also commits the DoT brief to the producer rule: every damage tick, from any future producer, goes through the chokepoint with a type and a source, so it drains layers and credits. That rule binds the later brief; nothing in this one builds or tests it.

**Non-binding sketch** for the DoT brief to start from. Nothing here ships with this brief, and `defineStatus` is not an SDK name:
```ts
export const burning = defineStatus({ damage: 3, type: burn, tickMs: 500, durationMs: 4000, stacking: "refresh" });
export const burn = defineDamageType({ health: 1.5, shield: 0.5 }, { inflicts: burning });
```
Questions the sketch leaves open:
- **Cycle.** `burning` names `burn` and `burn` names `burning`, so as two consts one reads the other before it exists; one side must reference the other lazily, by name, or by nesting the status inside the type.
- **Stacking.** Whether a second application refreshes, stacks intensity, stacks independent instances or is ignored, and whether the policy belongs to the status or to the target.
- **Refresh.** What a refresh resets (duration, tick phase, source) and whether a weaker application can refresh a stronger one.
- **Application chance.** Whether the chance to inflict lives on the weapon, on the damage type or on both, and how it combines with per-hit facts such as zone or broke.
- **Networking.** Statuses resolve on the host; whether a client sees status presence, remaining duration or only the resulting damage, and through which replication family.
- **Presentation.** How a HUD, the enemy overlay and impact policies observe a status, and whether each tick dispatches an impact or ticks stay policy-silent as script damage is today.

## Body order

Today a reaction's store writes do not apply at one moment on every source. Source:
- **Player and trigger events.** `partition_direct_reaction` keeps `grantHealth` and `addSlot` as consequential steps, and `bind_command_at` binds each as an in-tick command. `PlayerEventTable::fire_event` runs an event's commands in order, so body order already holds in-tick.
- **Reactions fired by address** (crossings, `levelLoad`, `fire` targets, UI presses). `dispatch_add_owner_slot` (`primitive_dispatch.rs`) validates the slot and resolves seats at fire time, then pushes `SystemReactionCommand::AddOwnerSlot`; a `setState` step pushes `SystemReactionCommand::SetState` through `dispatch_system_reaction`. The app drains that queue in order (`dispatch_system_commands` in `main.rs`), where `AddOwnerSlot` re-checks seat liveness, readonly and range, and `SetState` evaluates its IR value against live slots. `grantHealth` and `applyDamage` apply at dispatch through the reaction registry. So in `[grantLayer(shield, 25), damage(20)]` a queued grant would land after the damage, and a grant applied at dispatch would read capacity before an earlier `addSlot` lands.

**Connected clients today.** A client fires its own-state reactions (crossings over its own, owner-private or local slots, movement events, UI presses) and its host-mirrored ones (`levelLoad`, crossings reading only shared slots) through the same walker (`scripting.md` §12's class table). `addSlot` returns at dispatch on `owner_slot_writes_enabled`, the predicate group commands share, before resolving seats (`dispatch_primitive`, `primitive_dispatch.rs`; `group_resolution.rs`). A reaction `setState` on a per-owner slot is rejected at install on every machine (`SystemReactionIrBindings` rebuild). So a client's store writes are `setState` on its own global, writable slots, queued and applied at its own frame-end drain with no role gate (`write_state_slot_json`, `store_bridge.rs`). After a `wait`, a client lands only machine-local steps (`primitive_is_machine_local`).

`levelLoad` end to end, a connected client's included:
- **Fire.** Every machine fires `levelLoad` at its own install: `install_world_cpu_with_models` (`startup/lifecycle_world_cpu.rs`) calls `fire_named_event_with_sequences` with `FireOrigin::EveryMachine(MachineSource::HostTimeline)`, under no role gate. `suppress_host_replicated` skips only the `progress` membership capture there.
- **Pre-wait steps.** All of them dispatch. `client_landing_drops` filters only inside a scheduler landing's `LandingScope::client`, which the install fire never enters; `primitive_is_machine_local` filters tails, not pre-wait steps. `dispatch_primitive` refuses `addSlot` on `owner_slot_writes_enabled`, and a `setState` queues through `dispatch_system_reaction`.
- **Apply.** Each machine's own drain (`dispatch_system_commands`, `main.rs`) applies it through `write_state_slot_json`, readonly-, range- and per-owner-gated, with no role gate, so a client applies a local-slot write as the host does. The `--connect` drop in `scripting.md` §10.4 is `refuse_client_level_verb`, which covers `loadLevel` and `restartLevel` only.
- **Bindings.** `install_level_post_load_passes` (`startup/lifecycle_install_world.rs`) runs `rebuild_active_system_reaction_bindings` after `install_world_cpu_with_models` has fired `levelLoad`, on every machine. Its comment names the reason: the queued IR `setState` waits for the drain, which runs after the rebuild. A write at dispatch evaluates before that rebuild, so an IR value would meet the previous install's table and `SystemReactionIrDispatch::Unknown` would skip it.

The brief moves store writes to dispatch on every machine, so every step lands in body order. One rule because:
- The body-order Decision is an authoring rule. A host-only rule makes one body behave differently on a client, which a modder cannot see or test from one machine.
- Every machine already walks a body through the same dispatch path (`fire_named_event_with_sequences`), and `scripting.md` §12 runs one `ReactionScheduler` on every machine, so one rule is one change.
- The client's gates are unchanged: `addSlot` is still refused, and `setState` still reaches only that machine's slots.
- Within one body the client sees no new order, since its drain already applied queued steps in authored order; what changes is that the write is in the store when dispatch returns. Crossing detection collects every fire before dispatching any (`CrossingDetector::detect`), so a write made in the crossing stage is first seen by the next frame's detection, as it is after today's second drain.

Why it holds on every machine:
- **Frame order.** On every machine, `frame_loop` runs the first drain after the post-tick named-event dispatch, then the HUD publisher, then the crossing stage, then a second drain, then connected-client per-owner persistence. A write applied at dispatch lands no later than the drain that would have applied it, so crossing evaluation and persistence still see every write.
- **UI presses.** On every machine, `frame_loop::redraw` fires a press (`fire_focused_button_activation`, `app/ui_actions.rs`) in the game-logic phase before `sim::begin_tick` and the fixed ticks. Today its writes land at the first drain, after those ticks; at dispatch they land before them, so that frame's ticks read them: trigger and player-event conditions, assist pair values, and layer parameters at tick start. `ui.md` §4's N→N+1 contract still holds: the focus engine takes the intents captured on frame N at frame N+1's game-logic phase (`ui_dispatch.take_ready` before `advance_frame`), so the press and its writes reach game logic on frame N+1 either way. Slider steps and text-entry edits are not reaction steps and stay on the drain, so a slider step still applies after the frame's other writes.
- **`fire` targets.** `dispatch_sequence` collects `fire` names and the fired reactions run after the firing body, so pin S27 in `plans/done/reaction-body-composition/research.md` (`b` reads 1, `a` ends 2) holds with writes at dispatch. Pin S1 in the same file ("`a` then `b` are written at the drain, `b` reading 1") changes on timing only: both are written at dispatch and `b` still reads 1.
- **Checks move with the write.** Readonly and range run at dispatch on every machine. Seat liveness runs there only where `addSlot` resolves seats, on the host and in single player; a seat released earlier in the frame warns and is skipped, where the drain skips it silently today.
- **Wire.** `presentation_commands.rs` keeps `AddOwnerSlot` and `SetState` off the wire today, so no presentation routing changes.

Tests that move with the write:
- **Landings.** A post-wait landing dispatches its steps through the same system arm (`fire_prepartitioned_reactions_with_sequences`, then `dispatch_system_reaction`), so its `setState` writes at landing too.
- **`system_step_pin_tests.rs`.** S1's test (named in the brief's Path) asserts `a` is still 0 after the fire ("system steps wait for the drain") and needs that assertion inverted; its member step runs before `a` is written and still sees 0. It is the only test in the file that reads the store before a drain: S2, S7 and S8 write in-tick or assert after a drain, S3 and S27 assert after a drain, and S4, S5, S6 and the audience test run install validation only.
- **Sibling pin files.** `system_step_tests.rs`, `reaction_scheduler/client_tests.rs` and `host_activations/wait_tail_loopback_tests.rs` observe a `setState` step as a queued `SystemReactionCommand::SetState`, through each harness's `commands`, `kinds` or `writes` helper, so every test there that expects one queued fails once the step writes; the brief's Path names each. `s36_client_reads_across_its_own_dropped_write` still passes, but its guard that the client queues no `tail.shared` write passes vacuously. `landing_origin_tests` holds no store write.
- **Other harnesses.** These also take a crossing's or landing's `setState` off the queue: `both_edge_crossing_carries_direction_while_sourceless_dispatch_skips_it` (`scripting/reactions/mod.rs`, `drain_direction_write`), `a_reaction_losing_its_player_event_subscription_still_fires_under_a_crossing_for_the_local_player` (`player_events/validation_tests.rs`), the crossing harness in `netcode`'s `timed_slot_receive_crossing_test.rs`, the landing harness in `e18_timed_reaction_replication_harness_test.rs`, and `apply_slot_writes` in `presentation_conditioned_fixture.rs`.

## Per-tick cost

The bound comes from construction, and the stress run measures it (`context/lib/index.md` §1.1: "Measure, don't assume").
- **Visited set.** The step walks only entities carrying layers, so its cost is layered entities × layers per entity × parameter cost. Unlayered entities, the common case in a mod without layers, cost nothing.
- **Literal parameters.** A literal binds to a constant at install and hot reload and is never evaluated per tick. Precedent: `AssistPairTable::bind` (`crates/sim/src/sim/assist_pairs.rs`) turns a literal field into `BoundValue::Literal`, precomputes an all-literal profile into `BoundAssistable`'s `literal`, returns it before any evaluation, and stores no scope when every profile is literal. A layer with all-literal parameters only clamps and recharges.
- **Expression parameters.** Each is capped at depth 32 and 256 nodes, the cap `assistable` fields (`life_states.rs`) and weapon scale expressions (`scripting.md` §11) share through `MAX_ACTIVATION_IR_DEPTH` and `MAX_ACTIVATION_IR_NODES`. The IR binder (`foundation` `ir/`) carries no depth or node cap of its own, so the layer parser applies this one. Per-entity cost is then at most parameters per layer × 256 nodes.
- **No allocation.** `scripting.md` §11 forbids per-eval heap allocation. The brain proves it with `refresh_and_guard_eval_perform_zero_heap_allocations` (`crates/ai/src/brain_scope.rs`): bind before arming `AllocSnapshot`, warm once, then assert zero allocations across refresh plus eval. The layer test takes the same shape over scope seeding, parameter evaluation, clamp and recharge. Per-entity state (last good values, the last-hit stamp) is sized at spawn and hot reload, never per tick, and is dropped with the entity; the warning bits are per descriptor and field, sized at bind.
- **Timing surface.** Sim stages report through `SimStage` (`rendering_pipeline.md` §12) and sum across a frame's ticks, so the metric divides by ticks. Only the binary reads `POSTRETRO_CPU_TIMING=1` (`crates/postretro/src/cpu_timing/mod.rs`); it hands each timed crate a `TimingGate` value, and its windows count rendered in-level frames, so in a sim harness with no binary or render the env var does nothing. The harness passes the gate on and reads the stage record directly, or times the step around its call. Recharge runs in `begin_tick`, after the respawn drain; `begin_tick` takes no gate and sits outside `simulate_tick_with_presentation_aim`, the call `SimStage` documents its stages inside; a stage outside that call is scoped where it runs, as the binary scopes `PlayerEvents` in `frame_loop`.
- **Stress fixture.** A synthetic sim registry with no brains or render keeps AI, steering and the GPU from limiting the run before the layer step. Hits every 30 ticks (500 ms) keep layers below capacity and restart the delay, so the fixture's delay expression evaluates to 0 and its rate is positive; recharge then does real work between hits, where the 3000 ms default would never run. Expressions at the node cap reading a global slot are the worst case a mod can author. The literal-parameter run is the baseline, so the measurement isolates expression cost. A cap on layered entities stays out until a measurement shows the need.
