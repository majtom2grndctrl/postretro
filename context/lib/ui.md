# UI Layer

> **Read this when:** working on the UI layer — CPU model (`postretro-ui` crate) or renderer pass (`render/ui/`, `postretro` crate) — widgets, theming, HUD state binding, UI animation, the engine accessibility panel, button value text, theme variants, text scale, or the screen-reader snapshot.
> **Key invariant:** scripts declare widget trees and state values; Rust owns the live UI. Authoritative values live in the state store; anything the UI animates or displays is retained-UI-local presentation state that never writes back. The renderer only consumes the resulting draw list at the GPU boundary.
> **Related:** [Scripting](./scripting.md) (state store) · [Rendering Pipeline](./rendering_pipeline.md) (frame structure) · [Player Options](./player_options.md) (accessibility preferences) · [Input](./input.md) §5 (UI navigation)

## 1. Layer Shape

The CPU UI model (`postretro-ui` crate) builds the authoring model — serde descriptor trees (discriminated union per widget kind, camelCase wire) → a Rust-retained layout tree (taffy flex/grid, cosmic-text-measured text) → a device-pixel draw list. The renderer (`render/ui/`, `postretro` crate) consumes that draw list as a sibling pass to scene rendering, recorded after the world passes, before present, beneath the egui debug overlay, shaping and rendering text via glyphon. Layout happens in a 1280×720 logical reference space scaled to the native backbuffer; quads and panels snap to integer device pixels, glyphs stay anti-aliased.

**Text scale (decided, not yet built).** The player's text scale (about 100–200%, OS-seeded where the platform reports one) multiplies text only, through the text measure path; the reference space does not scale. Containers reflow to fit, text with an authored max width wraps at that width, and presentation-layer text scales too. Text never silently truncates. A change applies on the next frame without restart; at 100% layout is unchanged.

Stack containers normally content-size. An authored positive `width` fixes a `VStack`/`HStack` width in logical-reference pixels so nested grids, spacers, and stretched children can compose against a stable horizontal canvas.

Game logic and the renderer meet at exactly one point: a read-only snapshot published once per frame after game logic (descriptor tree, resolved slot values, frame time). The renderer never reads the live slot table. The retained gameplay tree diffs only bound slots frame-over-frame and splits invalidation: content changes relayout, appearance changes only redraw, a settled frame rebuilds nothing.

**A second, passive draw-list producer.** Besides the modal stack of retained trees, the draw list has a passive **presentation layer**: a CPU pool of world-anchored transient instances (CPU world→screen projection + fixed-cap pool + retained per-instance template layout cache over the same widget/theme/text machinery) that folds into the same per-frame composition but carries no retained gameplay-tree identity, modal or input state, focus, or hit-test — a purely passive producer, like the focus ring. Authored as two archetypes (spawn / overlay) via `definePresentationTemplate` / `present` / `defineOverlay`, for combat feedback (floating damage numbers, damaged-enemy status bars). Template roots admit only `Text`, `Bar`, `Image`, `VStack`, and `HStack`; interactive and other retained-tree widgets are rejected. Producer-stamped `{ fact }` binds are valid only in templates. Ordinary UI-tree drains reject them. `ModManifest.presentationOverlays` accepts one overlay descriptor, not an array.

Each presentation pool contains only feedback for that machine's local screen.
Host-addressed remote overlays stay in recipient-private fact streams and never
enter the host renderer's pool or compete with another recipient's cap.

Gameplay UI is a **modal stack** of trees: top tree's capture mode decides capture vs. passthrough (lower trees freeze; HUD passes through), and behavior-relevant properties — capture mode, text-entry target, initial focus — live on the declared `AnchoredTree` envelope, so a tree declares its own behavior. A pushed registration with `hideBelow: true` also omits lower pushed trees from composition while retaining them on the stack, so Back/pop restores the prior navigation state; always-on base layers are unaffected. Trees register by name in an app-side registry, and the render path resolves them **by name** — it never calls a layout builder, so content authoring is decoupled from the frame loop. Engine fallbacks and script registrations share the same registry seam. JSON assets cover layout-only engine screens such as the frontend fallback, pause menu fallback, and on-screen keyboard; SDK-authored mod trees are the production path for frontend, HUD, pause menu, and dialogs. The registry's name→tree lookup is the seam the per-frame snapshot reads through (a `&self` accessor; the mutating handle stays private). The boot splash is not gameplay UI: it is a renderer-owned boot path and never enters the registry, modal stack, UI image registry, or `UiReadSnapshot` snapshot flow.

### 1.1 Script authoring model

Scripts author UI as the same descriptor trees, built by SDK factory functions (one per widget kind; props-first, container children positional) and registered by name. `Tree(...)` builds the placement envelope; `defineUiTree({ name, tree, alwaysOn?, hideBelow? })` builds the returned registration entry while preserving the manifest wire shape. The factory output is wire-identical to JSON — the bridge converts a VM value to the descriptor and the wire round-trips byte-identically, so factory-built and JSON-built trees are indistinguishable downstream. The same "scripts declare, Rust executes; the VM drops after load" contract holds (`scripting.md` §1): registration is the only crossing, and the VM drops after each registration pass.

**Modder components are plain functions.** A reusable component is a function returning a descriptor subtree — no component registry, decorator, or inheritance. It takes the same props-first(-then-children) shape as a factory and nests inside SDK containers; the bridge sees no difference between a factory call and a component call. A component that uses presentation cells (via `ui.createLocalState`) declares its scope on the container it returns, since cell scope resolves to the nearest declaring ancestor — so each component instance owns an independent scope.

**Registration lifecycle.** `ModManifest` / `setupLevel` data carries UI registrations (named trees, theme tokens, font assets) alongside other manifest fields. The engine drains them into the registry, the live theme, and the font system **before** the short-lived authoring VM context drops — no new lifecycle stage, the same manifest→VM-drop boundary entity types use. A registered tree marked always-on composes as a per-frame base layer (the HUD case); otherwise it shows only when pushed. Tree precedence is **engine < mod < level**: a mod registration under an engine built-in's name shadows it, and a tree from a level's `setupLevel` data shadows both for that level's lifetime. Two names are exempt: `accessibilityPanel` and `displayModeConfirm` are reserved at every registration path (mod init, level load, staged reload). A mod- or level-scope registration under either is rejected with a load-time diagnostic, and the engine tree remains (§4.1). Level unload clears the level tier and drops any pushed instance of a level-tier tree. Engine `frontendMenu`, `hud`, and `pauseMenu` entries are minimal fallbacks. A mod `frontend.menuTree`, `hud`, or `pauseMenu` shadows the matching fallback when it uses the same registry name, and `hud.reticle` is a separate always-on mod tree for the centered reticle. The registry retains tiers rather than overwriting lower-tier entries, so removing a higher-tier tree reveals the next lower tier's tree with the same name on the next resolve — a mod tree's removal reveals the engine fallback, a level unload reveals the mod or engine tree. Malformed registrations are contained: a single malformed tree is logged and skipped; a structurally broken theme/font field surfaces a named load-time diagnostic the caller logs before continuing — a bad UI registration never aborts boot or level load.

**Staged replacement.** Staged mod init commits UI trees, theme, and frontend declaration with the same successful-generation boundary as returned stores. A successful current staged result replaces returned stores, the complete mod tree tier, the complete mod theme override, and the frontend declaration together. Omitted mod trees are removed from the mod tier, revealing engine fallbacks with the same name on the next open or always-on resolve. Omitted theme tokens revert to engine defaults. An omitted frontend declaration presents the engine fallback frontend menu. If a frontend menu is currently topmost, staged replacement or omission replaces that active frontend surface immediately. Failed or stale staged results preserve the current stores, registry, theme, and frontend declaration. Always-on layers resolve the updated registry on the next frame. Non-frontend pushed modal instances keep their cloned descriptor until closed, even if reload replaces or removes the registered tree. Reopened modals resolve the updated registry entry.

### 1.2 HUD Authoring Contract

The production HUD is authored through the SDK, returned through `ModManifest.uiTrees`, and retained by Rust after mod init drops. Durable contract points are:

- HUD authors import UI SDK factories, `bindState`, and `getGameState` from `"postretro/ui"`.
- A HUD module obtains `const { player } = getGameState()` when constructing its returned UI-tree registration.
- `bindState(player.health, options)` decorates the readonly ref for display. It does not read HP during authoring.
- The health bar uses `player.maxHealth` as a direct readonly max reference. There is no `player.healthFraction` slot; UI derives the displayed fill from `player.health / player.maxHealth`.
- Bar `styleRanges` evaluate the normalized displayed fill, so health bands use thresholds in `[0, 1]` with `styleRanges.max = 1.0`.
- The reticle is a separate always-on tree from the status HUD because one anchored tree has one viewport anchor.
- Charge feedback binds readonly local `player.weaponCharging` and `player.weaponChargeProgress`; progress is `[0, 1]` with bar max 1. These describe the active action's fixed-tick charge, independently of cell charge. The dev HUD shows the indicator while charging. Release, cancellation, switching, death, and input suspension clear it; render-only frames do not advance it (`scripting.md` §5).

Tree anchors and offsets are literal placement data. Theme tokens drive styling only: colors, fonts, spacing. Do not route placement through theme tokens.

## 2. Theme Tokens

Theme is three category-scoped maps — colors (linear RGBA), fonts (registered family), spacing (logical px). The category is carried by the referencing field, not a name prefix.

- **Semantic required set — the engine contract.** Colors `critical` / `warning` / `ok` / `panel.default` / `focus.ring` (`panel.default` and `focus.ring` are literal flat keys, dots and all), fonts `primary` / `mono`, spacing `xs` / `s` / `m` / `l`. Built-in screens, focus rings, and `styleRanges` resolve these names; a mod rethemes built-ins by overriding them.
- **Open key space — the primitive tier.** Maps accept arbitrary additional keys and widgets may reference them; a mod-defined primitive palette (`cyan.500`) is supported, not just tolerated.
- **Literal escape hatch.** Every token-capable field is an untagged union: a token name or an inline literal value. One-off treatments need no theme entry.
- **Override merge** is per-token after the complete mod theme override is chosen: the current override replaces only the names it ships; everything else resolves from the engine default. A selected variant merges the same way, one tier higher (below).
- **Unknown tokens degrade visibly, never panic:** unknown color → opaque magenta, unknown font → `primary`, unknown spacing → zero, each with a warning per tree build.
- **Token aliasing** (semantic → primitive references) is deferred; it widens theme entries additively when a consumer justifies it.

**Player-selected variants (decided, not yet built).** Precedence gains a third tier: **engine default → mod base → selected variant**. A mod ships accessible variants of its theme (high contrast, colorblind-safe) in its manifest; the player selects one as an option, OS-seeded from the OS contrast setting (`player_options.md` §5). A variant's omitted tokens resolve from the mod base, then the engine default. High contrast with no mod variant layers an engine high-contrast set over the mod theme; that set defines every text, background, button, panel, slider, and focus token. The variant tier sits above the mod so content never shadows the player's accommodation. Composition runs at the one theme chokepoint. The selection is stored outside the mod override, so it survives staged reload — including one that changes the base theme — and a reload that removes the mod's high-contrast variant falls back to the engine set. No frame draws a new base theme with the old variant set.

**Engine visuals are tokens (decided, not yet built).** Engine-drawn colors — interactive labels, slider track, thumb, and fill, buttons, panels, text — resolve from semantic tokens, never literals; slider fill no longer follows `focus.ring`. Focus visuals are authorable (background, text color, outline); an omitted one keeps the engine outline. `flashScreen` and `vignette` accept a theme color token beside a literal tuple, resolved against the selected variant when the reaction fires.

**Contrast floor diagnostic (decided, not yet built).** Theme drain checks engine-defined token pairs: text on background below 4.5:1 and a focus indicator below 3:1 each warn. A warning, never a load failure.

Theme registration arrives through returned manifest data. Custom font asset replacement/removal is not hot-reloadable until the font system has an explicit replacement contract. Staged reload may replace the theme token override, but changing custom font declarations, replacing custom font assets, or removing them requires an engine restart.

The TypeScript/Luau SDK ships `defineTheme(theme)` as authoring sugar for custom themes. It accepts nested singular `color` / `font` / `spacing` groups and returns the same flat `colors` / `fonts` / `spacing` object that `ModManifest.theme` accepts. `getDesignTokens(theme)` returns nested token leaves for the exact object returned by `defineTheme`; widget factories unwrap those leaves back into the flat token strings the descriptor wire already uses. The helper metadata is non-enumerable/non-retained: generic theme iteration and serialization see only the three category maps. Theme maps and token trees use prototype-safe tables/maps, and keys such as `__proto__`, `prototype`, and `constructor` are invalid authored token keys.

In TypeScript, token leaves are keyed from the concrete theme object, so editors autocomplete valid nested token paths at widget call sites. Leaves are object records with private SDK metadata; a hand-built `{ __postretroToken, token }` record does not unwrap, even through `as any`. Luau cannot express the dependent authored shape; its supported type-checking contract is an open nested tree per category, so wrong-category token use is typed while exact path existence remains runtime-authenticated by `getDesignTokens(theme)`. Luau's exported token record types are structural for the type checker only. Runtime accepts token records only when they come from `getDesignTokens(theme)`, not when hand-built. Missing authored token paths throw at SDK access time in both runtimes. `defineTheme` is not a new runtime theme format; descriptors still carry plain strings, and the Rust theme drain still consumes only the three category maps.

## 3. Display vs. Authoritative Values

Widgets bind authoritative store slots by state reference at the SDK layer and by dotted slot name on the retained wire. The retained UI may hold a per-node **display value** that eases toward the authoritative target over a declared duration and curve (tweening). Contract:

- The authoritative slot is always the target; the widget renders the display value, never the slot directly.
- A `Ring` may opt into `radiusRange: { inputMax, min, max }` for a bound radius. The retained UI first eases the neutral source value, then linearly maps `0..inputMax` into the presentation-only `min..max` logical-pixel radius and clamps outside that interval. The mapping never writes back to the source slot.
- Display state is presentation-only and retained-UI-local; the renderer consumes its resulting draw list at the GPU boundary. No store write ever originates in the UI module.
- A `Slider` composes a filled track, thumb, and numeric readout inside its one focusable rect. `valueDisplay: { min, max, suffix?, decimalPlaces? }` may linearly map the slider's raw `[min, max]` range into presentation units; interaction and `setState` writes always retain the raw value.
- Retargeting is continuous: a target change mid-flight eases from the current display value, never snaps.
- A `Button` may carry `valueText` cases: the first whose predicates all hold is its visible text, else its label. A setting that cycles is then one control showing its value, named by a label beside it through `labelledBy`. The node keeps its id as the text changes, so focus stays on it after a press. A text change relays out like a bound text change; a settled frame compares and does no work.
- Bar widgets may resolve `max` from either a literal number or a readonly numeric state reference. The bar fill normalizes the displayed value against that resolved max. `styleRanges` on a bar evaluate the normalized displayed fill; health bars use thresholds in `[0, 1]` and `styleRanges.max = 1.0`.
- A `Bar` may author positive logical-reference `width` and `height`; omission preserves the 120×12 default. `exitFade: { durationMs }` is deliberately Bar-only, requires `visibleWhen`, and is a linear retained-UI exit: on a true→false lifecycle transition it captures the terminal displayed numerator and denominator, retains both quads while alpha fades for the authored duration, then emits no quads. A false first resolution begins hidden; a true retrigger during the fade cancels it and renders the live bar fully opaque in that same frame. This is presentation-local state: gameplay publishes lifecycle/value snapshots and never drives the fade timer or opacity.
- UI time is dt-accumulated game time, never wall clock — pausing game logic pauses presentation.
- **Reduce motion.** While the player's reduce-motion switch is on, a UI tween reaches its target the frame it starts, a running tween included, in retained trees and presentation templates alike; a presentation instance spawns at its full rise; scatter and fade are not motion and stay (`player_options.md` §5). The App carries the switch to the renderer on the per-frame UI snapshot and hands it to the presentation pool at its frame-time call site, so no simulation code reads it.
- Structural tree rebuilds discard display state (in-flight values snap to target); rebuilds are rare, authored events.
- `styleRanges` (continuous value→style) evaluate the value the widget renders — the display value mid-tween; state crossings (`onStateCrossing`) watch the **authoritative** slot, engine-side, after game-logic writes. The two may diverge mid-tween by design.
- Diagnostics fire at tree build, never per frame. Unknown tokens (§2) and malformed binds (orphan `{local}`, unknown slot) warn once when the tree is built; the per-frame resolve path stays log- and allocation-free.

Engine-owned UI slots: `screen.flash` (RGBA, engine-decayed flash surface; the screen-effects resolve pass in `render/screen_effects.rs` consumes it), `screen.vignette` (RGBA — rgb tint, a = strength; mod-readonly), `screen.shake` ([dx, dy] offset; mod-readonly), `input.mode` (`pointer` / `focus`, app-written in the input phase), `session.openSeats` (readonly client-local number, absent until an admitted peer receives a status roster), `ui.textEntry` (writable string — the text-entry target), and writable, non-replicated `options.*` working-copy slots (`mouseSensitivity`, `invertY`, `viewFeelScale`, `crouchMode`, `shadowQuality`, `fogQuality`, `surfaceDepthQuality` — with a two-value `off`/`on` vocabulary, not `low`/`medium`/`high` — and `renderResolution`, valued `auto`/`native`/`half`/`third`/`quarter`). The options slots seed from in-memory `PlayerOptions` on menu open and bridge back with live apply plus debounced persistence; see `player_options.md` §4. Readonly, always-live `accessibility.*` slots carry each accessibility preference's resolved value for content that honors it, plus one readonly `accessibility.<field>FollowsSystem` bool per OS-seedable field, and every accessibility field but the flash limiter has an `options.*` working copy — `viewFeelScale` above, plus one per remaining field (`player_options.md` §5). Writable `options.windowMode` carries `windowed`/`borderless`/`exclusive`. Readonly client-local, nonpersistent `window.displayModeWidth`, `…Height`, `…RefreshHz`, `…BitDepth` and `…Monitor` describe the accepted, launch-default, browsed or pending picked choice; missing choices expose zero numbers and an empty monitor string. Refresh is a nominal display label when recognized; exact driver millihertz remain in storage/native apply. `window.displayModeCanApply` is a readonly boolean, false until browsing differs from the accepted choice; pending confirmation and Borderless force false. `window.displayModeRevertSeconds` is the rounded-up confirmation countdown, zero without a pending confirm (`player_options.md` §7). Writability, not ownership, gates event-time writes: readonly slots warn and no-op; engine-owned writable slots are valid targets.

## 4. Interaction

UI input rides one queued seam (`input/ui_dispatch.rs`) with kinded intents (nav / pointer-click / text): an event a capturing tree consumes on frame N reaches game logic no earlier than frame N+1 — the system's defining ordering contract. The focus engine is **app-side** (frame-order rule: it consumes intents, fires reactions, and writes slots — game-logic work; the renderer only displays). The renderer publishes a flat hit-test rect list once per frame (the reverse twin of the snapshot); the focused-node id rides the next snapshot, so the focus ring may trail a focus change by one frame, the same latency every UI event carries. Activation resolves to named, pre-registered reactions or closed engine-reserved UI actions — never a script callback. Hover is tracked cursor state, never a queued event.

**Focus stops are interactive widgets only** (today `Button` and `Slider`). A passive node — text, image, bar, ring, any container — is never a stop, even inside a focus group or with an authored id; a passive id exists for `labelledBy` references. A container that declares a focus policy opens a group whose members are the interactive descendants beneath it, through any passive containers, up to the next nested focus-policy container. Decided, not yet built: a `scroll: { maxHeight }` container attribute on `VStack` and `Grid` sizes to content up to `maxHeight`, then clips and scrolls vertically, keeping focus in view by the minimum distance; it creates no stop or group, and on an `HStack` it is ignored with a diagnostic. A `Glyph({ command })` widget draws the command's effective binding for the last-used device family (`keyboardMouse`, `xbox`, `playstation`, `nintendo`) from mod-supplied art, falling back to the input's name. Confirmation dialogs stay an authored pattern: `initialFocus` on the safe choice, pushed by `showDialog`. Authoring mistakes degrade at runtime (an `initialFocus` or `focusNeighbors` target that is not an interactive id falls back to initial focus or group policy) and warn once when the tree registers, never per frame; empty and duplicate interactive ids warn the same way.

Reserved UI actions live in the `ui.*` namespace. They are button `onPress` values that the App intercepts before named-reaction dispatch. `ui.commitTextEntry` commits the active text-entry modal. `ui.closeDialog` pops the active modal. `ui.exitToDesktop` requests the same clean app shutdown path as a window close. `ui.quitToMenu` returns to the frontend through the shared unload/backdrop-reload path used by `returnToFrontend()`, so engine fallback menus do not need a registered reaction. `ui.openAccessibility` opens the engine accessibility panel, and the closed family `ui.accessibility.<op>.<field>` writes accessibility preferences (§4.1). The closed family `ui.displayMode.<op>` (`next`, `previous`, `apply`, `keep`, `revert`) browses a session-local display selection, applies it, and resolves its confirm. `displayModeAction(op)` emits the same action in both SDKs. Browse actions never apply or save; Apply accepts a windowed selection or confirms an exclusive change. Pending confirmation and Borderless refuse browse/Apply (`player_options.md` §7). Decided, not yet built: `ui.openControls` opens the engine controls panel, a `core/ui/` tree generated from the effective command list. Its registry name is reserved like the accessibility panel's, and it is the only remapping surface (`input.md` §2). The reserved set stays closed and mirrors into the SDK in the same pass. Other `onPress` names keep the normal named-reaction path.

The production frontend menu is a capturing modal named by `ModManifest.frontend.menuTree`; the dev mod's title root presents Play / Options / Exit and pushes its level-select or options submenu. The engine keeps a minimal `frontendMenu` fallback for no-mod/no-map boot. If the declared menu tree is not registered, frontend presentation uses the engine fallback before any backdrop load starts. Frontend presentation forces capture on the pushed clone even if the registered tree was passthrough. While the frontend root exists anywhere in the pushed stack, the menu camera remains held and gameplay/HUD presentation stays suppressed; Back/cancel pops only the submenu, never the title root, and Start/menu input is ignored while another frontend modal is active.

The production pause menu is a capturing modal registered as `pauseMenu`. The mod-authored SDK tree is the normal production entry; the engine keeps a minimal fallback under the same name so Escape / Start still open and close a menu when no mod tree is registered. `nav.menu` opens `pauseMenu` only when the modal stack is empty, closes it when it is active, and is ignored while another modal is active. `nav.cancel` closes an active `pauseMenu` and pops a submenu pushed above it, so a submenu opened from the pause menu returns to it, as a frontend submenu returns to the title root; a modal with neither beneath owns its own cancel policy. The pause menu is not a true simulation pause: while it is active, UI capture suppresses player controls and releases the cursor, but game simulation, animation clocks, particles, audio, and UI time continue unless a separate true-pause system is added.

### 4.1 Accessibility panel

The engine accessibility panel is the floor that guarantees every player can reach every accessibility preference, whatever the mounted mod's menus omit. It is an engine-owned `core/ui/` descriptor under the reserved, non-shadowable registry name `accessibilityPanel` (§1.1). It carries every field of the accessibility group, resolves theme tokens so it follows the mod's look, and gives every control a name and role. Each row is a text label on the left and its control on the right: a slider, or for a toggle one button whose `valueText` shows the field's value, named by the label (§3).

- **Reach.** It opens from `ui.openAccessibility` on any button; the engine fallback frontend and pause menus carry one. No engine input is reserved for it (`input.md` §5). While it is the active tree, `nav.cancel` and a `ui.closeDialog` button close it, returning to whatever opened it. A mod reaches it from its own menus, or offers the fields itself through field actions.
- **Missing-entry warning.** When no mod- or level-scope tree has a button firing `ui.openAccessibility` or a field action, and no engine fallback menu that carries one is in use, a load-time warning names the fix and notes that players still see the panel on first launch. The check runs when the tree set changes — after mod init, a staged reload's UI commit, and level install — never per frame. It keeps its last verdict, so it warns once per state: again only after an entry appeared and was later removed.
- **First launch.** Boot shows the panel once, before any level loads (`boot_sequence.md` §1).
- **Write path.** Every panel control fires a reserved field action, `ui.accessibility.<op>.<field>`, that cycles a toggle or enum or steps a numeric (`op` is `cycle`, `increase`, or `decrease`; `field` is the slot's camelCase suffix). An OS-seedable toggle cycles System → On → Off, its value text reading the follows-system slot (`player_options.md` §5). The SDK types each op by field kind; a mismatched op warns and does nothing. The App intercepts the family before named-reaction dispatch, as it does `ui.exitToDesktop`, writes `PlayerOptions` directly, and persists through the same settled save as a menu write. No control depends on a mod-registered reaction, so the panel works under a mod that registers none. A family action fired from any tree — mod and level trees included — writes its field the same way.
- **Engine-routed sliders.** A `Slider` in an engine-tier tree bound to a readonly numeric `accessibility.*` slot routes each step to that field's step action, keeping gamepad left/right and hold-repeat. The step applies only while the tree that exported the slider, by name and tier, is still the active tree; the focus export names its tree and tier, recorded with the layout that produced its rects, so a frame that skipped layout never names a newer top tree. Only engine-tier trees get this routing; a mod slider bound to a readonly slot still warns and no-ops through the ordinary readonly write gate.
- **Flash limiter.** It has no working copy and its `accessibility.*` slot is readonly, so a button activation of its field action — from the engine panel or a mod or level menu — is the only way it changes. No reaction, manifest field, or script write reaches it: the App's field-action handler is its only store write site (`player_options.md` §5, `rendering_pipeline.md` §7.8).

**Display-mode confirm.** `core/ui/displayModeConfirm.json` is reserved as `displayModeConfirm`, so no mod or level tree replaces the dialog whose focus guards a blind confirm. Focus opens on Revert. Keep commits; Revert, cancel, 15-second expiry or removal of that modal instance restores the prior mode without saving the candidate. A later dialog with the same name cannot confirm an earlier transaction (`player_options.md` §7).

### 4.2 Accessibility snapshot (decided, not yet built)

Menus reach native assistive technology (screen readers) through an engine-built accessibility snapshot of the retained tree: resolved names (inline label and `labelledBy`), roles, states (selected, checked, disabled), bounds, slider values, a button's value text, and `Announce` live regions. Its focusable set is the focus export; static text and alt-texted images join as read-only nodes in tree order, so a dialog's message is read. A missing `labelledBy` target yields an empty name and a warning. An `Announce` produces one live-region entry when it becomes visible or its text changes, and none on a rebuild that changes neither.

The snapshot sits behind an app-side adapter seam. Platform accessibility types never enter descriptors, the UI crate, scripting core, or the SDK. Assistive-technology actions (activate, increment, decrement) enter at the Input stage and re-enter the existing activation and slider-step paths — never a script callback — so they carry the same N→N+1 latency as a nav intent. An action names a tree instance and node, not an authored id alone; a target no longer in the top tree does nothing. A focus change reaches the adapter no later than the frame the focus ring shows it.

## 5. Render Path & Asset Loading

- **One coordinated prepare phase per submitted UI composition.** The whole frame's UI — every modal-stack layer's shapes and text — is encoded as a **single composition**, not one encode per layer. UI shape and uniform writes stage in the renderer's per-frame upload batch (`rendering_pipeline.md` §1), which lands every write on the queue timeline before its submit's passes run, so recording a draw between overlapping writes does not snapshot the buffer. Glyphon's vertex writes are the exception: they go direct to the queue. Every shape batch therefore owns a disjoint instance-buffer region, and every mixed-order text span owns a disjoint glyphon renderer buffer. Changed spans prepare before the pass opens; every span records at its paint-stream position. **Change-gated prepare:** an unchanged span keeps its key — everything prepare reads — and draws from its retained vertices, and a span the encode does not draw forgets its key, so it prepares again when it returns. Atlas reclaim trims first, then prepares every live span in the same prepare phase, every 120 encodes with text and at once when glyphon reports the atlas full, so a skipped span's glyphs are never evicted. The UI stage counts spans prepared per frame (`ui_text_spans_prepared`, `rendering_pipeline.md` §12). `encode` takes the whole composition by type, so the historical per-layer glyph clobber is unrepresentable; a debug-only guard rejects a second encode before submission.

- **UI painter order is one mixed command stream.** UI draw data carries per-item paint order across panels, images, radial shapes, and text. Consecutive text runs remain one glyphon batch; a shape between text runs starts another prepared span. **Per-layer scoping:** a layer boundary also ends a span, and each layer paints inside its own depth band fixed by stack position, so a change in one layer never moves another layer's span keys; past the band bound, the frame falls back to whole-frame painter depth. The pass records those spans and shape batches in retained order, so translucent source-over blending follows authoring order. A private UI depth target remains the hard-occlusion backstop for opaque panels and backdrops.

- **Native UI layer.** Game UI renders at native resolution into its own premultiplied sRGB layer, never into scene colour, so it stays sharp at any render resolution. It lays out at the surface extent and keeps its private depth target. The layer clears transparent every frame, so a frame with no UI shows none of the last frame's. The resolve composites the layer over the upscaled scene without tonemapping it, and flash, shake, and vignette leave it untouched: each effect's covers-HUD switch is off (`rendering_pipeline.md` §7.8). Recording lives in `renderer_ui_layer.rs`. glyphon's default Accurate colour mode linearises glyph colours, so text in the sRGB layer matches text drawn into the old HDR target within ±2 per channel (a GPU test pins it).

- **Asset paths: cwd-relative at runtime, `CARGO_MANIFEST_DIR` only under `#[cfg(test)]`.** The engine runs with the tree holding `core/` and `content/` as its working directory — the workspace root in a checkout, the payload root in a packaged build (`build_pipeline.md` §Distribution packaging) — so loaders resolve `core/...` and `content/...` relative to the current directory. Tests anchor to `CARGO_MANIFEST_DIR` (`../..` to the workspace root) because `cargo test`'s working directory is the *crate* dir — gate that anchor behind `#[cfg(test)]`. **Never bake `CARGO_MANIFEST_DIR` into a production loader:** it embeds the build machine's absolute path into the shipped binary. Every asset loader (UI JSON, keyboard, boot splash image, maps, textures) follows this. Missing/malformed engine-shipped content warns once and degrades (the screen is absent, a black boot frame, or a minimal in-code fallback) — it never aborts boot.

- **`--core-root` overrides where the engine's own assets are found.** It names the directory holding `ui/` and `textures/` — the `core/` directory itself. Absent, resolution is the cwd-relative convention above, unchanged. The override exists because a launcher may pin the working directory to a *game project*, which correctly has no `core/` of its own: `postretro-tool run` does exactly that and passes the install's `core/`. Engine assets and mod content are independent lookups in both directions; `--mod` never redirects `core/`, and neither falls back to the other. The root is carried as a value (`postretro_ui::CoreRoot`), not rebuilt from a literal at each call site, so a loader cannot resolve an engine asset without naming a root. Boot resolves it once from argv; the splash decode and the built-in tree registration are its two consumers. Like every value-taking engine flag, it belongs in `resolve_map_path`'s skip list or its value is loaded as the level.

- **Engine-shipped UI assets live in `core/`, never under a mod root.** The five built-in descriptors (`core/ui/hud.json`, `pauseMenu.json`, `frontendMenu.json`, `keyboard.json`, `accessibilityPanel.json`) and the boot splash (`core/textures/splash/`) belong to the engine, not to whatever game is mounted, so `--mod` never redirects them and `core/` is deliberately a single path component — outside the `content/<mod>` two-component shape a mod root must have (`build_pipeline.md` §Baked texture mips). `hud.json` is a **fallback** that mod content shadows by registering the same name at a higher scope tier; `accessibilityPanel.json`'s registry name is reserved instead (§1.1, §4.1); the other three have no mod-side alternative. Decided, not yet built: the caption and cue layer, drawn above the mod HUD (`audio.md` §5), and the display-mode confirm join them. The two default typefaces are not assets at all: they are `include_bytes!`-ed into `postretro-ui` at compile time, and only their OFL licence text ships, from `core/licenses/`.

## 6. Non-Goals

- A live scripting VM driving UI logic, or per-frame script callbacks.
- Direct UI-module writes to authoritative state — event-time writes go through the `setState` reaction (and the text-edit reactions built on its gate), applied at the game-logic stage.
- DOM/CSS-style markup or cascade — descriptor objects only.
- Whole-UI reference-space scaling as an accessibility scale — text scale (§1) is the accommodation.
- Self-voicing text-to-speech — native assistive technology reads the accessibility snapshot (§4.2); a self-voicing path would read the same snapshot.
