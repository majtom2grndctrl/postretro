# E10 — Enemy Stuck Recovery (unwedge from concave geometry)

> **Wave:** E10 enemy-AI follow-up (refinement of the shipped `M10--enemy-ai-behavior` / `M10--pathfinding-path-following` foundation). Surfaced in manual play-testing: the enemy jams against a pillar when the player rounds it and stays immobile.
>
> **Adjacent specs:** `E10--enemy-steering-feel` (accel/turn-rate/arrival — different concern, same `agent_steering::tick` file) and `E10--enemy-locomotion-animation`. This spec is the **collision-recovery** gap; those are feel/animation.

## Goal

When a navigation agent's capsule wedges against concave world geometry (a pillar corner) and stops making progress despite having a valid route, detect the stall and recover — slide out and resume the chase — instead of staying frozen. Today there is **no stuck-detection anywhere in the steering loop**, so a wedged enemy is permanently and invisibly stuck.

## Background (the cause)

The wedge is a **collision-recovery gap**, not a routing failure:

- The brain re-aims the destination at the player's *raw* position every tick (`crates/postretro/src/scripting/systems/ai.rs:543-545`; the `SteeringIntent::Chase` arm; `set_destination(registry, outcome.id, player_pos)` is at 545), and `goal_speed` re-issues full `move_speed` toward the current waypoint while `integrated_steer_velocity` turns it into a heading each tick (`agent_steering.rs:488-551`).
- When the capsule contacts a concave corner, `collide_and_slide` projects the velocity to ~0 — two near-perpendicular wall normals consume it within the `SLIDE_ITERATIONS` budget (`agent/mod.rs:24`; 4 iterations; slide loop `agent/mod.rs:141-190`; `NORMAL_NUDGE` is only `1e-4`, `agent/mod.rs:42`). So the agent pushes into the corner and the harness correctly refuses to penetrate, yielding near-zero motion.
- Nothing in `tick` diffs the resolved position against the prior position — it writes `t.position = result.position` (`agent_steering.rs:418`) but never measures progress (`agent_steering.rs:248-425`). `AgentComponent` carries no `last_position` / `stuck_ticks` / progress field (`crates/entities/src/components/agent.rs:34-101`).
- Replans fire only on destination drift (`REPLAN_DEST_THRESHOLD` 0.5 m, `agent_steering.rs:86`) or staleness (~30 ticks), via `admit_replans` (`agent_steering.rs:445-482`). `blocked` stays **false** because the path is perfectly routable — the capsule simply can't physically traverse it. A fresh route still ends in a waypoint the wedged capsule must *move* to reach, so re-pathing alone does not unwedge it.
- Compounding: the navmesh erosion is coarse (Chebyshev/cell-quantized, `navmesh_bake.rs:399-441`; funnel string-pulls over portal segments, `nav/path.rs:244-309`), so a sub-cell sliver near pillar corners still lets the capsule make contact; and the separation pass can push neighbors *deeper* into a wedge in waves (`agent_steering.rs:655-697`).

## Scope

### In scope (Option A — the recommended, confined fix)

- **Stuck detection** in `agent_steering::tick`: track per-agent goal-projected progress (start-of-tick vs. resolved position, projected onto the goal/desired heading) and increment a `stuck_ticks` **detection counter** when progress is below `STUCK_PROGRESS_EPSILON` **while `!agent.path.is_empty() && !agent.blocked` and the agent intends to move** (i.e. `goal_speed` this tick is above `STUCK_INTENT_SPEED_EPSILON` — see gate below). Reset on real progress.
- **Recovery** on crossing `STUCK_TICKS_THRESHOLD`: (a) force a drift replan (clear the planned-destination latch so `admit_replans` recomputes a route), and (b) apply a **deterministic fixed-handedness perpendicular tangent** — computed from the pre-separation `steer_velocity` heading — biased into the desired velocity, sustained over an explicit bounded recovery window (`unstick_window_remaining`), so the capsule slides along the obstacle out of the corner rather than grinding into it. No RNG. Detection and recovery are **distinct phases with distinct state**: the counter detects; the window governs the slide.
- **Gating** so detection never fires for a legitimately stationary agent (idle / no path), a genuine no-route `blocked` state, or an arrived agent standing at the final waypoint with near-zero `goal_speed` — recovery must not mask a real navigation failure. Only accrue `stuck_ticks` when `!agent.path.is_empty() && !agent.blocked` AND `goal_speed` this tick is above `STUCK_INTENT_SPEED_EPSILON` (i.e. the agent intends to move; arrival/final-waypoint-reached where `goal_speed` ≈ 0 is excluded).
- **Post-implementation escalation gate.** After Option A lands, run a manual check on `campaign-test` or an equivalent pillar/wedge fixture. If tangent recovery still leaves visible wall hugging, repeat wedge failures, or route-valid-but-physically-invalid corners, open a separate navmesh-clearance / capsule-exact bake-refinement draft. A fixed-handedness backstop is **expected** to leave some hard corners unrecovered; that under-recovery is the designed escalation signal, not a defect in this spec. Do not implement that bake work here.

### Out of scope

- **Capsule-exact navmesh** (Option B): Euclidean radius erosion + funnel corner-offset so no waypoint sits within a radius of geometry. This touches the bake algorithm (bumps `NAVMESH_STAGE_VERSION`), region decomposition, and the funnel, and forces a re-bake of all maps. Deferred to a separate draft only if the post-implementation escalation gate fires.
- **Unstick inside `collide_and_slide`** (Option C, rejected): the sweep harness is intentionally intent-agnostic and cannot know which direction is "out," so recovery there would jitter. Recovery belongs in the steering tick, which owns intent.
- Player movement; inter-agent deadlock resolution beyond what the tangent slide + replan already give; flocking.
- Steering *feel* (accel/turn-rate/arrival) — `E10--enemy-steering-feel`.

## Acceptance criteria

- [ ] **Detection latency (AC1a):** An agent commanded toward a target whose straight path wedges it in a concave (pillar-corner) collider — near-zero goal-projected progress while it holds a route, is not `blocked`, and has `goal_speed` above `STUCK_INTENT_SPEED_EPSILON` — accrues `stuck_ticks` to `STUCK_TICKS_THRESHOLD` (default: 20 ticks) and fires recovery (runnable unit test on the steering tick against a concave-corner collider; asserts `stuck_ticks` reaches `STUCK_TICKS_THRESHOLD`, then recovery fires on the following tick — observed via `unstick_window_remaining` seeded to `UNSTICK_WINDOW`, since the counter resets to 0 on fire).
- [ ] **Escape latency (AC1b):** After recovery fires, net goal-projected displacement over the recovery window (`unstick_window_remaining`, seeded to `UNSTICK_WINDOW`, default 10 ticks) exceeds `UNSTICK_ESCAPE_DISTANCE` — the agent leaves the corner. Goal-projected progress DURING this window is expected and is governed by the recovery window, not by resetting `stuck_ticks`: the window persists through progress and is not cut short (runnable unit test on the same fixture; asserts stuck→escaped, not just that recovery fired).
- [ ] **Determinism + tangent sign (AC3):** Recovery is deterministic under the fixed tick (identical inputs → identical escape path). The recovery tangent is the canonical **fixed-handedness** perpendicular of the pre-separation `steer_velocity` heading: rotate its XZ components by a fixed +90° quarter-turn about world-up (+Y), `(x, z) -> (-z, x)`, holding Y fixed — the same handedness every call, no data-dependent sign, no contact normal, no destination reference. Asserted by reproducing the same recovery twice AND asserting the signed tangent equals `(-steer_velocity.z, steer_velocity.x)` in XZ (up to normalization/scale), not merely that it repeats. The slide stays collision-resolved (collide-and-slide), so a wrong-side tangent can at worst make no progress — it can never push through geometry. Recovery with a zero/near-zero `steer_velocity` produces no NaN and a no-op tangent (degenerate-heading guard is asserted).
- [ ] **Negative-case gating (AC4):** Stuck-detection does **not** fire for an agent that is legitimately stationary with no path (idle), nor for a genuine no-route `blocked` outcome, nor for an arrived agent standing at the final waypoint (where `goal_speed` ≈ 0 and the intent gate is not satisfied) — gated on `!agent.path.is_empty() && !agent.blocked` AND `goal_speed` above `STUCK_INTENT_SPEED_EPSILON` (runnable unit tests for all three negative cases, including an arrived agent standing on the player).
- [ ] **Edit-set + format lock (AC5):** The change is confined to the `agent_steering` module (`tick` + new module constants) plus two additive `AgentComponent` fields (`stuck_ticks: u32` detection counter and `unstick_window_remaining: u32` recovery window) and their initializers/serde attrs in the entities crate; no navmesh re-bake, no `NAVMESH_STAGE_VERSION` bump, no PRL/navmesh/wire format or version bump — the two additive `#[serde(default)]` component fields are the permitted change. Precedent: `steer_velocity` landed exactly this way (additive serde-default field with a back-compat test) at `crates/entities/src/components/agent.rs:58`.
- [ ] **Regression (AC6):** Existing path-preservation, replan-budget, separation, and determinism tests from `M10--pathfinding-path-following` remain green; the forced replan routes through `admit_replans`' budget (does not bypass it), so replan-budget tests are not invalidated.
- [ ] **Manual acceptance step (AC7, not a coded task):** Post-implementation manual check records whether tangent recovery resolves the wall-hugging/wedge fixture. If failures remain, the output is a new draft for navmesh clearance / capsule-exact bake refinement; this draft still ships no Option B code.

## Tasks

### Task 1: Progress fields + stuck detection
Add two additive `AgentComponent` fields — `stuck_ticks: u32` (detection counter) and `unstick_window_remaining: u32` (recovery-window countdown) — both initialized (to `0`) in `AgentComponent::new` and both `#[serde(default)]` for deserialization back-compat. In `tick`, compute start-vs-resolved goal-projected progress and update `stuck_ticks`, gated on `!agent.path.is_empty() && !agent.blocked` AND `goal_speed > STUCK_INTENT_SPEED_EPSILON`; increment when progress `< STUCK_PROGRESS_EPSILON`, reset `stuck_ticks` to `0` on progress. Detection runs **post-move** (progress needs `result.position`) and is **suspended while `unstick_window_remaining > 0`** — the recovery slide moves perpendicular to the goal, so it would otherwise keep the stall gate satisfied and re-arm the threshold mid-window. `unstick_window_remaining` is declared and zero-seeded here (inactive); Task 2 drives it. (Includes building the concave-corner test fixture — see Rough sketch.)

### Task 2: Tangent-slide recovery + forced replan
Recovery keys off the `stuck_ticks` accumulated through prior ticks (detection updates post-move — see Task 1), so it acts **pre-move**, before `collide_and_slide` runs. Pre-move, in order: (1) if `unstick_window_remaining == 0 && stuck_ticks >= STUCK_TICKS_THRESHOLD`, fire — clear the planned-destination latch (`agent.planned_destination = None`, routing the next `admit_replans`), seed `unstick_window_remaining = UNSTICK_WINDOW`, reset `stuck_ticks = 0`; (2) if `unstick_window_remaining > 0`, add the tangent bias to the pre-separation `desired` (the goal/steer component, before the separation pass composes) and decrement the window. Tangent bias: `desired += TANGENT_BIAS * move_speed * tangent_unit`, where `tangent_unit` normalizes the fixed-handedness perpendicular of `steer_velocity` — rotate its XZ by +90° about world-up (+Y): `(x, z) -> (-z, x)`. The goal component is RETAINED, so goal-projected escape accrues (AC1b). The window PERSISTS through goal progress: progress during it does not cut it short and does not reset it. Then the existing clamp re-caps `desired` to `move_speed` and the separation pass composes afterward, unchanged. Guard zero-length `steer_velocity` (no NaN; tangent is a no-op). Detection is suspended while the window runs (Task 1), so recovery cannot re-fire mid-window. Consumes Task 1's detection.

## Sequencing

**Phase 1 (sequential):** Task 1 — establishes the detection signal and the two component fields.
**Phase 2 (sequential):** Task 2 — consumes Task 1's `stuck_ticks` (recovery reads it pre-move; detection updates it post-move — a one-tick handoff); shares `agent_steering.rs`.

## Rough sketch

- Fields on `AgentComponent`: `stuck_ticks: u32` (detection counter) and `unstick_window_remaining: u32` (recovery-window countdown) — no `last_position`. Inside `tick`, both `position` (start-of-tick) and `result.position` (resolved) plus `steer_velocity` (the pre-separation path-following heading; `desired` gets the separation push folded in by the later separation pass and so is NOT the goal heading — hence the tangent's SOURCE is `steer_velocity`, while its TARGET is the pre-separation `desired`) are already in scope, so progress is computable from in-tick locals; no persisted prior position is needed. Initialize both to `0` in `AgentComponent::new` (crates/entities/src/components/agent.rs:110 — the single field-listing constructor; `from_nav_params`/`attach_agent` delegate to it). `#[serde(default)]` is only for back-compat deserialization, not spawn seeding (spawn goes through `new`).
- Detection: `progress = (resolved_xz - start_xz).dot(goal_dir_xz.normalize())` — displacement PROJECTED onto the goal/desired heading (net displacement toward the current waypoint), NOT raw XZ magnitude. Rationale: separation jitter adds raw XZ displacement without goal progress, which would reset `stuck_ticks` and mask a wedge in the multi-agent wave case. `if !agent.path.is_empty() && !agent.blocked && intends_to_move && progress < STUCK_PROGRESS_EPSILON { stuck_ticks += 1 } else { stuck_ticks = 0 }`, where `intends_to_move ≡ goal_speed > STUCK_INTENT_SPEED_EPSILON`. This update runs post-move (needs `result.position`) and is suspended while `unstick_window_remaining > 0`. The force-replan latch is `agent.planned_destination = None` (setting it None makes `admit_replans`' drift test fire next tick).
- Recovery at `stuck_ticks >= STUCK_TICKS_THRESHOLD`: set `agent.planned_destination = None` (routes through `admit_replans` budget — does not bypass it: `admit_replans` computes `drifted = planned_destination.is_none_or(|planned| distance > REPLAN_DEST_THRESHOLD)` (`agent_steering.rs:460-462`), so `None` makes `drifted` true and admits a drift replan next tick budget-permitting; budget-denied replan is acceptable because the tangent slide displaces the capsule so a later in-budget replan starts from a freed position; clearing the latch alone without the tangent slide is a near-no-op since the same start position re-routes the same wall-hugging path), seed `unstick_window_remaining = UNSTICK_WINDOW`, and reset `stuck_ticks = 0`. Tangent: the FIXED-HANDEDNESS perpendicular of the pre-separation `steer_velocity` heading — rotate its XZ by a fixed +90° quarter-turn about world-up (+Y), `(x, z) -> (-z, x)`, holding Y. No dot-product sign test, no contact normal, no destination reference — the same handedness every call, deterministic from a single in-tick local. Compose while `unstick_window_remaining > 0`: `desired += TANGENT_BIAS * move_speed * tangent_unit` on the pre-separation `desired` (goal component retained so goal-projected escape accrues), decrement the window, then the existing clamp re-caps to `move_speed` and the separation pass composes after. Recovery acts pre-move off prior-tick `stuck_ticks`; detection updates post-move and is suspended while the window runs, so there is no mid-window re-fire. Guard zero-length `steer_velocity` (no NaN; tangent is a no-op). A wrong-side slide is self-correcting: the slide stays collision-resolved (collide-and-slide), so at worst it makes no progress this window — it can never push through geometry. Under-recovery on hard corners is expected and is the escalation signal (see Open questions), not a bug — a smart (productive-side / destination-referenced) tangent is deliberately NOT used here because it duplicates Option B and mutes that signal.
- New module constants mirror the existing steering-constant style (`ARRIVAL_RADIUS_FACTOR`, `REPLAN_DEST_THRESHOLD`). Three dimensionally distinct thresholds — do not collapse them into one "stuck epsilon":
  - `STUCK_INTENT_SPEED_EPSILON` (world-units/sec): intent gate. `goal_speed` above it means the agent means to move; at/below it is arrival/idle and never accrues `stuck_ticks`. Sized well below `move_speed`.
  - `STUCK_PROGRESS_EPSILON` (world-units): per-tick goal-projected progress floor. Per-tick projected displacement below it counts as no progress. Sized well below a tick's expected goal-projected travel (`move_speed * dt`), generous enough to ignore separation jitter. A rate and a per-tick distance are not the same constant, so the gate (`goal_speed > STUCK_INTENT_SPEED_EPSILON && progress < STUCK_PROGRESS_EPSILON`) is not trivially always-true.
  - `UNSTICK_ESCAPE_DISTANCE` (world-units): net goal-projected displacement accumulated over the recovery window that AC1b asserts as "escaped".
  - `TANGENT_BIAS` (dimensionless): weight of the tangent relative to the retained goal component in the recovery blend (`desired += TANGENT_BIAS * move_speed * tangent_unit`). Default `1.0` (≈45° diagonal after the `move_speed` clamp — enough lateral slide to clear the corner while keeping goal-projected progress positive).
  Tick-count constants: `STUCK_TICKS_THRESHOLD = 20`, `UNSTICK_WINDOW = 10` (tunable; the defaults make AC1a/AC1b runnable as pass/fail without manual threshold selection). Detection is suspended during the window, so these two need no ordering constraint between them.
- **Test fixture requirement:** AC1a, AC1b, and AC3 require a concave-corner (pillar / interior-corner) trimesh fixture. The only existing steering test fixture is `LWall` (`agent_steering/tests.rs` ~86-230), a convex corner the agent successfully routes around — the opposite geometry and therefore unsuitable. The new fixture must be built the same single-source way as `LWall`: one wall description feeds BOTH the `CollisionWorld` trimesh AND a hand-built navmesh, with a navmesh route that stays valid through the wedge (so `agent.blocked` stays `false`). The fixture must be demonstrated to drive goal-projected progress to ~0 under the harness before stuck-detection is asserted; otherwise the test is vacuous. Because recovery uses the fixed-handedness `(x, z) -> (-z, x)` tangent, orient the fixture so that canonical side is the escaping side — otherwise the deterministic backstop legitimately under-recovers and AC1b fails by design, not from a code fault.

## Open questions

- **Thresholds.** `STUCK_INTENT_SPEED_EPSILON`, `STUCK_PROGRESS_EPSILON`, `UNSTICK_ESCAPE_DISTANCE`, and `TANGENT_BIAS` — tune against a concave-corner test fixture. `STUCK_TICKS_THRESHOLD` (default 20) and `UNSTICK_WINDOW` (default 10) are pinned defaults; adjust only if play-testing reveals false positives or too-slow recovery. `REPLAN_STALENESS_TICKS` (`agent_steering.rs:40`, currently 30) is **not changed in this spec** — it is shared replan tuning outside the confined-fix scope, and the forced-replan latch already routes through `admit_replans`; shrinking the staleness window is a separate follow-up concern.
- **Tangent sign (RESOLVED — fixed handedness).** Stuck-recovery is Option A, the cheap deterministic backstop; it does NOT compute a productive- or destination-referenced side. Use the fixed-handedness perpendicular of the pre-separation `steer_velocity` heading: `(x, z) -> (-z, x)` in XZ (+90° quarter-turn about world-up +Y), the same handedness every call. Deterministic from a single in-tick local; no dot-product test, no contact normal. A wrong-side slide is collision-resolved, so it can only fail to progress, never penetrate geometry. Making the backstop "smart" would duplicate Option B (`navmesh-capsule-clearance`) and mute the escalation signal — so it is deliberately kept simple.
- **Escalation gate (Option A owns it).** A fixed-handedness backstop is **expected** to leave some corner geometries unrecovered — by design, not a defect in this spec. Under-recovery on hard corners is acceptable here because the budgeted replan plus this gate catch it. Persistent wedges / wall-hugging on the `campaign-test` (or equivalent) fixture after this lands is the **designed** signal to open `navmesh-capsule-clearance` (Option B — routes traversable by construction); this spec owns the decision to build it. Do NOT add productive-side or destination-referenced sign logic to make the backstop smarter; that duplicates Option B and mutes the signal. Keep Option B code out of this implementation pass.
